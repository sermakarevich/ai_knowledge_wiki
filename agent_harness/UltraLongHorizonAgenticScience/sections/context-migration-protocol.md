## Context Migration Protocol

Context Migration (CM) is the governance layer of [[hierarchical-cognitive-caching]] that decides *when* and *how* information moves between the three cache tiers -- L1 (Evolving Experience), L2 (Refined Knowledge), and L3 (Prior Wisdom). Where hierarchical caching defines the data structures and their semantics, context migration defines the algorithms that animate them: prefetching at task start, assembling context at each step, and promoting information upward at phase and task boundaries.

The paper frames the full mechanism as three coordinated operations (Section 3.4, Figure 3):

1. **Context Prefetch** -- initialization via retrieval from L3 before exploration begins
2. **Context Hit** -- step-level context assembly via the cache-hit policy encoded in g(.)
3. **Context Promotion** -- consolidation operators P1 (phase-level) and P2 (task-level) that write distilled knowledge up the hierarchy

Together these three operations implement the [[cognitive-accumulation-paradigm]]: raw experience is born in L1, refined into knowledge at L2 phase boundaries, and crystallized into transferable wisdom in L3 at task end.

---

### 3.4.1 Initialization via Context Prefetch

**Purpose.** Before exploration begins on a new task, the agent needs a warm start: relevant prior strategies already in context rather than having to rediscover them from scratch. Context prefetch is the read path from L3 into the initial agent context.

**The task descriptor.** Each past task tau_n is represented in L3 by a compact descriptor d_n. The descriptor is a dense single-paragraph textual summary of the task, generated by a dedicated LLM call using the following prompt (Appendix A.1, verbatim):

```
You are an expert ML researcher.  Your job is to summarize a machine
learning competition task description into a single dense paragraph
optimized for embedding-based retrieval.

Your summary must:
- Focus ONLY on essential technical details present in the description.
- Be dense, precise, and semantic-rich.
- Stay strictly below 250 tokens.
- Contain all relevant elements:  task type, input format, output format,
  evaluation metric (and how it is computed), dataset structure and key
  fields/modalities, submission format, and any important constraints or
  rules.

STRICT FORMAT REQUIREMENTS:
- Output MUST be a single paragraph.
- No bullet points, no numbering, no markdown.
- No headings, no blank lines, no lists.
- No backticks or code blocks.
- No special characters other than standard punctuation.
- Do NOT introduce information that is not explicitly present in the task
  description.
- Do NOT explain ML concepts or provide suggestions, analysis, or
  background.

TASK DESCRIPTION:
--------
{task_description}
--------

Now output ONLY the summarized single paragraph, with no explanations:
```

This prompt is designed to produce a descriptor that is maximally informative per token and suitable for cosine-similarity retrieval -- technical facts, not narrative.

**The embedding and retrieval query.** For the current task tau with descriptor d_tau, the system computes:

```
q = E(d_tau)
```

where E(.) is a semantic embedding function. The query vector q is then compared against all stored embedding-value pairs in L3:

```
L3 = {(h_n, w_n)}_{n=1}^{N}
```

where h_n = E(d_n) is the stored retrieval key and w_n is the corresponding distilled wisdom text.

**The threshold-based prefetch operator.** Retrieval uses a threshold-based operator Omega_tau:

```
Omega_tau = {w_n | (h_n, w_n) in L3, cos(q, h_n) > delta}
```

where delta is the similarity threshold and cos(., .) denotes cosine similarity. Only entries whose embedding keys exceed the cosine similarity threshold delta are included in the retrieved set. The paper does not specify a fixed numerical value for delta; it is a configurable hyperparameter of the retrieval system.

**What gets loaded.** The retrieved set Omega_tau "represents a view of L3 and leaves the cache unchanged." This is a read-only operation -- prefetching does not modify L3. The number of entries retrieved is determined entirely by how many stored tasks exceed the threshold; there is no explicit cap stated in the paper.

**Fallback behavior.** If no stored entries exceed delta (i.e., Omega_tau is empty -- for example, when L3 is cold on first use), the agent simply starts without retrieved wisdom. The bootstrap dataset of 407 Kaggle competitions (excluding MLE-Bench tasks) exists precisely to ensure L3 is populated before evaluation begins, making the cold-start scenario rare in practice.

**Construction of the initial event.** The task description, user instructions, and retrieved prior wisdom are concatenated to form the initial environment event:

```
e_0 = concat(d_tau, u_user, Omega_tau)
```

The initial agent context is then:

```
C_0 = g(E_0) = e_0
```

This prefetching step ensures the agent starts with a strong and relevant context, "significantly enhancing its initial understanding and enabling a more informed exploration from the very beginning" (Section 3.4.1). In [[ml-master-architecture]] terms, the first action the agent takes -- generating a buggy-free initial code -- is already conditioned on prior wisdom about similar tasks.

### 3.4.2 Retrieval via Context Hit

**Purpose.** At every agent step t during exploration, the context construction function g(.) must assemble an input context C_{t-1} from the full interaction history E_{t-1}. Naively concatenating all events leads to context saturation. The context hit policy replaces that naive concatenation with a cache-like retrieval rule: consult L1 first, fall back to L2, discard otherwise.

**Formal definition.** At time t in [t_{p-1}, t_p) -- i.e., during execution of phase p -- the context constructor defines the retrieval function Psi_t(k) for each past event index k:

```
         | e_k,                              if e_k in L1(t),
Psi_t(k) = | kappa_{t_{r-1}+1 : t_{r-1}},   if e_k not in L1(t), e_k in L2(t), k = t_{r-1} + 1,
         | empty-set,                        otherwise.
```

Breaking down each case:

- **L1 hit (raw event):** If event e_k is in the current L1 cache, return the raw event verbatim. L1 contains the current research plan, raw code patches, terminal outputs, error logs, and metric results for the active phase. These are high-fidelity traces needed for precise debugging.
- **L2 fallback (compact summary):** If e_k is not in L1 but its phase is represented in L2, return the compact knowledge summary kappa for that phase. The index k = t_{r-1} + 1 means the representative index for phase r is its first event -- a single refined unit replaces the entire raw trajectory of that completed phase.
- **Discard:** If an event is in neither L1 nor L2, it is dropped entirely.

**Context assembly.** The full context is constructed by concatenating the retrieval results across all event indices up to t-1:

```
C_{t-1} = g(E_{t-1}) = concat{Psi_t(k)}_{k=0}^{t-1}
```

**Priority ordering.** The priority is strict:

1. L1 preferred (raw, full fidelity -- active phase only)
2. L2 fallback (compact summary -- one unit per completed phase)
3. Discard (everything else is dropped)

**What this achieves.** "This policy retrieves all plan events and active-phase traces in raw form, while representing each completed phase by a single refined unit, preventing context saturation without losing strategic continuity" (Section 3.4.2). The agent's context window always sees: the full event history before initial code generation (E_{t_0 - 1}), all phase boundary proposals (P_{p-1}), and the raw execution traces of the currently active phase (E_{t_{p-1}+1 : t}). Completed phases are compressed to a single kappa unit each. This is why the context length shown in Figure 4 stays bounded at ~70k tokens despite the full interaction history potentially exceeding 200k tokens.

**Relation to L1 definition.** The formal definition of L1 at step t is (Section 3.3.1):

```
L1(t) = E_{t_0 - 1} ∪ P_{p-1} ∪ E_{t_{p-1}+1 : t}
```

where:
- E_{t_0 - 1} = all events before reaching the initial code and its results
- P_{p-1} = {e_{t_r}}_{r=0}^{p-1} = all high-level plan proposals at phase boundaries
- E_{t_{p-1}+1 : t} = raw execution traces of the currently active plan

And the L2 cache at step t is (Section 3.3.2):

```
L2(t) = {kappa_{t_{r-1}+1 : t_{r-1}}}_{r=1}^{p-1}
```

one compact knowledge summary per completed phase.

### 3.4.3 Consolidation via Context Promotion

Context promotion is the write path: information flows *up* the hierarchy through two operators. The paper states: "The context promotion operator P performs LLM-based retrospective abstraction that compresses execution traces into concise knowledge or transferable wisdom." The full operator decomposes as P = (P1, P2).

---

#### Operator P1: Phase-Level Promotion

**Trigger.** P1 fires at every phase boundary -- when the agent reaches time step t_p and completes phase p. This is the end of one complete cycle of hierarchical research plan execution.

**Input.** The input to P1 is the set of all parallel exploration trajectories generated during phase p. Specifically, at the beginning of phase p, the agent proposes a hierarchical research plan with m exploration directions, each containing q concrete implementation suggestions. Each suggestion (i, j) in I_p = {1,...,m} x {1,...,q} induces an interaction trajectory:

```
sigma_{p,i,j} = (e_{a_{p,i,j}}, e_{a_{p,i,j}+1}, ..., e_{b_{p,i,j}})
```

where a_{p,i,j} and b_{p,i,j} are the start and end time steps constrained by the phase boundaries t_{p-1} < a_{p,i,j} <= b_{p,i,j} < t_p, for all (i,j) in I_p.

P1 takes the full collection of these trajectories as input:

```
{sigma_{p,i,j}}_{(i,j) in I_p}
```

**Output.** P1 maps all trajectories for phase p to a single textual knowledge summary kappa_p:

```
kappa_p = kappa_{t_{p-1}+1 : t_p - 1} = P1({sigma_{p,i,j}}_{(i,j) in I_p})
```

This is a single refined knowledge unit that captures what was learned across all m*q parallel explorations during phase p.

**The P1 prompt (verbatim, Appendix A.3).** The LLM call that implements P1 uses the following prompt:

```
You are a Kaggle Grandmaster with critical thinking skills participating in
a high-stakes competition.  I will provide you with: (1) the competition
task, (2) your memory of previous attempted research plans and summarized
results, and (3) your current research plan along with its raw results
(code outputs, logs, etc.).

Competition Information:
{task_description}

Memory:
{memory}

Current Research Plan:
{research_plan}

Corresponding Results:
{results}

# Your Task
Your goal is to perform a deep analysis of the current experiment and
synthesize it into a strategic summary.  Your summary needs to be concise
but informative.  **Do not just describe what happened.** You must evaluate
the **value** of the result.

Your output must cover two key aspects:
1.  **Execution Summary:** Concisely state whether the plan worked as
intended, the performance achieved.
2.  **Strategic Insights & Future Direction:** This is the most important
part.  Based on the current results AND your memory of past attempted
research plans:
* Identify **High-Potential Directions**:  Which direction seems to be
promising?  Which direction should be amplified or iterated upon in the
next step?
* Identify **Dead Ends / Low-Value Paths**:  Which directions are clearly
ineffective or have reached a performance plateau?  Explicitly advise
against continuing in these specific directions to save compute resources.

# Response Format
Your output should contain **only** the final analysis text.
Do not add any explanations, comments, greetings, or extra sentences before
or after the summary.
Do not wrap the answer with phrases like "Here is the summary".  Output the
content directly.
```

The template variables are:
- `{task_description}` -- the competition task text
- `{memory}` -- the current L2 cache contents (kappa units from prior phases)
- `{research_plan}` -- the high-level plan text proposed at the start of phase p
- `{results}` -- the raw terminal outputs, metric logs, and execution traces from all trajectories in phase p

**What the P1 output contains.** The prompt explicitly requires two sections: an Execution Summary (factual performance achieved) and Strategic Insights & Future Direction (which paths to amplify, which are dead ends). This maps directly to L2's role as "mid-term strategic memory" -- the output is not a transcript summary but a strategic analysis that guides subsequent phases.

**Cache update after P1.** After P1 completes:
- The new kappa_p is written to L2: L2 <- L2 ∪ {kappa_p}
- The raw trajectories for phase p are removed from L1: L1 <- L1 \ {e | there-exists (i,j) in I_p, e in sigma_{p,i,j}}

This is the eviction mechanism for L1. L1 content is discarded at phase boundaries, specifically after P1 has absorbed it into a compact L2 summary. Raw execution traces only live in L1 while the phase that produced them is still active.

**Which LLM runs P1.** The paper's experiment setup (Section 4.1) states: "we use Deepseek-V3.2-Speciale as the main backbone language model for coding and researching and Deepseek-V3.2 with thinking is sparingly used for context promotion." P1 is therefore run with Deepseek-V3.2 with thinking enabled (the reasoning/chain-of-thought variant), used sparingly because it is more expensive. This is a deliberate design choice: promotion is a high-stakes distillation step that benefits from extended reasoning, but it fires only O(phases-per-task) times rather than at every agent step.

---

#### Operator P2: Task-Level Promotion

**Trigger.** P2 fires exactly once per task -- when the agent completes a task at the maximum step limit t_max. This is the end of the entire task lifecycle.

**Input.** P2 takes the full structured task history at completion:

```
w_tau = P2(d_tau, L1(t_max), L2(t_max), h(E_{t_max}))
```

The inputs are:
- d_tau -- the task descriptor (compact text summary of the task)
- L1(t_max) -- the final state of the evolving experience cache at task end
- L2(t_max) -- the full set of phase-level knowledge summaries accumulated over the entire task
- h(E_{t_max}) -- the final solution code, obtained by applying the extraction function h(.) to the terminal interaction history

**Output.** P2 produces a task-level wisdom representation w_tau. This is a distilled, task-agnostic text entry that captures transferable strategies from the completed task.

**The P2 prompt (verbatim, Appendix A.3).** The LLM call that implements P2 uses the following prompt:

```
Here is the kaggle task description, exploration trajectories and the final
high performance code of the task {task_name}.

Based on these information.  Your job is to
1.  summarize the key point about the data loading and preprocessing of the
best code.
2.  summarize the key point about the model selection and the model
training of the best code.
Your response should be concise but not too short.  Do not omit any
parameters.  You should make sure an code engineer can basically reproduce
the code with your summarization.

Kaggle task description:
{task_description}

Trajectories and final code:
{trajectories}

Your answer should follow the format below:
DATA SUMMARY:
YOUR ANSWER
MODEL SUMMARY:
YOUR ANSWER
```

The template variables are:
- `{task_name}` -- the name of the Kaggle competition
- `{task_description}` -- the full competition description
- `{trajectories}` -- the exploration trajectories and final code (drawn from L1(t_max), L2(t_max), and h(E_{t_max}))

**What the P2 output contains.** The structured output format -- DATA SUMMARY / MODEL SUMMARY -- captures the two most reusable dimensions of an ML solution: how data was loaded and preprocessed, and how the model was selected and trained. The prompt explicitly requires parameter-level detail: "Do not omit any parameters. You should make sure a code engineer can basically reproduce the code with your summarization." This is what makes L3 entries useful as priors for future tasks rather than vague high-level summaries.

**How abstraction/generalization is achieved.** The P2 prompt implicitly generalizes by extracting the *method* from the specific *instance*: it describes what the best code does (data pipeline choices, model architecture, hyperparameters) in a way that is re-applicable to similar future tasks, rather than narrating the trial-and-error process. The task-agnostic framing is reinforced by using the task *description* as context rather than the full raw event sequence, directing the LLM to focus on the transferable technical content.

**Cache update after P2.** The wisdom w_tau is embedded and stored in L3:

```
L3 <- L3 ∪ {(E(d_tau), w_tau)}
```

where E(d_tau) is the embedding of the task descriptor, serving as the retrieval key for future prefetch operations. "Through this process, transient execution-level context is progressively crystallized into persistent, retrieval-ready wisdom, completing the cognitive accumulation loop" (Section 3.4.3).

### Eviction and Compression Summary

The paper does not describe a general eviction policy for L2 or L3 (they are treated as persistent and unbounded within a task). The eviction logic is entirely in L1:

| Event | Action |
|---|---|
| Phase boundary t_p reached | P1 fires; all raw trajectories from the completed phase are removed from L1 |
| Task completion t_max reached | P2 fires; task history is crystallized into L3 |
| No special event | L1 grows within the active phase; L2 and L3 are read-only during exploration |

L2 grows by one kappa unit per completed phase. Because each kappa is a compact strategic summary (not a raw transcript), L2 growth is slow and bounded by the number of phases per task. The paper does not describe a mechanism to compress L2 within a single task if it grows too large -- the implicit assumption is that per-phase summaries are compact enough to remain manageable within the 24-hour task budget.

L3 is persistent across tasks and is updated only upon task completion. It is never evicted; it only grows. The retrieval threshold delta governs which L3 entries surface at prefetch time, providing implicit filtering without deletion.

---

### Relevance Heuristics and Promotion Decisions

The question of what is worth promoting versus discarding is answered differently at each level:

**L1 to L2 (P1 decision).** P1 does not selectively promote -- it always fires at phase boundaries and always produces a kappa. The selectivity is in *what kappa contains*. The P1 prompt asks the LLM to evaluate the *value* of each direction: it explicitly requests identification of high-potential directions to amplify and dead ends to avoid. Directions that failed are not lost -- they are recorded as negative knowledge in the strategic summary ("explicitly advise against continuing in these specific directions to save compute resources"). This converts failure signals into reusable guidance, preventing the agent from re-exploring known dead ends in subsequent phases.

**L2 to L3 (P2 decision).** P2 fires unconditionally at task end and always writes to L3. There is no explicit quality gate. However, the P2 prompt filters by performance implicitly: it asks to summarize "the key points about the data loading and preprocessing of the **best code**" and "the key points about the model selection and training of the **best code**." Only the final high-performance solution is abstracted into L3, not the failed intermediate attempts. The wisdom entry therefore represents a validated, high-quality strategy.

**L3 to context (prefetch decision).** The retrieval threshold delta acts as a relevance gate at read time. Only sufficiently similar past tasks contribute to initialization. This prevents irrelevant wisdom from contaminating the initial context with misleading priors.

### Formal Algorithm: Full Context Migration Loop

Synthesizing from Sections 3.4.1--3.4.3, the complete context migration protocol for a single task tau is:

```
CONTEXT MIGRATION PROTOCOL for task tau:

--- INITIALIZATION ---
1. Compute task descriptor: d_tau <- LLM(task_description)   [A.1 prompt]
2. Embed descriptor: q <- E(d_tau)
3. Prefetch from L3: Omega_tau <- {w_n | (h_n, w_n) in L3, cos(q, h_n) > delta}
4. Construct initial event: e_0 <- concat(d_tau, u_user, Omega_tau)
5. Set initial context: C_0 <- g(E_0) = e_0

--- PER-STEP CONTEXT ASSEMBLY (at each step t in [t_{p-1}, t_p)) ---
6. For each k in {0, ..., t-1}:
       if e_k in L1(t):    Psi_t(k) <- e_k                           [L1 hit]
       elif e_k in L2(t) and k = t_{r-1}+1:
                           Psi_t(k) <- kappa_{t_{r-1}+1 : t_{r-1}}   [L2 fallback]
       else:               Psi_t(k) <- empty-set                      [discard]
7. Assemble context: C_{t-1} <- concat{Psi_t(k)}_{k=0}^{t-1}
8. Agent acts: e_t ~ pi(. | C_{t-1})

--- PHASE BOUNDARY (when t = t_p) ---
9. Collect all parallel trajectories: {sigma_{p,i,j}}_{(i,j) in I_p}
10. Run P1: kappa_p <- P1({sigma_{p,i,j}})   [A.3 P1 prompt, Deepseek-V3.2+thinking]
11. Update L2: L2 <- L2 ∪ {kappa_p}
12. Evict from L1: L1 <- L1 \ {e | exists (i,j) in I_p, e in sigma_{p,i,j}}
13. Agent proposes next research plan; p <- p + 1

--- TASK COMPLETION (when t = t_max) ---
14. Extract final solution: I* <- h(E_{t_max})
15. Run P2: w_tau <- P2(d_tau, L1(t_max), L2(t_max), I*)   [A.3 P2 prompt]
16. Embed and store in L3: L3 <- L3 ∪ {(E(d_tau), w_tau)}
```

### Concrete Example Trace: plant-pathology-2021-fgvc8

The paper provides an annotated example in Figure 3, using the Kaggle task *plant-pathology-2021-fgvc8* (a multi-label image classification task with RGB apple leaf images). The trace illustrates all three context migration operations:

**Context Prefetch (task start).**
The task descriptor is generated: "This is a multi-label image classification task where the input consists of RGB images of apple leaves, and [more task descriptions...]". This is embedded and used to query L3. The retrieved wisdom (Omega_tau) contains prior knowledge such as:

> "Augmentation: Apply training augmentation including cropping [more augmentation related wisdom...] Backbone: vit_base_patch16_224 (Vision Transformer); Initialization: [more model related wisdom...]"

These entries are retrieved because past similar image classification tasks produced this wisdom via P2. The initial agent context C_0 includes this retrieved prior, giving the agent a head start on architecture selection.

**Context Hit (during exploration, phase 1).**
During phase 1 execution, the context assembles as follows (visible in Figure 3, center column):

- The initial wisdom and task description (from prefetch) -- rendered in green as L3 priors
- The current best code: "Backbone: vit_base_patch16_224 (Vision Transformer)"
- Terminal outputs: "Epoch 8/8 - Loss: 0.1677 - Val F1 (0.5): 0.87701"
- The current research plan (raw, from L1): "The research confirmed that interventions like Asymmetric Loss proved..."
- The current plan direction: "Please implement the idea xxx based on current best code [current best code...]"

These are all L1 hits -- raw events from the active phase. There are no completed phases yet so L2 is empty and no fallbacks occur.

**Context Hit (during exploration, phase 2).**
By phase 2, phase 1 has been completed and promoted. The context now contains:
- The initial task and wisdom context (unchanged)
- A compact L2 summary kappa_1 replacing the entire phase 1 raw trajectory: "The research confirmed that scaling to a ConvNeXt Large backbone with 384x384 resolution was the decisive factor. [more refined knowledge...]"
- The new raw phase 2 events in L1

The compressed kappa_1 unit replaces what would have been many thousands of tokens of raw execution logs.

**Context Promotion (end of phase 1, P1).**
At the phase 1 boundary, P1 fires with inputs:
- `{task_description}` = plant pathology competition details
- `{memory}` = empty (no prior phases)
- `{research_plan}` = the phase 1 plan directions
- `{results}` = all raw terminal outputs from phase 1 trajectories

P1 (Deepseek-V3.2 with thinking) produces kappa_1, which synthesizes which directions worked (ConvNeXt Large with high resolution) and which to avoid in subsequent phases.

**Context Promotion (task end, P2).**
When the task completes, P2 fires. The input includes all phase kappas in L2 and the final high-performance code. P2 generates:

```
DATA SUMMARY:
[key points about data loading and preprocessing of the best code]

MODEL SUMMARY:
[key points about model selection and training, with parameters]
```

This w_tau entry is embedded via E(d_tau) and stored in L3, ready to be retrieved the next time the agent encounters a similar image classification task.

### Connection to the Broader [[ml-master-architecture]]

Context migration is what transforms the three-tier cache from a static storage structure into a living cognitive system. Without CM:
- L1 would grow unboundedly and saturate the context window
- L2 would never be populated (no P1 firing)
- L3 would never be updated (no P2 firing) and prefetch would always return cold results

The ablation study in Section 4.3 (Table 2, [[experimental-evaluation]]) directly validates CM's necessity: removing L2 (which is equivalent to disabling P1 and the L2 fallback in Context Hit) drops the any-medal rate from 72.7% to 59.1%. The context promotion mechanism is described as the mechanism that limits peak context length from >200k tokens to ~70k tokens (Figure 4), enabling the agent to execute a full 24-hour research loop without saturation.

The design philosophy mirrors hardware cache hierarchies: fast/small L1 for immediate work, medium L2 for validated intermediate results, slow/large L3 for persistent cross-session state. CM governs the replacement policy -- in hardware terms, a write-through policy from L1 to L2 at phase boundaries, and a write-through from task summary to L3 at task completion, with reads always preferring the lowest (most recent) level that holds valid data.
