# Technical Analysis: how-to-ralph-wiggum

**Repository:** https://github.com/ghuntley/how-to-ralph-wiggum
**Version analyzed:** main branch (no versioned manifest)
**Date:** 2026-06-22

---

## 1. Overview / What Problem It Solves

Autonomous AI coding agents require orchestration, but the common instinct is to reach for complex orchestration frameworks -- graph engines, state machines, retry managers, observability layers. This repo argues the opposite: that a `while` loop piping a markdown file to `claude` is sufficient infrastructure for production-quality autonomous software development when the prompt design is correct.

"The Ralph Wiggum Technique" is a documented AI development methodology authored by Geoffrey Huntley targeting individual developers and small teams who want an LLM agent to write, test, commit, and push code continuously with minimal human involvement. The "Ralph" persona -- named after the Simpsons character who blurts things out without worrying -- refers to an agent running in a loop that self-selects tasks from a prioritized markdown plan file, implements them, validates via tests, commits, and starts the next task. The "technique" is the whole method: file layout conventions, prompt templates, context budgeting, subagent parallelism, and backpressure design.

The repo is not a library or CLI tool; it is a collection of copyable template files and a long-form HTML guide (~138 KB). The primary user is a human developer who copies `files/` into their own project root and configures `AGENTS.md` for their build system.

## 2. High-Level Architecture

```
Human (initial setup)
        │
        ▼
  specs/*.md  ─────────────────────────────────────────────────┐
  IMPLEMENTATION_PLAN.md (state file)                          │
  AGENTS.md (build/run guide)                                  │
        │                                                       │
        ▼                                                       │
  loop.sh  ──► cat PROMPT_build.md | claude -p \              │
                 --dangerously-skip-permissions \               │
                 --output-format=stream-json \                  │
                 --model opus                                   │
                        │                                       │
                        ▼                                       │
              Claude (Opus) -- main agent                       │
              ├── up to 500 parallel Sonnet subagents (reads)  │
              ├── 1 Sonnet subagent (build/tests)              │
              ├── Opus subagents (complex reasoning)           │
              │        │                                        │
              │        ▼                                        │
              │   src/* (application code, written by Ralph)  │
              │   IMPLEMENTATION_PLAN.md (updated each iter.) ─┘
              │
              ▼
         git commit + git push  ──►  loop repeats
```

Data flow for one build iteration:
1. `loop.sh` reads `PROMPT_build.md` and pipes it to `claude -p`.
2. The Claude process (Opus) reads `specs/*`, `IMPLEMENTATION_PLAN.md`, and `AGENTS.md` from the working directory.
3. It spins up to 500 parallel Sonnet subagents to read/search source code without burning the main context.
4. Exactly one Sonnet subagent runs build and tests; the result gates whether the commit happens.
5. On success, the main agent commits (`git add -A && git commit`) and pushes. It then updates `IMPLEMENTATION_PLAN.md` to remove or mark the completed item.
6. `loop.sh` starts the next iteration, reading fresh `PROMPT_build.md` and the updated plan file.

Persistent state lives in `IMPLEMENTATION_PLAN.md` (task list) and `AGENTS.md` (operational learnings) on disk -- plain markdown files committed to git.

## 3. The Core Abstraction: IMPLEMENTATION_PLAN.md

`IMPLEMENTATION_PLAN.md` is the central shared-state object in the Ralph system. It is a flat, prioritized bullet list in markdown, deliberately human-readable and minimal. The file is:

- **Generated** by planning mode (PROMPT_plan.md, step 1) via an Opus subagent that compares `specs/*` against `src/*` and produces a sorted task list.
- **Consumed** each iteration start: the main agent reads it to pick the single highest-priority unfinished item.
- **Updated** mid-iteration: a dedicated subagent appends discoveries (bugs, missing specs, blockers) without the main agent holding the write lock.
- **Cleaned** periodically: when it grows large, the build prompt instructs a subagent to remove completed items.
- **Disposable**: explicitly intended to be deleted and regenerated when plans go stale or scope changes.

The template `files/IMPLEMENTATION_PLAN.md` is essentially empty (`<!-- Generated by LLM -->`), documenting that the file is entirely LLM-authored at runtime.

Key design choice: using markdown rather than JSON or YAML keeps the file within the "efficient range" of the context budget (markdown tokens are cheaper than JSON key/value overhead) and lets Opus reason over it without a parser.

## 4. LLM / External Service Integration

The repo does not ship its own LLM calls -- it is a methodology template that configures the Claude Code CLI (`claude`) as the execution engine.

- **Provider:** Anthropic Claude, accessed exclusively through the `claude` CLI (not the API SDK directly).
- **Required model:** `--model opus` for the primary agent (task selection, prioritization, architectural decisions). The build prompt explicitly allows `sonnet` as an override "for speed if plan is clear and tasks well-defined."
- **Subagent parallelism:** The build prompt authorizes up to 500 parallel Sonnet subagents for read/search operations. The constraint to exactly 1 subagent for build/test execution is a backpressure control preventing concurrent competing writes.
- **CLI flags used:**
  - `-p` -- headless mode, reads instructions from stdin.
  - `--dangerously-skip-permissions` -- bypasses all tool-use permission prompts; mandatory for unattended autonomous operation.
  - `--output-format=stream-json` -- structured JSONL output for log capture.
  - `--verbose` -- detailed execution trace.
- **No API keys in this repo** -- the Claude CLI handles authentication externally. The guide notes that sandboxed environments should receive "minimum viable secrets: API keys + deploy keys."
- **Cost implications:** Opus-as-primary is deliberately expensive per iteration. The methodology positions the approach as achieving "software costs less than a fast food worker's wage" through task efficiency rather than cheap model use.

## 5. The Main Pipeline: The Build Loop

The canonical build pipeline is a two-prompt system (plan then build) run through `loop.sh`.

**Phase 0 -- Requirements (human-authored, one-time):**
A developer uses an LLM conversation to identify Jobs to Be Done, breaks them into topics, and writes `specs/<topic>.md` files. These files describe acceptance criteria and expected behavior, not implementation steps. No automation; purely human work.

**Phase 1 -- Planning (`./loop.sh plan`):**

`PROMPT_plan.md:0a-0d` -- Orient: read `specs/*` (up to 250 parallel Sonnet subagents), `IMPLEMENTATION_PLAN.md`, `src/lib/*` (250 parallel Sonnet subagents), and `src/*`.

`PROMPT_plan.md:1` -- Gap analysis: one Opus subagent compares what specs describe against what source implements. It builds or overwrites `IMPLEMENTATION_PLAN.md` as a priority-sorted bullet list. "Ultrathink" instructs extended reasoning. This phase does NOT implement anything -- the prompt contains an explicit `IMPORTANT: Plan only. Do NOT implement anything.`

**Phase 2 -- Building (`./loop.sh` or `./loop.sh 20`):**

`PROMPT_build.md:0a-0d` -- Orient: read `specs/*` (500 parallel Sonnet), `IMPLEMENTATION_PLAN.md`, and `src/*`.

`PROMPT_build.md:1` -- Task selection: pick the highest-priority uncompleted item. Search source to confirm the feature is not already implemented (`don't assume not implemented`). Use Sonnet subagents for search, Opus for complex reasoning.

`PROMPT_build.md:2` -- Implement: write code, using parallel subagents for reads, a single subagent for build/test execution. Validate with the project's test suite.

`PROMPT_build.md:3-4` -- Finalize: update `IMPLEMENTATION_PLAN.md` (via subagent), `git add -A`, `git commit`, `git push`.

`loop.sh:47-54` -- After the `claude` process exits, `loop.sh` pushes the current branch and increments `ITERATION`. The loop immediately restarts.

**Guardrail rules** (numbered 99999 and above in PROMPT_build.md, ordered by priority):
- Capture the "why" in documentation.
- Single sources of truth; no migration layers.
- Fix all failing tests, even unrelated ones.
- Create a git tag when no build errors remain.
- Keep `AGENTS.md` operational-only; no progress notes.
- Implement completely; no placeholders or stubs.

## 8. CLI / Usage Surface

**Entry point:** `files/loop.sh` -- copy to project root, make executable.

**Commands:**

```bash
# Build mode, unlimited iterations (standard autonomous run)
./loop.sh

# Build mode, stop after N iterations
./loop.sh 20

# Planning mode, unlimited (regenerate IMPLEMENTATION_PLAN.md)
./loop.sh plan

# Planning mode, stop after N iterations
./loop.sh plan 5
```

**Environment variables:** None declared. The model is hardcoded as `--model opus`; overriding requires editing the script.

**Configuration files:**

## 9. Extensibility Points

- **Custom build/test commands:** Edit `AGENTS.md`. The build prompt instructs Claude to consult `AGENTS.md` for project-specific commands. Add any validation command (TypeScript typecheck, migration runner, coverage threshold) and Ralph will run it each iteration.

- **Alternative models:** Edit the `--model opus` flag in `loop.sh` to `sonnet` or any Claude model. The build prompt already suggests Sonnet for clear-cut tasks. A `CLAUDE_MODEL` env var could be added with a one-line shell change.

- **LLM-as-judge backpressure:** The guide describes creating a `llm-review.ts` fixture in `src/` that Claude discovers and runs for subjective acceptance criteria (tone, aesthetics, UX). Ralph will include it in the test gate once it exists in source -- no prompt changes required.

- **Work branches / scoped plans:** The guide proposes a `plan-work` mode by adding a third prompt file (`PROMPT_plan_work.md`) that scopes `IMPLEMENTATION_PLAN.md` to a single feature branch. `loop.sh` would need a new mode argument to select it.

- **Monitoring / observability:** `--output-format=stream-json` produces JSONL to stdout. Redirect `loop.sh` output to a log file or pipe to a JSONL parser (`jq`, Grafana Alloy, etc.) to track token usage and iteration timing.

- **Acceptance-driven tests:** Add acceptance criteria in `specs/*.md` in a structured format and add a planning phase step to derive test stubs from them. No code changes to the loop; only prompt and spec file conventions change.

## 10. Limitations and Gotchas

- **`--dangerously-skip-permissions` is fully autonomous.** The flag bypasses all Claude tool-use permission checks. A runaway loop can delete files, run destructive commands, or make unintended API calls. The guide acknowledges this: "it is not if it gets popped, it's when it gets popped." A sandbox is strongly recommended but not technically enforced by this repo.

- **No loop termination signal from Claude.** `loop.sh` only terminates when `MAX_ITERATIONS` is reached or the user sends SIGINT. There is no mechanism for Claude to signal "I'm done with the plan" and exit cleanly. Operators must either set an iteration cap or monitor `IMPLEMENTATION_PLAN.md` manually.

- **Unconditional `git push` after every iteration.** `loop.sh:50-53` pushes regardless of whether substantive work was done. If Claude takes a no-op iteration, the push may fail on an empty state, causing a confusing loop failure.

- **Model hardcoded in `loop.sh`.** There is no env var or argument to switch models without editing the script. Sonnet subagents are controlled via prompt text; if Claude interprets the prompt differently it may use Opus for reads, multiplying cost.

- **Context utilization is the silent failure mode.** The methodology's correctness depends on tasks being small enough to fit at 40-60% of Opus's context. A spec that is too large, or a source tree requiring many file reads, will push the context into the "dumb zone" (>80% utilization per the guide). There is no automatic detection or guard.

- **`IMPLEMENTATION_PLAN.md` write-race risk.** The build prompt instructs Claude to update the plan via a subagent both "when you discover issues" and "after committing." Multiple subagents writing to the same file in the same iteration can produce malformed or duplicated content. No file locking is provided.

- **No specs templates provided.** The `specs/` directory is referenced throughout every prompt but there are no example spec files in the repo. New adopters must infer the expected format from prose alone.

- **README and index.html are near-identical and very large.** README.md is ~62 KB and index.html is ~138 KB. Both appear to be independently maintained versions of the same content -- a significant documentation duplication that the repo accepts as a maintenance tradeoff.

## 11. How It Compares to Alternatives

**LangGraph / LangChain agent loops:** LangGraph provides typed state machines, retry logic, streaming, checkpointing to SQLite, and structured tool definitions. Ralph trades all of that for a shell loop and markdown files. LangGraph is appropriate when the workflow graph is complex, has multiple conditional branches, or needs resumability after crash. Ralph wins on adoption speed and zero framework overhead for the common "pick a task, implement it, commit" workflow.

**OpenHands (formerly OpenDevin):** OpenHands is a full autonomous agent platform with a web UI, Docker sandboxing, event stream architecture, and multiple agent implementations. It solves the same problem with a production-grade platform. Ralph is a methodology template -- no UI, no event replay, no multi-agent coordination beyond what the adopter wires up. OpenHands suits teams wanting an out-of-the-box product; Ralph suits individuals who want to control every part of the loop.

**Aider:** Aider is a CLI coding assistant with git integration, repo map generation, and multi-file context management. It is interactive-first (though it has a `--yes` autonomous mode). Ralph is non-interactive by design and treats Claude's native file access as sufficient context management. Aider's repo map is more sophisticated; Ralph's context management relies entirely on prompt instructions and subagent delegation.

**SWE-agent:** SWE-agent wraps LLMs with a structured action interface (read file, write file, run bash) and evaluates on GitHub issue resolution benchmarks. It is a research artifact, not a daily-driver development loop. Ralph lacks the structured action interface but is designed for continuous multi-day operation on real projects rather than single-issue benchmark episodes.

**Positioning:** Ralph is the minimal viable autonomous coding loop -- a methodology rather than a framework, optimized for individual adoption speed over platform robustness. Its core differentiation is radical simplicity: fewer moving parts mean fewer things to debug when the loop misbehaves.

## Appendix: Selected Code Snippets

**The outer loop -- `files/loop.sh:36-56`**

```bash
while true; do
    if [ $MAX_ITERATIONS -gt 0 ] && [ $ITERATION -ge $MAX_ITERATIONS ]; then
        echo "Reached max iterations: $MAX_ITERATIONS"
        break
    fi

    cat "$PROMPT_FILE" | claude -p \
        --dangerously-skip-permissions \
        --output-format=stream-json \
        --model opus \
        --verbose

    git push origin "$CURRENT_BRANCH" || {
        echo "Failed to push. Creating remote branch..."
        git push -u origin "$CURRENT_BRANCH"
    }

    ITERATION=$((ITERATION + 1))
    echo -e "\n\n======================== LOOP $ITERATION ========================\n"
done
```

**Build prompt orient + task selection -- `files/PROMPT_build.md:0a-1` (key excerpt)**

```
0a. Study `specs/*` with up to 500 parallel Sonnet subagents to learn the application specifications.
0b. Study @IMPLEMENTATION_PLAN.md.
0c. For reference, the application source code is in `src/*`.

1. Your task is to implement functionality per the specifications using parallel subagents.
Follow @IMPLEMENTATION_PLAN.md and choose the most important item to address.
Before making changes, search the codebase (don't assume not implemented) using Sonnet subagents.
You may use up to 500 parallel Sonnet subagents for searches/reads and
only 1 Sonnet subagent for build/tests.
Use Opus subagents when complex reasoning is needed (debugging, architectural decisions).
```

**Guardrail numbering convention -- `files/PROMPT_build.md` (trailing rules)**

```
99999. Important: When authoring documentation, capture the why.
999999. Important: Single sources of truth, no migrations/adapters.
9999999. As soon as there are no build or test errors create a git tag.
...
999999999999999. IMPORTANT: Keep @AGENTS.md operational only — status updates
and progress notes belong in IMPLEMENTATION_PLAN.md. A bloated AGENTS.md
pollutes every future loop's context.
```

The exponentially-growing rule numbers are intentional: instructions higher in the prompt take precedence in Claude's attention, so large trailing numbers push these rules to the bottom of the priority stack while keeping them present as absolute constraints.
