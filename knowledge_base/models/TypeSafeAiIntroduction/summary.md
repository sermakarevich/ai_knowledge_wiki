# Introduction - TypeSafe AI

**Article:** [TypeSafe docs](https://docs.typesafe.ai/introduction) — TypeSafe AI documentation (24 pages, fetched 2026-09-16)

## Human Readable TL;DR

Most AI models today are like talented essay writers: you ask them something and they write you a paragraph, and then your software has to carefully read that paragraph and figure out what decision was actually made. TypeSafe's Jev works more like a panel of judges holding up scorecards: you show them the same situation and each one instantly gives you a clean, usable verdict — a choice, a score, or a yes-or-no reading — that your code can act on directly without reading any essays. You can ask dozens of these quick gut-check questions at once, the way you might poll several experts in the same room simultaneously, and each answer stays independent so adding more questions barely slows things down, letting you combine simple answers with your own rules — like asking separately about a car's engine, price, and comfort instead of just asking "is this a good car?" — while using certainty scores to decide when to act automatically and when to ask a human. The docs then show how to build whole systems this way, with ready-made patterns, live demos like a smart-home assistant, SDKs (software development kits, meaning ready-made code libraries) for Python and JavaScript, a simple web API (application programming interface, meaning a URL your code can call), and even a helper package that teaches coding assistants to wire it all up for you.

## TL;DR

TypeSafe introduces Jev, its flagship System One model, which replaces text generation plus output parsing with fast, structured decisions that software consumes directly as typed values and probability distributions, evaluating one shared state (the content under judgment) against many questions in a single parallel call with minimal added latency and no context-rot. It exposes three modular and composable primitives — Choice for selecting among fixed options, Score for rating along an ordered rubric with fractional positions, and Noul for judging the truth of a statement as a 0–1 probability — where every question carries instructions plus criteria, returns full probability distributions with confidence derived from their shape, and accepts JSON structure (objects, arrays, labeled keys, taxonomies, examples) anywhere clarity demands it. The recommended usage pattern is atomic, well-scoped questions resembling fast expert gut-checks, decomposed ruthlessly and composed deterministically in code with weighted sums and risk-scaled confidence thresholds, supported by four documented patterns (speculative fan-out, confidence-gated routing, composite scoring, intent routing), a broad use-case map spanning support, moderation, routing, verification, and feature extraction, a smart-home demo pairing TypeSafe with an LLM (large language model) fallback, SDKs and a POST /v1/systemone HTTP API with standard error codes and automatic retries, and an agent skill that gives coding assistants full API context.

## Problem & Motivation

Large language models (LLMs, meaning the familiar text-generating AI systems) are designed to produce text for humans to read, which creates a mismatch when the consumer of a judgment is code rather than a person. In that setup developers must coerce a text-generation system into emitting structured decisions and then parse the results back into values the program can depend on, a round trip that is fragile, slow, expensive, and hard to trust for branching, sorting, and routing at scale. TypeSafe's motivation is to remove that mismatch entirely by training models for calibrated decisions instead of generated text, so that the model output arrives as typed values and probability distributions that code can branch on, sort by, threshold, and route with directly. The deeper bet, laid out in the AI primer, is that large-scale automation will be roughly 99% machine-to-machine rather than chat, so what matters is Machine Native Intelligence with software-like properties — structure, reliability, observability, testability, speed, consistency, and low cost — achieved through a third post-training path called RLCD (reinforcement learning for calibrated decisions) alongside RLHF (reinforcement learning from human feedback, which optimizes for what people prefer and yields chatbots) and RLVR (reinforcement learning with verifiable rewards, which yields slower reasoning models). Because RLHF rewards what sounds good to people, it can produce sycophancy, confident hallucinations, and mode dropping, whereas RLCD optimizes the output contract code actually needs: constrained decisions plus calibrated uncertainty, where calibration is a group rate (outcomes assigned 0.8 should occur about 80% of the time) that lets software decide when to act and when to escalate.

## Main Original Ideas

1. **System One models for direct software consumption:** the docs introduce System One models as a class of fast, intuitive-style decision models named after Kahneman's (psychologist Daniel Kahneman's) fast System 1 thinking, with Jev as TypeSafe's flagship and first such model. Like an LLM a System One model understands natural-language input, but instead of writing replies, code, or explanations it evaluates a state and returns typed decisions and probabilities, with confidence included so code can decide when to act and when to escalate to a person or a reasoning model.
2. **State as separated, structured input:** state is the content passed in the `state` field for the model to evaluate — a support message, a passage, or application state as a string, object, or array — with one state per request seen identically by every question. The guidance is to prefer objects with descriptive names so relationships stay clear, keep the facts in the state and the judgments in the questions, send only relevant context to avoid distraction, and reference nested fields with backticked dot-and-index paths such as `ticket.messages[0].text`.
3. **Three composable AI primitives:** TypeSafe exposes Choice (choose one of up to 255 fixed options, returning choice, probabilities summing to 1, and confidence), Score (rate along 2–10 ordered descriptive levels, returning a probability-weighted fractional score plus legend, probabilities, and confidence), and Noul (answer a yes/no question with a single 0–1 probability and no separate confidence). Every question has a caller-chosen ID that is never sent to the model, a type, instructions holding the actual question, and criteria (options map, ordered levels, or optional true/false descriptions), and the selection rule is to prefer whichever answer maps directly onto code — Choice onto branches, Score onto thresholds and rankings, Noul onto `if` statements.
4. **Parallel isolated evaluation with structured entries:** all three question types can be mixed in a single API call against the same state, each evaluated independently and in parallel so adding questions barely changes response time, costs only cheap question tokens within a ~32,000-token budget, never leaks one answer into another as hidden context, and never invents out-of-schema values. Instructions, Choice options, Score levels, and Noul criteria all accept JSON structure (string, object, array, or null), so rubrics like `what`/`not_for`/`examples`, taxonomy subtrees, schemas, and labeled multi-part instructions carry meaning the model actually uses, including walking deep taxonomies one Choice per level with beam search over probabilities.
5. **Confidence as an architectural second axis:** every Choice and Score answer carries the full probability distribution plus a 0–1 confidence number derived from its shape (peaked means confident, flat means uncertain), while a Noul near 0.5 directly signals ambiguity, and the full distributions are always returned so teams are never locked into TypeSafe's confidence definition. The docs prescribe three behavior bands (act automatically, proceed with caution, do not act) with risk-scaled thresholds inside one system — for example a 0.5 floor below which anything routes to a human, read-only balance checks proceeding above it, and destructive transfers needing above 0.9 plus confirmation — tuned conservatively against each team's own data by plotting confidence against accuracy.
6. **Code-owned AI-powered software and four patterns:** the build philosophy keeps control flow, deterministic rules, and side effects in code while System One handles only narrow common-sense judgments over unstructured data, decomposing broad questions into atomic ones (one "is this spam?" becomes six Nouls; one "are tool calls correct?" becomes nine checks), asking many in one parallel request, and combining probabilities in code with weighted sums or downstream classifiers. Four patterns make this concrete: speculative fan-out (ask everything possibly needed upfront, including conditional follow-ups, and let `if` statements ignore the irrelevant), confidence-gated routing (the answer tells you what, confidence tells you whether to act), composite scoring (normalize each Score dimension to 0–1 and combine with explicit weights, e.g. resume screening feeding both Senior IC and Engineering Manager formulas from one call), and intent routing (one fast cheap classification call dispatching to deterministic code, specialist LLMs, or humans).
7. **Delivery surface: SDKs, HTTP API, demos, and agent skill:** the system is consumed through a Playground for interactive trials, a `POST https://api.typesafe.ai/v1/systemone` endpoint taking state, model (`jev-latest`), and a caller-keyed questions map and returning answers plus token usage with standard 401/422/429/529 errors and SDK-automatic exponential-backoff retries, typed Python and JavaScript/TypeScript SDKs with automatic retries, a demos collection headlined by a smart-home assistant that evaluates every request against a long speculative question list in one call while pairing TypeSafe with an LLM that splits compound commands and handles conversational fallback, and a drop-in agent skill (via Claude Code plugin, skills CLI, pasted prompt, or manual copy) that gives coding agents full API context, patterns, example prompts, vibe-coding principles, and troubleshooting for stale skills and threshold misuse.

## Key Findings

The documentation establishes that structured decisions with calibrated probabilities can be returned directly as typed outputs, eliminating the generate-then-parse loop for code-consumed judgments while staying fast enough for real-time paths at around 100–150 ms and cheap enough (roughly 100× cheaper) to run background automation, map-reduce over giant corpora, universal verification of other AIs' prompts and traces, and harness engineering such as model routing and guardrails. It defines the exact contracts of state, the three primitives, confidence, and the single-call parallelism rule, showing through worked examples — ticket triage with department Choice at 0.39 confidence splitting returns versus billing, bug-severity Score of 1.30 at 0.54 confidence, urgency Noul at 0.999, taxonomy walks, invoice field checks, spam-risk weighted sums, and voice-banking gates at 0.6 and 0.85 — that reliability and control improve when complex judgments are split into atomic questions and recombined deterministically in user code. It further demonstrates that wording matters enormously (descriptive situation-based levels beat bare numbers or degrees, contrastive `what`/`not_for`/`examples` rubrics resolve confused options, matching examples concentrate probability and raise confidence from 0.54 to 0.90), that different distributions can share the same score so probabilities and confidence must always be read alongside it, and that speculative questioning plus confidence gating lets one request serve an entire decision tree with ordinary branching logic. The use-case map generalizes this into five capability categories and ten decision shapes (classification, detection, scoring, routing, search, retrieval, ranking, verification, ML feature extraction, structured extraction) across some nineteen automation domains from support, recruiting, insurance, financial crime, legal, marketplaces, moderation, advertising, gaming, risk, and forecasting to knowledge graphs, giving teams a recipe of finding the closest industry, scanning its example decisions, and adapting them to their own documents and actions.

## Suggestions & Future Directions

The docs point readers toward concrete next steps rather than open research questions: start in the Playground with pasted text and mixed questions, get an API key from the dashboard and make a first `POST /v1/systemone` call with `jev-latest`, install the Python SDK (`pip install typesafe-sdk`, Python 3.10+) or JavaScript SDK and call `system_one`, and install the agent skill so a coding agent structures evaluations correctly from the beginning. For building, the guidance is to read the primitives and confidence pages before the patterns, decompose inputs and questions ruthlessly, prefer structure where guidance would otherwise blur, batch independent questions into one parallel request, combine outputs with visible weights or classical ML features, route on uncertainty with risk-scaled thresholds tested against each team's own data, and consult the cookbooks for parallel batching, hierarchical classification, SDE cascades, structure recovery, autoresearch labeling, and self-consistency. Readers are also invited to share killer use cases for the demos and patterns pages, check the machine-readable documentation index at `/llms.txt` as the discovery entry point, and follow each page's pointers (state preparation, API reference, SDK install tracks, demo source and README, skill update channels) before exploring further.
