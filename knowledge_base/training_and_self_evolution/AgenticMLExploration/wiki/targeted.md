# Targeted Analysis: The A-MLE Loop, Reliability, REA, and Limits

## The five stages as a concrete loop
A single session of Agentic ML Exploration (A-MLE, an agent system that carries model-improvement ideas through the full try-train-evaluate cycle) runs end to end like this:

1. **Input: a (model, objective, compute) triple.** The session fixes which ads ranking model is being improved, what goal counts as success (for example click, conversion, or view), and how much training compute budget is available.
2. **Hypothesis generation, grounded in live model state.** The agent — here a Large Language Model (LLM, a large AI model trained on text and code) with tools — reads the current training config, baseline metrics, and history of already-tried techniques for this model. It proposes a small set of candidate techniques, each with an explicit reason it fits the current state. An LLM critic scores each idea for novelty and feasibility.
3. **Strategy plan, negotiated with the engineer.** The agent orders the candidates into a plan given limits on runs, compute, or wall-clock time. The plan mixes exploration (testing single hypotheses alone) with exploitation (combining the most promising ones and pushing them harder). The engineer reviews this trade-off at the checkpoint and can approve, request changes, or stop.
4. **Sandboxed execution: edit to train to recover.** The agent works in an isolated copy of the codebase, so mistakes cannot harm production code. The loop is: edit code or config, run type checks and unit tests, build a software image, run a short smoke pass to verify the job starts, launch full training, then monitor. If the run fails, the agent tells infrastructure errors apart from genuine training divergence (a run going off track), then retries, fixes code or config, or reports the failure. If one branch proves infeasible, it reroutes remaining compute to other branches instead of abandoning the session.
5. **Result analysis against a rolling baseline.** Each result is compared against a rolling baseline (a continuously updated reference setup, not a frozen snapshot that would drift out of date). The agent breaks metrics down by segment to catch localized regressions an average would hide, and auto re-runs jobs whose within-run variance (random spread across repeated runs) is too high. It builds a structured leaderboard of candidates, then either feeds it back into strategy for another round or assembles the final output.
6. **Output: proposal or documented null result.** A session always ends with a recorded artifact: either a launch proposal with experiment design, results, and statistical analysis, or a documented null result so negative outcomes also enrich the shared knowledge.

All stages read from and write to the same shared substrate: long-lived, versioned markdown (a simple text format) trees in source control, with eligibility notes for matching techniques to similar models and Track Record write-back of new outcomes at session end.

## What the sandbox plus HITL checkpoints buy
The sandbox and the Human-in-the-Loop (HITL, an engineer review gate at each stage boundary) are two separate safety layers, and each catches different mistakes:

- **The sandbox catches bad code before expensive training.** Pre-flight checks, type checks, unit tests, and the short smoke pass validate edits in the isolated copy first. This is where hallucinated APIs (Application Programming Interfaces, plausible-sounding but non-existent pipeline functions the agent invents) are caught — before any large training job is launched.
- **HITL gates catch miscalibrated plans and evaluations and bound blast radius.** At every stage boundary the engineer can approve continuation, ask for changes, or end the session. A hallucinated code change is caught before training launch; a miscalibrated evaluation is caught before proposal writing. No single bad agent decision can run far, because the blast radius (how much damage one mistake can cause) is limited to one stage.

Together they convert untrusted agent output into statistically rigorous launch candidates. The evidence for this is the proposal acceptance finding: agent-written proposals pass human review at a much higher rate than baseline because reviewers cite better-grounded statistical analysis, cleaner documentation of negative results, and explicit segment-level breakdowns.

## How A-MLE relates to Meta's REA
The A-MLE paper never names REA. The mapping below is synthesis: A-MLE is the published paper framing and evaluation of the same paradigm that REA productizes, by overlapping authors. All REA facts in this section come from the companion article (Meta engineering blog, 17 Mar 2026), not from the paper.

- **REA is the Ranking Engineer Agent** (from the companion article), the production system driving the end-to-end Machine Learning (ML, software that learns patterns from data) lifecycle for ads ranking models.
- **Execution layer:** A-MLE's sandboxed execution loop plus its explicit waiting operator (which suspends the agent until an async training job finishes and resumes cleanly) maps to the REA Executor plus hibernate-and-wake mechanism (from the companion article), where the agent launches a training job, delegates the wait to a background system, shuts down, auto-resumes on completion, and operates over multiweek spans. REA is built on the internal Confucius agent framework (from the companion article).
- **Shared knowledge:** A-MLE's shared substrate with eligibility annotations and Track Record write-back maps to the Historical Insights Database of past experiments plus the experiment logger that writes outcomes back (from the companion article).
- **Hypothesis sources:** A-MLE's hypothesis generators (model-state analyzers, training-efficiency analyzers, literature retrievers) map to the dual-source hypothesis engine (from the companion article): a Historical Insights Database plus an ML Research Agent doing deep research on baselines, where the best wins combine architectural and training-efficiency ideas.
- **Strategy:** A-MLE's exploration strategy mixing exploration and exploitation maps to the Three-Phase Planning Framework within engineer-approved compute budgets (from the companion article): Validation (test hypotheses in parallel), then Combination (combine promising ones), then Exploitation (push the hardest candidates).
- **Architecture and gates:** A-MLE's one agent over a skill library plus HITL (human-in-the-loop) checkpoints at each boundary maps to REA Planner plus REA Executor over a shared Skill, Knowledge and Tool System (from the companion article), with engineer-approved budgets and preflight checklists as the production safeguards (from the companion article). REA works only on the ads ranking codebase (from the companion article).
- **Reported production impact** (from the companion article): 2x average model accuracy over baseline across six models, and 5x engineering output — three engineers shipped launch proposals for eight models, versus a historical norm of two engineers per model.

## Failure modes and what still needs senior engineers
The paper reports five recurring failure modes. Each still needs a senior engineer somewhere in the loop:

1. **Hallucinated APIs.** The agent invents pipeline functions that do not exist. Pre-flight checks catch these before training, at the cost of extra compute. Senior need: keep review gates and typed procedures so invented calls never reach expensive runs.
2. **Baseline drift.** A concurrent baseline refresh wipes out the agent's measured win because the reference got stronger mid-session. The rolling baseline reduces but does not remove this risk. Senior need: recalibrate after baseline changes and judge whether a lost win is real or just a moved target.
3. **Infrastructure fragility.** Transient machine or cluster problems produce logs that look like training divergence, so the agent can abandon a good idea too early. The extended retry and error-discrimination loop helps. Senior need: exercise infra-versus-divergence judgment when the automatic call is uncertain.
4. **Over-confident triage.** The agent promotes a candidate from a single training seed (one random run) despite high variance, when one lucky run looks like a real gain. The auto re-run rule forces extra seeds when variance is high. Senior need: enforce multi-seed rigor and refuse single-seed promotions on noisy metrics.
5. **LLM-specific failures (LLM means large language model).** Weaker base models invent workflow identifiers, falsely claim completed work, or change behavior in non-monotone ways under stressful prompts (more pressure does not steadily help or hurt — the response flips unpredictably). The study finds prompt stress flips families differently, with Sonnet 4.0 best under stress. Senior need: prompt and behavior oversight, plus stress testing before trusting a swapped base model.

Structural limits beyond these five: technique transfer (reusing a proven technique on a structurally similar model) is the proven win, especially on long-tail models that rarely got expert attention. Novel-architecture depth — designing genuinely new architectures and pipelines — is future work, with the engineer as architect-in-chief and the agent as implementation and ablation partner.
