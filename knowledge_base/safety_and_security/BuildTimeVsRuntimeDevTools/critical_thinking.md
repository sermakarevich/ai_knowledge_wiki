# Critical Analysis: Build-Time vs. Run-Time: Why Dev Tools Fail in Production

## Claims vs. evidence

- **"Build-time tools are unsafe at runtime; runtime tools with fixed, parameterized SQL keep agents safe."** Suggestive, not strong. The only supporting evidence is a single narrated failure anecdote (an agent deleted a table when given an unrestricted build-time tool) and a *second* demo that was supposed to prove the positive case but whose video "failed to load" and was only described verbally (wiki 02, [6:31]-[6:40], [8:12]-[8:19]). No side-by-side run, no repeated trials, no rate of failure/success — one narrated incident is an anecdote, not a demonstrated causal mechanism.
- **"The source/tool evolution (source → read-only/allowed-datasets/output caps → custom tool → semantic tool → bound/authenticated parameters) eliminates confused-deputy risk and reaches 'zero trust.'"** Weak as stated. The seven-stage walkthrough (wiki 03) is a coherent engineering narrative, but "zero trust" is asserted, not tested against an adversarial scenario the way the salary-ticket example tested the *insecure* end of the spectrum. No equivalent "here's an attacker trying to break the hardened tool and failing" demo was shown live — the one demo meant to show the secured version working also didn't load.
- **"20 million tool calls last month" / "15.7K GitHub stars, 132+ contributors, 40+ databases" prove production readiness / adoption.** Unsupported as a proxy for safety or quality. These are unaudited, self-reported vendor metrics with no source cited, no time-series, no breakdown of what fraction of those calls used build-time vs. runtime tools (the very distinction the talk is about), and no independent verification. Popularity metrics say nothing about whether the security model actually holds under attack.
- **"Read-only restrictions were the most-requested customer feature."** Weak — an internal, unquantified product-feedback claim (no ticket counts, no survey data) used to justify a design choice.

## Genuinely new vs. repackaged

- Novel/useful as a *concrete engineering pattern* rather than a research contribution: the **"source" primitive** that moves connection details into a preconfigured YAML file outside agent reach, and the explicit **bound vs. authenticated parameter** distinction (application-injected identity vs. tool-validated signed token) as two named, implementable mechanisms for stripping identity out of agent control (wiki 03, stage 6). This is a reasonably specific product-level answer to a real problem.
- Repackaged / prior art, and the speakers themselves credit this: the **confused deputy attack** is decades-old computer-security terminology (Norm Hardy, 1988) applied here to LLM agents rather than invented by the talk. The **lethal trifecta** is explicitly attributed to Simon Willison (wiki 03, [9:12]-[9:38]) — the talk correctly cites it, but it is not the speakers' idea. **Read-only access / least-privilege / separating user-application-agent identity** is standard database and IAM (identity and access management) practice going back well before agentic AI; the talk's contribution is applying these known controls to an MCP tool-serving layer, not discovering a new security principle. The three-tier tool taxonomy (admin/NL2SQL/structured SQL) is also a restatement of "human-in-the-loop vs. autonomous," a distinction long made in general automation/RPA (robotic process automation) safety design.

## Weaknesses and blind spots

- **No live demo actually shown.** The failure demo is described from an error message, not shown running end-to-end; the intended runtime-safety demo's video failed to load entirely (wiki 02, [6:05]-[8:19]). For a talk whose entire persuasive structure is "watch the bad thing happen, then watch the fix prevent it," having zero working demonstrations is a material gap — the audience saw slides and narration, not evidence.
- **No quantified attack success/failure rate.** There is no ablation showing, e.g., how many prompt-injection or social-engineering attempts succeeded against the fully model-controlled tool versus the hardened "zero trust" tool. The salary-ticket example (wiki 03, [9:41]-[10:42]) is a single illustrative scenario, not a tested attack corpus.
- **No cost/latency discussion for the added guardrail layers.** Read-only checks, allowed-dataset enums, output-size caps, prepared-statement typing, and token validation all add configuration and runtime overhead; the talk never discusses this tradeoff, even though it separately claims structured SQL tools "help with latency" (wiki 01, [4:37]-[5:08]) — an unreconciled tension.
- **No comparison to competing approaches.** No mention of how this stacks up against LangChain's own tool-permission/human-approval mechanisms, Anthropic's MCP security guidance, or other vendors' database-MCP servers. The talk treats MCP Toolbox's design as *the* solution rather than *a* solution among several being developed industry-wide.
- **Vendor lock-in.** The entire hardening path is expressed as Google MCP Toolbox YAML configuration (sources, custom tools, semantic tools). Adopting the pattern conceptually is free; adopting the concrete mechanism ties a team to Toolbox's config schema and hosted "model armor" offering.

## Applicability

- Helps most: teams already running SQL-backed agents through MCP Toolbox (or willing to adopt a similar source/tool abstraction layer), where the "known query in advance" structured-SQL pattern fits the production use case (e.g., a support chatbot with a bounded set of actions like "cancel order" or "lookup flights").
- Doesn't transfer cleanly: non-SQL tool ecosystems (REST-API-only, file-system, or messaging tools) where there's no natural "source" primitive to bind connection/credential details to; NL2SQL-style analytical use cases where the whole point is open-ended querying (the talk's own admission — structured tools sacrifice the flexibility that made NL2SQL useful in the first place, wiki 01 [3:44]-[5:08]); teams without ownership of their tool-serving layer, who can't insert an equivalent identity-binding step between the agent and the database.

**Relevance to my work** —
- The **user/application/agent identity separation** (wiki 03, [10:59]-[12:03]) is directly applicable to designing agent access to the Elisity data lake via Athena: an agent should get the narrowest scoped, per-query credentials rather than reusing a broad application service-account, mirroring the "agent identity narrower than app identity" principle.
- The **bound vs. authenticated parameter** distinction is worth adopting literally: never let an LLM agent supply a `user_id`-equivalent value into an Athena query string; either inject it from an already-authenticated session (bound) or validate a signed token inside the tool (authenticated) — this maps cleanly onto any agent-facing wrapper around data-lake queries.
- The **confused-deputy / lethal-trifecta framing** is a useful checklist question for any agentic pipeline that reads private data (Athena tables) and also ingests untrusted text (tickets, emails, chat) with some exfiltration path (Slack post, email reply) — worth explicitly auditing Elisity's own agent tools against this trifecta rather than treating it as Google-specific.
- The **structured-SQL-over-NL2SQL-for-production** recommendation is a reasonable default for any customer-facing or automated agent over the data lake, but for internal analytics/exploration use cases (which is more of what Athena access typically supports) the NL2SQL pattern with a human reviewing output may remain the right tradeoff — don't over-apply the "always lock it down" lesson where the human-in-the-loop already exists.

## What this changes

If the claims hold, teams building database-backed agent tools get a concrete migration path (source → custom tool → semantic tool → bound/authenticated parameter) instead of having to invent one from scratch. This mainly affects **tool/platform engineers** configuring MCP servers, not model researchers or prompt engineers — the security burden shifts from "write a better system prompt" to "write a stricter YAML/tool-schema config." Second-order effect: more configuration surface (source definitions, per-tool SQL, parameter binding rules) becomes a new thing to security-review, replacing prompt-injection review with config-review — a net win only if that config is actually audited as rigorously as code, which the talk doesn't address.

## Verdict

This is a vendor engineering talk, not a research paper: it has no benchmarks, no ablations, no third-party validation, and its two live demonstrations — the one that was supposed to show a failure, and the one supposed to show the fix working — both weren't actually demonstrated running end-to-end. Its security taxonomy (confused deputy, lethal trifecta, least privilege) is correctly cited but is prior art the speakers openly credit rather than original research. The practical value is in the "source → semantic tool → bound parameter" engineering pattern, which is a reasonable, checklist-worthy design to borrow for SQL/data-lake agent tooling even though it's Google-Toolbox-flavored. Treat it as a solid practitioner checklist, not evidence of a solved problem: **trial** — worth prototyping the bound/authenticated-parameter pattern for data-lake agent access, but don't cite "20M tool calls" or "zero trust" as proof it's battle-tested.
