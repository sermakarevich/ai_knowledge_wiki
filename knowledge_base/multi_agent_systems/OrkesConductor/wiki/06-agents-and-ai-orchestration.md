# Agents and AI Orchestration
**In one sentence:** Orkes Conductor runs Large Language Model (LLM -- a model that generates text from context) agents as durable workflows, where model output is a proposal that the workflow validates, gates, executes as tasks, and persists turn by turn.
## Key points
- An agent is a turn loop (LLM proposes next action, Conductor validates and schedules it, workers/tools/people execute it, results persist as context for the next turn), and every turn is an ordinary persisted workflow task.
- Three authoring paths coexist in one graph: declarative AI workflows (LLM/MCP (Model Context Protocol -- a standard for exposing tools to models)/control-flow tasks placed directly in the definition), Conductor Agents (code-authored, compiled to a workflow graph, invoked via `AGENT`), and remote A2A (Agent2Agent -- a protocol for one agent calling another over a network) agents (independently deployed services called through a durable `AGENT` handoff).
- Conductor-native agents and bring-your-own-framework agents (OpenAI Agents SDK (Software Development Kit -- a language library for building against a platform), Google ADK (Agent Development Kit), LangGraph, LangChain, LlamaIndex, CrewAI, Vercel AI SDK) share one lifecycle: create, plan (inspect compiled graph), deploy (register named version), serve (run tool workers), run (execute once or invoke deployed version by name).
- Multi-agent systems are one parent agent plus a `strategy` field selecting dispatch logic: `handoff`, `router`, `sequential`, `parallel`, `swarm`, `round_robin`, `random`, `plan_execute`, `manual` -- with parallel fan-out compiled to `FORK_JOIN`, not a loop.
- Durability means each LLM call, tool call, approval, and loop iteration checkpoints before the next begins, so crashes, deploys, retries, and multi-day `HUMAN` pauses resume from the last persisted state instead of restarting.
- Governance is layered at enforcement points: input/output/tool-input/tool-output guardrails (regex (regular expression), LLM-judge, custom, external) with `retry`/`raise`/`fix`/`human` outcomes, `HUMAN` approval gates before writes, evals asserting on the durable trace (tools, arguments, handoffs, guardrail events, turns, terminal state), and failure semantics that separate deterministic step failure (retry the step) from model failure (validate, replan, or fail closed).
- The production pattern is agent proposes, workflow disposes: a parent workflow validates input, chooses an execution boundary (native tasks, `agentType: conductor`, or `agentType: a2a`), validates the returned result, requires approval before any write, and compensates via `failureWorkflow`.

## Agent concepts
An agent uses an LLM to decide what to do next, working in turns until a goal is met. The action proposed in a turn can be a tool call, a question for a person, a delegation to a sub-agent, or a final answer. In Conductor that loop runs as a workflow execution: the proposal is data, not a command. Conductor validates it against schemas and policy, applies approvals, schedules the work as tasks, then writes inputs, outputs, timing, retries, and terminal state to durable storage before the next turn starts.
Workflows and agents compose in both directions. A workflow calls an agent through the `AGENT` task, where the agent is one durable step that returns `text` plus structured `output`. An agent's tools run as tasks (`CALL_MCP_TOOL`, `HTTP`, `SIMPLE` workers, embedded LLM tasks), so one process can mix ordinary tasks, native AI tasks, deployed agents, and remote agents. The `AGENT` task field `agentType` selects execution mode (`conductor` for a deployed Conductor Agent selected by `name`, `a2a` for a remote endpoint), not the authoring framework. OpenAI Agents, Google ADK, LangGraph, and similar names never appear as `agentType` values.
Operating principles stated across the docs: model output is a proposal; state belongs in the workflow (not in agent-process memory); side effects cross task boundaries through bounded interfaces with retries and timeouts; every turn is governable (inspectable and recoverable).
## Conductor-native agents vs framework agents
A Conductor Agent is authored in code with a Conductor SDK (Python, Java, TypeScript/JavaScript, C#) and registered on the server, which compiles it into an ordinary workflow definition. Each model call becomes an LLM task, each tool call a tool task, the loop between them control flow. The compiled graph is visible in the UI (User Interface) and API (Application Programming Interface), versioned, schedulable, cancellable, and composable with branching, timers, and human tasks.
A framework agent keeps the framework's own agent object (for example `create_agent` in LangChain, a graph in LangGraph, an agent in OpenAI Agents SDK or Google ADK) and the Conductor SDK compiles and runs it as a durable execution. The path is uniform: `run` compiles and executes once during development, `plan` exposes the compiled graph for inspection and CI (Continuous Integration), `deploy` registers the named versioned agent, `serve` starts the long-lived worker process that executes local tool functions, and parent workflows invoke the deployed name through `AGENT` with `agentType: conductor`. `serve` blocks, so production separates it into its own worker process while `deploy` runs in CI/CD (Continuous Integration / Continuous Delivery). CrewAI and LlamaIndex are listed as supported authoring surfaces alongside the above; Vercel AI SDK is supported through the JavaScript SDK examples.
The `AGENT` invocation contract: on a fresh call `name` and `prompt` are required, `version` optionally pins the deployed version, and `sessionId`, `runId`, `context`, `media`, `model`, `timeoutSeconds`, `idempotencyKey` are available when needed. Output normalizes to A2A lifecycle states (`working`, `input-required`, `completed`, `failed`, `canceled`) mapped onto Conductor task statuses, with `executionId`, `agentName`, `state`, `text`, and structured `output`. Guards `maxDurationSeconds` (default 86400) and `maxPollFailures` (default 30) bound the full run and transient poll failures; both fail terminally with best-effort cancellation of the child execution. Resume uses `executionId` plus a new `prompt` (for example after a `HUMAN` task collects the answer); workflow cancellation propagates to the in-flight agent on a best-effort basis. Server requirement: `conductor.integrations.ai.enabled=true`, otherwise the deployed-agent control plane and `agentType: conductor` are unavailable.
## Durable agents and durable adaptive graphs
Durable-agent guidance now lives under the production architecture page; the old durable-agents page redirects there. The claim is that agent reasoning steps persisted as workflow tasks let long runs survive restarts: a crash at iteration 15 of 20 resumes from 15, each LLM prompt/response, tool input/output, and human decision recorded, retries scoped to the failed task (the LLM is not re-called when only the downstream tool failed).
A durable adaptive graph is the stricter variant: an agent chooses next steps at runtime, but only from approved paths, with every choice validated, persisted, and gated. The flagship example is a governed GitHub PR (Pull Request) reviewer built only from built-in tasks (`LIST_MCP_TOOLS`, `CALL_MCP_TOOL`, `LLM_CHAT_COMPLETE`, `JSON_JQ_TRANSFORM`, `FORK_JOIN_DYNAMIC`, `JOIN`, `HUMAN`, `SWITCH`, `SET_VARIABLE`, `DO_WHILE`), needing no custom worker. It runs three fixed evidence passes (PR context, changed files, CI (Continuous Integration) checks), then one adaptive pass where the model selects one or two deep-dive reads from a fixed set; a JQ (JSON Query -- a JSON transformation language) guard validates, deduplicates, and caps the selection before fan-out (capped at two calls, `DO_WHILE` fixed at four iterations, 20-minute workflow timeout). PR text, comments, and diffs are treated as untrusted evidence in prompts, never as instructions. The synthesized review carries a workflow-ID marker checked against existing comments before publishing, so duplicate or ambiguous writes reconcile by marker search rather than blind retry (comment creation uses retry count zero because it lacks an idempotency key). A `HUMAN` task must return `approved: true` before the single `add_issue_comment` write; rejection completes the workflow with a durable no-write decision.
## Multi-agent architectures
A multi-agent system is one parent agent with a sub-agent list and a `strategy` field. The dividing question is who decides: the model, the graph, or developer code. `handoff` (model picks one sub-agent, conversational takeover) and `router` (model classifies and dispatches without conversation; cheaper than `handoff`) expose sub-agents as callable tools. `sequential` and `parallel` run the graph's ordering without consulting the model; `parallel` compiles to `FORK_JOIN`. `swarm` passes control between sub-agents until one finishes. `round_robin` and `random` rotate or sample (the latter for A/B comparison of agent versions). `plan_execute` is the only strategy that replans: the model drafts a plan of sub-agent calls, runs it, revises from results. `manual` leaves selection to code as a business rule.
What Conductor adds: each delegation is its own execution (a specialist retries without re-running the routing decision), the choice of sub-agent and its reason are recorded in the execution, sub-agents keep their own tools and guardrails (a billing agent cannot reach fulfilment tools), and parallel execution is genuinely parallel. Delegation across service boundaries uses the A2A protocol: the parent's `AGENT` task durably tracks handoff status, retry/cancellation lifecycle, and returned artifacts, while the remote agent's internals stay private to its operator. Scatter-gather (fan out to parallel specialists, then join and compare) and parallel-specialist-review recipes follow the same `FORK_JOIN`/`JOIN` shape. Human-approved-action recipes insert a `HUMAN` gate between proposal and consequential tool call; cancellation recipes rely on workflow termination propagating best-effort to the child agent, with post-cancellation writes reconciled by idempotency key or marker.
## LLM orchestration building blocks
Declarative AI workflows compose the AI task family directly: `LLM_CHAT_COMPLETE` / `LLM_TEXT_COMPLETE` (model calls with provider, model, messages, temperature, token limits, JSON (JavaScript Object Notation) output mode), prompt templates (versioned reusable prompts bound to integration models), embeddings and retrieval tasks (`LLM_GENERATE_EMBEDDINGS`, `LLM_STORE_EMBEDDINGS`, `LLM_GET_EMBEDDINGS`, `LLM_SEARCH_EMBEDDINGS`, `LLM_INDEX_TEXT`, `LLM_INDEX_DOCUMENT`, `LLM_SEARCH_INDEX`, `CHUNK_TEXT`, `PARSE_DOCUMENT`, `GET_DOCUMENT`, `LIST_FILES`), media tasks (`GENERATE_IMAGE`, `GENERATE_AUDIO`, `GENERATE_VIDEO`, `GENERATE_PDF`), and MCP tasks (`LIST_MCP_TOOLS`, `CALL_MCP_TOOL`). Control flow (`SWITCH`, `DO_WHILE`, `FORK_JOIN_DYNAMIC`, `SET_VARIABLE`, `JSON_JQ_TRANSFORM`, `INLINE`, `HUMAN`, `WAIT`) turns these into loops with validation, memory, and gates.
RAG (Retrieval-Augmented Generation -- answering from retrieved documents rather than model memory alone) recipe: chunk documents, embed with a fixed model, index with stable `docId` plus metadata into a named vector store/index/namespace, then at query time `LLM_SEARCH_INDEX`, grade whether retrieved context suffices (a separate LLM call forbidden from answering), rewrite the query and retry up to a bound (three rounds in the reference), and refuse (`TERMINATE` with `insufficient_grounding`) rather than answer ungrounded. Index-time and query-time embedding models must match; ingestion lives in its own workflow so the answer path does not depend on write availability.
MCP tool-calling recipe: `LIST_MCP_TOOLS` discovers the catalog at runtime (never hardcode), `JSON_JQ_TRANSFORM` strips mutating verbs deterministically, a small cheap model shortlists up to five candidates, a JQ step intersects the shortlist with actually discovered names, a capable model picks one, and the workflow re-validates the pick before `CALL_MCP_TOOL`. Credentials travel in headers from a secret store, never in workflow input.
Deep-research recipe: a bounded `DO_WHILE` loop alternates plan, parallel research (`FORK_JOIN_DYNAMIC` over a validated capped tool set), reflection/evaluation (LLM-as-judge second call), and memory update (`SET_VARIABLE`), terminating on a `done` flag or iteration/token/cost budget.
Agent memory: `SemanticMemory` stores facts and retrieves by similarity through a `recall` tool the agent calls, so only `max_results` relevant facts enter the prompt and cost stays flat as memory grows; the store is swappable, scoped per tenant, timestamped for expiry, and treated as an injection surface (validate before writing, never store whole transcripts).
Scheduling agents uses the ordinary workflow scheduler (cron-like schedules starting a workflow or agent-backed workflow on a cadence); the agent itself needs no separate scheduler.
## Governance: guardrails, human-in-the-loop, evals
Guardrails attach at the closest enforceable point: agent-input (reject unsafe requests before the model), agent-output (constrain responses), tool-input (block dangerous arguments before a write -- the critical boundary for database, shell, payment, email, or repository mutations), tool-output (validate returned data), and tool-approval/`HUMAN` (pause for a person before a consequential action). Implementations: regex for PII (Personally Identifiable Information)/formats/allowlists/known-dangerous strings (deterministic, `block` by default, `allow` for constrained formats); LLM guardrails for tone, groundedness, policy interpretation at temperature zero (semantic check, never carrying raw secrets); custom guardrails as registered workers for domain policy needing application state; external guardrails routing to a central policy service. Every guardrail declares `onFail`: `retry` (re-generate with feedback, bounded by `maxRetries`), `raise` (fail closed on non-negotiable violations), `fix` (accept custom-guardrail `fixed_output`), or `human` (durable review where the reviewer approves, edits, or rejects). Strongest guardrail goes directly before the consequential tool call; prompt instructions alone are not protection. Complementary bounds: tool schemas, `maxCalls` per tool, `maxTurns` per agent, timeouts, known-tool allowlists rejecting undeclared plans, `allowedTransitions` on handoffs, `requiredTools` for mandatory checks, CLI (Command-Line Interface) allowlists with shell disabled and short timeouts, server-side credential resolution, `maskedFields` redaction from history and UI.
Human-in-the-loop uses the `HUMAN` task: a durable pause consuming no compute, surviving restarts and deploys, resumable in seconds or days via the Task Update API. Patterns: pre-execution review (LLM plans, human approves, tool executes), conditional post-execution review (`SWITCH` routes low-confidence/high-value/sensitive results to `HUMAN`, auto-approves the rest), LLM-as-judge first-pass review routing only exceptions to a person. Timeouts are opt-in (`timeoutSeconds` plus `TIME_OUT_WF` or `ALERT_ONLY`); escalation pairs `HUMAN` with a parallel `WAIT` branch.
Evals replay representative requests and assert on the durable trace, not just final text: tools used/order/arguments/forbidden tools, routing and handoffs, guardrail pass/fail events, turn counts, terminal state, output content/type/regex, plus an optional pinned-model LLM judge (threshold-scored) for groundedness or usefulness. Building blocks in the Python SDK: `EvalCase`, `CorrectnessEval`, `expect(result)`, `assert_*` helpers (`assert_tool_used`, `assert_tool_called_with`, `assert_tool_call_order`, `assert_handoff_to`, `assert_guardrail_passed/failed`, `assert_max_turns`, and others), `mock_run()` for scripted no-model runs, `record()`/`replay()` for regression traces, `assert_output_satisfies()` for the judge. Practice: deterministic routing/side-effect suites on every change, semantic judge separate from fast CI, sandbox fixtures for write-capable tools, no production credentials in eval corpora.
## Failure semantics and token efficiency
Failure handling distinguishes deterministic step failure from agent/model failure. An LLM provider failure (rate limit, timeout, outage) moves `LLM_CHAT_COMPLETE` to `FAILED` and retries per `retryCount`/`retryLogic`/`retryDelaySeconds`; only that call retries, upstream outputs are reused, and exhaustion triggers `failureWorkflow` or workflow `FAILED`. Malformed model output is different: the LLM task already `COMPLETED`, so the fix is downstream validation (`SWITCH`/`INLINE`/JQ contract guard) that re-prompts with correction or fails closed -- the LLM is not automatically re-called. Tool timeouts (`responseTimeoutSeconds` to `TIMED_OUT`) and worker crashes after side effects expose at-least-once delivery: the timed-out request may still be in flight, so tool workers and MCP tools must be idempotent (task ID or correlation ID as idempotency key), writes without idempotency keys use retry zero plus marker reconciliation, and irreversible effects get compensation workflows. `HUMAN` waits hold indefinitely with no compute cost; duplicate external callbacks are safe because terminal-state tasks reject re-transitions; partial `FORK/JOIN` branches, mid-flight definition changes, worker deploys, missing dynamic task types, network partitions, and multi-hour/day/week loops each have defined behavior (completed tasks preserved, only the in-flight unit retries), except that retrying a failed `DO_WHILE` restarts that loop's iteration history.
Token efficiency follows from the same persistence: completed LLM outputs (prompt, response, usage, model, latency) are written to durable storage before the next task schedules, so crash recovery, retry-from-failed-task, rerun-from-task, and loop checkpointing (per-iteration `DO_WHILE` checkpoints) never re-pay for finished calls -- only the in-progress unit re-executes. Reference magnitudes: resuming a 20-step agent at step 18 costs about 4K tokens instead of 40K; retrying only a failed PDF step after a RAG pipeline costs zero LLM tokens instead of 12K; resuming a 100-iteration loop at 95 costs about 10K instead of 200K. Long `HUMAN` pauses, deploys, scaling events, and debugging reruns preserve upstream tokens the same way.
## Production architecture
The reference shape is a parent workflow owning the business process with the agent behind an explicit execution boundary: validate request shape/policy/IDs, choose native tasks (workflow graph owns orchestration), deployed Conductor Agent (`AGENT` with `agentType: conductor`), or remote A2A agent (`AGENT` with `agentType: a2a`), then validate result schema/policy/artifacts and approve-then-write or compensate on failure. (`SUB_WORKFLOW`/`START_WORKFLOW` compose child workflows; they do not invoke agent runtimes.) Canonical loop mapping: `LLM_CHAT_COMPLETE` plans, `SWITCH` plus guarded `CALL_MCP_TOOL` selects an approved tool, tool tasks execute with retry/timeout/recording, `FORK/JOIN` or `FORK_JOIN_DYNAMIC` parallelizes bounded fan-out, `SET_VARIABLE` plus workflow variables carry memory, `HUMAN` gates approval, `WAIT` holds long timers, `DO_WHILE` with LLM-as-judge runs reflection loops, `loopCondition` enforces iteration/token/cost budgets, `failureWorkflow` compensates side effects with full execution context. Production contract at every boundary: validate input before and output after (never let an unvalidated model or remote response decide a consequential action), carry correlation and idempotency keys into every external effect, keep orchestration state in workflow variables (resumable agent state behind execution ID, remote continuation in A2A context/task IDs), return small artifacts and references rather than raw histories. Readiness checklist from the docs: server-side credentials, least-privilege tools, human approval before consequential writes, bounded turns/parallelism/time/tokens/retries/cancellation/compensation, one correlation-ID convention with monitoring on terminal state/duration/retries/timeouts/tool failures/budget exhaustion/approval age, one recovery drill (interrupt, locate by correlation ID, retry/resume/terminate, verify audit trail), and minimal releases against sandbox tools with a known-good definition retained for rollback. Observability is automatic for native and compiled-agent paths (graph, prompts, tool I/O, approvals with identity, iteration/loop state, retry history, variables); A2A paths expose the handoff boundary while remote internals stay private.
