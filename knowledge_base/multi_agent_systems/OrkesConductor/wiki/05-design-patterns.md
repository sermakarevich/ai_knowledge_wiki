# Design Patterns Cookbook
**In one sentence:** Orkes Conductor implements orchestration (central controller driving a multi-step flow) as declarative workflow definitions where each recurring problem -- chaining, branching, fan-out, waiting, retrying, compensating, polling, scheduling, reacting to events -- maps to a named task operator plus explicit failure configuration.
## Key points
- Sequencing is dataflow: tasks pass outputs forward with `${taskRef.output...}` expressions, and `SWITCH` routes branches on prior outputs.
- Static parallelism uses `FORK_JOIN` with fixed `forkTasks` branches plus a `JOIN`; runtime-sized parallelism uses `FORK_JOIN_DYNAMIC` with `forkTaskName`/`forkTaskInputs`, `dynamicTasks`/`dynamicTasksInput`, or `forkTaskWorkflow`.
- Waiting is a first-class task: `WAIT` with `duration`, with `until`, or with no input (block until an external signal arrives); signals complete the first blocked `WAIT` via `POST /api/tasks/{id}/{status}/signal` (async) or `.../signal/sync` (blocking).
- Resilience is configured per task definition: `retryCount`, `retryLogic` (`FIXED`, `EXPONENTIAL_BACKOFF`, `LINEAR_BACKOFF`), `retryDelaySeconds`, `maxRetryDelaySeconds`, `backoffJitterMs`, `responseTimeoutSeconds` (heartbeat window), `timeoutSeconds`, `totalTimeoutSeconds` (wall-clock cap), and `timeoutPolicy` (`RETRY`, `TIME_OUT_WF`, `ALERT_ONLY`).
- There are no distributed transactions: cross-service rollback is the saga pattern -- forward steps plus a separate compensation workflow registered as `failureWorkflow` that reads `failedWorkflow` and undoes only completed steps in reverse order, idempotently (a service call safe to repeat without double effects).
- Long external jobs use one `HTTP_POLL` task (`terminationCondition`, `pollingInterval`, `pollingStrategy`, `maxPollCount`) instead of a `DO_WHILE` + `HTTP` loop, and recurring work uses scheduler objects (`cronExpression`, `zoneId`, `runCatchupScheduleInstances`, `scheduleStartTime`/`scheduleEndTime`) rather than sleep loops.
- Evolution is versioned: every execution pins the definition snapshot from start time, so new versions never disturb running executions unless explicitly upgraded via terminate plus restart with `useLatestDefinitions=true`.
---
## 1. Microservice orchestration (chaining HTTP/worker tasks)
- **Problem:** a business operation spans several services (validate order, charge payment, reserve inventory, send confirmation), each needing the previous step's output.
- **Mechanism:** sequential `HTTP` system tasks (no worker code needed) with `http_request` blocks (`uri`, `method`, `body`, `headers`, `connectionTimeOut`, `readTimeOut`); custom logic runs as `SIMPLE` worker tasks polled by external workers; `SWITCH` (`evaluatorType` `javascript` or `value-param`, `expression`, `decisionCases`) adds conditional branches (e.g. enterprise vs standard onboarding); data passes via `${workflow.input.x}` and `${taskRef.output.response.body.field}`.
- **Failure notes:** per-task retries apply; a failing step can trigger the workflow-level `failureWorkflow` for compensation; `SWITCH` needs a `default_case` or unmatched outputs stall routing; HTTP timeouts (`connectionTimeOut`/`readTimeOut`) bound each call.
## 2. Fan-out/fan-in: static (FORK_JOIN) vs dynamic (FORK_JOIN_DYNAMIC)
- **Problem:** independent calls (credit score, purchase history, support tickets) should run concurrently, but the branch count is sometimes fixed and sometimes known only at runtime (list length, per-region batches).
- **Mechanism:** static -- `FORK_JOIN` with fixed `forkTasks` (array of branches) followed by `JOIN`; dynamic -- `FORK_JOIN_DYNAMIC` in three forms: (a) different tasks per branch via `dynamicTasks` (array of task defs with `name`, `taskReferenceName`, `type`) plus `dynamicTasksInput` map, wired through `dynamicForkTasksParam`/`dynamicForkTasksInputParamName`, typically built by a preceding `INLINE` (script task) step; (b) same task over many inputs via `forkTaskName` + `forkTaskInputs` (Conductor injects `__index` per branch); (c) parallel sub-workflows via `forkTaskWorkflow` + `forkTaskWorkflowVersion` + `forkTaskInputs`; every form ends with a `JOIN` that collects all branch results.
- **Failure notes:** `JOIN` waits for all branches, so one stuck branch stalls the fan-in -- bound branch tasks with timeouts; dynamic inputs come from a computed step, so validate that step's output shape first; for parallel sub-workflows, each instance carries its own retries and timeouts.
## 3. Wait/timer patterns (WAIT, timeouts, webhook/signal resume)
- **Problem:** flows need delays (cooldowns, rate limiting), continuation at a clock time (publish dates, deadlines), or pauses for humans/external callbacks (approvals, manual QA).
- **Mechanism:** `WAIT` operator in three modes: `duration` (`30 seconds`, `5 minutes`, `2 hours`, `1 day`, short forms `30s`/`5m`/`2h`/`1d`, combinable); `until` (formats `yyyy-MM-dd HH:mm z`, `yyyy-MM-dd HH:mm`, `yyyy-MM-dd`, value can be `${workflow.input.reportDate}`); bare `WAIT` with no input blocks until signaled. Resume paths: signal API (`POST /api/tasks/{workflowId}/COMPLETED/signal` async, `/signal/sync` with `returnStrategy` and `timeoutMillis` for callers needing the next state), event-handler `complete_task` action targeting `taskRefName`, or task-update endpoint for exact task targeting. Reject path: signal `FAILED` instead of `COMPLETED` to run the failure branch; signal output becomes `${approval.output...}` downstream. Related: `WAIT_FOR_WEBHOOK` system task and `HUMAN` task cover verified-webhook and human-assignment variants.
- **Failure notes:** a `WAIT` with no timeout waits indefinitely -- set workflow/task timeouts for SLA (Service Level Agreement, an explicit time promise) bounds; sync signal returns `404` when nothing is blocked; signals resolve the first non-terminal `WAIT` only and never `HUMAN` tasks; event-routed completion needs the real `workflowId` in the broker payload, a correlation id alone cannot target the task.
## 4. Timeouts, retries, idempotent (repeat-safe) workers
- **Problem:** workers crash, downstream APIs (Application Programming Interfaces, service call interfaces) flap, jobs outlive heartbeat windows, and mass failures retry in lockstep.
- **Mechanism:** task-definition fields registered via `POST /api/metadata/taskdefs`: `retryCount`, `retryLogic` (`FIXED` constant delay; `EXPONENTIAL_BACKOFF` doubling `retryDelaySeconds * 2^attempt`; `LINEAR_BACKOFF` incremental `retryDelaySeconds * attempt`), `retryDelaySeconds`, `maxRetryDelaySeconds` (cap), `backoffJitterMs` (random spread), `responseTimeoutSeconds` (heartbeat/lease window), `timeoutSeconds` (total per task incl. heartbeats), `totalTimeoutSeconds` (wall-clock budget across all retries, whichever limit hits first wins), `timeoutPolicy` (`RETRY` re-queues counting against `retryCount`; `TIME_OUT_WF` fails the workflow; `ALERT_ONLY` logs and lets the task continue), `concurrentExecLimit`. Long workers extend the lease by posting `IN_PROGRESS` with `callbackAfterSeconds` before `responseTimeoutSeconds` expires. Non-retryable errors return `FAILED_WITH_TERMINAL_ERROR` from the worker to skip remaining retries. Docs' recommended pairings: rate-limited APIs get `EXPONENTIAL_BACKOFF` + cap + jitter; long jobs get short heartbeat + worker heartbeats + long `timeoutSeconds`; SLA (Service Level Agreement) tasks get `totalTimeoutSeconds`; high fan-out gets jitter + `concurrentExecLimit`.
- **Failure notes:** without heartbeats a silent worker is marked `TIMED_OUT` and retried, then the late worker's result is discarded; retries re-execute side effects, so every write needs an idempotency key (a caller-supplied dedupe token such as `Idempotency-Key: {orderId}-charge`); thundering-herd retries without jitter hit a recovering service as one burst.
## 5. Saga and compensation (explicit undo vs DB transactions)
- **Problem:** each service owns its own data, so no single database transaction spans reserve-inventory, charge-payment, book-shipment; a late failure (carrier `503`) leaves partial effects with nothing to roll back.
- **Mechanism:** the main workflow declares `failureWorkflow` (plus optional `failureWorkflowVersion`); Conductor starts it only after the main workflow fails terminally. The failure workflow receives `reason`, `workflowId`, `failureStatus`, `failureTaskId`, and `failedWorkflow` (the full failed execution). Recipe shape: `JSON_JQ_TRANSFORM` (`determine_what_completed`) queries `failedWorkflow.tasks` for `COMPLETED` reference names, then per-undo `SWITCH` gates (`undoPayment`, `undoInventory`) run compensating `HTTP`/`SIMPLE` tasks (refund, release) in reverse order, keyed idempotently from the original business id (`orderId`). The output carries `conductor.failure_workflow` linking to the compensation run.
- **Failure notes:** never undo blindly -- gate each compensating task on what actually completed or a refund fires for a charge that never happened; give compensation more retries than the forward path (forward 1, undo 5 with backoff); compensation is a new transaction (refund ledger entry), not rollback -- design for eventual consistency; alert when compensation itself fails via its own `failureWorkflow` or status listener; terminate-and-restart of sagas can repeat side effects unless keys derive from caller ids.
## 6. Polling long-running external jobs (HTTP_POLL)
- **Problem:** a third-party API (Application Programming Interface) returns a job id for work taking minutes to hours; holding a thread or worker open is wasteful and hammering the vendor is rude.
- **Mechanism:** `submit_job (HTTP)` then one `await_job (HTTP_POLL)` task then `SWITCH` on outcome. `HTTP_POLL` accepts the standard `http_request` block plus `terminationCondition` (script over `$.output.response.body`/`$.input`; boolean done/keep-going, or `1` complete / `0` repoll / `-1` fail), `pollingInterval` (seconds), `pollingStrategy` (`FIXED`, `LINEAR_BACKOFF`, `EXPONENTIAL_BACKOFF`), `maxPollCount` (default `1000`). The task sleeps between polls holding nothing open and appears as a single task with a poll count.
- **Failure notes:** match every terminal state (`SUCCEEDED` and `FAILED`) in the condition or dead jobs poll until `maxPollCount`; `pollingInterval` is clamped to the server floor `conductor.worker.http_poll.min_poll_interval` (default 60s) -- size `maxPollCount` and workflow `timeoutSeconds` against the effective interval; prefer `EXPONENTIAL_BACKOFF` for unknown-length jobs; poll a cheap status URL and use `outputFilter` to keep payloads out of workflow state; the submit step needs an idempotency key or a retry creates a second job you are not polling. Explicit doc guidance: below the poll floor, use synchronous `HTTP`.
## 7. Scheduled/cron workflows
- **Problem:** run a workflow on a clock (every minute, weekday mornings, bounded campaign windows) including behavior after scheduler downtime.
- **Mechanism:** scheduler objects via Scheduler API (Application Programming Interface) (`POST /api/scheduler/schedules`) or CLI (Command Line Interface, terminal commands): `cronExpression` (e.g. `0 * * * * *`, `0 0 9 * * MON-FRI`), `zoneId` (IANA timezone, follows daylight-saving transitions), `startWorkflowRequest` (`name`, `version`, `input`, `correlationId`), `runCatchupScheduleInstances` (replay missed slots or skip), `scheduleStartTime`/`scheduleEndTime` (epoch-millisecond window bounds), `paused`. Scheduler injects `_scheduledTime`, `_executedTime`, `_startedByScheduler`, `_executionId`, `_schedulerCron` into workflow input for window computation (e.g. `INLINE` computing a 24h report window).
- **Failure notes:** catchup after downtime is a burst -- target workflows must be idempotent and capacity-aware; Conductor has no native overlap policy, so a new slot can start while the prior execution is still active -- design for concurrency or serialize externally; pin `version` in schedules when deterministic rollout matters since omitted version means latest.
## 8. Dynamic workflows in code (decide next tasks at runtime)
- **Problem:** the task graph is not known at authoring time (agent plans, per-batch steps) or JSON (JavaScript Object Notation, the definition format) hand-editing is too slow.
- **Mechanism:** SDK (Software Development Kit, the language client library) workflow-as-code: `ConductorWorkflow` plus `>>` chaining, `@worker_task` functions, `SwitchTask` (`switch_case`/`default_case`), `ForkTask`/`JoinTask`, `DoWhileTask` (`termination_condition`, `max_iterations`), `SubWorkflowTask`, and system-task builders (`HttpTask`, `JsonJQTask`, `WaitTask`); `workflow.register()` then `executor.execute()` for synchronous runs. Fully runtime graphs: build the task list in code and start with an inline `workflow_def` (`StartWorkflowRequest` with embedded definition) with no pre-registration; `DYNAMIC` task type covers late-bound task resolution.
- **Failure notes:** generated definitions still need the same retry/timeout/failure-workflow fields as static JSON; cap loops with `max_iterations`; synchronous `execute` blocks the caller -- use it for APIs (Application Programming Interfaces) and interactive apps, not for hours-long runs.
## 9. Event-driven choreography-to-orchestration (handlers, signals)
- **Problem:** pure choreography (services reacting to each other's events with no controller) is hard to observe and order; the fix is events at the edges with an orchestrated core.
- **Mechanism:** `EVENT` task publishes to a `sink` (`conductor:order-status` expands to `conductor:publish_order_event:order-status`; external sinks `kafka:`, `sqs:`, `nats:`, `amqp_queue:`/`amqp_exchange:`, `jsm:`, `nats_stream:` after enabling the matching module). Event handlers (`POST /api/event`) match `event` + `condition` (`$.status == 'READY'`) and fire actions: `start_workflow` (with `correlationId`, `input` mapping rooted at the event JSON) or `complete_task` (targets `workflowId` + `taskRefName`, completing a blocked `WAIT` from a broker message such as `kafka:order-approvals`). Incoming webhooks and `WAIT_FOR_WEBHOOK` cover push callbacks.
- **Failure notes:** handler payload expressions root at the `EVENT` task's published JSON -- schema drift silently stops matching, so version event payloads (`eventVersion`); `complete_task` requires the concrete `workflowId`, correlation id alone is not enough; gate handler conditions narrowly or every matching event spawns an execution; check the event-bus guide for delivery and idempotency semantics before relying on exactly-once assumptions.
## 10. Error-handling taxonomy, failure strategies, versioning for safe evolution
- **Problem:** task failure is not workflow failure, and conflating the layers produces either hair-trigger aborts or silent corruption.
- **Mechanism:** layers from the docs: (a) task retries (`retryCount`/`retryLogic`/`retryDelaySeconds`); (b) `optional: true` tasks -- workflow continues past their failure (analytics, notifications); (c) `FAILED_WITH_TERMINAL_ERROR` -- worker declares deterministic failure, skipping retries; (d) per-task `timeoutSeconds`/`responseTimeoutSeconds` + `timeoutPolicy` (`RETRY`/`TIME_OUT_WF`/`ALERT_ONLY` selection table in the error guide); (e) workflow-level `failureWorkflow` compensation or Slack-alert workflows; (f) `workflowStatusListenerEnabled` + `WorkflowStatusListener` interface (self-hosted) or CDC (Change Data Capture, the production event stream) on Orkes Cloud for completion/failure notifications. Versioning: definitions carry `version`; each execution pins its start-time snapshot; rollout = register new version, canary with pinned `--version`, move callers/schedules/parents, compare, keep the old version until migration ends; upgrade of a running execution = terminate then restart with `useLatestDefinitions=true` (UI: Terminate, then Restart with latest definitions; API: bulk terminate + bulk restart).
- **Failure notes:** restarting without `useLatestDefinitions` silently re-runs the old snapshot -- no upgrade happens; terminate-and-restart repeats side effects, so prefer letting executions drain unless idempotent or compensated; unpinned starts/schedules float to latest, which trades convenience for rollout control.
## When NOT to use Conductor
- Sub-second latency paths belong inside a service: the docs state `HTTP_POLL` floors at a 60s server-side minimum and say directly not to use it for sub-second work -- use synchronous `HTTP` instead, and by extension keep tight request/response loops out of the orchestrator.
- Do not model busy-spinning or high-frequency polling as `DO_WHILE` + `HTTP` loops: executions grow two tasks per iteration and become unreadable past dozens of iterations, with hand-built backoff and ceilings.
- Do not use workflows as a cron replacement for overlapping-sensitive jobs without external thought: the scheduler has no overlap policy and catchup replays can burst.
- Do not treat compensation as rollback: refunds/releases are new transactions needing their own retries, keys, alerts, and ledger entries.
