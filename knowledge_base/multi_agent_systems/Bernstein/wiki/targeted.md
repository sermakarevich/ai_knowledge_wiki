# Bernstein Deep Dive for Fleet: Targeted Comparison
**In one sentence:** Fleet should borrow Bernstein's deterministic (fully predictable, no randomness) coordination loop, bounded retries with model escalation, dead-letter queue (DLQ, a permanent list of tasks that failed for good), per-task worktrees with a serial merge queue, and a plugin-style adapter registry.
## Key points
- Coordination is plain Python with no model call on the decision path: one single-threaded tick loop matches tasks to agents and verifies completion (`src/bernstein/core/orchestration/orchestrator.py:1470`).
- Reproducibility comes from recording model responses to `llm_calls.jsonl` and replaying them strictly — a cache miss aborts instead of calling the live model (`src/bernstein/core/orchestration/deterministic.py:21`).
- Failed tasks retry on a bounded budget (hard cap of 2 regular retries), escalating effort first then model strength (haiku to sonnet to opus), and exhausted tasks land in a JSONL (JSON Lines, one JSON object per line) dead-letter queue the operator can resubmit (`src/bernstein/core/tasks/task_lifecycle.py:120`, `src/bernstein/core/tasks/dead_letter_queue.py:180`).
- Warm retries that resume an old session are only allowed when a verified checkpoint exists and the workspace hash still matches; anything else restarts cold from zero (`src/bernstein/core/tasks/checkpoint_retry.py:493`).
- Each task works in its own git worktree (a separate checked-out copy of the repo) on its own `agent/<session_id>` branch, and merges go through a strict FIFO (first-in-first-out) queue one at a time with lint, type-check, and test gates (`src/bernstein/core/git/worktree.py:1046`, `src/bernstein/core/git/merge_queue.py:277`).
- Double-claims are blocked by version checks (Compare-And-Swap, CAS: the claim only succeeds if the task version is unchanged) and stale claims from crashed workers reset to open on restart (`src/bernstein/core/tasks/task_store_core.py:2163`, `src/bernstein/core/tasks/task_store_core.py:758`).
- Any coding-agent CLI (command-line tool) plugs in through one adapter registry: a name-to-class dict plus a shared `spawn` interface, so fleet could support many coder backends without rewriting orchestration (`src/bernstein/adapters/registry.py:86`).

## Design principles
Bernstein is built on three rules: a deterministic scheduler, no model in the coordination loop, and policy-as-code (rules written as code and data, not as model prompts).
**Deterministic scheduler.** One tick equals one pass of `tick()`, which wraps `_tick_internal()` in a telemetry span and warns if a tick exceeds 30 seconds (`src/bernstein/core/orchestration/orchestrator.py:1470`). The `run()` loop is single-threaded — `while self._running or self._has_active_agents()` (`src/bernstein/core/orchestration/orchestrator.py:3313`) — so ticks never run concurrently. Task order comes from `topological_iter_with_parallel`, which walks the DAG (Directed Acyclic Graph: tasks plus dependencies, no cycles), sorts ready tasks by id for stable output, and yields serial tasks one at a time (`src/bernstein/core/orchestration/task_dag.py:200`). Randomness in routing is pinned by seeding Python's `random` module from the `BERNSTEIN_DETERMINISTIC_SEED` environment variable (`src/bernstein/core/orchestration/deterministic.py:17`).
**No model in the coordination loop.** LLM (Large Language Model, the AI text model) calls happen only for planning and decomposition, and every one is recorded as prompt-plus-model to `llm_calls.jsonl` (`src/bernstein/core/orchestration/deterministic.py:1`). Replay serves cached responses in per-key FIFO (first-in-first-out) order instead of calling the model (`src/bernstein/core/orchestration/deterministic.py:173`). Strict mode is the default: a cache miss raises `ReplayMissError` and aborts the run, and only the `BERNSTEIN_REPLAY_ALLOW_LIVE_MISS` opt-in flag downgrades misses to live fall-through (`src/bernstein/core/orchestration/deterministic.py:21`, `src/bernstein/core/orchestration/deterministic.py:57`).
**Policy-as-code.** Legal state jumps live in the `TASK_TRANSITIONS` table, and any illegal jump raises instead of silently proceeding (`src/bernstein/core/tasks/lifecycle.py:150`). Retry behavior is arithmetic over failure type and ladder position, not model judgment: the model ladder is `["haiku", "sonnet", "opus"]` (`src/bernstein/core/tasks/task_lifecycle.py:380`), and the retry budget is the minimum of the per-task limit, the reason-based limit, and a hard cap of 2 (`src/bernstein/core/tasks/task_lifecycle.py:120`).
## Worker restart and retry handling
**Janitor.** The janitor is the automatic quality checker that verifies completed work before a task may close. A task that fails the janitor verdict is reopened under the same id, counted in `janitor_reopen_count`, with a default budget of 2 reopen cycles configurable via `BERNSTEIN_JANITOR_REOPEN_MAX` (`src/bernstein/core/tasks/task_lifecycle.py:5133`). With no budget left the task fails permanently.
**Checkpoint retry.** Retries resume the old session (warm), branch a new session from the old checkpoint (fork), or restart from zero (cold); the modes are defined in `RetryMode` (`src/bernstein/core/tasks/checkpoint_retry.py:77`). The decision function `decide_retry` is pure — same inputs always give the same byte-identical decision (`src/bernstein/core/tasks/checkpoint_retry.py:425`). The safety rule is a workspace-hash comparison: the live worktree hash must equal the checkpoint's recorded hash, and any mismatch forces cold (`src/bernstein/core/tasks/checkpoint_retry.py:475`, `src/bernstein/core/tasks/checkpoint_retry.py:493`). Warm and fork retries send only a fixed corrective template naming the failed gate, never free text (`src/bernstein/core/tasks/checkpoint_retry.py:90`).
**Dead-letter queue.** Tasks that exhaust retries go to a DLQ stored as JSONL under `.sdd/runtime/dlq.jsonl` instead of being dropped silently (`src/bernstein/core/tasks/dead_letter_queue.py:144`). `enqueue` creates and appends the entry with task id, title, role, reason, retry count, and last error (`src/bernstein/core/tasks/dead_letter_queue.py:180`). Operators can list entries newest-first with role and pending filters, read one entry, see counts by role and reason, and replay an entry as a new task (`src/bernstein/core/tasks/dead_letter_queue.py:228`, `src/bernstein/core/tasks/dead_letter_queue.py:269`, `src/bernstein/core/tasks/dead_letter_queue.py:327`).
**Failed-task routing to a different model.** Retries escalate along the haiku-to-sonnet-to-opus ladder, leaving unknown model names unchanged so provider aliases are never swapped for a wrong tier (`src/bernstein/core/tasks/task_lifecycle.py:403`). The first retry only raises effort; the second and later retries escalate the model and reset effort to high, while large-scope tasks go straight to the strongest model (`src/bernstein/core/tasks/task_lifecycle.py:380` per the ladder and retry-policy code nearby). An operator-pinned model always wins and is carried through retries unchanged.
**Crash recovery.** On server restart, `recover_stale_claimed_tasks` resets every CLAIMED and IN_PROGRESS task to OPEN and clears the claim owner, writing the reset to the log at once so a second crash cannot resurrect the stale claim (`src/bernstein/core/tasks/task_store_core.py:758`).
## Conflict resolution
**Per-task worktrees.** Each agent session gets its own git worktree under `.sdd/worktrees` (`src/bernstein/core/git/worktree.py:40`), created per session id on branch `agent/<session_id>` (`src/bernstein/core/git/worktree.py:1046`). Two agents therefore never write to the same files during work.
**Merge gates and queue.** Before a merge lands, quality gates can run lint (`ruff check .`), type-check (`pyright`), and tests, with lint on and the other two opt-in (`src/bernstein/core/quality/quality_gates.py:203`, `src/bernstein/core/quality/quality_gates.py:205`, `src/bernstein/core/quality/quality_gates.py:207`). Merges are serialized through a thread-safe FIFO merge queue: `submit` enqueues the job, blocks until it reaches the head, holds the merge lock while git runs, then dequeues (`src/bernstein/core/git/merge_queue.py:200`, `src/bernstein/core/git/merge_queue.py:277`). Conflicts are detected before merging with `git merge-tree`, which simulates a merge without touching files (`src/bernstein/core/git/merge_queue.py:139`). Each merge job builds its branch name as `agent/<session_id>` (`src/bernstein/core/git/merge_queue.py:47`).
**Atomic backlog claims.** Atomic here means the whole take-a-task step happens as one unbreakable unit. Claims run inside a lock and move the task from OPEN to CLAIMED in one guarded step; claiming by id adds a CAS check that rejects the claim when the version has moved, the role mismatches, or the task is no longer open, with the HTTP layer mapping that refusal to 409 Conflict (`src/bernstein/core/tasks/task_store_core.py:2163`).
## Workflow abstraction
Work is expressed as a task graph with declared dependencies, executed in topological order with the planner's parallel-safety flags honored batch by batch (`src/bernstein/core/orchestration/task_dag.py:200`). Multi-agent sessions move through fixed phases `PLANNING` to `DISPATCH` to `WORKER_EXECUTION` to `SYNTHESIS` (`src/bernstein/core/orchestration/coordinator.py:16`). Task states are a fixed enum (open, claimed, in progress, done, failed, and others) so every component uses the same names (`src/bernstein/core/tasks/models.py:187`), and every state change passes through the `TASK_TRANSITIONS` allow-table (`src/bernstein/core/tasks/lifecycle.py:150`). Tasks that produce files instead of code skip git entirely: `needs_git_worktree` returns false for them and they run in a plain directory instead of a checkout (`src/bernstein/core/tasks/artifact_completion.py:168`). Proof of completion is a signed evidence bundle — test output, lint results, and other artifacts stored content-addressed and bound into one signed record (`src/bernstein/core/evidence/bundle.py:459`) — verifiable offline by recomputing the signature, the lineage-spine anchor, and every blob hash (`src/bernstein/core/evidence/bundle.py:899`), with the bundle mirrored into the audit chain (`src/bernstein/core/security/audit_chain.py:4283`).
## Multi-harness support
Every coding-agent CLI plugs in through one registry: `_ADAPTERS` is a plain dict mapping short names like `claude` to adapter classes (`src/bernstein/adapters/registry.py:86`). `get_adapter()` looks the name up, instantiates the class, stamps the lookup name on the instance, and raises `ValueError` listing what exists for unknown names (`src/bernstein/adapters/registry.py:232`, `src/bernstein/adapters/registry.py:275`, `src/bernstein/adapters/registry.py:284`, `src/bernstein/adapters/registry.py:293`). The `generic` adapter wraps any unprofiled CLI with a configurable command shape and is special-cased before the table lookup (`src/bernstein/adapters/registry.py:266`). Because orchestration only talks to the shared `spawn` interface, adding a harness means adding one dict entry plus one adapter class — the tick loop, claims, retries, and merge queue never change.
## What fleet can borrow
1. Single-threaded tick orchestration with no model on the decision path (`src/bernstein/core/orchestration/orchestrator.py:1470`) — maps to fleet's Python orchestrator: keep spawn, claim, and completion decisions as plain code over the beads database so runs stay predictable and cheap.
2. Strict recorded replay of model responses (`src/bernstein/core/orchestration/deterministic.py:21`) — maps to fleet by logging every planner prompt plus model and parameters to a JSONL file per run, so a failed fleet run can be re-executed byte-identically for debugging.
3. Bounded retries with effort-then-model escalation and an operator pin that always wins (`src/bernstein/core/tasks/task_lifecycle.py:403`, `src/bernstein/core/tasks/task_lifecycle.py:120`) — maps to fleet workers by retrying a failed bead first with a stronger effort setting, then a stronger coder model, capped at 2 retries unless the operator pins otherwise.
4. Workspace-hash-gated warm retries (`src/bernstein/core/tasks/checkpoint_retry.py:493`) — maps to fleet worktrees by hashing the worktree before resuming a crashed session there and restarting cold from zero on any mismatch, so resumed workers never inherit silently diverged state.
5. Dead-letter queue with operator replay (`src/bernstein/core/tasks/dead_letter_queue.py:180`, `src/bernstein/core/tasks/dead_letter_queue.py:269`) — maps to fleet's beads store as a permanent failed-bead list with a resubmit command, so exhausted beads stay visible and re-runnable instead of vanishing.
6. CAS claims plus restart reset of stale claims (`src/bernstein/core/tasks/task_store_core.py:2163`, `src/bernstein/core/tasks/task_store_core.py:758`) — maps to fleet's beads claims by adding a version number per bead, rejecting claims with a stale version, and resetting beads stuck in claimed or in-progress back to open on orchestrator restart.
7. Serial FIFO merge queue with pre-merge gates and conflict pre-flight (`src/bernstein/core/git/merge_queue.py:277`, `src/bernstein/core/quality/quality_gates.py:203`, `src/bernstein/core/git/merge_queue.py:139`) — maps to fleet's per-bead worktrees by merging one branch at a time onto main only after lint passes, with `git merge-tree` simulation catching conflicts before touching the tree.
8. Adapter registry decoupling harnesses from orchestration (`src/bernstein/adapters/registry.py:86`, `src/bernstein/adapters/registry.py:232`) — maps to fleet's coder workers by defining one `spawn` interface and a name-to-class table, so fleet can run different coder CLIs per bead without touching the beads database or the orchestrator loop.
