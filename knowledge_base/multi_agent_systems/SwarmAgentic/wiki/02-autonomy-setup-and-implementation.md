# Autonomy Criteria, Experimental Setup, and SwarmAgentic Implementation
**In one sentence:** This chunk defines three autonomy properties and scores seven prior frameworks against them, distinguishes SwarmAgentic from MODEL SWARMS, fixes exact dataset splits and metrics, and publishes the Role and Team code, the Particle Swarm Optimization pseudocode, and the full prompt repository that drives generation and optimization.
## Key points
- Autonomy is judged on three properties, namely from-scratch agent generation without predefined modules, self-optimizing agent functionality that rewrites an agent's own behavior from feedback, and self-optimizing agent collaboration that restructures sequencing, dependencies, and coordination, with only SwarmAgentic satisfying all three.
- Solo Performance Prompting fails all three properties while Evolutionary Agent and AgentSquare satisfy only functionality, and AutoAgents, AFlow, Agent Symbolic Learning, and Automated Design of Agentic Systems satisfy functionality plus collaboration but fail from-scratch generation.
- MODEL SWARMS optimizes pretrained model weights by interpolation to emit one opaque model, whereas SwarmAgentic constructs executable multi-agent systems from task descriptions with a Failure-Aware Velocity Update that symbolically rewrites roles and workflows.
- Training and evaluation splits are fixed as 128 train and 800 test for Multilingual Grade School Math, 5 train and 95 test out of 100 tasks for Creative Writing, 8 Trip Planning plus 10 Meeting and Calendar Scheduling examples for Natural Plan with a disjoint 10% held-out validation set, and 9 train queries against 180 evaluation queries for TravelPlanner.
- Baselines comprise Direct, Chain-of-Thought, Self-Refine, Solo Performance Prompting, Evolutionary Agent, and Automated Design of Agentic Systems with 7 hand-written seed agents, with prompt wording adapted per task but no extra search beyond each original algorithm.
- The implementation encodes each particle as a Team of Role objects plus generated forward code, searched by Algorithm 1 over at most T iterations with swarm size N, fitness function J, and Large Language Model operators for initialization, evaluation, flaw diagnosis, velocity, and position updates.
- Every velocity step fuses failure-driven learning that must not repeat documented failed adjustments with personal-best and global-best guidance, and every position step applies Add, Modify, Delete, and Reorder operations to roles and to workflow steps including inputs, outputs, and order.

## Defining autonomy: three core properties
Appendix A.1 states three properties that are mutually exclusive and jointly capture whether a framework can construct, adapt, and scale agent-based solutions. From-scratch agent generation requires dynamically synthesizing complete agent instances including roles, decision logic, and internal structure without relying on predefined functional modules such as hard-coded operators or task-specific behaviors, where only minimal task-agnostic scaffolding like input and output wrappers or abstract interfaces may be reused and all task-specific reasoning strategies, coordination flows, and behavioral compositions must be newly generated from the task context. The text stresses that manual design and fixed generation pipelines impose structural priors that hinder adaptability and block generalization to novel scenarios, which is essential for open-ended tasks involving high-level planning, system-level coordination, and creative reasoning. Self-optimizing agent functionality asks whether an agent's internal logic such as its role, responsibility, or execution policy can be automatically refined by the system itself during execution or across iterations in response to feedback without manual intervention, where the adaptation must target the agent's own behavior rather than merely global workflow wiring and must go beyond a fixed static prompt. Without this ability the system would depend on brittle static prompts and external corrections, which undermines autonomy and scalability in exploratory tasks with ambiguous goals or unexpected failures. Self-optimizing agent collaboration asks whether the framework can autonomously reconfigure collaborative structures including task sequencing, dependency refinement, inter-agent coordination, and the addition or removal of execution steps, because task decomposition, role delegation, and information flow often need mid-execution revision in open-ended multi-agent settings and systems that cannot restructure workflows cannot recover from coordination failures or adapt to emergent constraints.
## Evaluation of existing frameworks
Appendix A.2 justifies each binary assignment behind Table 1 for seven baselines. Solo Performance Prompting fails from-scratch generation because it relies on a hard-coded multi-persona scaffold prescribing persona identification, brainstorming, and revision with two hand-crafted examples, so roles, dialogue order, and interaction protocol are predefined rather than synthesized from the task, and it also fails both self-optimizing properties because prompts and decision policies are frozen so feedback changes only answer text while the interaction pattern can never be expanded, pruned, or reordered at run time. Evolutionary Agent fails from-scratch generation because evolution starts from a hand-written specialist supplied by MetaGPT, AutoGen, or a similar template and merely mutates roles, skills, and prompts, yet it satisfies functionality because language-model-guided mutation plus fitness evaluation iteratively refines each agent's internal behavior, while it fails collaboration because the interaction topology is fixed by the underlying framework so evolution can modify individuals but cannot reorder tasks, alter message routing, or create new coordination flows. AgentSquare fails from-scratch generation because search starts from a fixed library of four standardized module types for planning, reasoning, tool use, and memory extracted from sixteen existing agents, so new agents are only recombinations or mutations of predefined modules, yet it satisfies functionality since each module can be mutated or rewritten and retained or discarded on performance, while it fails collaboration because it optimizes a single-agent modular architecture and never reconfigures multi-agent interaction patterns or execution topology. AutoAgents fails from-scratch generation because it is hard-wired with four manager roles for Planner, Agent-Observer, Plan-Observer, and run-time Action-Observer that embed planning, evaluation, and dispatch logic beyond minimal scaffolding, constraining team structure and execution plans to a fixed template that cannot handle open-ended tasks like TravelPlanner with dynamic multi-role constraint coordination, yet it satisfies functionality through a THINK, PLAN, ACT, and REFLECT loop that rewrites each expert's prompt, plan, and memory, and it satisfies collaboration because the planner-observer dialogue can add or remove experts and resequence steps while the Action-Observer adjusts plans during execution. AFlow fails from-scratch generation because it assembles workflows from a fixed palette of hard-coded Generate, Revise, Ensemble, and Test operators so logic is selected rather than synthesized, yet it satisfies functionality since execution feedback triggers automatic prompt edits, control-flow tweaks, and operator replacement, and it satisfies collaboration because Monte Carlo Tree Search can reorder tasks, add or prune branches, and revise coordination strategies. Agent Symbolic Learning fails from-scratch generation because it starts from a manually crafted pipeline inherited from prior work rather than synthesizing roles from the task description, yet it meets functionality as each node's prompt and tool usage are refined via symbolic gradients driven by language loss, and it satisfies collaboration since the pipeline optimizer can add, delete, or move nodes to restructure coordination. Automated Design of Agentic Systems fails from-scratch generation because search starts from seven hand-written seed agents so candidates are mutated variants rather than creations from the task description alone, yet it satisfies functionality as the meta agent repeatedly rewrites each candidate's code, prompts, and tool calls preserving only the best variants, and it satisfies collaboration since the meta agent can insert or remove internal roles and reorder interactions across iterations.
## Comparison with MODEL SWARMS
Appendix B contrasts MODEL SWARMS with the present work across objective, search space, optimization strategy, and output structure despite shared swarm-intelligence inspiration. MODEL SWARMS is described as a collaborative optimization framework that adapts pretrained language experts by searching in model weight or token probability space, applying Particle Swarm Optimization to iteratively interpolate and update a pool of existing models guided by a task-specific utility function in order to discover a single adapted model that performs well under limited data without fine-tuning or strong assumptions about expert composition. The chunk then draws four categorical differences, namely that MODEL SWARMS optimizes parameters within a fixed expert pool while SwarmAgentic explores a language-based design space and constructs executable multi-agent systems from scratch with dynamic roles, internal logic, tool usage, and coordination strategies from task descriptions alone, that MODEL SWARMS relies on interpolation and performance-based selection while SwarmAgentic introduces a Failure-Aware Velocity Update performing symbolic rewriting of functionalities and flows, and that MODEL SWARMS emits a single opaque model for static evaluation while SwarmAgentic emits a modular interpretable system capable of reasoning, adapting, and evolving in complex dynamic environments. The appendix frames this as a paradigm shift from model fusion to full-system generation.

Initialization loops over N particles to create position x(0) via team initialization at temperature tempi, score fitness j(0) via J, diagnose problem p(0) via evaluation, summarize reflection f(1) via flaw identification, initialize velocity v(1), set personal best to the initial position, and update position to x(1), then sets the global best to the argmax over initial personal fitness values. The main loop runs t from 1 to T with all particles in parallel, updating fitness j(t), identifying problem p(t), summarizing reflection f(t+1), refreshing global and personal bests on improvement, and then updating velocity as v(t+1) equals the velocity operator applied to the failure term from failure learning, the personal-best term from personal guidance, and the global-best term from global guidance, corresponding to equations 3 through 6, before updating position x(t+1) via the position operator per equation 7. ## Prompt repository and operator roles
Appendix D.3 states the division of labor across eleven operators that together complete one optimization iteration. Team initialization creates roles and team composition, write-forward generates executable code from roles and workflow, evaluation analyzes workflow and execution to reveal issues and root causes, flaw identification traces problems to role or team configuration defects, velocity initialization gives direction and momentum from team state plus flaws, failure identification extracts ineffective changes from the prior plan, failure learning proposes improved strategies that avoid past failures, global-best and personal-best prompts mine transferable improvements without outright copying, velocity update integrates the three guidance sources to balance exploration and exploitation, and position update rewrites the team configuration per the velocity plan. The prose emphasizes that initialization ensures consistent allocation, evaluation references intended process deviations such as incorrect execution or missing information, and failure handling documents exact failed adjustments so future plans do not reintroduce them.
## Verbatim agent and initialization prompts
The shared agent template caps answers at 100 words and reads verbatim as ROLE_PROMPT with name, task instance, helpful information from teammates, responsibility, step-by-step policy instruction, and output guidance. Initialization demands highly specialized modular roles with a single primary aspect per role, strictly modular information flow where each step consumes structured upstream outputs and may reference the task definition only implicitly, single-role steps, structured outputs reusable as downstream inputs, and a final integration role, with deliverables defined as per-role name, responsibility, and policy plus an explicit collaboration structure and a sequential workflow listing role, input from prior outputs or empty, and output per step. System compilation instructs an expert Python programmer to emit a function wiring available roles per the given workflow using only team.call with role name, upstream-output inputs list, and double-quoted output specification, forbidding nonexistent roles, assumptions, and unused variables while requiring completeness against runtime failures with worked examples supplied.
## Verbatim evaluation, flaw, and velocity prompts
Evaluation asks an expert assistant to analyze the given workflow against the task and the reported team-result problem and to explain the root cause at identified steps with reference to task details and deviations from the intended process. Flaw identification reflects on that feedback against the current team and restricts verdicts to seven types, namely missing role with the needed role named, redundant role with the role named, role policy deficiency with gaps or contradictions and the role named, missing workflow step with the two neighboring steps named, redundant workflow step with role and exact step number, insufficient input with responsible role and step number, and inappropriate output only after checking whether the requested output exceeds the role's scope, in which case the task is reassigned or a new role created rather than blaming the current role. Velocity initialization then applies role operations of Add Role with name, responsibility, and policy when a subtask overburdens current roles, Modify Role for manageable policy refinements within scope, and Delete Role for redundant or conflicting roles, plus workflow operations of Add Step with role, upstream-output input, and expected output, Modify Input to incorporate prior outputs, Modify Output to align deliverables with downstream needs, Delete Step for redundant or overlapping steps, and Re-order Steps to fix sequencing without breaking dependencies, requiring each feedback flaw to be restated with its exact proposed adjustment. Failure identification instead asks a strategic advisor to map each current flaw to the previous adjustment plan and to quote the exact prior proposed adjustment for the same flaw or state None, while failure learning repeats the same Add, Modify, and Delete role and step operations but additionally quotes the failed adjustment per flaw and forbids reintroducing or rewording that same failed solution. The global-best prompt, truncated at the end of the chunk, frames a strategic assistant that improves the current team by analyzing a higher-performing example team for the same task type and suggesting practical non-copied improvements conditioned on current feedback.
