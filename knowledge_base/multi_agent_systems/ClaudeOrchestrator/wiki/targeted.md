# Claude-Orchestrator Skill + Orchestration-Playbook Core — Targeted Deep Dive

**In one sentence:** A harness-agnostic orchestration discipline (evidence levels, dispatch contract, acceptance iron rules, ORC-01–18 anti-patterns) plus a Claude Code adapter that enforces it through synchronous worktree batches, bounded task contracts, and mandatory cross-model review.

## Key points

- The core loop is decompose → contract → parallel dispatch in isolated worktrees → accept → merge → cross-model review → next batch; the orchestrator alone owns merge, push, and worktree removal (playbook `README.md:19-25`).
- Evidence discipline has four levels — direct (real target env), proxy (substitute/intermediary), local (dev/test only), blocked (needs human/external) — and upgrading a label is treated as lying (playbook `README.md:29-38`; adapter `SKILL.md:508-524`).
- Every dispatch carries a ten-field contract (outcome, anti-shallow-slice classification, minimum-change rationale, boundaries, gates, evidence, duty-to-challenge, restart policy, rubric, handoff); no contract, no dispatch (playbook `README.md:40-53`; adapter template `SKILL.md:350-464`).
- Acceptance iron rules: committed ≠ evidence until `git log <branch> --not main` is non-empty; never trust self-reported gates, re-run them; review ≠ authorization to merge/push/deploy/cleanup (playbook `README.md:55-60`).
- Same-module tasks are serialized, never parallelized — measured merge-conflict rate went 43% → 0% — and parallel work is allowed only across modules with disjoint write sets (`SKILL.md:472-496`; playbook `README.md:23`).
- Cross-model review (different model family as reviewer) caught 15×P1 + 37×P2 findings that self-review and mechanical checks both missed; two consecutive skipped reviews means stop the run (`SKILL.md:321-325,670`; playbook `README.md:62-66`).
- The Claude adapter is synchronous by design (no ledger, heartbeat, or stale-task rescue — those live in the async codex sibling with its Go helper CLI); durable state is PROGRESS.md, inbox.md, concepts/glossary, and Batch Status Reports (`SKILL.md:54-56,780-784`; adapter `README.md:97`).
- Three adapters share one core: codex-orchestrator (Codex App, async), claude-orchestrator (Claude Code, sync), kimi-orchestrator (Kimi Code); ORC IDs are identical across all three (playbook `README.md:7,68-91`).
- Fleet-borrowable ideas (7): evidence labels + no-upgrade rule, ORC-ID review vocabulary, anti-shallow-slice classification, review-gate-with-trace + P2 escalation, dispatch-contract checklist, whole-invariant (not patch) re-review, runbook prune rule — each cited below.

## 1. Design principles (Loop Engineering, evidence discipline, acceptance iron rules)

**Loop Engineering (their term for the batch loop as the unit of control).** Work flows in synchronous batches: `Dispatch → agents run concurrently → all return → review each branch → merge accepted / reject failed → cleanup → next batch` (`SKILL.md:58-68`; `full-guide.md:31`). The loop is deliberately synchronous — Claude Code agents "run and return results within the current session. No fire-and-forget, no heartbeat polling" (`SKILL.md:54`) — because synchronous dispatch "is what makes review→merge gates enforceable" (`SKILL.md:56`). Async fan-out is the explicitly rejected tradeoff. A Batch Status Report (Delivered / Completed / Rejected / Blocked / Repo State / Next) closes each loop and doubles as the context-rebuild checkpoint after compaction (`SKILL.md:56,729-757`).

**Evidence discipline (four levels, no upgrade).** Every acceptance claim carries one label (playbook `README.md:29-38`):

| Label | Meaning | Examples |
|---|---|---|
| `direct` | Real target environment | device readback, production log, payment confirmation, callback-backed ACKED, DB/API artifact |
| `proxy` | Substitute or intermediary | staging, screenshot, TCP liveness, SENT status, oral confirmation, mock |
| `local` | Dev/test only | unit test, local build, `diff --check`, static analysis |
| `blocked` | Unobservable | needs human, credentials, hardware, production access, product decision |

Founding incident: "a local unit test got labeled proxy, and weeks later was cited as direct" (playbook `README.md:38`); house slogan "Upgrading an evidence label is lying". Adapter rules: never upgrade `local→proxy` or `proxy→direct` (`SKILL.md:519`); `SENT`/TCP/screenshot/oral = proxy at best (`SKILL.md:520`); `direct` requires device readback, callback ACKED, processor/DB artifact, or physical evidence (`SKILL.md:521`); project-specific evidence rules take precedence (`SKILL.md:524`). Reviewers must actively catch exaggeration — local claimed as proxy, TCP reachability as payment proof (`SKILL.md:252-253`; anti-pattern ORC-02, `SKILL.md:702`).

**Acceptance iron rules (four, playbook `README.md:55-60`).** (1) A worker's "committed" is not evidence — step one is proving `git log <branch> --not main` is non-empty (founding incident: uncommitted work was force-removed with the worktree and lost). (2) Don't trust self-reported gates — re-run key gates on the acceptance side. (3) Review ≠ authorization — one passing review never licenses merge + push + deploy + cleanup; those are separate decisions. (4) Remove worktrees/branches only after the merge is verified. The adapter adds a fifth operational gate: the **live-proof gate** — anything touching runtime/production/device/payment/hardware/provider/external-service needs `direct` proof or an explicit item-specific waiver before landing; `local` gates are insufficient (`SKILL.md:258`). A post-merge integration test is mandatory after every batch because per-branch gates passing does not prove the layers work together (`SKILL.md:302-309`).

## 2. Worker restart handling (ledger, heartbeat, stale-task rescue)

**Short answer: the Claude adapter has none of these — by design — and says so.** No ledger, heartbeat, stale-task rescue, routines engine, or helper CLI exists in `SKILL.md` / `full-guide.md` / `README.md`; the synchronous model waits for return instead of polling (`SKILL.md:54-56`). What exists instead:

- **Package ledger (lightweight, human-readable).** A running record of milestone outcome, active worker contracts, merge order, gates, and blocked evidence that "prevents losing package shape across batches, esp. after compression" (`SKILL.md:122`). Durable coordination state is plain markdown: `concepts.md`/`GLOSSARY.md` + `inbox.md` + `PROGRESS.md` + Batch Status Reports, which "survive compression/handoffs" but are explicitly coordination state, not proof (`SKILL.md:780-784`).
- **Phantom-commit handling.** Check `git -C <worktree> status --short --branch` + `log --oneline -3` (`SKILL.md:227-231`); if uncommitted, the orchestrator commits on the agent's behalf (`add -A` + `commit -m "<task-slug>: <brief>"`) before review (`SKILL.md:233-238`). Uncommitted work is called the "#1 Claude Code subagent failure mode" (`SKILL.md:712`, ORC-11); the commit-rate metric went 40% → 100% after the rule (adapter `README.md:85`).
- **Retry / rescue discipline.** Dispatch failure: stay in the orchestration layer — report the blocker, fix the dispatch, or ask the user; never implement the task yourself just because dispatch failed (ORC-07, `SKILL.md:221`). Rejected branch: leave branch/worktree in place and fix via `SendMessage` to the same agent (preserves context) or a new agent carrying the rejection findings (`SKILL.md:286`). Restart policy inside the contract: repeated same-gate failure, contract drift, or noisy patch-on-patch → stop and recommend a clean restart from the contract (`SKILL.md:414-416`; playbook `README.md:51`). Content-filter refusal: record slug + prompt, retry next batch rephrased; if it fails again mark `blocked`, never halt the whole run (`SKILL.md:569-575`).
- **Where ledger/heartbeat actually live: the Codex sibling.** `codex-orchestrator` adapts the same philosophy to Codex App's async session model "with a Go CLI helper for persistent ledger, heartbeat, routines, and policy/eval" (adapter `README.md:97`). Playbook `README.md:102` confirms: "When you want the full runtime (ledger, heartbeat, packs, routines), see the three adapter repos." Fleet comparison note: fleet already has a centralized ledger DB + supervisor heartbeats, i.e. fleet resembles the codex-side async runtime, while the claude-side sync batch loop is the piece fleet lacks (bounded batches with merge gates).

## 3. Conflict resolution (bounded contracts, serialization, diff boundaries, cross-model review)

**Bounded task contracts.** Each candidate task declares allowed paths, forbidden paths, required gates, evidence type, and hardware/payment/human needs (serialize if yes) (`SKILL.md:113-118`). Shared surfaces (proto, migrations, API, command/event handlers) must be identified and serialized before parallel work (`SKILL.md:101`). A contract-sync gate blocks dispatching a contract-only branch when consumers of that contract need to change in lockstep — either fold minimal consumer wiring into the same serial task or stop with a blocker (`SKILL.md:103`; `full-guide.md:85`). Agents must challenge unclear/risky/over-broad contracts and stop instead of guessing (`SKILL.md:385-389`; playbook `README.md:50`).

**Same-module serialization.** Default: one agent per module; serialize A → merge → push → B when tasks share navigation/resource/config (`SKILL.md:472`). Two agents only across different modules/projects (backend + frontend); three only when all of: no shared contract/migration/API, no hardware/payment, clean main, disjoint modules and write sets (`SKILL.md:474-480`). Rationale with numbers: same-module parallelism "almost never saves time" — 10–15 min conflict resolution per batch exceeds wall-clock gain (`SKILL.md:489`); shared-file only-append auto-merge succeeds only ~57% (`SKILL.md:491`); measured conflicts 43% parallel → 0% serial (`full-guide.md:17`; adapter `README.md:86`; playbook `README.md:23`). Forced same-module parallelism requires only-append discipline, scoped naming (`OdPaymentStatus` vs `PaymentStatus`), and a 10–15 min/batch budget (`SKILL.md:493-496`). Violations are ORC-12 (parallel name collision) and ORC-13 (same-module parallelism) (`SKILL.md:714-715`).

**Diff boundary checks.** Review opens with `git -C <worktree> diff --name-status main..HEAD` + `diff --check main..HEAD`, verifying allowed-paths-only and no forbidden contracts (`SKILL.md:242-249`, checklist `SKILL.md:247-258`). Out-of-bounds/stale-base rescue is a documented cherry-pick procedure: `checkout main` + `cherry-pick <commit> --no-commit`, inspect staged, `reset`/`checkout --` the forbidden files, commit in-scope only, remove worktree, delete branch (`SKILL.md:272-284`; `full-guide.md:80`). Simple doc conflicts: keep both entries; conflicts in shared contracts/migrations/aggregates/protocols → stop for manual review (`SKILL.md:288`). Shared resource files (strings.xml, nav graphs, DI, route registries): ONLY APPEND, never reorder/reformat/touch existing lines (`SKILL.md:438-442`). Merge hygiene: be on main before merging (`SKILL.md:265`); merge with `--no-ff` (`SKILL.md:264-283`); push to `origin/main` after merging a serial batch so the next parallel worktrees (created from origin, not local main) can see prior work — the "worktree base trap", ORC-14 (`SKILL.md:72-79,314`).

**Cross-model review.** After batches merge, one independent review runs with a **different model family** (Codex or Pi reviewing Claude-orchestrated work), because same-family reviewers share blind spots (`SKILL.md:641-647`). Yield: 15×P1 + 37×P2 findings that self-review and mechanical checks both missed in the 53-batch run (DTO mismatches, state-machine gaps, missing tenant filters, float-cents bugs, fake success toasts, null handling) (`SKILL.md:670`; playbook `README.md:62-66`); the case study shows plan-text-only review (GPT) missing a runtime landmine that repo-access review (DeepSeek) caught (`CASE-STUDY.md:31-33`). Mechanics: run via the companion script `node "$PLUGIN_ROOT/scripts/codex-companion.mjs" review --wait --base <pre-merge-commit>`, never standalone `codex review` (`SKILL.md:651-657`). Enforcement: the review gate requires (1) current-batch review launched (background OK, not-started blocks next dispatch), (2) previous findings processed (P1 fixed, P2 recorded), (3) a written trace (findings count in docs — no record = not run); two consecutive skips stop the run (ORC-15, `SKILL.md:321-325,717`). P2s unfixed for 3+ batches escalate to P1 (`SKILL.md:343-346`). High-risk changes (money/permissions/contracts/migrations/sync/concurrency) are reviewed BEFORE merge as commit A → review → commit B fixes → merge, preserving a two-commit audit trail (`SKILL.md:327-341`).

## 4. Workflow abstraction (SKILL.md, dispatch-contract fields, routines, ledger helper CLI)

**SKILL.md as the workflow definition.** The skill installs as a symlink into `~/.claude/skills/build-orchestrator` and is invoked as `/build-orchestrator`, in two modes: single-feature (default) and roadmap-driven (`--roadmap docs/roadmap.md`, looping done → re-read → pick next → continue until a stop condition) (`README.md:25,37`; `SKILL.md:24-40`). There is no separate workflow engine, DAG DSL, or routines runner in the Claude adapter — the abstraction is the dispatch contract plus the batch loop. (`Workflow` is named once as an alternative for complex multi-phase work with schemas, `SKILL.md:70`. Routines/packs and the ledger helper CLI belong to the async codex sibling, adapter `README.md:97`.)

**The ten dispatch-contract fields (playbook `README.md:40-53`):** (1) Outcome definition — what counts as correct vs a real blocker; (2) Anti-shallow-slice classification — `vertical-completion | runtime-proof | blocked-removal | owner-gated` + why this isn't repeating a completed first slice; (3) Minimum-change rationale — why reuse/deletion/config/docs-only can't solve it; (4) Boundaries — allowed paths, forbidden paths, branch name, base commit; (5) Acceptance gates — concrete commands, "not green = not done"; (6) Evidence requirements — labeled per the four-level discipline; (7) Duty to challenge — report and ask for a narrower contract before editing, don't guess; (8) Restart policy — repeated same-gate failure → clean restart from contract; (9) Subjective rubric — axes/weights/scale/evidence source whenever taste/UI/workflow/parity matters ("without rubric, looks good is unfalsifiable"); (10) Handoff format — branch, commit hashes, file list, actual output of every gate (not the word "passed"), residual risks. "No contract, no dispatch."

**Adapter implementation (`SKILL.md:350-464`).** The template expands the ten fields into twelve prompt sections (Task, Classification, Minimum-Change Rationale, Scope, Gates, Evidence, Rules, Common P1 Patterns, Minimalism Ladder, Shared Resource Files, Subjective Rubric, Handoff), pinning `Base: origin/main`, `Branch: build/<task-slug>`, a MUST-COMMIT rule (`SKILL.md:366-370,390-393`), and a ≤~30-line handoff cap with detail pushed into repo files (`SKILL.md:453-463`). Notable workflow-level additions absent from the core: the **Minimalism Ladder** (delete → stdlib → dependency → inline → keep-minimum; never simplify security/error-handling/a11y, `SKILL.md:427-436`), **Common P1 Patterns** (five checks — DTO naming, all-states coverage, tenant/store scoping, integer cents, null handling — claimed ~40% of P1s, `SKILL.md:418-425`), the **Design-First gate** for high-risk work (design doc → verify premises by opening cited code → implement, `SKILL.md:143-168`), **model-tier-by-consequence** (tier by cost of a wrong answer, not task size; reviewer lanes must differ in family, not tier, `SKILL.md:170-198`), and **Decision Brief discipline** (What/Why/evidence-gathered-vs-missing/Options/Recommendation/Branch, `SKILL.md:680-690`).

## 5. Multi-harness support (claude/codex/kimi adapters)

**Shared discipline vs per-harness adapter.** The playbook declares itself "the harness-agnostic core" with three concrete adapter repos: codex-orchestrator (Codex App), claude-orchestrator (Claude Code), kimi-orchestrator (Kimi Code) (playbook `README.md:7`). Shared across all harnesses: the core loop, the four-level evidence discipline, the ten-field dispatch contract, the acceptance iron rules, cross-model review, and the ORC-01–18 IDs, which "are shared across all three adapters" (playbook `README.md:19-91`). The playbook's adoption ladder tells any harness to (1) copy evidence + iron rules into the system prompt, (2) use the ten contract fields as a dispatch checklist, (3) run one cross-model review per package, (4) cite ORC IDs in review (playbook `README.md:96-102`).

**How the Claude adapter differs.** Synchronous execution within one session (`SKILL.md:54`); primary tool `Agent` with `isolation:"worktree"`, concurrent via multiple calls in one message (`SKILL.md:70`); the origin/main worktree-base discipline (`SKILL.md:72-79`); recon checklist (`git status/log/worktree list` + PROGRESS/roadmap/concepts/inbox/shared contracts, `SKILL.md:89-103`); package lane guard + package ledger + Batch Status Reports (`SKILL.md:56-122`); the review-gate/P2-escalation machinery and pre-merge review order for high-risk paths (`SKILL.md:321-346`); cross-model review via the codex-companion script (`SKILL.md:649-657`). **How the Codex adapter differs** (per the Claude README's sibling note): same philosophy but an async session model with a Go CLI helper providing persistent ledger, heartbeat, routines, and policy/eval (adapter `README.md:97`). No per-harness diff table or adapter interface spec ships in the analyzed files; the Kimi adapter was not analyzed (its existence is attested only by the playbook link). Sync hygiene is enforced by a living-runbook prune rule: every long run or codex↔claude sync, each gate must show evidence of catching a real bug or be demoted/deleted — "syncing means importing new discipline *and* trimming dead discipline" (`SKILL.md:20`; ORC-17 runbook bloat, `SKILL.md:719`).

## 6. What fleet can borrow (7 ideas with file:line citations)

1. **Evidence labels + no-upgrade rule + live-proof gate.** Tag every worker claim `direct/proxy/local/blocked`; forbid upgrades; require `direct` proof (or explicit waiver) at runtime/production/payment boundaries. (`SKILL.md:508-524`; `SKILL.md:258`; playbook `README.md:29-38`.) Fleet fit: acceptance checks on worker RESULT.json claims, which today can conflate "tests pass locally" with "works in production".
2. **ORC-ID review vocabulary (ORC-01–18).** Numbered anti-patterns — shallow-slice disguise, evidence upgrade, blind self-report trust, slot-filling dispatch, review-as-authorization, constraint amnesia, orchestrator-writes-worker-code, merge-before-review, silent stop, idempotency blindness, phantom commit, parallel name collision, same-module parallelism, stale worktree base, review skip, role drift, runbook bloat, motion-vs-progress — shared verbatim across harnesses. (`SKILL.md:700-721`; playbook `README.md:68-91`.) Fleet fit: supervisor rejection reasons and worker guidance keyed by ID.
3. **Anti-shallow-slice classification in the task contract.** Every dispatch declares `vertical-completion | runtime-proof | blocked-removal | owner-gated` plus minimum-change rationale; read-only shells/placeholders are rejected unless they remove a named blocker. (`SKILL.md:126-141`; playbook `README.md:45-46`.) Fleet fit: a required field in fleet task specs to stop placeholder "progress".
4. **Review gate with trace + P2 escalation.** Next-batch dispatch is blocked until the current review is launched and previous findings are processed; every review leaves a findings-count trace (no record = not run); two consecutive skips stop the run; P2s unfixed 3+ batches escalate to P1. (`SKILL.md:321-325,343-346`.) Fleet fit: supervisor dispatch precondition + finding ledger.
5. **Whole-invariant re-review (no review ping-pong).** When a finding exposes a shared-invariant bug, fix every face of the invariant at once, then run ONE review of the whole diff — symptom of the trap is 2+ rounds with findings in the same just-touched subsystem. (`SKILL.md:668`.) Fleet fit: rework-loop policy for supervisor/worker iterations.
6. **Cherry-pick rescue for out-of-bounds diffs.** Instead of rejecting a whole branch for stray files, `cherry-pick --no-commit`, unstage forbidden paths, commit in-scope only. (`SKILL.md:272-284`.) Fleet fit: validation-step salvage procedure for worktree branches that drift out of scope.
7. **Runbook prune rule.** Each gate/anti-pattern must periodically show evidence of catching a real bug or be demoted to an appendix/deleted; cross-harness syncs import *and* trim. (`SKILL.md:20`; ORC-17 `SKILL.md:719`.) Fleet fit: periodic fleet-protocol review so the supervisor prompt doesn't accrete dead rules.

## 8. Caveats (read before adopting)

- Scale numbers (53 batches / ~95 agents / ~70k lines; 43%→0% conflicts; ~57% only-append auto-merge; ~40% of P1s from five patterns; 15×P1+37×P2 yield) ship without datasets, windows, or false-positive rates; the adapter README itself warns that counts measure activity, not capability (adapter `README.md:85-89`). Treat thresholds (2-skip stop, P2→P1 after 3 batches, ≤5-line hotfix, max 2–3 parallel) as heuristics, not derived constants (`SKILL.md:325,346,610,777`).
- The case study's "zero behavior change" rests on re-run gates plus a retained 40-line shell around a runtime self-parsing landmine every mechanical gate waved through — the strongest evidence for cross-model review with repo access, and a warning that grep-level parity checks are unsound (`CASE-STUDY.md:22-37`).
- The adapter assumes pushing to `origin/main` is always allowed and leaves severity definitions (P1/P2/P3) implicit in handling rather than stated (`SKILL.md:314,664-666`).
