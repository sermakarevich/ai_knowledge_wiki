# Overstory Deep Dive — Targeted Brief for Fleet

**In one sentence:** Overstory runs a strict coordinator → lead → leaf-worker hierarchy of single-purpose agents in isolated git worktrees (separate directory checkouts of one repo per agent), coordinated through typed mail in SQLite (an embedded relational database stored in a local file), guarded tool calls, tiered watchdog supervision, and a FIFO (first-in first-out) merge queue with 4-level conflict escalation.

## Key points

- Hierarchy is 3 levels: coordinator at depth 0 spawns only leads; leads at depth 1 spawn scouts/builders/reviewers at depth 2; leaf workers cannot spawn (`agents/coordinator.md:144`, `agents/coordinator.md:153`).
- Workers are restartable because state lives in files, not conversation history: per-agent `checkpoint.json`, `handoffs.json` for session replacement, and a three-layer model where the session is ephemeral but the worktree (sandbox) and identity records persist (`src/types.ts:752`, `src/agents/lifecycle.ts:72`, `src/agents/lifecycle.ts:120`).
- The watchdog escalates in 4 stages (warn → nudge → AI triage → terminate) instead of killing stalled workers immediately, and nudges the coordinator once when a whole run completes (`src/watchdog/daemon.ts:703`, `src/watchdog/daemon.ts:190`).
- Merge conflicts go through 4 tiers (clean merge → auto-resolve → AI-resolve → reimagine) with guards against silent data loss and prose output, plus a learning loop that skips tiers that repeatedly failed (`src/merge/resolver.ts:256`, `src/merge/resolver.ts:387`, `src/merge/resolver.ts:576`).
- There are no `orchestrate` or `plan-worktrees` commands; the workflow is `ov sling` (spawn) + `ov spec write` (task spec files) + `ov group` (batch tracking) + `ov merge`, all shaped by `.overstory/config.yaml` (`src/index.ts:267`, `src/index.ts:294`, `src/commands/spec.ts:40`).
- Multi-harness support is one interface (`AgentRuntime` in `src/runtimes/types.ts:148`) plus one registry file mapping names to adapters (`src/runtimes/registry.ts:16`); orchestration code never calls a harness CLI (command-line interface) directly.

## Design principles

Coordinator, lead (supervisor is a deprecated alias kept only for compatibility), scout, builder, reviewer, merger — each role has exactly one job. See [[01-agent-roles-and-overlays|Agent Roles and Overlays]] for the full role catalog.

- **Coordinator (depth 0, project root, no overlay).** Thinks, decomposes objectives into high-level tracker issues, dispatches leads only, monitors via mail and status checks, merges only after an explicit `merge_ready` mail. Spawning anything but a lead is code-enforced as an error, and the coordinator has no write access (`agents/coordinator.md:144`, `agents/coordinator.md:49`, `agents/coordinator.md:225`).
- **Lead (depth 1, owns a work stream).** Receives a dispatch, decomposes into subtasks, writes specs, spawns scouts/builders/reviewers at depth 2, verifies each worker branch (commits exist, issue closed, exit code clean) before sending `merge_ready` (`agents/supervisor.md:223`, `agents/supervisor.md:241`). Supervisor files carry a deprecation header pointing at lead (`agents/supervisor.md:1`).
- **Scout (depth 2, leaf, read-only explorer).** Systematically investigates the codebase and persists findings with `ov spec write`, never via long mail bodies (`agents/scout.md:65`, `agents/scout.md:107`). Blocked from Write/Edit and all destructive bash (`agents/scout.md:23`).
- **Builder (depth 2, leaf, implementer).** Owns exactly the files in its file scope inside its worktree, runs quality gates (tests, lint, typecheck), commits to its own branch, sends `worker_done` mail, then closes its issue (`agents/builder.md:27`, `agents/builder.md:52`, `agents/builder.md:62`).
- **Reviewer (depth 2, leaf, read-only validator).** Diffs the branch, runs quality gates, reports PASS/FAIL with actionable feedback by mail; never modifies code (`agents/reviewer.md:65`, `agents/reviewer.md:101`, `agents/reviewer.md:115`).
- **Merger (depth 2, leaf, integrator).** Merges branches in dependency or completion order through the tiered process, verifies tests after each merge, records reusable resolution patterns (`agents/merger.md:70`, `agents/merger.md:148`).

**Overlays + guards** are the control plane. `generateOverlay()` renders a per-task instruction file from a template plus role definition, file scope, branch, parent, depth, quality gates, and dispatch overrides (`src/agents/overlay.ts:274`, `src/agents/overlay.ts:299`). It is written to the worktree instruction path (default `.claude/CLAUDE.md`), never to the canonical root — a path-comparison guard refuses root writes (`src/agents/overlay.ts:369`, `src/agents/overlay.ts:380`, `src/agents/overlay.ts:373`). Read-only roles (scout, reviewer) get a lightweight completion section instead of quality gates (`src/agents/overlay.ts:57`). Guards are shared constants: 10 banned native team tools, 3 banned interactive tools, 3 banned write tools, ~37 dangerous bash patterns, 11 safe prefixes (`src/agents/guard-rules.ts:13`, `src/agents/guard-rules.ts:31`, `src/agents/guard-rules.ts:34`, `src/agents/guard-rules.ts:40`, `src/agents/guard-rules.ts:85`). Default quality gates (tests, lint, typecheck) apply when config lists none (`src/config.ts:41`, `src/agents/overlay.ts:120`).

## Worker restart handling

Tiered watchdog T0/T1/T2, checkpoints, handoffs, session resume. T0 is the mechanical daemon in `src/watchdog/daemon.ts:1`; T1 is the AI triage agent in `src/watchdog/triage.ts:1`; T2 (a patrolling monitor agent) is declared but not yet implemented, with T3 reserved for per-project supervisor monitors (`src/watchdog/daemon.ts:13`).

- **T0 — mechanical daemon.** `startDaemon()` polls on an interval; `runDaemonTick()` loads all sessions, skips completed ones, re-checks liveness every tick, updates state forward-only, and persists back (`src/watchdog/daemon.ts:338`, `src/watchdog/daemon.ts:397`, `src/watchdog/daemon.ts:452`, `src/watchdog/daemon.ts:526`). Defaults come from config: 30s interval, 5min stale threshold, 10min zombie threshold, 60s between escalation stages, AI triage off by default (`src/config.ts:82`, `.overstory/config.yaml:41`).
- **Progressive escalation, not instant kill.** Level 0 warns via callback, level 1 sends a forced nudge, level 2 invokes AI triage (skipped when disabled), level 3 kills the session; ceiling is 3 (`src/watchdog/daemon.ts:42`, `src/watchdog/daemon.ts:704`, `src/watchdog/daemon.ts:716`, `src/watchdog/daemon.ts:740`, `src/watchdog/daemon.ts:788`). Recovery resets the escalation counters (`src/watchdog/daemon.ts:603`). Headless agents (no tmux, direct subprocess) are killed by PID (process identifier) tree, TUI (terminal user interface) agents via their tmux session — a deliberate fix for a blast-radius bug where an empty session name matched everything (`src/watchdog/daemon.ts:368`).
- **T1 — AI triage.** Reads the last 50 lines of the agent's most recent session log, asks the model to answer with exactly one word, and classifies into `retry` / `terminate` / `extend`; missing logs or model failure safely default to `extend` (`src/watchdog/triage.ts:29`, `src/watchdog/triage.ts:67`, `src/watchdog/triage.ts:105`, `src/watchdog/triage.ts:176`, `src/watchdog/triage.ts:52`).
- **Checkpoints.** A checkpoint is a JSON (JavaScript Object Notation) snapshot — agent, task, session id, timestamp, progress summary, modified files, branch, pending work, expertise domains — stored at `.overstory/agents/{name}/checkpoint.json` (`src/types.ts:720`, `src/types.ts:723`, `src/agents/checkpoint.ts:14`, `src/agents/checkpoint.ts:48`, `src/agents/checkpoint.ts:86`).
- **Handoffs and session resume.** `initiateHandoff()` builds a checkpoint and appends a handoff record with reason `compaction | crash | manual | timeout`; `resumeFromHandoff()` picks the most recent record whose replacement session is still null and reloads its checkpoint; `completeHandoff()` stamps the new session id and clears the checkpoint (`src/agents/lifecycle.ts:72`, `src/agents/lifecycle.ts:120`, `src/agents/lifecycle.ts:157`, `src/types.ts:738`). The persistence model is three layers: ephemeral session, persistent worktree sandbox, permanent identity (`src/types.ts:752`). Compacted agents recover via `ov prime --compact`, which renders the checkpoint as a session-recovery section (`src/commands/prime.ts:250`).
- **Run-level completion.** After each tick the daemon checks whether every non-persistent worker (coordinator and monitor excluded) in the active run is completed; if so it nudges the coordinator once with a phase-aware message, guarded by a marker file against repeats (`src/watchdog/daemon.ts:190`, `src/watchdog/daemon.ts:48`, `src/watchdog/daemon.ts:218`, `src/watchdog/daemon.ts:232`).
- **False-positive suppression.** Headless agents with an RPC (remote procedure call) connection get a live `getState()` poll that refreshes activity timestamps; ones without RPC fall back to recent-event detection in the event store (`src/watchdog/daemon.ts:490`, `src/watchdog/daemon.ts:509`).

## Conflict resolution

Isolated worktrees, cross-review rework loop, FIFO merge queue with 4-tier resolution. See [[04-merge-queue-and-conflicts|Merge Queue and Conflicts]] for depth.

- **Isolated worktrees.** Every writer works inside its own worktree path and commits only to its own branch; canonical-branch writes and `git push` are forbidden (`agents/builder.md:27`, `src/agents/overlay.ts:236`). The merge side additionally auto-commits orchestration bookkeeping files and stashes leftover dirty files so unrelated state never blocks a merge (`src/merge/resolver.ts:102`, `src/merge/resolver.ts:709`).
- **Cross-review rework loop.** Builder completion alone authorizes nothing: the lead must verify commits, issue state, and exit code, then send `merge_ready`; the coordinator merges only on that signal and closes the issue only after the merge succeeds (`agents/supervisor.md:223`, `agents/coordinator.md:225`, `agents/coordinator.md:291`). Reviewers feed the loop with PASS/FAIL result mail plus bug-level detail (`agents/reviewer.md:115`). Failures retry at most twice before escalation (`agents/supervisor.md:249`).
- **FIFO merge queue in SQLite.** `createMergeQueue()` opens a WAL-mode (write-ahead logging, a mode allowing concurrent readers) database; the next entry is always the lowest-id pending row; entries carry branch, task, agent, modified files, timestamps, status, and resolving tier (`src/merge/queue.ts:104`, `src/merge/queue.ts:135`, `src/merge/queue.ts:188`, `src/merge/queue.ts:169`). Statuses are `pending | merging | merged | conflict | failed` and tiers `clean-merge | auto-resolve | ai-resolve | reimagine` (`src/merge/queue.ts:53`, `src/merge/queue.ts:55`).
- **Tier 1 clean merge** runs `git merge --no-edit` and collects conflicted files on failure (`src/merge/resolver.ts:235`). **Tier 2 auto-resolve** keeps the incoming agent side per conflict block but refuses files where the canonical side has real content, escalating those instead of silently discarding work; `merge=union` files concatenate both sides (`src/merge/resolver.ts:256`, `src/merge/resolver.ts:273`, `src/merge/resolver.ts:173`). **Tier 3 AI-resolve** prompts the configured model per file and rejects prose-looking output (preambles, fencing, apologies) (`src/merge/resolver.ts:340`, `src/merge/resolver.ts:387`). **Tier 4 reimagine** aborts the merge and reimplements branch changes onto the canonical file versions from scratch (`src/merge/resolver.ts:415`). Upper tiers are optional flags (`src/config.ts:75`, `src/merge/resolver.ts:659`).
- **Learning loop.** Every outcome is recorded as a searchable conflict pattern; files with 2+ past failures and zero successes at some tier cause that tier to be skipped, and past successes enrich the AI prompt (`src/merge/resolver.ts:626`, `src/merge/resolver.ts:549`, `src/merge/resolver.ts:576`).

## Workflow abstraction

How implemented: task specs, `ov sling` / `ov spec` / `ov group` / `ov merge` commands, config files. Note: this repo has no `orchestrate` or `plan-worktrees` commands — the equivalent workflow is assembled from the commands below (`src/index.ts:267`, `src/index.ts:294`).

- **Task specs are files, not chat messages.** `ov spec write <task-id>` persists the assignment to `.overstory/specs/<task-id>.md` with optional author attribution (`src/commands/spec.ts:40`, `src/commands/spec.ts:61`). Scouts write specs and then send one-line result mail pointing at the file (`agents/scout.md:107`). The overlay injects the spec path plus a read instruction into every worker's instructions (`src/agents/overlay.ts:295`).
- **Spawning is `ov sling <task-id>`.** Flags select capability (`builder | scout | reviewer | lead | merger`), agent name, spec path, exclusive file scope, parent, depth, plus lead modifiers (`--skip-scout`, `--skip-review`, `--max-agents`) and runtime/base-branch overrides (`src/index.ts:267`, `src/index.ts:271`). Leads re-dispatch with incremented depth (`src/agents/overlay.ts:250`).
- **Batching is task groups.** The coordinator creates a named group over issue ids, checks `group status`, and treats auto-close (all member issues closed) as batch done (`agents/coordinator.md:244`, `agents/coordinator.md:259`). Mail carries the lifecycle signals: `dispatch`, `assign`, `worker_done`, `merge_ready`, `merged`/`merge_failed`, `escalation`, `question`, `error`, `result` (`agents/coordinator.md:172`, `agents/supervisor.md:147`).
- **Issues are the unit of work.** The tracker client interface exposes `ready / show / create / claim / close / list / sync` over a `beads | seeds` backend (`src/tracker/types.ts:25`, `src/tracker/types.ts:52`). `auto` resolves by probing for `.seeds/` then `.beads/`, defaulting to seeds; CLI (command-line interface) names are `sd` and `bd` (`src/tracker/factory.ts:35`, `src/tracker/factory.ts:59`).
- **Config is layered.** `DEFAULT_CONFIG` provides every field (25 max concurrent agents, depth ceiling 2, 5 agents per lead, WAL timeouts, disabled AI-resolve fallback values); `.overstory/config.yaml` overrides it; `config.local.yaml` (git-ignored) overrides that for machine-specific tuning (`src/config.ts:47`, `src/config.ts:914`, `src/config.ts:806`). The checked-in example sets the canonical branch, quality gates, tracker, merge tiers, watchdog thresholds, and default runtime (` .overstory/config.yaml:4`, `.overstory/config.yaml:35`, `.overstory/config.yaml:41`, `.overstory/config.yaml:58`).

## Multi-harness support

Claude, Pi, Copilot, Codex, Gemini, OpenCode, Cursor — how implemented (`AgentRuntime` interface `src/runtimes/types.ts:148` + registry, cite files). See [[02-multi-harness-runtime|Multi-Harness Runtime]] for adapter detail.

- **One interface, ~200–400 lines per adapter.** Every harness implements `AgentRuntime`: stable identity (`id`, `stability`, per-worktree `instructionPath`), spawn builders (interactive tmux command, headless print/argv, direct-spawn argv), config deployment, readiness detection, transcript parsing, transcript discovery, and model-to-environment mapping (`src/runtimes/types.ts:148`, `src/runtimes/types.ts:149`, `src/runtimes/types.ts:156`, `src/runtimes/types.ts:159`, `src/runtimes/types.ts:165`, `src/runtimes/types.ts:174`, `src/runtimes/types.ts:184`, `src/runtimes/types.ts:190`, `src/runtimes/types.ts:199`, `src/runtimes/types.ts:206`). Orchestration code calls only these methods, never a harness CLI (command-line interface) directly (`src/runtimes/types.ts:141`).
- **Registry is the only file importing adapters.** A name→factory map holds `claude`, `codex`, `pi`, `copilot`, `cursor`, `gemini`, `opencode` (plus `sapling`); `getRuntime()` resolves name → per-capability override → config default → hardcoded `claude`, with Pi receiving extra config for model-alias expansion (`src/runtimes/registry.ts:16`, `src/runtimes/registry.ts:67`, `src/runtimes/registry.ts:76`, `src/runtimes/registry.ts:79`).
- **Cross-harness differences are data.** `OverlayContent` (instruction markdown) and `HooksDef` (agent name, capability, worktree path, quality gates) are runtime-agnostic; each adapter translates them (Claude writes hooks JSON, Pi writes a guard extension, Codex needs no hooks) (`src/runtimes/types.ts:42`, `src/runtimes/types.ts:52`). Readiness is a 3-phase value (`loading | dialog | ready`); headless harnesses always report ready, and TUI (terminal user interface) quirks like Claude's beacon resend are per-adapter flags (`src/runtimes/types.ts:34`, `src/runtimes/types.ts:220`). Optional RPC (remote procedure call) methods (`connect`, `followUp`, `abort`, `getState`) let Pi bypass tmux; headless harnesses add `buildDirectSpawn` + NDJSON (newline-delimited JSON) event parsing instead (`src/runtimes/types.ts:227`, `src/runtimes/types.ts:234`, `src/runtimes/types.ts:241`, `src/runtimes/types.ts:248`). Token usage is normalized to one summary shape for cost accounting (`src/runtimes/types.ts:66`).
- **AI-assisted internals reuse the same abstraction.** Conflict resolution and watchdog triage both obtain their model caller via `getRuntime(printCommand ?? default)` and `buildPrintCommand`, so AI-resolve follows the configured harness rather than hardcoding Claude (`src/merge/resolver.ts:367`, `src/watchdog/triage.ts:144`).

## What fleet can borrow

Concrete, portable ideas — each with the file to copy from:

- **SQLite mail with concurrent-access pragmatics.** WAL mode plus 5s busy timeout, `CHECK`-constrained schema, inbox and thread indexes, typed/prioritized/threaded messages with unread tracking and purge-by-age/agent (`src/mail/store.ts:177`, `src/mail/store.ts:184`, `src/mail/store.ts:46`, `src/mail/store.ts:135`). See [[03-sqlite-mail-messaging|SQLite Mail Messaging]].
- **Tool-call guards as data.** Central blocklists (native delegation tools, interactive tools, write tools, ~37 dangerous bash patterns) checked after a safe-prefix allowlist (`src/agents/guard-rules.ts:13`, `src/agents/guard-rules.ts:31`, `src/agents/guard-rules.ts:34`, `src/agents/guard-rules.ts:40`, `src/agents/guard-rules.ts:85`); fleet can enforce role-shaped CLIs the same way without trusting prompts.
- **Agent identity CVs (curriculum vitae, i.e. work-history records).** YAML (human-readable data format) file per agent with capability, session count, expertise domains, and the last 20 tasks; updates merge domains and append completions (`src/agents/identity.ts:253`, `src/agents/identity.ts:335`, `src/agents/identity.ts:7`).
- **Runtime-agnostic pricing table.** Per-million-token input/output/cache-read/cache-create rates keyed by model-name substring, with a single `estimateCost()` over normalized usage (`src/metrics/pricing.ts:30`, `src/metrics/pricing.ts:101`, `src/metrics/pricing.ts:123`).
- **Tiered merge with anti-footgun checks.** Keep-incoming auto-resolve that refuses contentful canonical sides, prose detection on model output, and stash/auto-commit pre-steps around `git merge` (`src/merge/resolver.ts:273`, `src/merge/resolver.ts:387`, `src/merge/resolver.ts:709`).
- **Conflict learning loop.** Record every merge outcome as a searchable pattern; skip tiers with 2+ failures and zero successes on overlapping files; inject past successes into the resolver prompt (`src/merge/resolver.ts:626`, `src/merge/resolver.ts:576`).
- **Checkpoint/handoff/session-resume trio.** File-based snapshots plus pending-handoff records decoupled from any conversation context, with a three-layer (session/sandbox/identity) mental model (`src/agents/checkpoint.ts:14`, `src/agents/lifecycle.ts:72`, `src/agents/lifecycle.ts:120`, `src/types.ts:752`).
- **Progressive watchdog with run-completion detection.** Warn → nudge → triage → terminate staging plus a dedup-marked "all workers done" nudge to the coordinator, excluding long-lived roles (`src/watchdog/daemon.ts:703`, `src/watchdog/daemon.ts:190`, `src/watchdog/daemon.ts:48`).
