# agent_memory

**Research:** 20 sources, date range unavailable (sources.md pending at time of writing), focus: Which of these 20 agent second-brain GitHub projects are worth using for a system that captures sources, connects ideas, remembers context, and helps agents act on it, and how do they compare across capture, linking, memory/recall, and agentic action?

## Human Readable TL;DR

Think of these 20 projects as competing designs for an agent's second brain — like giving an assistant a notebook, a filing cabinet, and a set of habits instead of just a good memory for the current conversation. The unanimous verdict is that the notebook should be plain readable files kept on your own machine, with a tidy index card catalog beside them, and that nothing gets filed or connected without a human-readable trace of where it came from and a checkpoint before it becomes permanent. Where the projects split is on emphasis: some are built like in-trays that catch anything you throw at them (clipboard snippets, chat messages, whole document folders), others like librarians that link notes into webs of ideas, others like memory palaces with layered summaries for fast recall, and a final group like foremen that hand out jobs to teams of sub-agents and check their work. No single project does all four jobs well, so a working system would borrow the in-tray from one group, the librarian from another, and the foreman from a third.

## TL;DR

Across the four sub-topic digests, the 20 projects converge on a single architecture: a local-first pipeline that runs from heterogeneous capture lanes into typed, provenance-preserving stores (usually plain Markdown), then into an explicit linking or graph layer, then into hybrid scoped recall, and finally into skill-packaged agentic action guarded by approvals and checkpoints — with network and model calls pushed to explicit opt-in edges throughout. Capture (Chubbyskills, OpenWiki, AgentSecondBrain, Docsagent, DocMason) is local by default with provenance recorded at ingest and nightly or incremental index maintenance rather than one-shot filing. Linking (ClaudeObsidian, Swarmvault, SageWiki, VaultCurate) keeps interlinked Markdown as the human layer with a derived graph/provenance companion, hybrid lexical plus vector plus graph retrieval, and gated writes (staging areas, approval bundles, verdicts) before any link becomes canonical. Memory and recall (TencentDBAgentMemory, OpenViking, Agentmemory, Hindsight, MemU, OpenSecondBrain) favor layered distillation and inspectable file substrates over flat chat replay or pure vector search, with scoped, budgeted recall (subtrees, banks, ACLs, token caps) and a split between capture seams and recall seams. Action harnesses (CogSecondBrain, Mateclaw, RowBot, SecondBrainCloudflare, Makerskills) package work as executable skills over the memory substrate, with delegated multi-agent orchestration, checkpointed recovery instead of replay, provider routing with failover, and non-optional human gates on outward effects. The practical upshot is that project choice hinges on which lane matters most — lightest viable picks are the file-only skill harnesses and vault-native stores, while the heaviest governance and orchestration come from the self-hosted runtimes — and every quantitative claim (LoCoMo, LongMemEval, R@5/token figures) is vendor-reported and unevenly evidenced, so structural fit should drive selection, not benchmarks.

## What is established

The digests agree that the capture-to-store path stays local by default, with source identity preserved at ingest time and ingest treated as the head of a maintained pipeline (index, dedup, sync, rebuild) rather than dead filing. They agree that durable memory is compiled interlinked Markdown plus an explicit graph or provenance companion, that links without provenance are untrustworthy, and that retrieval must fuse lexical, vector, and graph signals with a deterministic fallback when models are unavailable. They agree that flat chat history and single-method vector retrieval are insufficient, that memories must be human-inspectable and editable, that recall should be scoped and budgeted rather than total, and that graph writes and outward actions pass through gates — staging, approvals, verifiers, audit trails. Full detail lives in [agreements.md](agreements.md), and per-dimension evidence in the four topic digests.

## What is contested

- Capture keep-decision: human-gated per item versus agent-classified with nothing dropped versus build-validated publishing — see [disagreements.md](disagreements.md).
- Graph weight: persistent typed graph artifact versus ledgers plus file links versus ephemeral suggestions only — see [disagreements.md](disagreements.md).
- LLM dependence: LLM on every memory path versus embedding-only or keyless-BM25 service with the model kept at the edges — see [disagreements.md](disagreements.md).
- Store shape: relational banks versus virtual filesystem versus team asset hub versus flat vault files — see [disagreements.md](disagreements.md).
- Who runs the model in action harnesses: zero-inference file-only skills riding the host agent versus multi-provider routed runtimes — see [disagreements.md](disagreements.md).
- Verification posture: opt-in off-by-default checks versus always-on governance with audit — see [disagreements.md](disagreements.md).
- Orchestration weight: heavyweight durable multi-worker runs versus lightweight skill composition by name — see [disagreements.md](disagreements.md).
- Freshness model: bi-temporal invalidation versus decay scoring versus live Hot/Cold tiering versus lint-reported staleness — see [disagreements.md](disagreements.md).

## What is open

The biggest open items are measurement and internals: none of the action harnesses reports task-success, latency, or recall-precision figures for the full loop, and the recall benchmarks that do exist are vendor-reported with uneven harnesses and versions, so comparative effectiveness remains unproven and is tracked in [open_questions.md](open_questions.md). Engine internals are also thin — several underlying summaries flag truncated chunks and unmapped `src/` modules, leaving ranking formulas, index schemas, and handler-level behavior unverified. Selection guidance (which project or combination to adopt for a given deployment shape — single owner-operator, team, or user-owned cloud) and the cost of the governance and orchestration layers at scale remain judgment calls rather than settled findings.
