# Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents

**Paper:** [Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents](https://arxiv.org/pdf/2609.27334) — arXiv, 23 Sep 2026

## Human Readable TL;DR

Most AI agents today take notes like a student who summarizes each lesson before knowing what the exam will ask, throwing away details that later turn out to matter. Just-in-Time Memory instead keeps the full unedited diary of everything the agent did and only writes the cheat sheet once the new question is known, tailoring it to exactly what is needed. It is like keeping all your raw cooking videos instead of one fixed recipe card, then cutting a custom tutorial for tonight's dish. Even without any extra training this custom briefing already beats older fixed-note methods, and training the note-writer on whether the dish actually succeeded makes it better still while using fewer words and fewer steps.

## TL;DR

JITMEM reframes agentic memory around when curation happens: instead of distilling each trajectory into a fixed query-independent artifact at write time, it stores raw trajectories losslessly and curates them just in time at read time into a compact task-conditioned payload. The system runs a Retrieve, Curate, Execute, Update loop with a frozen executor and an LLM-as-judge admission gate, and trains only the curator with GRPO against immediate same-task reward, which collapses credit assignment to a single interaction. Across ALFWorld, WebShop, and τ²-bench it outperforms no-memory agents and heuristic and RL-trained write-time baselines by 16.2, 16.3, and 3.9 absolute success-rate points respectively, while cutting input tokens and executor steps and transferring across executors without retraining.

## Problem & Motivation

LLM agents are increasingly expected to solve streams of tasks over time, so reusing past experience through persistent memory is attractive because memory is useful only insofar as it improves future task performance. The dominant paradigm curates at write time: after each task the trajectory is distilled into reflections, insights, workflows, executable skills, or reasoning strategies, and later retrieved by similarity search into context. This forces the system to decide what matters before the future task is known, which creates two fundamental costs. First, information loss is premature and irreversible, since details discarded at storage can never be recovered by a later task that needs them. Second, a single fixed artifact must serve many different future queries even though the same trajectory could teach different lessons, such as a household episode teaching a heating pattern to one task and a placement pattern to another. Learning a write-time curator is additionally hard because the value of a storage decision may only appear many tasks later when a matching query arrives, creating a long-horizon delayed-utility credit-assignment problem that prior learned methods such as SkillOS can only address with artificial task-grouping scaffolds and auxiliary judge rewards.

## Main Original Ideas

1. **Read-time just-in-time curation.** The core principle is to defer all distillation until read time when the current task is known, so the curator jointly reads the retrieved traces plus the new task and extracts exactly what is useful for that task. The same stored trajectory therefore yields different payloads for different downstream queries, paralleling the reconstructive view of episodic memory, which is something query-independent write-time artifacts cannot provide.

2. **Retrieve–Curate–Execute–Update loop over a raw episodic bank.** JITMEM keeps the memory bank as a passive store of complete unabstracted trajectories with no summarization at storage, retrieves top-k traces with untrained BM25 over task descriptions only, synthesizes an ephemeral compact natural-language briefing of relevant experiences, extracted strategies, and task-specific guidance, executes with a frozen pretrained LLM that never consumes raw traces directly, and appends the new trajectory only if the executor-as-judge deems it successful. The payload is never stored, only the resulting trajectory is considered for insertion, and the retriever operates identically at train and test time.

3. **GRPO training on immediate same-task reward.** Only the curator is trainable, optimized with GRPO without a value network: per training task a group of candidate payloads is generated, the frozen executor attempts the task with each, and ground-truth task reward gives advantages relative to the group mean without standard-deviation normalization. Because the payload is consumed on the same task it was produced for, the temporal gap between action and reward is zero, which eliminates task-grouping machinery, auxiliary content rewards, and return shaping, while training uses a fixed bank of base-executor successes for stability and evaluation cold-starts from an empty streaming bank.

4. **Decoupled curator–executor modularity with cross-executor transfer.** By freezing the executor and separating curation from execution, one curator trained with a small model such as Qwen3-8B can serve stronger executors such as Gemini-2.5-Pro and GPT-5.4 without retraining, unlike concurrent read-time approaches that entangle adaptation and execution in a single policy. This makes memory a portable component that can be evaluated in isolation and deployed across model upgrades.

## Key Findings

With a Qwen3-8B executor, RL-trained JITMEM reaches 77.4% success on ALFWorld versus 61.2% for RL-trained SkillOS and 32.8% versus 16.5% success on WebShop with score 61.1 versus 40.6, while with Gemini-2.5-Pro it reaches 86.2% versus 80.2% and 50.5% versus 41.3%, and with GPT-5.4 it reaches 86.7% and 45.4% for gains of roughly 6 to 11 points on stronger executors. Remarkably, even the untrained JITMEM-base is already competitive with or better than strong write-time baselines, including beating same-model ReasoningBank and SkillOS-base on ALFWorld and letting a weak Qwen3-8B curator with a GPT-5.4 executor outperform GPT-5.4-curated write-time methods, which shows that task-adaptive read-time curation itself is a major source of gain that RL then compounds. Efficiency also improves substantially: with a GPT-5.4 executor on ALFWorld, JITMEM-base adds only about 1.9K input tokens over no memory compared with 10.7K and 13.4K for ReasoningBank and SkillOS-base while cutting steps by roughly a fifth, and RL training further reduces input tokens, output tokens, and steps. Ablations confirm each design choice matters independently, with write-time distillation before storage costing up to 8.2 points on WebShop, empty-retrieval controls dropping up to 14.8 points on ALFWorld and 15.2 on WebShop to prove RL learns to distill retrieved experience rather than parametric hints, staged bank refresh helping only modestly, test-bank warm-starting proving negligible, and retrieval count proving insensitive. Qualitative cases show the same retrieved episode curated into heat-cool guidance for one task versus placement guidance for another, and the trained curator recovering environment-specific workflows absent from the prompt, while training curves show validation success climbing and executor turns falling steadily over 100 GRPO steps under a single task reward.

## Suggestions & Future Directions

The paper itself flags three limitations that point directly to follow-ups: the BM25 retriever is deliberately simple for baseline consistency but may bottleneck as the bank grows large and diverse, the curator adds one extra LLM call per task, and the payload format is fixed and hand-designed per benchmark. Natural next steps are therefore to jointly optimize the payload format rather than hand-specifying its sections, to explore stronger learned or dense retrievers and adaptive retrieval budgets, and to extend curation from once per task to turn- or step-level adaptation as new observations arrive. Broader questions include how to maintain bank quality over very long deployments beyond success-filtering, how to handle mixed-quality or failure trajectories more expressively, and how task-adaptive read-time curation composes with in-session working-memory compression and skill-evolution methods.
