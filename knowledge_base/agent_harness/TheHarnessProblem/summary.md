# We improved 15 LLMs at coding in one afternoon. Only the harness changed. — Stencil

**Article:** [We improved 15 LLMs at coding in one afternoon. Only the harness changed.](https://stencil.so/blog/the-harness-problem) — Stencil

## Human Readable TL;DR

Imagine blaming the pilot every time the landing gear jams, when the real problem is the runway equipment on the ground. This article argues that coding agents fail mostly for the same reason: the model usually knows what fix to make, but the tools it must use to edit files are so fiddly that its good ideas never land. The authors swapped only the edit tool for a simpler system of short line tags and watched the same models suddenly succeed far more often while using fewer tokens, like giving every pilot one clear set of landing instructions that works at any airport.

## TL;DR

The article argues the "which model is best at coding" debate misses the point, because the harness — tool schemas, error messages, state management, everything between the model knowing what to change and the issue being resolved — is where most practical failures happen. Surveying current edit tools (OpenAI-style apply_patch blobs, str_replace exact-match swaps, Cursor's separate merger model), it concludes none gives the model a stable, verifiable way to point at lines without perfectly reproducing content it already saw. It proposes Hashline, in which every line the model reads comes back with a short 2–3 character content hash that the model then cites for replacements, ranges, and inserts, with mismatched hashes rejecting stale edits before files get corrupted. In a benchmark of 180 React-codebase mutation tasks with 3 runs each across 16 models, Hashline beats patch in 14 of 16 models with roughly +15 points average gain at zero training compute, matches or beats str_replace-style tools for most models, cuts output tokens substantially, and helps the weakest models most dramatically.

## Problem & Motivation

The piece opens by calling the current conversation — GPT versus Opus versus Gemini versus whatever dropped this week — increasingly misleading, because it treats the model as the only variable that matters when one of the real bottlenecks is far more mundane: the harness. The harness shapes the user's first impression, supplies every input token, and forms the interface between model output and every change made to the workspace, yet tool schemas, error messages, and state management receive far less attention than model weights. A concrete example is given of a strong model leaking raw JSONL from sub-agent outputs and wasting hundreds of thousands of tokens, the kind of defect an open harness can simply fix by switching subagents to structured output. The motivation is therefore practical and economic: harness experiments cost an afternoon and about $300 in benchmarking, while model upgrades cost enormous training compute, yet the article's harness-only change delivered gains comparable to or larger than most model upgrades.

The edit-tool survey grounds this motivation in detail. Codex-style apply_patch expects a blob following strict diff-like rules, which works for models tuned to it but produces very high patch failure rates for others (about 50.7% for Grok 4 and 46.2% for GLM-4.7 in this benchmark), prompting the line that these are not bad models, they just do not speak the language. Claude-style str_replace is simple to reason about but demands character-perfect reproduction of old text including whitespace and indentation, rejects ambiguous matches, and produces the notorious "string to replace not found" failure with its own issue megathread, while Gemini adds only fuzzy whitespace matching on top of the same idea. Cursor went so far as to train a separate 70B merger model just to land draft edits correctly, and even then found full-file rewrites beat aider-like diffs for small files. Prior benchmarks reinforce the point: format choice alone once swung a GPT model from 26% to 59%, no single edit format dominates across models, and realistic editing remains hard — so the article concludes the format matters as much as the model.

## Main Original Ideas

1. **The harness is the real variable.** The article reframes agent quality as a harness problem rather than a model problem, arguing that being model-agnostic makes an open harness a great testing ground where the model is just a parameter and contributors using different models fix the failures they personally encounter, which no single vendor will do for competitors' models.

2. **Hashline content-hash line tags.** The central proposal tags every line the model reads or greps with a short pseudo-random content hash (for example `2:f1`), so the model can say "replace line 2:f1" or "replace range 1:a3 through 3:0e" or "insert after 3:0e" without reproducing old content or whitespace. If the file changed since the read, the hashes optimistically mismatch and the edit is rejected before corruption, on the theory that recalling a pseudo-random tag is strong evidence the model knows what it is editing.

3. **A cheap, mechanical mutation benchmark.** The evaluation takes random files from the React codebase, introduces mechanical bugs framed as plain-English issues (operator swaps, boolean flips, off-by-one errors, removed guard clauses or optional chains, renamed identifiers), and runs fresh agent sessions with only read, edit, and write tools, comparing the result against the original file after formatting. This keeps fixes objective enough that reverting the mutation is usually the expected solution while still allowing legitimately different fixes.

4. **Harness gains as free R&D.** The article frames a second-order idea that vendor lock-in around harnesses is backwards: a different edit format improving even a vendor's own models by 5 to 14 points while cutting output tokens by around 20% is not a threat but free research, captured in the lines "the model is the moat, the harness is the bridge" and "you're blaming the pilot for the landing gear."

## Key Findings

Across sixteen models, three edit tools, and the stated protocol, the outcome is presented as unambiguous: patch is the worst format for nearly every model, Hashline matches or beats the replace-style baseline for most models, and the weakest models gain the most. Only the edit tool changed, yet the average gain over patch was about 15 points with zero training compute, with Hashline beating patch in 14 of 16 models and a revised v2 improving further in 12 of 16. The most extreme case is Grok Code Fast 1 rising from 6.7% to 68.3%, described as a tenfold improvement caused by catastrophic patch failures previously hiding its real coding ability, alongside large jumps such as MiniMax M2.1 (+41.7 over patch), Devstral Medium (+40.5), GLM-4.5 Air (+27), and GLM-4.7 (+23.3). The largest v2 revision gain cited is GPT-5.1 Codex Mini moving from 60.0% to 77.5%, while DeepSeek V3.2 is the notable outlier that lost ground (-5 over patch).

Token efficiency improved alongside success rates because models stopped burning tokens on retry loops, with best-case output tokens falling 61% for Grok 4 Fast and declines around 20–49% for many others (for example roughly 49% for Grok Code Fast 1, 42% for MiniMax, 32% for GLM-4.7, and low-20s percentages for Claude Sonnet 4.5, Haiku 4.5, and Gemini 3 Flash). The article highlights that even an 8-point success-rate gain for Gemini from the harness alone exceeds what most model upgrades deliver, at a benchmarking cost of only about $300. A vendor-side observation closes the findings: blocking third-party harnesses or banning benchmarking accounts is framed as short-sighted, since open harnesses tune for all models precisely because no vendor will optimize for a competitor's model.

## Suggestions & Future Directions

The article's explicit direction is to keep treating the harness as an open, shared optimization surface rather than a solved or vendor-owned layer, with all code, benchmarks, and per-run reports released for others to build on. Implicit next steps include iterating on the Hashline format itself (the v2 revision already shows further gains for most models), extending the same hash-anchored thinking to other tools and state management beyond file edits, and broadening benchmarks so format comparisons cover more models and use cases, in the spirit of prior findings that no single format dominates everywhere. It also urges vendors to treat independent harness work as complementary research rather than misuse, since improvements that cut tokens and raise success rates benefit their own models and APIs. The closing stance is normative as much as technical: do not force builders to use only first-party harnesses, because burning those bridges means fewer people cross to the models at all.
