# Targeted: What Fleet Can Learn from Harness
**In one sentence:** Harness's borrowable core is lease-based worker recovery, two-stage permit scheduling, declarative submissions over a plan store, and policy-as-data enforcement — all backed by Postgres rather than in-memory state.
## Key points
- Policy is data, not code: three-valued `ExecDecision` (`crates/harness-rules/src/exec_policy.rs:9-15`) over tokenized command patterns (`crates/harness-rules/src/exec_policy.rs:17-30`), loaded at startup and queried offline.
- Restart recovery is lease-expiry-driven, not startup-replay: expired `running` jobs become reclaimable (`crates/harness-workflow/src/runtime/job_claim.rs:90-100`), claims bump `lease_generation` (`crates/harness-workflow/src/runtime/model.rs:590-602`), and workers renew mid-execution (`crates/harness-workflow/src/runtime/worker.rs:245-274`).
- Concurrency is a two-stage permit queue (project slot, then global slot) with RAII release on drop (`crates/harness-server/src/task_queue/mod.rs:40-44`, `crates/harness-server/src/task_queue/mod.rs:70-82`) and aging anti-starvation (`crates/harness-server/src/task_queue/permits.rs:1-4`).
- Work intake is a submissions API (`crates/harness-server/src/http/http_router.rs:88-92`) over `WorkflowInstance` + `RuntimeJob` rows, with a separate `ExecPlan` plan object (`crates/harness-exec/src/plan.rs:7-19`) created from a spec (`crates/harness-exec/src/plan.rs:55-78`).
- Parallel-agent conflicts are reduced by prompt-level sibling constraints (`crates/harness-core/src/prompts/context.rs:23-40`), per-task git worktrees with classified add-failures (`crates/harness-server/src/workspace_worktree_add.rs:7-30`), and dual-reviewer synthesis (`crates/harness-core/src/prompts/review.rs:351-379`).
- Multi-agent support is a trait plus registry: `AgentBackend` (`crates/harness-core/src/agent.rs:84-92`) resolved by `AgentRegistry` (`crates/harness-agents/src/registry.rs:13-17`) assembled in one function (`crates/harness-agents/src/builder.rs:135-190`).
- The highest-value borrows for Fleet are the Starlark-style exec policy, lease/generation recovery, GC draft staging (`crates/harness-gc/src/draft_store.rs:37-59`), OTLP trajectory export (`crates/harness-observe/src/otel_export.rs:306-311`), and context dedup keys (`crates/harness-context/src/composer.rs:415-453`).

## 1. Design principles (orchestration, policy enforcement, observability)
Harness separates orchestration (Axum REST + JSON-RPC control plane over Postgres), enforcement (policy stores queried at spawn/commit time, not inline interceptors), and observation (event log plus optional OTLP export). The submissions surface is explicit REST: list/create on `/api/workflows/runtime/submissions`, get by id, artifacts, prompts, proof, and SSE stream (`crates/harness-server/src/http/http_router.rs:88-112`). Policy input is a typed enum, not strings: `ExecDecision::{Allow, Prompt, Forbidden}` (`crates/harness-rules/src/exec_policy.rs:9-15`) matched against `PatternToken::{Single, Alts}` command prefixes (`crates/harness-rules/src/exec_policy.rs:17-30`). Enforcement loops are bounded: the hook circuit breaker opens after 3 consecutive blocks and auto-passes for 300 s (`crates/harness-server/src/hook_circuit_breaker.rs:5-8`), with `Closed`/`Open`/`HalfOpen` states (`crates/harness-server/src/hook_circuit_breaker.rs:10-18`). Observability is a pipeline struct over OpenTelemetry logs/metrics/traces (`crates/harness-observe/src/otel_export.rs:1-11`) with a `trajectory` flag defaulting off (`crates/harness-core/src/config/misc.rs:404-417`, `crates/harness-observe/src/otel_export.rs:121-139`) and per-operation span recording for `workflow_root`, `activity`, and `agent_turn` (`crates/harness-observe/src/otel_export.rs:231-243`). For Fleet: keep the orchestrator thin, push policy into versioned data files, and bound every enforcement loop with a circuit breaker rather than retrying indefinitely.
## 2. Worker restart handling (turn lifecycle, reconcile, GC signal detection)
A worker turn is one claimed `RuntimeJob` executed once; claiming sets `status=Running`, bumps `lease_generation`, and stamps owner plus expiry (`crates/harness-workflow/src/runtime/model.rs:590-602`). The claim query accepts `pending` jobs or `running` jobs whose `data.lease.expires_at` has passed (`crates/harness-workflow/src/runtime/job_claim.rs:90-100`), so a crashed worker needs no explicit restart handler — its job simply becomes reclaimable on TTL expiry. Mid-execution the worker renews at a computed interval and extends only if it still owns the lease (`crates/harness-workflow/src/runtime/worker.rs:245-274`). Lease health is tri-state (`ActiveLeased`/`ExpiredLease`/`MissingLease`) derived from status plus `expires_at` (`crates/harness-workflow/src/runtime/lease_state.rs:6-36`). Host liveness is heartbeat-derived (`now - last_heartbeat_at <= heartbeat_timeout_secs`) (`crates/harness-server/src/runtime_hosts.rs:223-234`). Boot recovery is workspace-centric: release foreign orphaned leases first, then reconcile directories against live tasks (`crates/harness-server/src/workspace_reconcile.rs:57-86`). GC signal detection is orthogonal to crash recovery: `SignalDetector::detect` aggregates `RepeatedWarn`, `ChronicBlock`, `HotFiles`, `SlowSessions`, `WarnEscalation`, `LinterViolations` over the event log (`crates/harness-gc/src/signal_detector.rs:20-29`), and `detect_from_external` maps GitHub CI failure to `ChronicBlock` and `changes_requested` to `RepeatedWarn` (`crates/harness-gc/src/signal_detector.rs:31-47`). For Fleet: replace supervisor liveness checks with lease-expiry reclamation plus a generation counter, and keep hygiene signals (stuck tasks, hot files) on a separate path from crash recovery.
## 3. Conflict resolution (worktree isolation, cross-agent review, no-self-review)
Isolation is per-task git worktrees, not branches in a shared checkout: `git worktree add` failures are classified into `StaleWorktreeEntry`/`LockContention`/`PathCollision`/`MissingRef`/`Unknown` for ops aggregation (`crates/harness-server/src/workspace_worktree_add.rs:7-30`, `crates/harness-server/src/workspace_worktree_add.rs:32-55`), and orphan worktree cleanup plus `git worktree prune` run under a repository lease. The OS sandbox narrows this further: `SandboxSpec` carries `mode`, `project_root`, token-derived `allowed_write_paths`, and an orthogonal `network_policy` (`crates/harness-sandbox/src/lib.rs:39-47`); `DangerFullAccess` is a passthrough (`SandboxEngine::None`) unless token paths or a network policy narrow it (`crates/harness-sandbox/src/lib.rs:79-96`), and `.git`/`.harness` are always protected (`crates/harness-sandbox/src/lib.rs:28-36`). Cross-agent conflicts in parallel dispatch are reduced at the prompt level: `SiblingTask{issue, description}` (`crates/harness-core/src/prompts/context.rs:5-13`) renders a do-not-touch block listing what other agents own (`crates/harness-core/src/prompts/context.rs:23-40`). Review avoids self-confirmation structurally: periodic review picks a secondary agent that must differ from the primary (`crates/harness-server/src/periodic_reviewer/tick_helpers.rs:60-72`), the challenger protocol forces `CONFIRMED`/`FALSE-POSITIVE`/`MISSED` verdicts per primary finding (`crates/harness-core/src/prompts/cross_review.rs:21-30`), and dual reviews are merged by a synthesis prompt that instructs verifying findings against the code and scoring `health_score = 100 - deductions` (`crates/harness-core/src/prompts/review.rs:351-379`); the `AgentBackend::id` default exists precisely to detect primary==challenger misconfigurations (`crates/harness-core/src/agent.rs:84-92`). For Fleet: keep worktree-per-task, add prompt-level sibling ownership blocks, and route supervisor validation through a different model/backend than the implementor.
## 4. Workflow abstraction (submissions API, ExecPlan, project queue permits — cite crates)
`harness-server` exposes work as submissions (`crates/harness-server/src/http/http_router.rs:88-92` for create/list, `crates/harness-server/src/http/http_router.rs:93-112` for detail/stream/proof/merge/cancel/unblock/retry); the durable model is `WorkflowInstance` plus child `RuntimeJob`s assembled in `crates/harness-server/src/workflow_runtime_submission/mod.rs:1-17`, with `CreateTaskRequest` and `MAX_TASK_PRIORITY = 2` defined in `runtime_request.rs` (`crates/harness-server/src/workflow_runtime_submission/runtime_request.rs:12-15`) and declarative intake recorded by `record_declarative_submission` (`crates/harness-server/src/workflow_runtime_submission/declarative.rs:32`). Plans are a separate durable object from jobs: `ExecPlan{id, purpose, project_root, progress, concrete_steps, decision_log, surprises, validation, status}` in `harness-exec` (`crates/harness-exec/src/plan.rs:7-19`), initialized from a spec document with status `Draft` (`crates/harness-exec/src/plan.rs:55-78`) and persisted through the plan DB (`crates/harness-workflow/src/plan_db.rs:4-5`). Scheduling is a two-stage permit queue in `harness-server`: `TaskPermit` holds a global plus a project slot released on drop (`crates/harness-server/src/task_queue/mod.rs:40-44`); `AcquirePhase::{ProjectWait, GlobalWait}` tracks which stage a waiter holds (`crates/harness-server/src/task_queue/mod.rs:70-82`); the engine is a priority queue with aging-based anti-starvation capped at `MAX_PRIORITY_LEVEL = 2` (`crates/harness-server/src/task_queue/permits.rs:1-22`) that ranks by effective priority then FIFO sequence (`crates/harness-server/src/task_queue/permits.rs:65-76`). For Fleet: mirror this split — a plan record (what/why) separate from attempt records (who ran what), intake through one submissions function, and per-project plus global concurrency caps.
## 5. Multi-agent support (Claude/Codex/API — harness-agents adapters + registry, cite files)
All backends implement `AgentBackend: Send + Sync` (`crates/harness-core/src/agent.rs:84-92`); one-shot CLIs implement `execute`, stateful protocols (`codex_adapter.rs`, `opencode_adapter.rs`) override the turn/control surface. `AgentDescriptor{backend, control_backend, turn_backend_factory}` (`crates/harness-agents/src/registry.rs:13-17`) is stored in `AgentRegistry` (`crates/harness-agents/src/registry.rs:19-24`), which preserves side channels across re-registration (`crates/harness-agents/src/registry.rs:44-60`). Assembly is a single function: register `claude`, `codex` plus a `CodexAdapter` turn factory, `opencode` plus an `OpenCodeAcpAdapter` turn factory, and `anthropic-api` only when `ANTHROPIC_API_KEY` is present (`crates/harness-agents/src/builder.rs:135-190`). Provider overload is isolated per phase: `ProviderBackpressureGate{global, phase_limits}` with `ProviderBackpressurePermit` holding phase plus global semaphore permits (`crates/harness-agents/src/provider_backpressure.rs:50-62`). For Fleet: define one worker-backend trait, resolve model/CLIs through a registry with a default plus per-turn factories, and gate external API calls with per-phase semaphores rather than a single global limit.
## 6. What Fleet can borrow (5-8 concrete features with file:line citations: Starlark policy engine, GC drafts, OTLP observability, skill dedup, + others you find)
- Starlark-style exec policy as data: `ExecDecision` plus `PatternToken` prefix rules (`crates/harness-rules/src/exec_policy.rs:9-30`) with a parse-and-query store — Fleet could add a `policy/` file of allow/prompt/forbidden command prefixes checked by the supervisor before and after each worker turn, replacing ad-hoc shell blocklists.
- Atomic GC draft staging: `DraftStore::adopt_if_pending` runs side effects under a transition mutex and only then flips `Pending` to `Adopted` (`crates/harness-gc/src/draft_store.rs:37-59`), with `save_if_status` for guarded writes (`crates/harness-gc/src/draft_store.rs:65-80`) — Fleet could stage every worker diff as a pending draft in beads and adopt only after supervisor validation passes.
- OTLP trajectory export with safe defaults: span/log/metric exporters for `OtlpHttp` (4318) vs `OtlpGrpc` (4317) with endpoint overrides (`crates/harness-observe/src/otel_export.rs:306-311`, `crates/harness-observe/src/otel_export.rs:395-396`) behind an opt-in `trajectory` flag (`crates/harness-core/src/config/misc.rs:404-417`) — Fleet could emit per-task spans (queue, execute, validate) to an OTLP collector without changing its beads schema.
- Context dedup by key: every context provider sets `dedupe_key` (`skill:`, `contract:task`, `contract:exec-plan:`, `brief:task`, `draft:` in `crates/harness-context/src/providers.rs:45-290`) and `dedupe()` keeps one survivor per key ordered by provider precedence rules < contract < exec-plan < skills < brief < gc-drafts (`crates/harness-context/src/composer.rs:415-453`, `crates/harness-context/src/composer.rs:642-653`) — Fleet could dedupe supervisor prompts (system, plan, skills, drafts) by key before spawning each coder worker to cut tokens.
- Skill freshness classification: `Fresh`/`Active`/`Dormant`/`Stale` from 7/30/90-day thresholds plus a 5-sample minimum (`crates/harness-skills/src/freshness.rs:6-26`) — Fleet could rank its skill/coding-convention notes by recency-plus-usage instead of injecting all of them every turn.
- Cross-reviewer synthesis instead of self-review: secondary agent must differ (`crates/harness-server/src/periodic_reviewer/tick_helpers.rs:60-72`), challenger verdicts are protocol-enforced (`crates/harness-core/src/prompts/cross_review.rs:21-30`), synthesis merges both into scored JSON (`crates/harness-core/src/prompts/review.rs:351-379`) — Fleet could run validation with a different backend than implementation and require CONFIRMED/FALSE-POSITIVE verdicts per finding.
- Lease-generation recovery: claim bumps `lease_generation` (`crates/harness-workflow/src/runtime/model.rs:590-602`), expired leases are re-claimable by SQL predicate (`crates/harness-workflow/src/runtime/job_claim.rs:90-100`), renewal runs concurrently with execution (`crates/harness-workflow/src/runtime/worker.rs:245-274`) — Fleet could add `lease_owner`, `lease_expires_at`, `lease_generation` columns to its beads tasks and let stalled worker tasks be reclaimed without a central watchdog.
- Two-stage permit scheduling with aging: project-then-global acquisition (`crates/harness-server/src/task_queue/mod.rs:70-82`) with RAII release (`crates/harness-server/src/task_queue/mod.rs:40-44`) and `MAX_PRIORITY_LEVEL = 2` aging (`crates/harness-server/src/task_queue/permits.rs:14-22`) — Fleet could cap concurrent workers per worktree-group and globally with the same two-stage semaphore, preventing one large task batch from starving small fixes.
