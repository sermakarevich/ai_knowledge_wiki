# Cross-Agent Review and Garbage Collection
**In one sentence:** Harness checks agent output through a primary-plus-challenger review protocol and independent quality gates, and reclaims degraded work through a signal-driven garbage-collection loop that drafts, stores, and optionally adopts rule, guard, or skill fixes.
## Key points
- Cross-agent review means a primary agent produces a review and a distinct challenger agent confirms, contests, or extends each issue over bounded rounds, with `Approved` returned only when no consensus issues remain (crates/harness-server/src/handlers/cross_review.rs:138-145, 265-339).
- Self-review is prevented by identity comparisons on agent identity, not on GitHub author login: `distinct_challenger` drops a challenger whose `candidate.id() != primary.id()` fails, `quality_trigger` skips when `primary.name() == challenger.name()`, and the periodic reviewer picks a secondary agent with `agent != primary_agent` (crates/harness-server/src/handlers/cross_review.rs:419-424; crates/harness-server/src/quality_trigger.rs:198-207; crates/harness-server/src/periodic_reviewer/tick_helpers.rs:60-72).
- The periodic reviewer runs on an interval loop with per-project watermarks, guard scans, primary enqueue, optional secondary review under `ReviewStrategy::Cross`, and watermark advance only after parseable output (crates/harness-server/src/periodic_reviewer/mod.rs:195-210; crates/harness-server/src/periodic_reviewer/tick.rs:107-142).
- Structured review reports (`ReviewReport`, `ReviewGateResult`) are parsed from fenced `harness-review-report` JSON, legacy `ISSUE:` lines, or terminal `APPROVED`, and required providers must all approve or the gate returns `ChangesRequested` or `Blocked` (crates/harness-core/src/review.rs:106-170, 172-257).
- Post-task quality grading over a 1-hour event window can trigger garbage collection (GC): grades below threshold plus cooldown expiry start a bounded `gc_agent.run` with timeout and scan-watermark handling (crates/harness-server/src/quality_trigger.rs:16-21, 317-376).
- Per-turn and per-PR gates include `PostExecutionValidator` (pre-commit/pre-push shell commands plus PR-existence verification), the `local_review_gate` workflow state, a revision-bound quality-gate workflow, PR-feedback repair with a 3-round convergence stop, and hygiene repair for `DIRTY`/`BEHIND` merge states (crates/harness-server/src/post_validator.rs:233-344; crates/harness-workflow/src/runtime/pr_feedback.rs:86-116; crates/harness-server/src/github_pr_hygiene.rs:246-251).
- GC signals mark work as garbage: `RepeatedWarn`, `ChronicBlock`, `HotFiles`, `SlowSessions`, `WarnEscalation`, `LinterViolations`, derived from event thresholds, persisted `rule_check` violations, and external GitHub payloads (CI failure to `ChronicBlock`, review `changes_requested` to `RepeatedWarn`) (crates/harness-gc/src/signal_detector.rs:20-29, 35-96; crates/harness-core/src/types.rs:323-349).
- A GC draft is a persisted `Draft { id, status, signal, artifacts, rationale, validation, generated_at, agent_model }` with `Pending/Adopted/Rejected/Expired` states; drafts are saved immediately per signal, expire by time-to-live (TTL, i.e. maximum pending lifetime), and reach disk only through `adopt_if_pending` path validation or `RulesOnly` auto-adoption, or through `reject` guarded by `save_if_status` (crates/harness-core/src/types.rs:543-578; crates/harness-gc/src/draft_store.rs:37-82, 125-138; crates/harness-gc/src/gc_agent.rs:182-258, 269-373).

## Review model
Primary-challenger review is orchestrated in `run_cross_review_with_context` (crates/harness-server/src/handlers/cross_review.rs:173-182): the primary review is executed first, then the challenger is invoked for up to `max_rounds - 1` additional rounds with outstanding issues re-injected into each prompt (crates/harness-server/src/handlers/cross_review.rs:265-293). Challenger output is classified by line-prefix tags `CONFIRMED:`, `MISSED:`, and `FALSE-POSITIVE:`; confirmed plus missed issues form the next round's consensus set (crates/harness-server/src/handlers/cross_review.rs:295-299, 341-345). An empty consensus set yields `Approved`; a reply with no tag prefix at all yields `ProtocolFailure` with a bounded 280-character excerpt, and remaining issues after the round budget yield `NotConverged` (crates/harness-server/src/handlers/cross_review.rs:301-339, 350-395). Without a challenger the result degrades to `SingleModelDegraded` with `ApprovedDegraded` (never bare `Approved`) when the primary reported no `ISSUE:` lines (crates/harness-server/src/handlers/cross_review.rs:194-216). Report parsing and gate evaluation are shared in `harness-core`: fenced JSON, raw JSON, legacy `ISSUE:` lines, or terminal `APPROVED`, with missing or failed required providers blocking the gate (crates/harness-core/src/review.rs:106-170, 172-257).
## No-self-review enforcement
There is no GitHub author-versus-reviewer login check in the reviewed paths; independence is enforced by comparing agent identities at three call sites. The lowest-level guard is `distinct_challenger`, which filters the challenger candidate by `candidate.id() != primary.id()` where both are `CodeAgent::id()` strings, degrading to single-model mode on equality (crates/harness-server/src/handlers/cross_review.rs:416-424). The post-task path in `quality_trigger` repeats the check on agent names (`primary.name() == challenger.name()`), skipping cross-review with a warning to avoid correlated verdicts, and additionally refuses primary or challenger agents advertising `Write`/`Execute` capabilities so the background gate cannot mutate the workspace (crates/harness-server/src/quality_trigger.rs:198-243). The periodic scheduler enforces the same rule by name string in `pick_secondary_review_agent`, selecting the first registered candidate with `agent != primary_agent` and warning when `ReviewStrategy::Cross` has no secondary available (crates/harness-server/src/periodic_reviewer/tick_helpers.rs:60-72; crates/harness-server/src/periodic_reviewer/tick.rs:130-142).

```rust
/// Identity guard (GH-1767): a challenger resolving to the same agent
/// identity as the primary is no challenger at all — degrade instead of
/// "reviewing" with a single model twice.
fn distinct_challenger(
    primary: &Arc<dyn CodeAgent>,
    challenger: Option<Arc<dyn CodeAgent>>,
) -> Option<Arc<dyn CodeAgent>> {
    challenger.filter(|candidate| candidate.id() != primary.id())
}

/// True when any line carries one of the three protocol tag prefixes, even
/// with an empty body (which `extract_tagged` filters out).
fn has_any_tag_prefix(output: &str) -> bool {
    output.lines().map(str::trim).any(|line| {
        line.starts_with("CONFIRMED:")
            || line.starts_with("MISSED:")
            || line.starts_with("FALSE-POSITIVE:")
    })
}
```
## Quality gates
`QualityTrigger` grades only the trailing 1-hour event window (plus the latest `rule_scan` violation count) so lifetime passes cannot mask a recent failure, logs the grade, and proceeds only if the grade is in the auto-GC set and the cooldown has elapsed (crates/harness-server/src/quality_trigger.rs:16-21, 133-177, 306-334). Cross-review applies only when a challenger, task context (diff plus PR description, diff truncated at 4096 bytes), and a non-`A` grade coincide; `NotConverged` or `ProtocolFailure` downgrades the grade one step (`B->C`, `C->D`, `D` floor) before the GC decision (crates/harness-server/src/quality_trigger.rs:180-304). `PostExecutionValidator` runs configured `pre_commit` commands, then `pre_push` commands only if the first set passed, then GitHub REST verification of any claimed PR URL, joining failures with `[COMPILE ERROR]`/`[TEST FAILURE]`/`[LINT ERROR]` prefixes and retrying up to `max_retries` (crates/harness-server/src/post_validator.rs:14-20, 220-344). Workflow-level gates use the `local_review_gate` state (`run_local_review` activity with `LocalReviewPassed`/`LocalReviewChangesRequested`/`LocalReviewBlocked` signals), a `quality_gate` child workflow running revision-bound validation commands, and PR-feedback repair capped by `MAX_FEEDBACK_REPAIR_ROUNDS = 3` with round-limit, missing-baseline, and no-progress stops (crates/harness-workflow/src/runtime/pr_feedback.rs:13-17, 86-116, 368-436; crates/harness-workflow/src/runtime/quality_gate.rs:6-10, 36-73; crates/harness-workflow/src/runtime/validator.rs:243-254). Hygiene repair targets open pull requests (PRs) whose `mergeStateStatus` is `DIRTY` or `BEHIND` plus dirty-age thresholds, while merge itself is a server-executed API call with expected-head-SHA (secure hash algorithm revision identifier) protection; the reconciliation test path marks a `local_review_gate` workflow `done` when the external PR is observed merged (crates/harness-server/src/github_pr_hygiene.rs:30-33, 246-251; crates/harness-server/src/github_pr_merge.rs:80-102; crates/harness-server/src/reconciliation_local_review_gate_tests.rs:39-97).
## GC signals and drafts
`SignalDetector::detect` aggregates six detectors over the scanned event slice, each gated by `SignalThresholdsConfig` counts (warn repetition, block chronicity, hot-file edits, slow-operation counts, warn-rate escalation requiring at least 20 events, and `rule_check` linter violations), with `from_violations` and `detect_from_external` adding live violations and GitHub webhook mappings (crates/harness-gc/src/signal_detector.rs:20-29, 98-168, 220-291). `recommended_remediation` maps each signal to a Guard, Rule, or Skill artifact type and `signal_priority` orders processing with `ChronicBlock` first and `SlowSessions` last (crates/harness-gc/src/remediation.rs:4-25). `GcAgent::run_with_external` expires stale drafts, selects full versus incremental scan via `GcCheckpoint { last_scan_at, head_commit }` filtering (`filter_events_since`, partition on `ts <= cutoff`), sorts signals by priority, invokes the code agent with read-only tools under a per-signal budget, persists each draft immediately for cancellation safety, and advances the checkpoint only in a synchronous post-loop phase (crates/harness-gc/src/gc_agent.rs:104-153, 182-258; crates/harness-gc/src/checkpoint.rs:9-74). A draft persists as one JSON file per `DraftId` under `drafts/`; `adopt` canonicalizes the project root, lexically normalizes each artifact path, resolves symlinks through the nearest existing ancestor, and writes files only when the status transition `Pending -> Adopted` holds under a mutex, while `auto_adopt_matching` additionally requires `RulesOnly` policy, `Rule` remediation, non-empty artifacts, and all paths under the configured prefix (crates/harness-gc/src/draft_store.rs:37-82; crates/harness-gc/src/gc_agent.rs:269-373). `expire_stale_drafts` deletes `Pending` drafts older than `draft_ttl_hours`; `reject` flips `Pending -> Rejected` through `save_if_status` so a racing `adopt` cannot be silently overwritten (crates/harness-gc/src/draft_store.rs:125-138; crates/harness-gc/src/gc_agent.rs:360-373).

```rust
pub fn detect(&self, events: &[Event]) -> Vec<Signal> {
    let mut signals = Vec::new();
    signals.extend(self.detect_repeated_warns(events));
    signals.extend(self.detect_chronic_blocks(events));
    signals.extend(self.detect_hot_files(events));
    signals.extend(self.detect_slow_sessions(events));
    signals.extend(self.detect_warn_escalation(events));
    signals.extend(self.detect_linter_violations(events));
    signals
}
```
