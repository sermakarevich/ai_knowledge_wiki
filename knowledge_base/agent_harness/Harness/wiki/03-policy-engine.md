# Starlark Policy Engine and Sandboxing
**In one sentence:** Harness constrains agents through a Starlark-based exec policy (allow/prompt/forbidden prefix rules over command tokens) evaluated by `RuleEngine::check_command_policy`, plus shell-operator safety checks, post-tool-use guard scans with a circuit breaker, tool allowlists with capability tokens, and OS-level sandboxing (Seatbelt on macOS, Landlock/bwrap on Linux) with an orthogonal network policy.
## Key points
- The executable-command policy lives in `crates/harness-rules`: `exec_policy.rs:9-15` defines the three-valued `ExecDecision` (Allow, Prompt, Forbidden), `exec_policy.rs:40-60` defines prefix matching over tokenized commands, and `exec_policy.rs:209-216` evaluates a command to the maximum (most severe) matched decision.
- Starlark files declare policy with two builtins only — `prefix_rule` and `host_executable` (`exec_policy/parser.rs:307-388`); the dialect disables `def`, `lambda`, `load`, and top-level statements (`exec_policy/parser.rs:51-58`), caps source size at 512 KiB (`exec_policy/parser.rs:42`) and call-stack depth at 512 (`exec_policy/parser.rs:22`).
- A second policy source, `requirements.toml`, converts to the same `ExecPolicy` type but may only express `prompt`/`forbidden`: an `allow` decision is rejected (`requirements.rs:77-82`), and merging across `.star` files plus requirements is additive via `merge_overlay` (`exec_policy.rs:155-182`).
- Command evaluation is exposed through `RuleEngine::check_command_policy` (`engine/mod.rs:763-769`), loaded at server startup from `rules.exec_policy_paths` and `rules.requirements_path` (`http/builders/engines.rs:83-88`), and queryable offline via `harness execpolicy check` (`commands/execpolicy.rs:62`); no per-tool-call gate on this path was found — it is a load-and-query policy store, not an inline dispatch interceptor.
- Post-execution enforcement is split: `hook_enforcer.rs:106-195` scans `event.affected_files` with registered guard scripts after each tool use and returns violation feedback, while `command_safety.rs:14-16` (delegating to `shell_safety.rs:14`) rejects unquoted shell operators (`|`, `&&`, `;`, backticks, `$(`, newlines) in hook/validator commands, and `tool_isolation.rs:17` post-scans agent output for disallowed tool tags as defense in depth.
- The hook enforcer fails open by design: it passes when disabled, when `CI` is set, when no guards exist, or when no affected files are reported (`hook_enforcer.rs:107-128`); host-side git inspection is deliberately disabled so `detect_modified_files` returns empty until agent telemetry supplies file lists (`hook_enforcer.rs:70-76`).
- A per-session circuit breaker bounds enforcement loops: 3 consecutive blocks open the circuit and auto-pass for 300 seconds (`hook_circuit_breaker.rs:6-8`, `hook_circuit_breaker.rs:65-106`), explicitly modeled on Claude Code's `stop_hook_active` (`hook_enforcer.rs:22-31`).
- Filesystem sandboxing has four modes — `read-only`, `read-only-with-network`, `workspace-write`, `danger-full-access` (README `README.md:98-100`, enum `config/agents/permissions.rs:94-100`) — enforced at spawn by wrapping the agent command (`spawn_contract.rs:227-234` via `sandbox/src/lib.rs:79-96`): macOS uses `sandbox-exec`/Seatbelt profiles (`sandbox/src/lib.rs:212-273`), Linux prefers `harness-landlock` then falls back to `bwrap` (`sandbox/src/lib.rs:190-203`), and `danger-full-access` is a passthrough (`SandboxEngine::None`) unless token paths or a network policy narrow it (`sandbox/src/lib.rs:87-108`).
- Network policy is orthogonal to the filesystem mode (`sandbox/src/network_policy.rs:6-14`): `Deny` adds `--unshare-net` (bwrap, `linux.rs:78-86`) or `--network deny` (landlock, `linux.rs:15-23`) and emits no Seatbelt outbound allowance, while `danger-full-access` plus deny-all networking still gets a network-only bwrap wrapper (`sandbox/src/lib.rs:176-188`); scoped-permission hosts with an empty allowlist resolve to `DenyAll` (`isolation_health.rs:80-90`) and startup health probing reports host/container/microvm tier availability (`isolation_health.rs:67-78`).

## The rules engine
`crates/harness-rules/src/engine/mod.rs` hosts `RuleEngine` (`engine/mod.rs:50-58`), which bundles three distinct rule systems. Markdown guidance rules are discovered across repo, user, admin, and builtin layers (`engine/mod.rs:84-122`) and parsed from `## ID: Title` sections with severity inferred from body keywords and category from ID prefix (`engine/mod.rs:232-280`); builtin content is compiled in from `rules/` (`engine/mod.rs:167-196`, covering `golden-principles.md` plus `common/`, `go/`, `python/`, `rust/`, `typescript/` quality files). Guard scripts (`*.sh`, registered by filename stem, `engine/mod.rs:570-619`) execute as `bash <guard> <project_root> [<file>]` and their `FILE:LINE:RULE_ID:MESSAGE` stdout lines become `Violation`s (`engine/mod.rs:638-649`, `engine/mod.rs:672-703`). The third system, the exec policy, is stored as an `ExecPolicy` field and queried separately (`engine/mod.rs:763-769`). `crates/harness-rules/src/scanner.rs:1-2` adds no API; scanning lives on the engine. `RulesConfig` (`config/misc.rs:301-317`) wires this together with `discovery_paths`, `builtin_path`, `exec_policy_paths`, `requirements_path`, `auto_fix`, and `hook_enforcement`.
## Exec policy
Policy authors write Starlark restricted to two calls. A minimal rule, verbatim from the test suite (`engine/tests.rs:200-205`):
```starlark
prefix_rule(pattern = ["git", "push"], decision = "prompt")
```
A fuller form with self-testing examples comes from the parser tests (`exec_policy/parser.rs:395-417`):
```starlark
prefix_rule(
  pattern = ["git", ["push", "pull"]],
  decision = "prompt",
  justification = "needs approval",
  match = ["git push"],
  not_match = ["git status"],
)
```
Patterns are prefix lists whose elements are literal strings or alternation lists (`exec_policy/parser.rs:189-240`); the first token selects the program bucket and remaining tokens must match the command prefix (`exec_policy.rs:45-60`). `match`/`not_match` examples are validated at parse time against a fresh policy and fail the load on mismatch (`exec_policy/parser.rs:118-153`). `host_executable(name, paths)` pins bare-name rules to absolute host paths with basename checks (`exec_policy/parser.rs:364-387`), and absolute-path commands resolve through basename rules only when `MatchOptions.resolve_host_executables` is set (`exec_policy.rs:251-286`). The `requirements.toml` form expresses the same prefix rules with `{token, any_of}` entries (`requirements.rs:20-30`) and is merged as an overlay at load (`engine/mod.rs:726-748`). Enforcement routing: startup loads both sources into the shared engine (`http/builders/engines.rs:83-88`), and the only in-tree caller of the check outside tests is the `execpolicy check` CLI (`commands/execpolicy.rs:62`), which serializes `ExecPolicyCheckOutput` (`exec_policy.rs:125-142`) as JSON.
## Enforcement hooks
Two `TurnInterceptor`-adjacent gates run around agent work. Before/after validation commands execute, `post_validator.rs:243-258` rejects configured `pre_commit`/`pre_push` strings containing shell operators via `validate_command_safety` (`command_safety.rs:14-16` → `shell_safety.rs:14-81`, strict mode with `allow_redirections = false`; setup commands elsewhere use lenient mode per `shell_safety.rs:9-13`). After each tool use, `HookEnforcer::post_tool_use` (`hook_enforcer.rs:106-195`) snapshots guards under a read lock, scans `affected_files`, logs a `hook_enforcement` event with a `Pass`/`Warn` decision, records the outcome in the circuit breaker, and returns violations as next-turn feedback text. `Decision::Warn` (not block) is used even when violations exist (`hook_enforcer.rs:156-160`), and scan failures also pass clean (`hook_enforcer.rs:141-154`). Tool scoping complements this: `CapabilityProfile` maps to explicit allowlists (`config/agents/permissions.rs:3-36`, `tool_isolation.rs:76-96`), enforced primarily at the CLI boundary with `validate_tool_usage` as a secondary output scan (`tool_isolation.rs:1-16`), while `CapabilityToken` binds parallel subtasks to canonicalized write paths with TTL expiry (`capability.rs:14-50`).
## Sandbox tiers
The four README modes (`README.md:98-100`) map to the `SandboxMode` enum (`config/agents/permissions.rs:94-100`, default `DangerFullAccess`). `wrap_command` (`sandbox/src/lib.rs:79-127`) selects the engine (`SandboxEngine::{None, Seatbelt, Landlock, Bubblewrap}`, `sandbox/src/lib.rs:30-36`): macOS generates a Seatbelt profile — deny-default with `file-read*`, scoped `file-write*` to the workspace or token paths, explicit deny for `.git`/`.harness` (`PROTECTED_RELATIVE_PATHS`, `sandbox/src/lib.rs:28`), plus mode-derived network rules (`network_policy.rs:40-58`) — and execs via `sandbox-exec` (`sandbox/src/lib.rs:129-148`). Linux builds `harness-landlock --mode <mode> --network <allow|deny> --workspace <paths> --readonly-path <protected>` (`linux.rs:7-53`) or `bwrap` with `--ro-bind / /`, `--tmpfs /tmp`, optional `--unshare-net`, `--bind` for writable roots, `--ro-bind` for protected paths, and `--chdir` to the project (`linux.rs:55-123`). `workspace-write` grants the project root (or all `allowed_write_paths` from a capability token); `read-only` mounts nothing writable and cuts network; `read-only-with-network` restores network; `danger-full-access` skips wrapping except for the deny-network special case. Resource limits (CPU, memory, PIDs, output, wall time via `ulimit`/`timeout` wrappers, `resource_limits.rs:305-348`) and capability-gated eval limits (`resource_limits.rs:8`) sit alongside but outside the filesystem/network sandbox. `harness.toml.example:1-16` contains no sandbox or policy keys (only `vibeguard`/`refine` review settings), so operator-facing defaults for these tiers live in code and docs (`usage-guide.md:430`, `README.md:59-67` on the Linux Landlock/bwrap requirement and the macOS Claude Seatbelt exception), not in the example config.
