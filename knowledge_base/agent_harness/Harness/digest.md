# Harness — Digest
This digest lists the eight wiki pages in order, from control-plane architecture to Fleet lessons.
## 1. [[wiki/01-overview-architecture|Harness Workspace and Control-Plane Architecture]]
**In one sentence:** Harness is a Rust workspace (13 crates) whose central design bet is a persistent central control plane — an Axum HTTP server backed by Postgres — that schedules, isolates, and reconciles work executed by pluggable agent executors (Claude Code, Codex) running outside the request path.
- The workspace declares 13 members in `Cargo.toml:3-17` and pins them all to version `0.6.34` via `Cargo.toml:19-20` and `Cargo.toml:31-42`.
- `harness-core` holds the domain model, configuration, prompts, and agent traits (`crates/harness-core/Cargo.toml:7`); `harness-protocol` defines the JSON-RPC 2.0 method/message types (`crates/harness-protocol/Cargo.toml:5`); `harness-workflow` implements the workflow runtime state machine (`crates/harness-workflow/Cargo.toml:5`).
- `harness-server` contains the HTTP server, task runner, and workflow runtime glue (`crates/harness-server/Cargo.toml:5`); `harness-agents` adapts external agent CLIs, Claude Code and Codex (`crates/harness-agents/Cargo.toml:5`); `harness-exec` provides process-execution helpers (`crates/harness-exec/Cargo.toml:5`).
- `harness-sandbox` provides isolation primitives (`crates/harness-sandbox/Cargo.toml:5`); `harness-gc` handles garbage collection and workspace cleanup (`crates/harness-gc/Cargo.toml:5`); `harness-rules` loads and evaluates policy rules (`crates/harness-rules/Cargo.toml:5`); `harness-skills` handles skill discovery and management (`crates/harness-skills/Cargo.toml:5`).
- `harness-context` composes deterministic agent context (`crates/harness-context/Cargo.toml:5`); `harness-observe` provides logging, tracing, and metrics (`crates/harness-observe/Cargo.toml:5`); `harness-cli` is the operator command-line interface (`crates/harness-cli/Cargo.toml:5`).
- All durable state lives in Postgres (image `postgres:16`, `docker-compose.yml:4`) accessed through `sqlx` with the `postgres` feature (`Cargo.toml:61`); pool construction uses `PgPoolOptions` with per-store `max_connections` and `acquire_timeout` (`crates/harness-core/src/db_pg.rs:497-501`), defaulting to 8 connections and 10 s acquire timeout (`crates/harness-core/src/db_pg.rs:13-14`).
- The operator-facing control plane is the Axum (`Cargo.toml:48`) REST surface built in `crates/harness-server/src/http/http_router.rs:29-30` and served by binding a `TcpListener` in `crates/harness-server/src/http/mod.rs:97-98`, defaulting to `127.0.0.1:9800` (`config/default.toml.example:16`, `crates/harness-core/src/config/server.rs:259`); the agent-facing data plane is the JSON-RPC router in `crates/harness-server/src/router/mod.rs:1-8`, which explicitly excludes task submission and project registration.
- Local boot is `start-server.sh` (builds `./target/release/harness` via `cargo build --release -p harness-cli` per `start-server.sh:327`, starts Postgres with `docker compose up -d --wait postgres` per `start-server.sh:356`, then execs `harness serve --transport http` per `start-server.sh:376`).
## 2. [[wiki/02-task-turn-lifecycle|Task, Thread, and Turn Lifecycle]]
**In one sentence:** Harness models agent work as a `Thread` of `Turn`s (single agent-loop iterations) driven by leased `RuntimeJob`s claimed by `RuntimeWorker`s, with a periodic GitHub-state reconciler and startup workspace/lease reconciliation recovering crashed workers.
- A `Thread` (project-scoped container with `turns`, status `idle`/`active`/`archived`) advances through `Turn`s (one agent-loop iteration each: `running` → `completed`/`cancelled`/`failed`, carrying `items`, token usage, and timing), defined in `crates/harness-core/src/types.rs:81-90,150-169`.
- The durable unit of execution is a `WorkflowInstance` plus its `RuntimeJob` rows (`pending`/`running`/terminal), not the in-memory `Thread`; a worker turn is one claimed job executed once via `RuntimeWorker::run_once` (`crates/harness-workflow/src/runtime/worker.rs:80-95`, `crates/harness-workflow/src/runtime/model.rs:521-543`).
- Claiming is lease-based: `RuntimeJob::claim` sets `status=running`, bumps `lease_generation`, and stamps `owner` + `expires_at` (`crates/harness-workflow/src/runtime/model.rs:590-602`); the claim SQL accepts `pending` jobs or `running` jobs whose `data.lease.expires_at` has passed, so a dead worker's job becomes reclaimable on expiry (`crates/harness-workflow/src/runtime/job_claim.rs:90-100,168-200`).
- Lease health is tri-state (`active_leased` / `expired_lease` / `missing_lease`) computed from `job.status` and `lease.expires_at` (`crates/harness-workflow/src/runtime/lease_state.rs:6-36`); the worker renews mid-execution at half-TTL intervals and, on losing the lease, cancels the agent and dead-letters the result instead of committing it (`crates/harness-workflow/src/runtime/worker.rs:245-310,168-207`).
- The periodic reconciler (timer loop with 15 s init delay, then every `interval_secs`) does not drive turns: it only closes the gap with external GitHub truth for non-terminal `github_issue_pr` workflows (`done` on merged, `cancelled` on closed) and raises `ready_to_merge` aging alerts (`crates/harness-server/src/reconciliation.rs:174-252`, `crates/harness-server/src/reconciliation_periodic.rs:6-43`).
- Startup recovery is workspace- and host-centric: `reconcile_startup` releases foreign orphaned leases, preserves directories with live persisted leases, and deletes terminal/orphan workspaces (`crates/harness-server/src/workspace_reconcile.rs:57-121`); host/pool topology is restored from the `runtime_state` snapshot keyed by `store_key`, rejecting schema mismatches (`crates/harness-server/src/runtime_state_store.rs:194-246`); host liveness itself is heartbeat-derived (`now - last_heartbeat_at <= heartbeat_timeout_secs`, default 60 s) in `crates/harness-server/src/runtime_hosts.rs:8-10,223-234`.
- Terminal states are definition-scoped: `WorkflowTerminalState` is only `succeeded`/`failed`/`cancelled` (`crates/harness-workflow/src/runtime/state_registry.rs:37-41`), mapped per definition (e.g. `github_issue_pr/done` → `Succeeded`); `WorkflowCommandStatus` further distinguishes `completed`/`failed`/`blocked`/`cancelled`/`skipped`/`superseded`/`handled_inline` (`crates/harness-workflow/src/runtime/status.rs:4-52`), and `is_terminal` consults the definition registry (`crates/harness-workflow/src/runtime/model_workflow_instance.rs:31-37`).
- GC (garbage-collector agent, not git-gc) signals are derived aggregates over the `Event` log — `RepeatedWarn`, `ChronicBlock`, `HotFiles`, `SlowSessions`, `WarnEscalation`, `LinterViolations` — plus mapped external GitHub payloads (CI failure → `ChronicBlock`, `changes_requested` → `RepeatedWarn`), feeding Guard/Rule/Hook/Skill remediation (`crates/harness-gc/src/signal_detector.rs:20-47`, `crates/harness-core/src/types.rs:321-349`).
## 3. [[wiki/03-policy-engine|Starlark Policy Engine and Sandboxing]]
**In one sentence:** Harness constrains agents through a Starlark-based exec policy (allow/prompt/forbidden prefix rules over command tokens) evaluated by `RuleEngine::check_command_policy`, plus shell-operator safety checks, post-tool-use guard scans with a circuit breaker, tool allowlists with capability tokens, and OS-level sandboxing (Seatbelt on macOS, Landlock/bwrap on Linux) with an orthogonal network policy.
- The executable-command policy lives in `crates/harness-rules`: `exec_policy.rs:9-15` defines the three-valued `ExecDecision` (Allow, Prompt, Forbidden), `exec_policy.rs:40-60` defines prefix matching over tokenized commands, and `exec_policy.rs:209-216` evaluates a command to the maximum (most severe) matched decision.
- Starlark files declare policy with two builtins only — `prefix_rule` and `host_executable` (`exec_policy/parser.rs:307-388`); the dialect disables `def`, `lambda`, `load`, and top-level statements (`exec_policy/parser.rs:51-58`), caps source size at 512 KiB (`exec_policy/parser.rs:42`) and call-stack depth at 512 (`exec_policy/parser.rs:22`).
- A second policy source, `requirements.toml`, converts to the same `ExecPolicy` type but may only express `prompt`/`forbidden`: an `allow` decision is rejected (`requirements.rs:77-82`), and merging across `.star` files plus requirements is additive via `merge_overlay` (`exec_policy.rs:155-182`).
- Command evaluation is exposed through `RuleEngine::check_command_policy` (`engine/mod.rs:763-769`), loaded at server startup from `rules.exec_policy_paths` and `rules.requirements_path` (`http/builders/engines.rs:83-88`), and queryable offline via `harness execpolicy check` (`commands/execpolicy.rs:62`); no per-tool-call gate on this path was found — it is a load-and-query policy store, not an inline dispatch interceptor.
- Post-execution enforcement is split: `hook_enforcer.rs:106-195` scans `event.affected_files` with registered guard scripts after each tool use and returns violation feedback, while `command_safety.rs:14-16` (delegating to `shell_safety.rs:14`) rejects unquoted shell operators (`|`, `&&`, `;`, backticks, `$(`, newlines) in hook/validator commands, and `tool_isolation.rs:17` post-scans agent output for disallowed tool tags as defense in depth.
- The hook enforcer fails open by design: it passes when disabled, when `CI` is set, when no guards exist, or when no affected files are reported (`hook_enforcer.rs:107-128`); host-side git inspection is deliberately disabled so `detect_modified_files` returns empty until agent telemetry supplies file lists (`hook_enforcer.rs:70-76`).
- A per-session circuit breaker bounds enforcement loops: 3 consecutive blocks open the circuit and auto-pass for 300 seconds (`hook_circuit_breaker.rs:6-8`, `hook_circuit_breaker.rs:65-106`), explicitly modeled on Claude Code's `stop_hook_active` (`hook_enforcer.rs:22-31`).
- Filesystem sandboxing has four modes — `read-only`, `read-only-with-network`, `workspace-write`, `danger-full-access` (README `README.md:98-100`, enum `config/agents/permissions.rs:94-100`) — enforced at spawn by wrapping the agent command (`spawn_contract.rs:227-234` via `sandbox/src/lib.rs:79-96`): macOS uses `sandbox-exec`/Seatbelt profiles (`sandbox/src/lib.rs:212-273`), Linux prefers `harness-landlock` then falls back to `bwrap` (`sandbox/src/lib.rs:190-203`), and `danger-full-access` is a passthrough (`SandboxEngine::None`) unless token paths or a network policy narrow it (`sandbox/src/lib.rs:87-108`).
- Network policy is orthogonal to the filesystem mode (`sandbox/src/network_policy.rs:6-14`): `Deny` adds `--unshare-net` (bwrap, `linux.rs:78-86`) or `--network deny` (landlock, `linux.rs:15-23`) and emits no Seatbelt outbound allowance, while `danger-full-access` plus deny-all networking still gets a network-only bwrap wrapper (`sandbox/src/lib.rs:176-188`); scoped-permission hosts with an empty allowlist resolve to `DenyAll` (`isolation_health.rs:80-90`) and startup health probing reports host/container/microvm tier availability (`isolation_health.rs:67-78`).
## 4. [[wiki/04-agent-adapters|Multi-Agent Adapters and Registry]]
**In one sentence:** Harness puts the Claude Code CLI (`claude.rs`), Codex CLI (`codex.rs`), OpenCode CLI (`opencode.rs`), and the direct Anthropic HTTP API (`anthropic_api.rs`) behind the single `AgentBackend` (alias `CodeAgent`/`AgentAdapter`) trait, with `registry.rs`/`builder.rs` resolving a name such as `claude|codex|opencode|anthropic-api` to a backend and `spawn_contract.rs`+`spawn_supervisor.rs` executing every CLI backend as a supervised, sandboxed child process whose JSONL output is parsed by per-agent streaming parsers.
- The common interface is `AgentBackend: Send + Sync` (`crates/harness-core/src/agent.rs:84`), aliased as `CodeAgent` (`crates/harness-core/src/agent.rs:180`) and `AgentAdapter` (`crates/harness-core/src/agent.rs:173`); one-shot CLI backends implement `execute`/`execute_stream`, stateful protocol backends (`codex_adapter.rs`, `opencode_adapter.rs`) override `start_turn`/`interrupt`/`steer`/`respond_approval`, and all unimplemented control operations default to `Unsupported` (`crates/harness-core/src/agent.rs:109-165`).
- `AgentRegistry` (`crates/harness-agents/src/registry.rs:19`) stores `AgentDescriptor { backend, control_backend, turn_backend_factory }` per name (`crates/harness-agents/src/registry.rs:13-17`); lookup is `get(name)` (`crates/harness-agents/src/registry.rs:109`), control side-channel is `get_adapter(name)` (`crates/harness-agents/src/registry.rs:114`), fresh stateful turn backends come from `turn_execution_adapter(name)` (`crates/harness-agents/src/registry.rs:121`), and complexity-based routing is `dispatch(task)` (`crates/harness-agents/src/registry.rs:148-163`).
- `registry_from_config` (`crates/harness-agents/src/builder.rs:135`) is the single assembly point: it registers `claude` (`crates/harness-agents/src/builder.rs:142`), `codex` plus a `CodexAdapter` turn factory (`crates/harness-agents/src/builder.rs:151-163`), `opencode` plus an `OpenCodeAcpAdapter` turn factory (`crates/harness-agents/src/builder.rs:165-180`), and `anthropic-api` only when `ANTHROPIC_API_KEY` is present (`crates/harness-agents/src/builder.rs:182-190`); the configured `default_agent` string (the `--agent` selection) resolves via `resolved_default_agent_name`/`default_agent` (`crates/harness-agents/src/registry.rs:129-146`).
- Per-adapter executors are `ClaudeCodeAgent` (`crates/harness-agents/src/claude.rs:28`), `CodexAgent` (`crates/harness-agents/src/codex.rs:52`), `AnthropicApiAgent` (`crates/harness-agents/src/anthropic_api.rs:9`), and `OpenCodeAgent` plus `parse_opencode_run_line` (`crates/harness-agents/src/opencode.rs:48`); Claude carries a provider-backpressure gate, stream timeout, reasoning budget, and optional API key (`crates/harness-agents/src/claude.rs:28-40`), Codex carries CLI path, model, reasoning effort, cloud config, and stream timeout (`crates/harness-agents/src/codex.rs:52-61`).
- The spawn contract (`crates/harness-agents/src/spawn_contract.rs:200`) has two implementations, `HostSpawn` (`crates/harness-agents/src/spawn_contract.rs:208`) and `ContainerSpawn` (`crates/harness-agents/src/spawn_contract.rs:257`), selected by isolation tier in `prepare_agent_spawn` (`crates/harness-agents/src/spawn_contract.rs:436`); egress policy derives from `AgentEgressMode::resolve(permission_mode, allowlist)` (`crates/harness-agents/src/spawn_contract.rs:217`), and container spawns become `docker run --rm` with bind mounts, `--env` propagation, and proxy/canary wiring (`crates/harness-agents/src/spawn_contract.rs:294-432`).
- `spawn_agent` (`crates/harness-agents/src/spawn_supervisor.rs:45`) builds the `tokio::process::Command`, applies `apply_process_env`, validates the capability token, retries once on `ETXTBSY` (`crates/harness-agents/src/spawn_supervisor.rs:140-155`), writes a provisional run binding, and wraps the child in `ManagedChild` (`crates/harness-agents/src/lib.rs:137`), which owns process-group kill, bounded tail capture with idle-timeout zombie detection (`crates/harness-agents/src/lib.rs:242-345`), and synchronous drop-time reaping; stale Docker resources are reconciled at startup (`crates/harness-agents/src/docker_reconciliation.rs:8`).
- Streaming output is parsed per agent: Claude `--output-format stream-json` lines become `AgentEvent`s via `parse_stream_json_events` (`crates/harness-agents/src/claude_stream_json.rs:25`), Codex `exec --json` output becomes `ParsedCodexExecEvent` items via `parse_codex_item`/`parse_codex_exec_output` (`crates/harness-agents/src/codex_exec_parser.rs:77`), OpenCode `run --format json` lines become `OpenCodeRunEvent::{Text, ToolUse, StepFinish}` (`crates/harness-agents/src/opencode.rs:25-96`), stderr is classified into warn/debug with agent-internal prefix suppression (`crates/harness-agents/src/streaming.rs:240-328`), and non-streaming output is bounded tail capture with cross-chunk secret redaction (`crates/harness-agents/src/output_capture.rs:41-113`).
- Permission and prompt shaping sit above spawn: Claude maps `allowed_tools`/capability profile to `--allowedTools` scoping (`crates/harness-agents/src/claude.rs:199`), Codex maps `allowed_tools == Some([])` to deny-all and forwards `approval_policy` via `-c approval_policy=...` (`crates/harness-agents/src/codex.rs:160-196`), OpenCode merges restrictions through the inlined `OPENCODE_PERMISSION` JSON env (`crates/harness-agents/src/opencode.rs:18`), nested Claude session markers are stripped (`crates/harness-agents/src/spawn_contract.rs:45-51`), and cross-cutting guards include the provider backpressure semaphore gate (`crates/harness-agents/src/provider_backpressure.rs:50-60`), scoped GitHub tokens (`crates/harness-agents/src/scoped_token.rs:7-9`), and the Anthropic-backed compression model reusing `AnthropicApiAgent` (`crates/harness-agents/src/compress_model.rs:23-55`).
## 5. [[wiki/05-workflow-runtime|Workflow Runtime and Worktree Isolation]]
**In one sentence:** GitHub issues enter via a submissions API that builds planning or implementation decisions, which the dispatcher gates on budget, isolation, and profile policy before claiming, enqueueing, and executing them as leased runtime jobs in per-task git worktrees subject to validator and quality-gate checks.
- Submissions API (`runtime/submission.rs:62`) maps an issue to one of three actions — `RunPlanning`, `RunImplementation`, `WaitForDependencies` (`runtime/submission.rs:34-39`) — emitting an `EnqueueActivity` command for `implement_issue` or the plan activity plus a `task_submission` evidence record.
- `ExecPlan` (`harness-exec/src/plan.rs:6-19`) is the plan data model: `purpose`, `project_root`, `progress` milestones, `concrete_steps`, `decision_log`, `surprises`, `validation` criteria, and `status`, constructed by `from_spec` (`harness-exec/src/plan.rs:56-78`) and mutated by `activate`, `add_milestone`, `add_step`, `log_decision`, `complete`, `abandon`.
- Dispatch is claim-then-gate-then-enqueue in `RuntimeCommandDispatcher::dispatch_command` (`runtime/dispatcher.rs:178-346`): skip non-runtime commands, drop terminal workflows, resolve effective profile, enforce agent-contract and isolation availability, apply the budget gate, then `enqueue_runtime_job_for_claimed_command` with `AlreadyDispatched` dedupe on `dedupe_key`.
- Profile selection (`runtime/dispatcher_profile_selector.rs:56-68`) resolves workflow-activity > activity > workflow > default; `effective_profile_for_command` (`runtime/dispatcher.rs:139-147`) layers eval policy and candidate-budget rewrites on top before the same profile is rechecked at enqueue.
- Throttling and budgets live in `budget_gate_outcome` (`runtime/dispatcher.rs:370-462`) with `daily_throttle_breach` (`runtime/dispatcher_throttle.rs:38-85`): workflow-budget exhaustion, per-profile daily caps, and a throttle band that yields to an under-threshold alternative profile (via `peek_claimable_commands`) rather than starving a lone busy profile; shadow mode records `BudgetShadowDecision` and dispatches, enforce mode defers with a barrier.
- Concurrency is bounded at two layers: `TaskQueue` holds a global `PriorityPermitQueue` plus per-project queues requiring both permits (`harness-server/src/task_queue/mod.rs:222-248`), and `WorkspacePool::acquire_with_capacity` (`harness-server/src/workspace_pool.rs:91-114`) issues per-project semaphore permits keyed by `project_limit_key` (`harness-server/src/workspace_pool.rs:141-154`) with default capacity 4 (`harness-server/src/workspace_pool.rs:8`).
- Each task executes in an isolated git worktree: `WorkspaceManager` creates `config.root/<sanitized_task_id>` from `remote/base_branch` on branch `harness/<task_id>` (`harness-server/src/workspace_create.rs:8-13`), verified by `is_registered_worktree` and removed by `remove_worktree` (`harness-server/src/workspace_helpers.rs:201,478`), with orphan reclamation (`harness-server/src/workspace_reconcile.rs:504-542`) and `WORKFLOW.md:14-18` declaring `strategy: worktree`, `branch_prefix: harness/`, `cleanup: on_terminal`.
- Validators and quality gates close the loop: `TransitionRule` (`runtime/validator.rs:31-40`) constrains allowed and required commands and evidence per state transition, `build_quality_gate_run_decision` (`runtime/quality_gate.rs:36-73`) enqueues `run_quality_gate` with explicit `validation_commands`, and `WORKFLOW.md:75-89` binds `implement_issue` to `cargo fmt --check`, `cargo check`, `cargo test`, and `clippy -D warnings`.
## 6. [[wiki/06-review-and-gc|Cross-Agent Review and Garbage Collection]]
**In one sentence:** Harness checks agent output through a primary-plus-challenger review protocol and independent quality gates, and reclaims degraded work through a signal-driven garbage-collection loop that drafts, stores, and optionally adopts rule, guard, or skill fixes.
- Cross-agent review means a primary agent produces a review and a distinct challenger agent confirms, contests, or extends each issue over bounded rounds, with `Approved` returned only when no consensus issues remain (crates/harness-server/src/handlers/cross_review.rs:138-145, 265-339).
- Self-review is prevented by identity comparisons on agent identity, not on GitHub author login: `distinct_challenger` drops a challenger whose `candidate.id() != primary.id()` fails, `quality_trigger` skips when `primary.name() == challenger.name()`, and the periodic reviewer picks a secondary agent with `agent != primary_agent` (crates/harness-server/src/handlers/cross_review.rs:419-424; crates/harness-server/src/quality_trigger.rs:198-207; crates/harness-server/src/periodic_reviewer/tick_helpers.rs:60-72).
- The periodic reviewer runs on an interval loop with per-project watermarks, guard scans, primary enqueue, optional secondary review under `ReviewStrategy::Cross`, and watermark advance only after parseable output (crates/harness-server/src/periodic_reviewer/mod.rs:195-210; crates/harness-server/src/periodic_reviewer/tick.rs:107-142).
- Structured review reports (`ReviewReport`, `ReviewGateResult`) are parsed from fenced `harness-review-report` JSON, legacy `ISSUE:` lines, or terminal `APPROVED`, and required providers must all approve or the gate returns `ChangesRequested` or `Blocked` (crates/harness-core/src/review.rs:106-170, 172-257).
- Post-task quality grading over a 1-hour event window can trigger garbage collection (GC): grades below threshold plus cooldown expiry start a bounded `gc_agent.run` with timeout and scan-watermark handling (crates/harness-server/src/quality_trigger.rs:16-21, 317-376).
- Per-turn and per-PR gates include `PostExecutionValidator` (pre-commit/pre-push shell commands plus PR-existence verification), the `local_review_gate` workflow state, a revision-bound quality-gate workflow, PR-feedback repair with a 3-round convergence stop, and hygiene repair for `DIRTY`/`BEHIND` merge states (crates/harness-server/src/post_validator.rs:233-344; crates/harness-workflow/src/runtime/pr_feedback.rs:86-116; crates/harness-server/src/github_pr_hygiene.rs:246-251).
- GC signals mark work as garbage: `RepeatedWarn`, `ChronicBlock`, `HotFiles`, `SlowSessions`, `WarnEscalation`, `LinterViolations`, derived from event thresholds, persisted `rule_check` violations, and external GitHub payloads (CI failure to `ChronicBlock`, review `changes_requested` to `RepeatedWarn`) (crates/harness-gc/src/signal_detector.rs:20-29, 35-96; crates/harness-core/src/types.rs:323-349).
- A GC draft is a persisted `Draft { id, status, signal, artifacts, rationale, validation, generated_at, agent_model }` with `Pending/Adopted/Rejected/Expired` states; drafts are saved immediately per signal, expire by time-to-live (TTL, i.e. maximum pending lifetime), and reach disk only through `adopt_if_pending` path validation or `RulesOnly` auto-adoption, or through `reject` guarded by `save_if_status` (crates/harness-core/src/types.rs:543-578; crates/harness-gc/src/draft_store.rs:37-82, 125-138; crates/harness-gc/src/gc_agent.rs:182-258, 269-373).
## 7. [[wiki/07-observability-persistence|Observability, Persistence, Skills, and Context]]
**In one sentence:** Harness records every tool decision as a Postgres event row plus optional OTLP traces/metrics/logs, attributes token and cost usage per agent turn, and reassembles skills, rules, and memory into a budgeted prompt at compose time.
- OTLP export covers three signals from one pipeline: traces (per-event spans plus workflow/activity/agent-turn trajectory spans), metrics (four counters/histograms), and logs (one record per event), configured by `OtelConfig` and defaulting to disabled (`crates/harness-core/src/config/misc.rs:404-439`, `crates/harness-observe/src/otel_export.rs:98-117`).
- Endpoint resolution order is explicit config endpoint, then `OTEL_EXPORTER_OTLP_ENDPOINT` environment variable, then `http://127.0.0.1:4318` (HTTP) or `http://127.0.0.1:4317` (gRPC), followed by a TCP reachability probe that fails startup of the pipeline when unreachable (`crates/harness-observe/src/otel_export.rs:380-432`).
- The event store is a Postgres table (`events`) with eight versioned migrations, keyed by `(store_key, id)`, with batched inserts using `ON CONFLICT DO NOTHING`, JSONL backfill on first startup, and batched retention purges (`crates/harness-observe/src/event_store/migrations.rs:5-102`, `crates/harness-observe/src/event_store/mod.rs:167-229`, `crates/harness-observe/src/event_store/events.rs:51-80`).
- Usage and cost accounting centers on `UsageMetrics` (input, output, cache-read, cache-creation, reported-total) where the reported provider total takes precedence over the recomputed sum, and per-turn cost is attached to agent-turn spans from `turn.token_usage` (`crates/harness-observe/src/usage.rs:5-93`, `crates/harness-server/src/workflow_runtime_worker/otel_trajectory.rs:68-84`).
- Postgres schema management uses one schema per logical store via `PgStoreContext`, a `schema_migrations` ledger with a per-schema advisory lock, and a `harness_admin.schema_ownership` registry with keep/drop classification for orphaned path-derived schemas (`crates/harness-core/src/db_pg.rs:331-464`, `crates/harness-core/src/db_pg.rs:653-722`, `crates/harness-core/src/db_pg_schema_registry.rs:231-255`).
- Skill dedup is mechanical name-collision resolution by tier priority (Repo 4 > User 3 > Admin 2 > System 1) executed at the end of `discover()`, so a user-persisted skill shadows a same-named builtin (`crates/harness-skills/src/store.rs:204-212`, `crates/harness-skills/src/store.rs:383-410`, `crates/harness-skills/src/store.rs:781-788`).
- Memory and context retrieval is lexical: `LexicalKnowledgeRetriever` scores prompt-to-field token overlap with weights and a phrase bonus, and `ContextComposer` enforces token budgets, per-class quotas, `dedupe_key` elimination, and degradation levels before rendering (`crates/harness-core/src/retrieval.rs:287-348`, `crates/harness-context/src/composer.rs:415-456`, `crates/harness-context/src/types.rs:230-281`).
## 8. [[wiki/targeted|Targeted: What Fleet Can Learn from Harness]]
**In one sentence:** Harness's borrowable core is lease-based worker recovery, two-stage permit scheduling, declarative submissions over a plan store, and policy-as-data enforcement — all backed by Postgres rather than in-memory state.
- Policy is data, not code: three-valued `ExecDecision` (`crates/harness-rules/src/exec_policy.rs:9-15`) over tokenized command patterns (`crates/harness-rules/src/exec_policy.rs:17-30`), loaded at startup and queried offline.
- Restart recovery is lease-expiry-driven, not startup-replay: expired `running` jobs become reclaimable (`crates/harness-workflow/src/runtime/job_claim.rs:90-100`), claims bump `lease_generation` (`crates/harness-workflow/src/runtime/model.rs:590-602`), and workers renew mid-execution (`crates/harness-workflow/src/runtime/worker.rs:245-274`).
- Concurrency is a two-stage permit queue (project slot, then global slot) with RAII release on drop (`crates/harness-server/src/task_queue/mod.rs:40-44`, `crates/harness-server/src/task_queue/mod.rs:70-82`) and aging anti-starvation (`crates/harness-server/src/task_queue/permits.rs:1-4`).
- Work intake is a submissions API (`crates/harness-server/src/http/http_router.rs:88-92`) over `WorkflowInstance` + `RuntimeJob` rows, with a separate `ExecPlan` plan object (`crates/harness-exec/src/plan.rs:7-19`) created from a spec (`crates/harness-exec/src/plan.rs:55-78`).
- Parallel-agent conflicts are reduced by prompt-level sibling constraints (`crates/harness-core/src/prompts/context.rs:23-40`), per-task git worktrees with classified add-failures (`crates/harness-server/src/workspace_worktree_add.rs:7-30`), and dual-reviewer synthesis (`crates/harness-core/src/prompts/review.rs:351-379`).
- Multi-agent support is a trait plus registry: `AgentBackend` (`crates/harness-core/src/agent.rs:84-92`) resolved by `AgentRegistry` (`crates/harness-agents/src/registry.rs:13-17`) assembled in one function (`crates/harness-agents/src/builder.rs:135-190`).
- The highest-value borrows for Fleet are the Starlark-style exec policy, lease/generation recovery, GC draft staging (`crates/harness-gc/src/draft_store.rs:37-59`), OTLP trajectory export (`crates/harness-observe/src/otel_export.rs:306-311`), and context dedup keys (`crates/harness-context/src/composer.rs:415-453`).
## The system in five moves
1. An issue enters through the submissions API as a planning or implementation decision backed by a WorkflowInstance, RuntimeJob rows, and a separate ExecPlan.
2. Policy-as-data constrains execution through exec-policy prefix rules, guard scans with a circuit breaker, and sandboxed spawn with orthogonal network policy.
3. The dispatcher gates claimed commands on profile, budget, and isolation before leased jobs execute once in per-task worktrees under two-stage permit concurrency.
4. Registry-resolved agent backends run as supervised child processes whose streaming output is parsed per agent, with lease renewal and reclaim on expiry.
5. Primary-plus-challenger review with no-self-review, quality gates, and PR-feedback repair decide whether output advances.
6. GC signals stage rule, guard, or skill fixes as pending drafts while Postgres events, OTLP trajectories, and the GitHub reconciler close the observe-and-merge loop.
