# Automation, Security, and Architecture
**In one sentence:** Hermes combines built-in cron scheduling, subagent delegation with programmatic code execution, checkpoint rollback, layered security, and a modular agent-gateway architecture that also supports batch research and RL (Reinforcement Learning) training.
## Key points
- Built-in cron runs one-shot or recurring agent tasks via a single `cronjob` tool with natural-language or cron-expression schedules and full pause, resume, edit, trigger, and remove lifecycle.
- Cron jobs run in fresh isolated agent sessions on a 60-second gateway tick, support skill attachment, project workdir, model pinning, preflight validation, and delivery to origin chat, local files, or any connected platform.
- `delegate_task` spawns child subagents with fresh context and inherited toolsets for single or parallel work, while `execute_code` handles mechanical multi-step pipelines with lower token cost.
- Checkpoints and rollback use shadow git repos plus snapshots so destructive or exploratory work can be reviewed and reverted.
- Security is defense-in-depth across eight layers including command approval, user authorization, file-write guards, container isolation, credential filtering, and injection scanning.
- A hardline blocklist of catastrophic commands can never be overridden, even in YOLO (You Only Look Once, auto-approve-all) mode or headless cron approval modes.
- One platform-agnostic `AIAgent` core serves CLI, gateway, ACP (Agent Client Protocol, IDE integration), batch, and API entry points with shared prompt building, provider resolution, and tool dispatch.
- Batch processing, trajectory export, and Atropos integration make agent runs reusable as research data and RL training material.
---
## Cron automations
Cron is first-class agent scheduling, not shell scheduling. Jobs are stored in `jobs.json`, ticked every 60 seconds by the gateway daemon, and each due job starts a fresh `AIAgent` session with the normal static tool list. Management is available in chat, via CLI, or through conversation: the agent itself uses the unified `cronjob` tool.
Schedules accept natural language such as `every 2h` or `every morning at 9am` as well as standard cron expressions. Jobs can be one-shot or recurring, created paused as a safe canary, edited without recreation, and referenced by ID or case-insensitive name.
Skill-backed jobs attach zero, one, or multiple skills that load in order before the prompt runs, so reusable workflows do not need to be pasted into the prompt. A `workdir` option runs the job inside a project directory, injecting `AGENTS.md`, `CLAUDE.md`, or `.cursorrules` and setting file and terminal tools to that directory.
Delivery is explicit. Targets include `origin`, `local` files under cron output, named platforms such as Telegram, Discord, Slack, WhatsApp, Signal, Matrix, email, and SMS, specific chats or topics, `bot-chat` for delivery into another bot session as actionable input, and `all` for fan-out to every connected home channel. Execution and delivery failures are tracked separately, with `delivery_failed`, failure streaks, per-signature incidents, execution ledgers, and a read-only `cron doctor` health check.
Reliability guards include pre-dispatch validation that blocks misconfigured jobs before any LLM (Large Language Model) call, per-job model and reasoning-effort pins, provider fallback and credential rotation, model-drift protection for unpinned jobs, response wrapping, push-notification control, `[SILENT]` suppression for healthy monitoring ticks, and continuable deliveries that can be replied to in-thread.
Two special modes extend the pattern. No-agent mode runs a script on schedule with stdout delivered verbatim and no LLM involvement, which suits watchdogs, disk or memory alerts, heartbeats, and CI (Continuous Integration) pings. Chaining via `context_from` prepends upstream job output into downstream prompts, while `continuity` injects a job's own previous output so recurring scouts can dedupe. By default scheduled agents cannot create more cron jobs; agent-managed scheduling is opt-in.
## Delegation patterns and code execution
`delegate_task` spawns child `AIAgent` instances with isolated context, inherited tool access, and separate terminal sessions. Each child starts with a fresh conversation containing only the parent-supplied `goal` and `context`, plus workspace project files when available. Only the final summary returns to the parent, keeping token use efficient.
Patterns include single-task delegation, parallel batches of up to 3 concurrent subagents by default with configurable limits, parallel research fan-out, code review plus fix, and large multi-file refactoring. Batch results return as one consolidated message by default, with opt-in independent completions and grouping for synthesis workflows. Nested orchestration is opt-in through `role=orchestrator` plus `max_spawn_depth`, while leaf children cannot delegate, clarify with the user, write shared memory, send cross-platform messages, or schedule cron jobs.
Operational controls include per-child iteration limits, opt-in wall-clock timeouts, progress-based stall detection for background children, durable background completions across restarts, live append-only transcripts, `/agents` monitoring, parent- or operator-driven steering and stop controls, process handoff from child to parent, optional git worktree isolation per child, optional cheaper worker models behind a frontier planner, and a `/review` command that dispatches an independent background reviewer.
`execute_code` is the complementary primitive. Where `delegate_task` provides full LLM reasoning in a fresh conversation, `execute_code` provides programmatic tool calling for mechanical data processing and scripted workflows with only stdout returned. The rule of thumb is delegation for judgment-heavy subtasks and code execution for deterministic pipelines. Related automation features in the same family include kanban multi-agent boards, persistent goals, recurring loops, session heartbeats, event hooks, voice mode, and automation blueprints.
## Checkpoints and rollback
Checkpoints give Hermes a safety net for exploratory or destructive work. Shadow git repos track file changes while snapshots capture session state, so an agent run can be inspected and rolled back after failed edits, bad refactors, or risky automation.
The intended workflow is checkpoint before risky work, review the diff or session outcome, then continue or revert. Direct hand-editing of control files such as cron job stores is discouraged; supported tools and commands should mutate scheduler and session state through their APIs.
## Security model
Hermes uses an eight-layer defense-in-depth model: user authorization, dangerous-command approval, file-write safety, container isolation, MCP (Model Context Protocol) credential filtering, context-file scanning, cross-session isolation, and input sanitization.
Approval checks shell commands against curated dangerous patterns. Modes are `smart` for LLM-assisted risk assessment, `manual` for always prompting, and `off` for trusted environments. Cron, single-query, webhook, and API sessions have separate headless approval policies that default to deny. CLI prompts offer once, session, always, or deny, while messaging platforms accept yes or no replies. YOLO mode bypasses approval for a session but never bypasses the hardline blocklist. User-defined `approvals.deny` glob patterns add custom always-block rules, and approval history can be mined into allowlist proposals without ever proposing destructive classes.
File-write safety blocks credential stores, Hermes secrets, project secret files, and other protected paths for `write_file` and `patch`, with optional `HERMES_WRITE_SAFE_ROOT` sandboxing. These are model stop signals rather than OS-level sandboxes, since the terminal tool runs as the same OS user.
User authorization for the gateway checks per-platform allow-all flags, DM (Direct Message) pairing approvals, platform allowlists, global allowlists, and global allow-all in order, defaulting to deny. DM pairing issues time-limited cryptographic codes with rate limits, lockouts, and secure storage.
Isolation backends include local, SSH (Secure Shell), Docker, Singularity, Modal, Daytona, and Vercel Sandbox. Local and SSH retain dangerous-command checks, while container and cloud sandbox backends treat the container as the boundary. Docker containers drop all Linux capabilities except narrowly added ones, block privilege escalation, and cap processes, temp space, CPU, memory, and disk use.
Environment handling strips sensitive variables from `execute_code` and `terminal` children by default, with skill-scoped passthrough for declared skill variables and manual config passthrough for task-specific keys. Credential files such as OAuth (Open Authorization) tokens can be mounted read-only into sandboxes. MCP subprocesses receive only safe system variables plus explicitly configured values, with credential redaction in errors. Additional guards include website blocklists, SSRF (Server-Side Request Forgery) protection against private-network and cloud-metadata targets, Tirith pre-execution scanning, context-file prompt-injection detection, hardened cron storage paths, and supply-chain advisory checks.
## Architecture internals
The system centers on one platform-agnostic `AIAgent` class. Entry points include CLI, messaging gateway, ACP server, batch runner, API server, and Python library. All flow through shared prompt building, provider runtime resolution, and tool dispatch, with session storage and tool backends underneath.
The agent loop handles provider selection, prompt construction, API calls in three modes covering chat completions, Codex responses, and Anthropic messages, tool execution, retries, fallback, callbacks, compression, and persistence. The tool registry holds more than 70 tools across about 28 toolsets, with terminal, browser, web, file, vision, MCP, and code-execution backends.
Gateway internals handle platform adapters, message events, user authorization, session routing, response delivery, slash commands, hooks, cron ticking, pairing, mirroring, and background maintenance across more than 25 messaging platforms. Session storage uses SQLite with FTS5 (Full-Text Search version 5) search, lineage tracking, per-platform isolation, and atomic writes.
Prompt assembly builds ordered tiers from stable identity and tool guidance through context files to volatile memory, profile, and timestamp blocks. Context compression summarizes middle turns when thresholds are exceeded, while Anthropic prompt caching preserves stable prefixes. Provider resolution maps provider-plus-model tuples to API mode, credentials, base URLs, aliases, OAuth flows, and credential pools. Design principles emphasize prompt stability, observable execution, interruptibility, platform-agnostic core logic, loose coupling through registries, and profile isolation.
## Research and batch capabilities
Batch processing generates trajectories from many agent sessions for offline analysis. Trajectory export produces ShareGPT-style training data, and Atropos integration supports RL training loops. Combined with deterministic code execution, isolated delegation, persistent execution ledgers, and live transcripts, this makes Hermes runs auditable and reusable as research material rather than throwaway chat sessions.
