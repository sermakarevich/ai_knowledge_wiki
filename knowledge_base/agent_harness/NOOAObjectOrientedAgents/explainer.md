# Native Python Object-Oriented Agents — In Plain Language

## What is this about?

Imagine hiring a new employee and, instead of giving them one clear job description, you hand them five unrelated documents: a script for how to talk to customers, a separate binder listing which tools they're allowed to touch, a flowchart for who to call when something goes wrong, and a stack of sticky notes for things to remember. That's roughly how most "AI agents" — computer programs that use a large language model (an AI like the one behind ChatGPT) to make decisions and take actions — are built today. The instructions, the list of allowed actions, the rules for handling results, and the memory are all scattered across different files and formats, and every AI framework invents its own version of these five documents.

This paper, from NVIDIA, proposes something much simpler: write the whole employee — sorry, agent — as a single, ordinary piece of Python code (Python is one of the world's most common programming languages), the same way programmers already write everyday software. Concretely: an agent is just a "class" (think of it as a fill-in-the-blank job description template). Its "fields" hold what the agent knows and remembers, like a filing cabinet. Its "methods" are the things it can do, like a numbered list of duties. Some duties are spelled out with exact step-by-step instructions, like a payroll calculation — the computer does exactly that, every time, with no room for interpretation. Other duties are deliberately left blank, marked with just three dots ("..."), meaning "use your judgment" — and at that point the AI itself steps in and decides what to do, on the fly.

The name NOOA ("NVIDIA Object-Oriented Agents") captures the trick: "object-oriented" is a decades-old, mainstream way of organizing code into these class/field/method templates. NOOA's bet is that nothing new needs to be invented — the tools programmers already use for organizing ordinary software turn out to be exactly the tools needed to organize AI-driven software too, because the AI itself was trained on enormous amounts of ordinary Python code and already understands this structure.

## Why does it matter?

The scattering problem is expensive twice over. Human developers have to learn a new bespoke mini-language every time they adopt a new agent framework — new ways to write prompts, new config files, new plumbing for tools and memory — even though ordinary programming already solved most of these problems (how to store data, how to call a function, how to check that a result is the right shape). And the AI models themselves are, in a real sense, being asked to learn a foreign dialect: they were trained mostly on ordinary code and prose, not on any particular agent framework's private conventions, so every bespoke framework adds friction the AI has to work around.

If this approach works, it changes what "building an AI agent" feels like: instead of learning a new tool ecosystem, you write a Python class, the same way you'd write any other piece of software. That means agent behavior can be tested, reviewed, version-controlled, and debugged with the exact same habits and tools software engineers already use for regular code — because it genuinely is regular code, with a few blanks left for the AI to fill in. The paper argues (and tries to measure) that this isn't a trade-off: making things simpler for humans does not make things worse for the AI — in several tests it does noticeably better.

## How does it work?

Picture a customer-support employee's job description, written as a single form:

1. **The state (fields).** At the top of the form is a list of things the employee has access to — for instance, "the order database." This is the agent's memory/context: durable facts it can read and, if allowed, update.
2. **The deterministic duties (real code).** Some line items are spelled out exactly, like "an order is refund-eligible if it was delivered and it's been 30 days or less" — plain, predictable logic with one correct answer every time. No AI judgment is needed or used here; it's a calculator, not a decision-maker.
3. **The judgment-call duties (the "..." trick).** Other line items just say, e.g., "classify this customer message" or "triage this ticket and produce a report" — followed by "..." instead of instructions. When execution reaches one of these, the surrounding machinery (the "harness," i.e., the runtime scaffolding around the AI) hands control to the language model.
4. **Showing the AI just enough, not everything.** Before asking the AI to decide, the harness builds a compact briefing: the instructions (the form's own description doubles as the prompt), a running log of what's happened in this task so far, and a snapshot of the relevant data. Crucially, for huge pieces of data — say, a list of 10,000 numbers — the AI is not shown the whole list. It's shown a small preview (type, size, and a first/last handful of entries), the way a librarian might show you a book's cover, page count, and first and last page instead of photocopying the whole book. But the actual full list still exists and is fully usable — the AI can write code that loops over every single item, it just doesn't need the whole thing pasted in front of it to do so. This is called "pass by reference": working with the real thing via a handle, instead of being handed a copy of everything, everywhere, every time.
5. **The AI acts by writing code, not filling out forms.** Rather than the AI producing a rigid checkbox-style command ("call tool X with argument Y"), NOOA lets it write a short piece of real Python — a few lines that can loop, branch, call the exact-instruction duties from step 2, or even call other judgment-call duties. This is "code as action": writing a small script is a far more expressive way to act than picking one option from a menu, especially for tasks like "do this for each of 50 items."
6. **Checking the homework.** Whatever the AI ultimately reports back must match a strict template — a "type contract," like a form that gets bounced back if you write "maybe" in a box that requires a number. If it doesn't match, the AI gets an error message and gets to try again, automatically, until it produces something valid — or it gives up after too many tries.
7. **Repeat and log.** Each of these back-and-forth exchanges — a step of writing code, running it, seeing what happened, deciding what's next — is logged into a running history, and the whole cycle repeats until the AI finally returns a valid answer. Reusing the same fixed opening briefing on every round (rather than re-explaining everything from scratch) also makes each round cheaper and faster to process.

## Where can this be used?

The paper's own tests span: fixing real bugs in open-source software (a benchmark called SWE-bench), operating a command-line computer terminal to install and configure software (Terminal-Bench), hunting for security vulnerabilities in code and proving they're real (CyberGym), and — the headline result — learning to play a brand-new video game with no instructions given up front (ARC-AGI-3), where a single NOOA agent with a short "skill" (a one-page strategy guide) replaced a much larger six-agent system and matched or beat its results.

Beyond the paper's own examples, the same idea applies anywhere someone currently glues together a chatbot with a pile of separate config files and custom tool definitions: a customer-support triage bot (the paper's own worked example), a research assistant that has to dig through gigabytes of spreadsheets or logs without choking on them, a coding assistant embedded in a company's internal tools, a personal assistant that manages your calendar and email with clear rules for routine tasks but judgment calls for ambiguous ones, or a scientific-data pipeline where some steps must be exact (unit conversions, statistics) and others require interpretation (labeling, summarizing). Any workflow that mixes "always do exactly this" steps with "use good judgment here" steps is a candidate for this style of design — the object-oriented structure doesn't care whether the domain is software, customer service, or games.

## Conclusions & takeaways

The one idea worth keeping a month from now: an AI agent can be written as an ordinary piece of code — a class with fields for memory, methods for actions, and a special "figure it out yourself" marker (the "..." body) for the parts that need judgment rather than fixed rules. Everything else in the paper — bounded previews of big data, live handles instead of copies, code as the action format, a strict "does the answer fit the template" check — follows from taking that one idea seriously.

The paper backs this up with real numbers: on standard tests, this approach matched or beat comparable AI-coding tools while using fewer computational resources (tokens, cost), and it let a giant six-part system for learning to play unfamiliar games shrink down to one small agent with better efficiency. That's a meaningful result, not just a tidy idea.

Honest limitations: current AI models mostly handle this style of working well, but the paper's own "stress tests" caught real slip-ups — for example, a top-tier model computed a perfectly correct 50-item answer with code, then carelessly retyped the results by hand from memory in a later step and got one wrong, when it could have just reused the value it already had. So the interface is not foolproof; disciplined habits still matter, and models occasionally take a needlessly risky shortcut even when a safe one is sitting right there. The paper is also explicit that running the AI's code directly alongside your own program is fast and convenient but is not, by itself, a security boundary — if you can't fully trust what the AI might do, you still need to wrap the whole thing in an outside safety layer (like a locked-down virtual sandbox), exactly as you would for any tool that can run arbitrary commands. Finally, the six underlying ideas aren't all brand new — other frameworks already have partial versions of most of them — the paper's contribution is combining all six cleanly on one surface, not inventing each piece from scratch.

## Jargon decoder

| Term | Plain meaning |
|------|---------------|
| Agent (AI agent) | A program that uses a language model to decide what actions to take, not just to answer a single question |
| Agent loop | The repeating cycle of "show the AI the current situation → let it act or answer → record what happened → repeat" until it's done |
| LLM (large language model) | The underlying AI (like the models behind ChatGPT or Claude) that reads text and generates responses or decisions |
| Docstring | A short block of description attached to a piece of code explaining what it does; here, it doubles as the AI's instructions |
| Type annotation / contract | A label stating exactly what shape/kind of answer is expected (e.g., "a whole number from 1 to 5"), checked automatically |
| Pass-by-reference | Giving the AI a live handle to the real data (so it can work with all of it via code) instead of pasting a full copy into its briefing |
| Code as action | Letting the AI act by writing a small real program (with loops, conditions, etc.) instead of filling out one fixed-menu command at a time |
| Context window | The limited amount of text an AI can "see" at once in its briefing — like the size of a sticky note versus a whole filing cabinet |
| Sandbox | An isolated, locked-down environment that limits what a running program (including AI-written code) is allowed to do or touch |
| World model | An internal, code-based simulation the AI builds and keeps updating to predict what will happen next in an unfamiliar environment |
| Pareto frontier | The best possible trade-off line between two things you care about (here, how good the results are versus how much it costs) — being "on the frontier" means no cheaper option gets equally good results, and no equally-priced option does better |
| Benchmark (e.g., SWE-bench, Terminal-Bench) | A standardized test suite used to compare different AI systems on the same fixed set of tasks |
