# Related Work and Conclusion

**In one sentence:** The paper traces NOOA's six interface capabilities (typed I/O, code as action, pass by reference, loop engineering, object state, harness APIs) back to their research lineages, then closes by stating NOOA's precise limitations — its validator protects the agent loop but not the host process — and proposing three future directions: rewriting the whole agent, turning skills into real software packages, and using reinforcement learning to teach harness-level reasoning.

## Key points

- Typed I/O: NOOA makes the *method* itself the unit of typing — type annotations at the generation-method boundary are enforced by the runtime — rather than bolting on a separate schema object the way DSPy's signatures, LMQL/Outlines' decoding-time constraints, or Instructor/TypeChat's post-hoc validate-and-reprompt pattern do.
- Code as action: building on CodeAct's argument that executable code should be the action modality itself (shown to outperform JSON- and text-based action formats), NOOA realizes that idea as a full object-oriented Python runtime, and the authors argue bash tools are themselves a weak form of code as action — which is why tool-as-CLI packaging is displacing tool-as-MCP packaging, since a CLI's output can be filtered and composed programmatically while an MCP call dumps its entire result into the context window.
- Pass by reference: most agent frameworks use "copy-as-text" at every interface boundary, serializing inputs and outputs through text; NOOA instead follows the CodeAct/smolagents/Recursive-Language-Models lineage of shared live program state, realized through live objects in the session namespace, `return_result(variable)`, and a size-bounded input-inspection preview — a fuller realization than the common file-as-pass-by-reference middle ground, which the authors call powerful but lossy because it discards type information.
- Loop engineering: unlike LangGraph, Microsoft Agent Framework, and Google ADK's graph- or DSL-based workflow languages, NOOA needs no separate workflow language at all — outer loops are ordinary developer-written Python methods and inner loops are ordinary model-written code inside a CodeAct turn, both expressed in the same object model.
- Object state: where MemGPT pages information between an in-context tier and external memory tiers and most harnesses keep durable state as untyped text (memory files, searchable transcripts, memory-tool stores), NOOA's state is object-scoped and part of the method contract — typed fields rendered into the prompt from the live agent instance on every turn, held out of history eviction entirely.
- Harness APIs: following MemGPT/Letta's model-callable memory tools and Memory-R1's RL-trained memory management, NOOA exposes its harness uniformly as model-callable APIs (context blocks and queryable event history) with developer-controlled, per-agent visibility, on the authors' stated belief that direct programmatic access to context and history is key to new agentic behavior on long-running tasks.
- Limitations: the paper states plainly that NOOA's validator protects the agent loop (type-checking candidate return values) but **not** the host — it is not a security sandbox and makes no claim about what model-written code can do to the process or machine — a trade-off the authors accept deliberately because in-process execution is exactly what preserves pass by reference, and they recommend OpenShell for the process-level isolation NOOA itself does not provide.
- Future directions: the authors propose rewriting every part of the agent (prompts, docstrings, signatures, helper code, retry loops) via GEPA-style reflective optimization rather than prompt search alone; turning "skills" into full versioned software libraries with typed APIs, tests, and docs that agents can inspect and extend; and using reinforcement learning over complete agent trajectories, in the spirit of DeepSeek-R1, to teach the inductive reasoning long-running agents need over context, memory, and code use as a learned action space.

Section 6 of the paper takes the six interface capabilities scored in the harness comparison ([[07-comparison-to-other-frameworks|Comparison to Other Frameworks]], Sec 5 — typed I/O, code as action, pass by reference, loop engineering, object state, harness APIs) and traces each one back to the research threads it grew out of, naming the specific papers and systems NOOA is building on or diverging from. Section 7 then closes the paper: a one-paragraph summary, an explicit limitations statement about what NOOA's in-process execution model does and does not protect against, and three directions the authors want the field to pursue next — rewriting the whole agent (not just its prompt), turning skills into real software packages, and using reinforcement learning to teach inductive, harness-level reasoning.

## Typed I/O

The authors trace typed, structured LLM programming through several lineages before landing on NOOA's own take. **DSPy** [26] made declarative *signatures* — named, typed input and output fields — the basic unit of LLM programming, decoupling declared intent from prompt wording and making pipelines programmatically optimizable. **LMQL** [13] frames prompting itself as a query language whose output constraints (including type constraints) are enforced *at decoding time*. **Outlines** [55] takes a related but distinct approach, enforcing output structure during generation by compiling regular expressions and grammars down to finite-state machines and pushdown automata that mask invalid tokens at each decoding step. At the engineering-library layer, **Instructor** [30] and **TypeChat** [36] validate model output against a schema after the fact and re-prompt the model with the validation errors when it fails. The text notes that mainstream agent frameworks have converged on the same need from the outside in: **LangChain** agents [14] and **PydanticAI** [46] both accept a developer-supplied output schema, and **Google's ADK** [22] goes a step further, enforcing an output schema on every agent reply and additionally accepting an *input* schema when an agent is exposed as a callable tool via its agent-as-tool path.

Against this backdrop, NOOA's move is to make the *method* the unit of typing rather than a bolt-on schema: agentic methods and tools are ordinary Python methods, and type annotations at the generation-method boundary are enforced by the runtime itself, with no separate signature object to keep in sync with the code.

## Code as action

This is the thread the paper spends the most space on, since "executable code as the action modality" is one of NOOA's central bets. **PAL** [21] and **Program of Thoughts** [15] were early demonstrations of offloading computation from the LLM to a generated program rather than having the model do arithmetic or logic in free text. **Chain of Code** [29] extended this by interleaving real interpreter execution with LM-*simulated* execution for the lines an interpreter can't run. **CodeAct** [52] is the paper the authors treat as consolidating the argument outright: executable code should be the action modality itself, and it empirically outperforms JSON- and text-based action formats. **smolagents** [48] packaged that paradigm as a library, executing model-written code in a restricted interpreter with tools exposed as callable functions, and **OpenHands** [53], built on CodeAct, demonstrated the paradigm at scale on real software-engineering tasks — though the text notes its V1 SDK rebuild has since moved back to discrete shell and file tools (see the harness comparison in Sec 5). **SWE-Agent** [57] is cited as a complementary result: it showed that the agent–computer interface itself — not just the action format — is a first-class design surface. Outside the CodeAct lineage narrowly, **Anthropic's programmatic tool calling** [6] is cited as a related mechanism: it has the model invoke tools as functions from *within* an executing program rather than as one JSON call per turn, which keeps bulk intermediate results out of the context window. **Recursive Language Models** [58] and **Recursive Agent Harnesses** [32] are cited for a related but distinct concern — long-context decomposition through recursive model or harness calls rather than through code-as-action per se.

The authors add their own observation here: bash tools are themselves a *weak* form of code as action, since a shell command line is a small program with pipes and loops for control flow and CLIs as callable tools — and they suggest this is why tool-as-CLI packaging has been displacing tool-as-MCP packaging: a CLI is called from code, so the model can filter, transform, and compose its output programmatically, whereas an MCP tool call is a single JSON round-trip whose entire result lands in the context window. The shell's limits remain real, though — it operates only on untyped text, with no variable persistence outside of files. Finally, the section cites recent survey work that frames the whole shift as **"code as agent harness"** [38]: code as the substrate not just for reasoning but for acting, environment modeling, execution-based verification, planning, memory, tool use, and multi-agent coordination. NOOA is presented as having realized that design fully, as an object-oriented Python runtime rather than a bare code-execution sandbox.

## Pass by reference

Most agent frameworks, the paper argues, use "copy-as-text" at every interface boundary: inputs are serialized to text, tool-call inputs are generated as text by the model, outputs come back as text, and the host language has to parse LLM output back into structured data [41]. The related-work thread here is about systems that instead let prompts and live program state interact directly. **Cheng et al.** [16] propose shared program state as a natural function interface and built **Nightjar**, a programming system that embeds natural-language code blocks inside Python, using angle-bracket notation (`<var>` to reference, `<:var>` to assign) so the LLM can read and write live variables through explicit references. **AskIt** [40] provides a type-guided domain-specific language that turns typed prompt templates into callable functions, serializing captured host variables into the prompt and parsing typed output back out. **ANPL** [24] interleaves user-written Python-like sketches with LLM-implemented natural-language "holes." **CodeAct** [52] reappears here as the direct ancestor of NOOA's default execution strategy: it replaces structured tool-calling with a Python REPL in which tools are ordinary functions and live objects persist across turns. **smolagents** [48] follows the same lineage, injecting developer-supplied Python objects directly into the executor's namespace for the model to use by name. **Recursive Language Models** [58] are cited again here as pushing reference-passing to its logical conclusion: the prompt itself becomes a variable in a REPL that the model inspects, slices, and recursively queries via sub-model calls rather than reading in full. **TaskWeaver** [47] maintains cross-step state as live Python variables in a similar spirit.

The text also flags a widely-used middle ground: many popular frameworks treat *files* as a variant of pass by reference, handing the agent a filename and letting it explore the file's contents via tool calls. The authors call this powerful but lossy — it discards all type information and forces the agent to reconstruct any embedded types by re-reading text. NOOA's own realization of pass by reference — live objects in the session namespace, `return_result(variable)`, and the size-bounded input-inspection preview at the start of every call — is covered in depth on the [[02-agent-loop-strategies-and-context|Agent Loop, Strategies, and Context]] page; this section positions it as the fullest expression of the reference-passing lineage above, rather than a file- or text-based approximation of it.

## Loop engineering

For developer- and model-facing control flow, the paper surveys the current landscape of orchestration DSLs and contrasts them with NOOA's stance that no separate workflow language is needed. **LangGraph** [27] expresses control flow as a graph of nodes that read and write typed shared state. **Microsoft Agent Framework** [37] builds workflows as directed graphs of executors exchanging typed messages. **Google's ADK** [22] pairs developer-defined workflow agents with model-callable control primitives, letting the model itself invoke certain orchestration primitives at runtime. **smolagents** injects developer-defined *managed agents* into the model's code namespace, so the model can write loops over subagents as part of its own generated actions. **Claude Code's** dynamic workflows [10] go further in giving the model authorship: given a task, the agent itself writes a script that fans out tens to hundreds of parallel subagents, with verification stages, before results are returned.

NOOA's position relative to all of these: it needs no separate workflow language at all. Outer loops are just ordinary Python methods that a developer writes; inner loops belong to the model, expressed as ordinary code inside a CodeAct turn; and because both use the same object model, the agent can write and invoke exactly the same control-flow constructs a developer would.

## Object state

The starting observation is that for most agents, conversation history *is* the state — and as conversations grow long and get compacted, state held only in history can be silently lost. **MemGPT** [43] is the key prior system here: it treats the LLM as an operating system that pages information between an in-context tier and external memory tiers, reserving a fixed-size read/write "working context" section of the prompt that is exempt from eviction so key facts survive long conversations. The paper then characterizes three ways today's harnesses keep durable state, none of which it attributes to a single named system but which recur across the Sec 5 comparison: model-edited files (memory files like `MEMORY.md` re-injected at session start, todo/plan stores, `AGENTS.md`-style instructions), searchable conversation history (full-text or vector search over past session transcripts), and dedicated memory tools with explicit add/replace/remove verbs over a store. All three survive compaction and session boundaries, but — the authors stress — all three hold state as *untyped text sitting outside the model's working state*.

NOOA's contrast is that its state is object-scoped and part of the method contract: typed fields and named context blocks live directly on the agent instance, and public fields are rendered into the prompt from the *live object* on every turn — held out of history eviction entirely, rather than reconstructed from a transcript after the fact.

## Harness APIs

The final thread covers systems that expose the harness's own machinery — memory, compaction, history search — as APIs the model itself can call, rather than mechanisms the model can only trigger indirectly through conversation. **MemGPT** and its successor **Letta** [43, 2] expose the harness itself as model-callable tools: the model can edit its own in-context memory blocks, search its message history, and page file content in and out of context — though the paper notes an important caveat, that context *compaction* in these systems remains harness-triggered, with the model only ever warned of memory pressure rather than controlling compaction directly. **Memory-R1** [56] trains these capabilities with reinforcement learning rather than hand-designed heuristics: a memory-manager agent learns add/update/delete/no-op operations over a memory store, while a separate answer agent learns to filter and reason over what gets retrieved.

NOOA's stance is to expose its harness *uniformly* through the object model: static and dynamic context blocks and the queryable event history are all model-callable APIs, with per-agent, developer-controlled opt-in visibility and scoped overrides available to harness code. The authors state their belief plainly: giving agents direct, programmatic access to their own context and history will be key to unlocking new agentic behavior on long-running tasks — a claim that anticipates the reinforcement-learning direction taken up again in the conclusion below.

## Conclusion and limitations

The paper's closing argument is that NOOA brings together these recent advances into a single ergonomic development kit in which an agent is simply a Python object with methods and state — making agentic software *ordinary* software, where developers and agents share the same interface, the same libraries, and the same tools. The evaluation, the authors say, shows current models already operate this interface effectively despite never having been trained on it specifically.

The limitations paragraph is precise and worth stating exactly as scoped. **NOOA executes model-written code in the agent's own process.** The validator described in Sec 3.4 protects the *agent loop* — it type-checks and validates candidate return values so a malformed or mistyped result doesn't get returned to the caller — but it does **not** protect the host: it is not a security sandbox, and it makes no claim about what arbitrary model-written code is allowed to do to the process or machine it runs in. The paper is explicit that this makes NOOA's isolation philosophy identical to that of *any* harness with a shell tool: sandboxing — a container, a VM, or an OS-level permission system — has to go *around* the agent process from the outside, because a shell tool is no safer than in-process Python, and most of the harnesses surveyed in Sec 6/Sec 5 ship a shell tool anyway. This is framed as a genuine trade-off rather than an oversight: executing in-process is exactly what preserves pass by reference (this is the direct link back to [[01-introduction-and-design-principles|Introduction and Design Principles]], where pass-by-reference over live objects is one of the six foundational capabilities NOOA is built around) — sandboxed code-execution modes trade that capability away, since they only receive *serialized copies* of data at the sandbox boundary rather than references to the live objects themselves. The authors state their preferred deployment posture for addressing this is **OpenShell** [39], which supplies the process-level isolation NOOA itself deliberately does not.

## Three future directions

**Agent optimization via agent rewriting.** The authors argue optimization work should move beyond prompt search alone and instead rewrite *every* part of the agent: prompts, docstrings, typed method signatures, helper code, tool descriptions, context policies, retry loops, and decomposition structure. They cite **GEPA-style reflective optimization** [1] as a natural starting point, but frame the real target as broader still — the whole agent object and its harness together, not just the text fed to the model.

**Skills as full software packages.** Second, the authors argue that typed interfaces and libraries open a path toward self-evolving agents. Today's "skills" (as seen across the harnesses in the Sec 5 comparison) are mostly text snippets or informal procedures. NOOA's authors expect skills to become full software libraries instead — with typed APIs, documentation, tests, examples, subagents, dependencies, and versioned interfaces that agents can inspect, call, repair, and extend on their own, rather than static instructions injected into a prompt.

**Reinforcement learning to unlock inductive reasoning.** Third, the authors look to reinforcement learning to target the *inductive* reasoning that long-running agents need. They cite **DeepSeek-R1** [18] as showing that outcome-driven RL can induce useful reasoning behavior once a model is allowed to search through its own intermediate reasoning steps, and expect a similar effect for object-oriented agents — but over a much richer action space than text alone. A NOOA agent's inductive decisions include: what context to reveal, which variables to preserve, when to write deterministic helper code, when to promote a pattern into a reusable library, and when to decompose a task into deterministic orchestration — all decisions that require generalizing from prior trajectories to new tasks. The paper's hypothesis is that reinforcement learning over *complete agent trajectories* could teach models to use harness APIs, dynamic context, pass-by-reference objects, and code-as-interface as a learned reasoning substrate — in this view, the harness stops being merely an execution environment and becomes the action space in which agents learn to construct, test, and reuse problem-solving structure.

The paper's final claim ties these three together: progress in agent capability will come not only from larger models or better prompts, but from the *co-development of model and harness*, and the authors believe the software interface is the right place for that co-development to happen. NOOA is offered as one step toward it — an object-oriented harness in which agents are programs that both humans and models can read, execute, test, and improve.
