# Discussion, Related Work, and Conclusion

**In one sentence:** Beyond documenting 307 confirmed skill-induced failures, the paper argues skill loading should become a costed, validated configuration decision — via future compatibility checks, cost-aware packaging, and budget-aware execution — while positioning its contrastive attribution method against prior skill benchmarks, context-engineering research, empirical agent-failure studies, and software-bug taxonomies, and acknowledging the judgment-based and benchmark-scoped limits of its own evidence.

## Key points

- The paper proposes three concrete future directions rather than leaving the findings as pure diagnosis: **skill-task compatibility checks** (compare task requirements against candidate skill contents before/during execution to catch conflicting defaults, paths, or package-state assumptions), **cost-aware skill packaging and selection** (estimate marginal context cost, move task-specific examples to lazy-loaded references, predict extra exploration/verification/repair work before a skill is selected), and **budget-aware execution policies** (treat skill loading itself as a decision with a cost budget, not a free action).
- These three directions map directly onto the paper's own root-cause taxonomy: compatibility checks target the applicability/environment/task-implementation/artifact mechanisms behind functional failures, while cost-aware packaging and budget-aware execution target the Excessive-Procedure mechanism behind efficiency regressions — the discussion is explicitly framed as "what would prevent the failures we just catalogued."
- **Internal-validity threat:** root-cause labeling involves human judgment, which is inherently subjective. The authors mitigate this by (1) excluding ambiguous or verifier-narrow cases during dataset refinement rather than force-labeling them, (2) requiring group consensus before a case is finalized, and (3) using SkillTriage itself as an independent consistency check against manual labels — i.e., the tool that automates triage is also used to cross-validate the humans who built the taxonomy.
- **External-validity threat:** the study spans seven domains (software engineering, healthcare, manufacturing, cybersecurity, natural science, finance, mathematics) via SkillsBench and SWE-Skills-Bench, which the authors present as broad coverage of problem-solving and software-engineering scenarios. They explicitly caveat that some findings may depend on the specific task distribution, agent harness (OpenCode), model (Claude Opus 4.6), or skill ecosystem (smithery.ai, skillsmp.com) used, and say they tried to avoid conclusions tied specifically to these two benchmarks.
- **Related work — Agent Skills abstraction:** the paper positions SKILL.md-based agent skills as an extension of earlier work on skill libraries, executable code actions, and tool-oriented fine-tuning (e.g., Voyager-style skill libraries, "executable code actions elicit better LLM agents," GPT4Tools) — skills package the same idea of reusable procedural knowledge but deliver it as on-demand natural-language documents rather than learned policies or fine-tuned parameters.
- **Related work — prior skill benchmarks:** SkillsBench and SWE-Skills-Bench are the direct empirical foundation this paper builds on, since both already show skills can raise average pass rate while also causing regressions, zero-gain cases, and heavy token overhead. This paper's contribution is a different question: not *whether* skills help on average, but *which skill contents and induced trajectory changes* cause the failures and regressions — i.e., mechanism-level attribution rather than aggregate benefit measurement.
- **Related work — context engineering / long-context distraction:** skill loading is framed as one instance of context engineering inside the agent's reasoning-and-acting (ReAct-style) loop. Prior literature (Lost in the Middle, distraction-by-irrelevant-context studies, prompt-format sensitivity studies, "more documents same length" RAG studies, input-length-vs-reasoning-performance studies) shows added context is not monotonically helpful — models can ignore middle content, get distracted, degrade with more documents, or react to formatting. These studies motivate *why* skill loading is risky in principle; this paper's distinct contribution is analyzing *how* loaded skill context concretely changes executable repository actions, implementation choices, verification behavior, and cost — not just showing that longer/more context can hurt.
- **Related work — empirical agent-failure studies:** MAST builds a failure taxonomy from multi-agent traces; Agentless and SWE-agent show that scaffold/harness design materially changes agent outcomes; SWE-bench and its extensions (OpenHands, Multi-SWE-bench, SWE-Lancer, and related evaluation infrastructure) provide the evaluation substrate for software agents generally. This paper's attribution target differs from all of these: it attributes failures and cost regressions specifically to *loaded skills* under controlled contrastive comparisons, rather than to the base agent, scaffold, or task difficulty alone.
- **Related work — bug taxonomies:** the paper's own root-cause taxonomy draws on empirical software-engineering studies of performance bugs, ML/deep-learning bugs, and configuration bugs (real-world performance bug studies, JavaScript/TensorFlow bug studies, deep-learning fault taxonomies, configuration-error and over-designed-configuration studies). These perspectives are adapted to a new unit of analysis: agent trajectories as shaped by a loaded skill, rather than source code or system configuration directly.
- **Conclusion's framing of the contribution:** the paper states it studied skill-induced agent failures as a distinct failure class, built via a contrastive analysis dataset of 307 confirmed cases (125 functional failures, 182 high-confidence efficiency regressions); functional failures arise through applicability, environment, task-implementation, and artifact mechanisms, while efficiency regressions arise mainly through Excessive Procedure rather than prompt length alone. The headline takeaway is normative: skill loading should be treated as a **costed and validated configuration decision**, supported by compatibility checks, cost prediction, and paired correctness/cost evaluation — with SkillTriage offered as a taxonomy-guided triage tool that normalizes paired cases, extracts differential evidence, and attributes confirmed failures/regressions to root causes.

## VII. Discussion

### A. Future Research Directions

The paper's findings motivate three directions for making skill reuse safer and more cost-aware:

1. **Skill-task compatibility checks.** Because many functional failures arise from topically *relevant* skills that nonetheless distort task-required implementation elements or verifier-visible surfaces, future platforms should compare task requirements against candidate skill contents both before and during execution. Such checks could extract required fields, APIs, paths, output formats, domain rules, and environment constraints from the task, then warn when a skill introduces conflicting defaults, examples, templates, paths, or package-state assumptions relative to those requirements.
2. **Cost-aware skill packaging and selection.** The paper's efficiency-regression findings show skill cost comes from two sources — always-loaded context *and* induced extra trajectory steps — not from prompt length alone. Future tooling should estimate the marginal context cost of a skill, move task-specific examples or checklists to lazy-loaded references (rather than always-loaded content), and predict the extra exploration, implementation, verification, or dependency-repair work a skill is likely to induce before it is selected for a task.
3. **Budget-aware execution policies.** Taken together, points 1 and 2 imply skill loading itself should be governed by an explicit cost/correctness budget at execution time, rather than being treated as a free, always-beneficial action — i.e., a skill should be loaded (or not) based on predicted compatibility and predicted marginal cost, not merely topical relevance.

### B. Threats to Validity

**Internal validity.** Root-cause labeling of each case necessarily involves human judgment, which introduces subjectivity risk. The paper mitigates this in three ways:
- Ambiguous or verifier-narrow cases are excluded during dataset refinement rather than force-fit into a root-cause category (see the refinement step reducing 665 labeled candidates to 307 confirmed cases in the methodology).
- Every remaining case is finalized only after **group consensus** among the labelers, rather than by a single annotator's judgment.
- **SkillTriage** — the paper's own taxonomy-guided triage tool — is used as an independent consistency check, cross-validating the manually assigned root causes rather than being trusted blindly as ground truth.

**External validity.** The study covers seven domains — **software engineering, healthcare, manufacturing, cybersecurity, natural science, finance, and mathematics** — spanning SkillsBench's 11 domains and SWE-Skills-Bench's software-engineering task instances, which the authors frame as reasonably broad coverage of problem-solving and software-engineering scenarios. However, they explicitly acknowledge that some findings may be specific to the **task distribution, agent harness (OpenCode), model (Claude Opus 4.6), or skill ecosystem (smithery.ai / skillsmp.com)** used in the study and might not generalize to all settings. To mitigate this, the authors report they deliberately avoided drawing conclusions that are specific only to these two benchmarks.

## VIII. Related Work

**Agent Skills abstraction and prior skill/tool work.** The Agent Skills abstraction packages reusable procedural knowledge as on-demand `SKILL.md` documents. This extends earlier work on agent capabilities: skill libraries (e.g., Voyager, an open-ended embodied agent that accumulates a skill library), executable code actions ("executable code actions elicit better LLM agents"), and tool-oriented tuning (e.g., GPT4Tools, teaching LLMs to use tools via self-instruction). Agent Skills differ from these mainly in packaging format — natural-language, on-demand documents rather than learned code/policies or fine-tuned tool-use behavior.

**Prior skill benchmarks (this paper's direct foundation).** SkillsBench and SWE-Skills-Bench show that skills can improve average pass rate but also introduce regressions, zero-gain cases, and substantial token overhead. This paper builds on both benchmarks but asks a different question: not whether skills help *on average*, but **which skill contents and induced trajectory changes cause functional failures and efficiency regressions** — shifting from aggregate utility measurement to mechanism-level attribution.

**Context engineering and long-context distraction.** Skill loading is framed as a form of context engineering inside the agent's reasoning-and-acting (ReAct) loop. Prior work establishes that additional context is not monotonically helpful: models can ignore middle context ("Lost in the Middle"), become distracted by irrelevant content, degrade as the number of documents or input length grows even at fixed total length, and react strongly to prompt format. These studies motivate why loading skill context is inherently risky; this paper's contribution is analyzing concretely **how** loaded skill context changes executable repository actions, implementation choices, verification behavior, and cost — going beyond showing that longer or more numerous inputs can hurt.

**Empirical agent-failure studies.** MAST builds a failure taxonomy from multi-agent LLM traces; Agentless and SWE-agent demonstrate that scaffold/harness design can materially change agent outcomes; SWE-bench and its extensions (OpenHands, Multi-SWE-bench, SWE-Lancer, and related work) supply evaluation infrastructure for software agents broadly. This paper's attribution target is different: it attributes failures and cost regressions specifically to **loaded skills** under controlled contrastive comparisons, rather than attributing them to the base agent or task difficulty alone.

**Bug taxonomies underlying the root-cause categories.** The paper's own taxonomy also draws on empirical software-engineering studies of performance bugs, ML/deep-learning bugs, and configuration bugs — including real-world performance-bug studies, JavaScript and TensorFlow bug studies, deep-learning fault taxonomies, and configuration-error/over-designed-configuration studies. The paper adapts these established bug-classification perspectives to a new unit of analysis: **agent trajectories as shaped by a loaded skill**, rather than source code or system configuration directly.

## IX. Conclusion

The paper studied **skill-induced agent failures** as a distinct failure class in LLM agents. By constructing a contrastive analysis dataset, the authors identified **307 confirmed cases: 125 functional failures and 182 high-confidence efficiency regressions**. The analysis shows skills induce functional failures through **applicability, environment, task-implementation, and artifact mechanisms**, and induce efficiency regressions mainly through **Excessive Procedure** rather than prompt length alone. The paper's overarching recommendation is that skill loading should be treated as a **costed and validated configuration decision** — supported by compatibility checks, cost prediction, and paired correctness/cost evaluation, rather than assumed to be free or uniformly beneficial. As a concrete step toward that goal, the authors developed **SkillTriage**, a taxonomy-guided triage tool that normalizes paired cases, extracts differential evidence, and attributes confirmed failures and regressions to root causes.
