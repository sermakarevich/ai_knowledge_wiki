# How We Claude Code at Anthropic

**Source:** [How We Claude Code -- Anthropic Workshop (Ara, 2025)](https://www.youtube.com/watch?v=IlqJqcl8ONE)

## Human Readable TL;DR

Imagine you're building a house and instead of writing a long list of requirements your contractor might misread, you show them a 3D mockup and walk through it room by room. This workshop explains how Anthropic engineers do something similar: they let Claude interview them to uncover what they really want, use rich visual HTML mockups instead of plain text documents, and then bake automated "inspection checklists" directly into the app so the AI agent can verify its own work -- no human babysitting required.

## TL;DR

A workshop by Anthropic applied AI architect Ara demonstrating three practices that maximize leverage from long-running Claude Code agents: (1) using Claude itself to interactively extract requirements via the `ask_human` tool rather than upfront spec writing, (2) generating HTML design explorations instead of markdown specs for richer human-in-the-loop feedback, and (3) embedding agent-native DOM-contract verification (via Storybook fixtures, data attributes, and Playwright MCP) directly into React components so that Claude Code can run, record, and report verification end-to-end without human intervention.

---

## Problem & Motivation

As models become more capable, agents can run for longer with more complex tasks -- but this amplifies the cost of a bad spec. A misaligned requirement discovered after 10k tokens of agent work is far more expensive than one caught upfront. Traditional markdown specs are too long to read, too static for visual feedback, and not structured for agent consumption. The workshop addresses how to close these gaps: get better specs faster, give agents richer feedback surfaces, and make verification self-driving.

---

## Main Original Ideas

1. **Claude-as-interviewer (spec extraction)** -- Instead of the developer writing requirements upfront, a prompt instructs Claude to use the `ask_user_question` tool to iteratively interview the user, surfacing latent requirements domain by domain. Parallel to Richard Sutton's "bitter lesson": don't over-specify, let the model extract. The prompt focuses Claude on audience, scope, and open-ended exploration rather than a predetermined structure.

2. **HTML design explorations over markdown specs** -- Markdown files become unreadable beyond ~200 lines and convey no visual intent. Claude (Opus 4.7 recommended for its vision model) generates 4+ HTML design directions from the spec; the developer picks and annotates. Screenshots of the HTML can be fed back to Claude for precise visual feedback. Token cost is lower long-term because fewer misalignment iterations occur.

3. **Agent-native DOM contract verification** -- React components publish their internal state to the DOM via `data-*` attributes (e.g., `data-verify-unit`, `data-total`, `data-done`, `data-active`). Storybook fixtures define known component states; invariants are declared alongside the fixture. A human-readable verification dashboard, an agent-driven Playwright MCP flow, and a headless `bun verify` CLI all consume the same DOM contract. Verification evidence (videos) is recorded as clips and can be stored on S3 or shared with colleagues -- matching how the Claude Code team ships.

4. **Fast mode + auto mode for spec iteration** -- `shift+tab` cycles into auto mode (recommended always-on); `/fast` toggles fast mode (Opus 4.x with faster output) for rapid spec iteration. `/effort xhigh` is the recommended effort level. Cost is higher per token but lower per iteration.

## Key Findings

| Approach | Tool/Mechanism | Use case |
|---|---|---|
| Requirement extraction | `ask_user_question` tool in prompt | Replace upfront spec writing |
| Design exploration | HTML files generated by Opus 4.7 | Visual feedback before coding |
| Human verification | Browser dashboard with Storybook fixtures | Interactive pass/fail review |
| Agent verification | Playwright MCP + DOM contracts | Claude Code runs checks headlessly |
| CI verification | `bun verify` | Automated test matrix in CI |
| Evidence recording | Video clips → S3 | Shareable proof of frontend correctness |

- Deliberately-broken fixture (3+4≠10 hardcoded) confirms the dashboard and the agentic path catch the same failure.
- Breaking the DOM contract (removing a `data-*` attribute) fails verification without breaking the app -- separating contract health from functional health.
- Opus 4.7 is specifically recommended over Sonnet for this workflow due to its stronger vision model.

---

## Suggestions & Future Directions

1. **Headless agent-driven CI** -- The verification loop (Playwright → DOM contract → record) is already pointed at running fully headlessly in CI, closing the human-in-the-loop gap entirely.
2. **Scale fixture generation to Claude** -- Fixtures, schemas, and invariants are currently hand-authored; the next step is having Claude generate them from component code, scaling coverage without developer effort.
3. **Clip-based audit trail** -- Recorded verification clips stored on S3 form a continuous audit trail that makes frontend regressions visible across releases, not just at the moment of check-in.
4. **Broader HTML artifact types** -- The same "HTML as rich artifact" pattern applies beyond design mockups: requirements dashboards, API contracts, and data schemas can all benefit from HTML over markdown.
