# AI Native Call Center

**Article:** [rasonyang/ai-native-callcenter](https://github.com/rasonyang/ai-native-callcenter) — GitHub /

## Human Readable TL;DR

Imagine a call center where a smart voice assistant always picks up the phone first, like a capable receptionist who handles routine questions herself and only buzzes a human specialist when one is really needed. This project is an open-source toolkit for building exactly that, pairing a telephone switchboard in FreeSWITCH with modern speech-to-speech AI models from OpenAI, Qwen, Doubao, or Gemini. Human agents work from an ordinary browser window while a separate phone extension handles the audio, and everything from the robot chat to the human conversation ends up in a single tidy call record. It ships as one easy-to-run Go program plus a database and the phone switch, complete with demo teams, queues, and bilingual example flows so you can try it immediately.

## TL;DR

rasonyang/ai-native-callcenter is an Apache-2.0 open-source AI-native call center in which voice AI is the default answer rather than an add-on, answering inbound calls over a provider-native speech-to-speech Realtime connection that the Go application terminates itself with G.711 passed through byte for byte where supported. The system is packaged as a single Go binary containing the REST API, SSE event stream, and embedded React UI, backed by PostgreSQL and FreeSWITCH, with FreeSWITCH reading directories and mod_callcenter queues from the database via Lua and a static XML dialplan delegating to lookup scripts. AI-to-human handover targets real mod_callcenter queues with screen-pop over SSE and a shared call identity minted before any leg exists, while agents use the browser surface for presence, control, and callbacks and a separate web-sip-phone Chrome extension for the SIP audio leg, unified into one CDR with one transcript and one recording stored on filesystem or S3-compatible storage. One provider serves every call in a deployment, selected at startup among qwen or doubao inside mainland China, openai or gemini elsewhere, or a self-hosted gateway, with English and Chinese supported throughout and flow-driven dialogue where phases carry instructions, tools, transitions, and verbatim script lines. The repository snapshot shows 62 stars, 14 forks, 4 watchers, and 594 commits on main, with a demo seed of a team, two queues, six published bilingual flows behind English, Chinese, and US numbers, eighteen simulated customer phones, and a week of history, while performance budgets remain intentions pending a benchmark campaign and cascaded ASR plus LLM plus TTS pipelines are deliberately out of scope.

## Problem & Motivation

Traditional call centers treat automation as a bolt-on menu layered in front of human queues, which fragments the caller experience into disconnected interactive voice response steps, bot turns, and agent legs with separate records and lost context. At the same time, modern speech-to-speech realtime models can hold natural spoken conversations but need telephony grounding, deterministic business control, clean handover to people, and operable packaging before they are useful in production service desks. This project is motivated by flipping the default so that AI answers first and people are the escalation path, without sacrificing queueing semantics, agent workflows, auditability, or deployment simplicity. It therefore combines FreeSWITCH as a proven telephony and queueing substrate with a single Go service that owns call orchestration, flow control, event distribution, and the product surface, aiming for a bilingual, provider-flexible, self-hostable alternative to proprietary contact-center-as-a-service offerings.

## Main Original Ideas

1. **AI-first answering with provider-native passthrough:** calls arriving at FreeSWITCH are bridged to an application-terminated speech-to-speech connection where audio flows straight to the voice provider, with G.711 passed through byte for byte where the provider accepts it so nothing decodes or resamples on the way. This keeps latency and fidelity close to what the model vendor intended while letting one Go process own dialogue, recording, and control instead of chaining separate speech recognition, language model, and synthesis stages.

2. **Flow-owned phases over model-owned dialogue:** the model owns the conversation while a JSON-defined flow owns the phase, where each phase carries instructions and an allowed tool list and transitions fire on tool results, optionally including verbatim greeting, handover, and goodbye lines that Doubao receives as words to speak and the other providers are instructed to repeat word for word. The separation gives product builders deterministic steering and safe escalation without micromanaging every utterance.

3. **Queue-native handover with pre-minted call identity:** transfers go into real FreeSWITCH mod_callcenter queues rather than ad-hoc bridges, with the call identifier created before any leg exists so it survives the transfer and unifies bot transcript, agent conversation, recording, and CDR into one record. A PARTY_RINGING event over SSE pops the agent screen with caller identity and userData while the bot-phase transcript is already visible, so the human starts informed rather than asking the caller to repeat everything.

4. **Split browser surface plus extension phone with actor-model core:** agents do presence, call control, and callbacks as REST calls in the embedded React UI, carried to the audio device over ESL uuid_phone_event, while voice itself lives in a separate web-sip-phone Chrome extension holding the agent SIP leg. Internally every live call is an actor with one goroutine as sole mutator and mailbox snapshots, avoiding shared call-state locks except for the AI leg's playback and recording state, and the domain model follows Genesys lineage with calls aggregating parties and PARTY_* versus CALL_* events.

5. **One-binary operability with spec-first extensibility:** the REST API, SSE stream, and UI ship as one Go binary plus PostgreSQL and FreeSWITCH, deployable via Docker Compose with two environment lines, `make dev-up` and `make build` workflows, and a demo seed that makes the system explorable on first login. Extension points are deliberately narrow and documented, with new voice providers added as profiles, new flows as validated JSON documents, new screens per web conventions, and the OpenAPI document as single source of truth enforced by generation and contract checks.

## Key Findings

The snapshot describes a functionally complete path for both the human leg and the AI leg, including the product surface and packaging, verified against live FreeSWITCH and live providers, which suggests the architecture is more than a diagram and can actually take, automate, escalate, and complete calls. The repository scope at capture time spans telephony integration, realtime provider handling, queueing, browser agent tooling, persistence, and build and test harnesses, supported by 594 commits and conventional Go and web lint, race-enabled tests, and API compatibility checks. The demo content is unusually rich for an infrastructure project, with bilingual flows, multiple inbound numbers anchored on main line 800-555-0199, simulated customers, and historical data that let evaluators exercise routing, handover, and reporting without wiring real carriers. At the same time the project is explicit that performance is not yet a claim, offering a capacity budget and latency target alongside a load-test harness but no completed benchmark campaign, so adopters should treat scaling numbers as design intentions. The deliberate exclusion of in-process cascaded pipelines reinforces the architectural bet that provider-native realtime speech is the right primitive, pushing alternative compositions into separate services behind the same protocol rather than complicating the core.

## Suggestions & Future Directions

The most immediate next step implied by the documentation is to run the included load-test harness and publish a benchmark campaign that turns the capacity budget and latency target into measured claims under realistic concurrency, provider variability, and queueing load. A second natural direction is broadening provider and deployment coverage, including maturing the self-hosted Realtime gateway option and validating behavior differences such as verbatim prompting across OpenAI, Gemini, Qwen, and Doubao in both English and Chinese. Product depth could grow around richer flow authoring and evaluation, expanded reporting over the unified CDRs and transcripts, recording lifecycle management across filesystem and S3-compatible stores, and hardening the split browser-plus-extension agent experience for everyday operations. Finally, ecosystem work such as additional flow packs, provider profiles, and operator guides would lower adoption friction, while keeping the core commitment to one binary, spec-first APIs, and queue-native handover that makes AI the default answer and humans the well-briefed fallback.
