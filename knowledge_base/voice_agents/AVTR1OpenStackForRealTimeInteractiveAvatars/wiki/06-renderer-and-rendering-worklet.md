# Renderer and rendering worklet
**In one sentence:** The renderer turns each five-frame motion request into video with cached LivePortrait appearance (TensorRT engines, Euler flow sampling with noise truncation, per-region classifier-free guidance, ~0.64 MB session state) while the rendering worklet drives it continuously with lead time Tlead = 100 ms, fusing each frame with its 40 ms of avatar speech at the source.
## Key points
- Renderer role: registers the source portrait once, then per request predicts a motion chunk, renders it with cached LivePortrait appearance, and returns the updated state for the next request.
- Session init: face detector + two landmark models define the crop; LivePortrait motion extractor gives source motion parameters, appearance extractor gives the cached volumetric feature; source frame, crop transform, pasteback mask, and source motion (the reference condition) are cached.
- Audio context bridging: per motion chunk both channels are batched into one encoder call; 5 present + 5 future features are kept, 3 past outputs dropped as cached; 75 cached features prepended so the motion window spans 75 past / 5 present / 5 future per stream; present features cached after generation while future features are recomputed next step — encoder input stays a fixed 13-frame window.
- Flow sampling: progressive noise with correlation α = 2 plus truncation τ = 1.2 (each coordinate bounded to [−τ, τ] with the interval depending on the preceding noise value, preserving correlation); Euler ODE solver with four model evaluations per chunk; truncation visibly suppresses extreme deformations/rotations (Figure 4).
- Classifier-free guidance: past-only latent as baseline; four combinations batched per solver step (past alone, + self audio, + other audio, + reference); per-region weights scale the three residuals (Equation 9); the released API uses one value per condition across all four regions.
- Rendering path: de-normalize 42-dim motion, axis-angle → rotation matrix, combine with source-held parameters into driving keypoints; LivePortrait stitching network refines from source keypoints; warp cached appearance, decode face crop, paste back; MODNet alpha matte blends avatar with background.
- Session state (~0.64 MB): 75-frame motion history (first request repeats source motion), 75 frames dual-stream audio features, 120 ms past audio per channel, final noise frame; kept on-GPU in-process, serialized between requests in the HTTP API; the renderer itself holds no state — each request receives what the previous one returned.
- TensorRT runtime: audio encoder engine once with batch 2 (self+other in parallel); motion generator split into encoder + decoder engines with only the decoder run 4× for ODE integration; LivePortrait Appearance Warping + Stitch at effective batch 5 in parallel, Face Decoder + MODNet per frame at batch 1; source motion extractor once in fp32 ONNX at init; single CUDA stream, no CPU sync; fp16 everywhere except fp32 normalization layers.
- Per-GPU performance (Table 2, per five-frame/200 ms chunk): L40S 71 ms (2.81×, TTFF 42 ms), A100 91 ms (2.20×, TTFF 54 ms), RTX 4060 Ti 162 ms (1.24×, TTFF 99 ms), RTX 3070 180 ms (1.11×, TTFF 94 ms), L4 202 ms (0.99×), RTX 3060 Ti 207 ms (0.97×), RTX 4060 232 ms (0.86×); real-time factor = 200 ms / request duration.
- Rendering worklet loop: per iteration pulls present+future windows for both streams from the schedulers, issues the renderer request immediately after, publishes five frames to the bus; pairs each frame with its 40 ms of present-window avatar speech before publication (sync at the source); stamps frames on the media timeline spaced 40 ms apart.
- Lead time: each request starts Tlead ahead of its frames' transport departure; Tlead = 100 ms covers renderer TTFF on the authors' hardware (later frames need only per-frame decode and follow at sub-40 ms gaps); at most one chunk of rendered-but-unplayed video is held — earlier adds delay every reply pays, later leaves no inference-variation margin; an adaptive 99th-percentile-TTFF variant is suggested.
- Liveness: the loop never blocks under normal conditions because schedulers always have a window pair ready; a mid-segment scheduler block delays the request and the miss surfaces as a clock-absorbed pause, not added response latency.

## Request timing shape
First frame arrives after the longer TTFF (one-shot motion generation dominates); remaining four follow at shorter per-frame-decode intervals, each still ahead of its own play moment, with the last frame's play time as the hard bound.
