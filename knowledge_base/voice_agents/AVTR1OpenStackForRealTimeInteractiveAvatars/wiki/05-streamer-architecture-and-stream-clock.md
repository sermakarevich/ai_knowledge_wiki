# Streamer architecture and stream clock
**In one sentence:** The streamer closes the gap between chunk-based generation and a live video call with three worklets (transport, conversation engine, rendering worklet) communicating only through a type-routed event bus, synchronized to a shared stream clock that absorbs inference overruns by shifting the media timeline instead of skipping or accelerating frames.
## Key points
- Gap statement: renderer accepts fixed-size audio chunks and returns five frames per request, interprets no speech, and generates no speech; a video-call experience needs constant-rate frames, voice-agent integration, bounded reply delay, and instant barge-in response — plus continuous generation during silence so the model exhibits trained reactive listening instead of freezing.
- Architecture: three parallel worklets — transport (user-facing comms, jitter-free delivery, ships as direct WebRTC peer), conversation engine (adapts a voice agent: ASR-LLM-TTS pipeline or end-to-end speech-to-speech; ships OpenAI Realtime API and Cartesia Line adapters sharing only published events), and rendering worklet (holds one speech scheduler per stream, drives the renderer, returns fused audio-video frames) — connected only by a type-routed event bus with per-consumer queues, so engine and transport are replaceable without touching the render loop.
- Speech streams: two independent streams (user mic audio → voice agent + model's other channel; avatar reply → model's self channel + user playback); each is non-overlapping segments of start marker + variable-sized fragments + end marker, with fragments arriving no slower than real time within a segment and arbitrary gaps between segments.
- Stream clock: per-session media timeline with two operations (sleep until a deadline; measure overrun past a deadline); accumulated overruns shift the reported timeline right so deadlines computed before an overrun stay valid and no worklet ever discovers itself late.
- Transport worklet: publishes mic audio as a speech stream segmented by data availability (no VAD — a gap means no audio available, not user silence); releases fused frames at media timestamps at constant 25 fps; starts the clock on first delivered frame so setup/inference warm-up costs nothing on the timeline; on late frames absorbs the overrun into the clock (visible as a pause of exactly that duration) and never skips or accelerates — every sample eventually plays.
- Conversation engine: forwards user audio to the voice agent, publishes replies as segments, forwards interruption requests; relies on the voice agent for turn-end and barge-in decisions.
- Control plane: session start/stop, user presence, and similar events ride the same bus with control-plane worklets attached exactly like media-path worklets.
---
## Design consequences
Because audio and video are fused at the source with media timestamps (see the rendering-worklet page), downstream components never re-derive sync from separately timestamped streams; because the clock absorbs overruns, repeated delays grow a timeline offset rather than compounding latency.
