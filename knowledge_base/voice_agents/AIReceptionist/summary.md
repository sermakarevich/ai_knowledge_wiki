# AI Receptionist -- Open Source, Self-Hosted, No Compromises

**Article:** [AI Receptionist -- Open Source, Self-Hosted, No Compromises](https://github.com/kirklandsig/AIReceptionist) — GitHub, 2026-06-03

## Human Readable TL;DR

Imagine replacing a $200–500 per month robotic phone-answering service with a free, do-it-yourself receptionist that lives on your own server and sounds almost human. AIReceptionist does this by plugging your business phone line, through LiveKit and a SIP provider like Twilio or Telnyx, directly into OpenAI's Realtime speech-to-speech model instead of chaining together separate transcription, chatbot, and voice-synthesis steps like most competitors do. You configure each business with a simple YAML file covering greeting, hours, FAQs, call routing, and voice, and one running agent can answer for many different phone numbers at once. The catch is that you pay OpenAI per minute of talk time and you host everything yourself, so it trades a flat SaaS bill for metered API usage plus full control of your caller data and code.

## TL;DR

AIReceptionist is a production-grade but actively developed open-source, self-hosted AI phone receptionist built on OpenAI's Realtime speech-to-speech API (gpt-realtime-2.1) with LiveKit plus SIP trunking for inbound calls, positioned as a drop-in replacement for SaaS receptionists such as Bland AI, Vapi, Retell AI, Smith.ai, and Ruby. It ships with working voice conversations, FAQ answering, call transfers, message taking, noise cancellation, after-hours handling, and recording/transcripts, licensed under AGPL-3.0 with caller data kept on operator infrastructure. A critical 2026-06-03 change notes that OpenAI sunset the Realtime Beta API, so deployments must authenticate with a standard `sk-...` API key (`voice.auth.type: api_key`, `voice.model: gpt-realtime-2.1`) because the ChatGPT/Codex OAuth path now connects but yields silence. Configuration is per-business YAML with multi-business, multi-language, retention, Google Calendar booking, and flexible message/recording delivery, at an estimated metered cost of ~$0.20–0.30 per minute of conversation with no platform fee.

## Problem & Motivation

The project starts from frustration with typical SaaS AI receptionists that cost $200–500 per month yet still sound robotic, respond in one to three seconds, interrupt callers, and handle turn-taking awkwardly because they cascade separate speech-to-text, language-model, and text-to-speech stages. On top of the quality gap, those services create vendor lock-in through proprietary platforms and dashboard-only customization while storing sensitive caller data on third-party servers. AIReceptionist is motivated by the arrival of OpenAI's Realtime speech-to-speech model, the same technology behind ChatGPT Advanced Voice, which promises sub-second responses and model-native turn-taking with near-human fidelity. The goal is therefore to give small and medium businesses a self-hosted, fully customizable, no-platform-fee alternative where metered OpenAI usage replaces the SaaS subscription and the operator keeps the data, the source code, and the routing logic.

## Main Original Ideas

1. **Direct speech-to-speech receptionist stack:** instead of building another STT-to-LLM-to-TTS pipeline, the project wires the phone system straight into OpenAI's Realtime API for native listening, reasoning, and speaking with natural interruptions and pauses. This design choice is presented as the core quality differentiator, trading the simplicity of cascaded components for the low latency and conversational feel of a single multimodal model connected via LiveKit and SIP.

2. **One agent process for many businesses via per-number YAML:** a single running agent serves multiple businesses by mapping each inbound number through SIP dispatch-rule metadata to its own config file under `config/businesses/`, with sections for business info, voice, greeting, personality, hours, routing, FAQs, and messages. This makes multi-tenancy a configuration pattern rather than separate accounts or deployments, which directly addresses the cost and operational overhead of running receptionists for several storefronts or clients.

3. **Operator-owned telephony, messaging, and storage plumbing:** the project standardizes the unglamorous but essential receptionist work — SIP origination URIs with REFER support, `tel:{number}` transfers with an overridable `sip.transfer_uri_template` for non-standard trunks like Asterisk chan_sip, file/email/webhook message channels with background retries and failure quarantine, local or S3 recording/transcripts with consent preambles, retention sweeps, and Google Calendar availability and booking tools — into declarative YAML plus CLI helpers. The emphasis is on reliability and self-hosting rather than novelty, so a small office can reproduce a full front-desk workflow without surrendering data or logic to a vendor.

## Key Findings

The snapshot describes a working system rather than an experiment: voice conversations, FAQ answering, transfers, message taking, LiveKit noise cancellation, after-hours detection, multi-language handling with auto-detection in gpt-realtime-2.1, and calendar booking with spoken confirmation are all listed as functional, though the project warns of active development with breaking changes and rough edges. Deployment requires Python 3.11+, an OpenAI API key with Realtime access, a LiveKit server, and a SIP trunk with a phone number, and the 2026-06-03 Realtime Beta sunset is called out as a hard requirement to use `api_key` auth since `oauth_codex` no longer authenticates Realtime. Economics are metered at roughly $0.20–0.30 per minute, with worked examples from about $5 per day for a small office to about $22 per day for a busy front desk, which the project frames as comparable or lower than SaaS for typical volumes while delivering clearly better voice quality and full ownership. Community traction includes at least one external contribution credited for the Asterisk transfer-URI fix, and the AGPL-3.0 license is explicitly chosen to allow free use and self-hosting while requiring hosted-service modifications to be shared back.

## Suggestions & Future Directions

The implied direction is stabilization and operational hardening of what already works, since the repository itself flags breaking changes and rough edges while core calling features are in place. Natural extensions from the wiki material include broader language whitelists beyond the documented English, Spanish, and French primary/allowed pattern, richer calendar and CRM integrations beyond the current Google Calendar service-account/OAuth booking flow, and more resilient messaging and retention operations around the existing retry, `.failures/`, and sweep tooling. Operators also need continued attention to telephony edge cases, as shown by the Asterisk `sip:{number}` override, plus clearer migration guidance after the Realtime Beta sunset so new deployments default to API-key auth and supported models. Longer term, the cost framing suggests a need for usage monitoring and guardrails, because per-minute billing can exceed flat SaaS fees at high volumes even as quality and control remain the project's main selling points.
