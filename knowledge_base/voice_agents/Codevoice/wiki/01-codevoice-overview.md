# CodeVoice: AI-Powered Technical Interview Simulator
**In one sentence:** CodeVoice is a real-time voice-to-voice AI interviewer that routes browser audio through LiveKit to a Pipecat pipeline (Deepgram STT/TTS + Krutrim LLM) backed by a Django control plane.
## Key points
- Service-oriented architecture with three layers: browser client (`test_room.html` + LiveKit client over WebRTC), LiveKit server router (Docker, port 7880), AI bot pipeline (`src/apps/simulation`), and Django control plane (user management, sessions, PostgreSQL, Celery + Redis task queue).
- Bot voice pipeline is a 7-stage Pipecat assembly line: `transport.input()` → STT → user aggregator → LLM → TTS → `transport.output()` → assistant aggregator, passing AudioRawFrame, TranscriptionFrame, TextFrame, LLMMessagesFrame, and TTSAudioRawFrame between stages.
- Speech services are Deepgram for both STT (default streaming model) and TTS (voice `aura-helios-en`); the brain is Krutrim AI (OpenAI-compatible) with model `gpt-oss-120b` at endpoint `https://cloud.olakrutrim.com/v1`.
- Turn detection uses `LocalSmartTurnAnalyzerV3` (ONNX) via `TurnAnalyzerUserTurnStopStrategy` to distinguish natural vs. thinking pauses using silence, speech patterns, and end-of-sentence markers, so the LLM is only triggered when the candidate is done speaking.
- Conversation memory is a full `LLMContext` message list (system → assistant → user → assistant) sent to the LLM each turn, enabling greetings, follow-ups, and contextual evaluation.
- Two LiveKit tokens gate the room `interview-room-1`: bot token (identity `ai-interviewer`, generated by `run_bot.py`) and user token (identity `human-candidate`, generated by `get_user_token.py`), each with join plus publish/subscribe audio permissions.
- Browser connection persistence quirk: an open `test_room.html` tab keeps its old LiveKit connection alive, so the page must be refreshed after restarting the bot, regenerating a token, or changing room configuration.

## Complete Interaction Flow
**Covers:** Bot initialization, user join, conversation loop

### Phase 1: Bot Initialization (`python src/manage.py run_bot`)
- Management command (`run_bot.py`): generates bot token via LiveKit API keys; bot identity `ai-interviewer`; room name `interview-room-1`; calls `run_ai_bot(ws_url, token, room_name)`.
- Bot startup (`bot.py` → `run_ai_bot()`): initializes STT (Deepgram, default streaming model, audio → text in real-time), LLM (Krutrim AI, OpenAI-compatible, model `gpt-oss-120b`, endpoint `https://cloud.olakrutrim.com/v1`), TTS (Deepgram, voice `aura-helios-en`, text → natural audio); creates `LiveKitTransport` participant connection with audio input/output; builds the 7-stage pipeline shown above.
- Bot status: connected to room, waiting for participants.

### Phase 2: User Joins the Interview (`test_room.html` → Connect)
- Browser: requests microphone permission, connects with user token, publishes local microphone audio track.
- LiveKit routing: notifies bot ("New participant joined!") and establishes bidirectional audio stream.
- Bot handler fires:
```python
@transport.event_handler("on_first_participant_joined")
async def on_first_participant_joined(transport, participant):
    logger.success(f"👤 User joined: {participant}")
    messages.append({
        "role": "system",
        "content": "Greet the candidate and ask the first technical interview question."
    })
    await task.queue_frames([LLMMessagesFrame(messages)])
```
- Result: system instruction → Krutrim LLM → greeting plus first question (e.g. *"Hello! I'm your AI interviewer. Let's begin. Can you explain the difference between a process and a thread?"*) → TTS → audio streamed to browser.

### Phase 3: The Conversation Loop
- Repeating 8-step loop: (1) candidate speaks into microphone (e.g. "A process has its own memory space, while threads..."); (2) browser → LiveKit real-time audio packets; (3) LiveKit → bot `transport.input()` raw audio frames; (4) Deepgram STT real-time transcription; (5) user aggregator with `LocalSmartTurnAnalyzerV3` analyzes silence, speech patterns, and natural pauses and waits for turn end ("User stopped talking"); (6) Krutrim LLM consumes system prompt + conversation history + latest transcript and returns evaluation plus follow-up (e.g. "That's correct! Processes are isolated. Can you explain why thread synchronization is important?"); (7) Deepgram TTS synthesizes `aura-helios-en` audio; (8) bot → LiveKit → browser playback.

## Key Technical Components
**Covers:** Turn detection system, context management, Pipecat pipeline

### 1. Turn Detection System
- Purpose per source: "Prevents the bot from interrupting you mid-sentence."
```python
user_params=LLMUserAggregatorParams(
    user_turn_strategies=UserTurnStrategies(
        stop=[
            TurnAnalyzerUserTurnStopStrategy(
                turn_analyzer=LocalSmartTurnAnalyzerV3()
            )
        ]
    )
)
```
- Mechanism: `LocalSmartTurnAnalyzerV3` (specialized ONNX AI model) analyzes audio patterns in real time — natural vs. thinking pauses, end-of-sentence markers, silence duration — and only triggers the LLM when confident the user finished, preventing awkward interruptions.

### 2. Context Management (Conversation Memory)
```python
messages = [
    {
        "role": "system",
        "content": "You are an AI technical interviewer..."
    }
]
context = LLMContext(messages)
```
- Mechanism: full history retained; each turn appends user speech as "user" and AI reply as "assistant"; the LLM sees the entire conversation each call.
- Example flow:
```json
[
  {"role": "system", "content": "You are an AI interviewer..."},
  {"role": "assistant", "content": "Hello! What is a process?"},
  {"role": "user", "content": "A process is an instance of a program..."},
  {"role": "assistant", "content": "Correct! Now explain threads..."}
]
```

### 3. The Pipecat Pipeline (Data Flow)
- Described as "a factory assembly line for audio/text processing" with the same 7 stages; frame types flowing through: AudioRawFrame (raw audio), TranscriptionFrame (STT text), TextFrame (LLM text), LLMMessagesFrame (context updates), TTSAudioRawFrame (synthesized speech); each processor receives frames from the previous stage, processes them, and outputs new frames downstream.

## Token System
**Covers:** Two-token design and browser connection persistence

| Token | Identity | Generated by | Permissions |
|---|---|---|---|
| Bot token | `ai-interviewer` | `run_bot.py` (automatic at bot start) | Join room, publish/subscribe audio |
| User token | `human-candidate` | `get_user_token.py` (needed for browser connect) | Join room, publish/subscribe audio |

> **Key Insight**: If your browser tab (`test_room.html`) remains open, it maintains the LiveKit connection even with an old token. This is why the bot was responding before you updated the token - the browser was still connected from a previous session!
- Fix: always refresh the browser page after restarting the bot, generating a new token, or changing room configuration.
