# CodeVoice: AI-Powered Technical Interview Simulator

**Article:** [CodeVoice](https://github.com/Raihan2511/codevoice) — GitHub

## Human Readable TL;DR

CodeVoice is like a flight simulator for job interviews: instead of rehearsing answers in your head, you sit down with a robot interviewer that talks to you out loud, listens to your answers, and fires back follow-up questions in real time. Under the hood it works like a telephone exchange wired to a factory assembly line, where your voice travels from the browser through a central audio router and then down a chain of AI stations that transcribe your speech, think up a reply, and speak it back to you. A clever pause-detector acts like a polite conversation partner, waiting until you have genuinely finished your sentence before the bot jumps in, so the exchange feels like a natural phone call rather than a walkie-talkie. Around this voice loop sits an ordinary web backend that keeps track of users, interview sessions, and scores, making the whole thing feel like a small rehearsal studio with a tireless interviewer on call.

## TL;DR

CodeVoice is a real-time, voice-to-voice AI technical interview simulator that routes browser audio through a LiveKit server into a Pipecat streaming pipeline (Deepgram STT and TTS plus a Krutrim-hosted LLM) backed by a Django control plane with PostgreSQL and Celery plus Redis. The documented architecture splits into a browser client (`test_room.html` with the LiveKit client over WebRTC), a LiveKit audio and video router, an AI bot pipeline in `src/apps/simulation`, and Django services for user management, sessions, and orchestration. The bot runs a seven-stage pipeline from audio input through transcription, turn-aware aggregation, LLM reasoning, and speech synthesis back to audio output, with full conversation history retained in an `LLMContext` message list each turn. Sessions are orchestrated with two LiveKit tokens in the room `interview-room-1` (bot identity `ai-interviewer`, user identity `human-candidate`), launched via the `run_bot` and `get_user_token` Django management commands, and the wiki additionally documents the interviews and users data models, environment and Docker Compose setup, troubleshooting, and a roadmap toward orchestration APIs, dashboards, and richer evaluation.

## Problem & Motivation

Technical interview preparation is difficult to make realistic because static question lists and text chatbots miss the pressure, pacing, and spoken dynamics of a real interview, while human mock interviews are expensive and hard to schedule. CodeVoice is motivated by this gap: it aims to provide an always-available voice interviewer that greets candidates, asks technical questions aloud, listens to spoken answers, and responds with evaluations and follow-ups in a continuous conversation. The choice of voice-to-voice interaction rather than plain text reflects the belief that spoken fluency, turn-taking, and real-time comprehension are central skills worth rehearsing, which pushes the design toward low-latency streaming audio, careful turn detection so the bot does not interrupt mid-sentence, and persistent conversation memory so each reply builds on what the candidate actually said.

## Main Original Ideas

1. **Three-layer voice interview stack:** the system separates concerns into a browser WebRTC client for audio capture and playback, a LiveKit server router that shuttles real-time audio between participants, and a Pipecat AI bot backed by a Django control plane handling user management, sessions, PostgreSQL persistence, and a Celery plus Redis task queue.
2. **Streaming voice-to-voice pipeline:** the core loop chains audio input through Deepgram streaming STT, a user aggregator, a Krutrim-hosted LLM (`gpt-oss-120b` at an OpenAI-compatible endpoint), and Deepgram TTS (voice `aura-helios-en`) back to audio output, with typed frames (raw audio, transcription, text, LLM message, and synthesized-speech frames) flowing between seven pipeline stages like an assembly line.
3. **Turn-aware aggregation:** the user aggregator pairs with a `LocalSmartTurnAnalyzerV3` ONNX model via a turn-stop strategy that analyzes silence, speech patterns, and end-of-sentence markers to distinguish natural from thinking pauses, so the LLM is triggered only when the candidate has genuinely finished speaking.
4. **Bot-first room orchestration:** each session follows a scripted startup in which the bot connects first via `python src/manage.py run_bot` (generating the `ai-interviewer` token and building the pipeline), the candidate then joins from the browser with a separately minted `human-candidate` token, an `on_first_participant_joined` handler greets the candidate and queues the opening question, and an `on_participant_left` handler cleans up on disconnect; the wiki also notes the operational quirk that an open browser tab keeps its old LiveKit connection alive, so the page must be refreshed after bot restarts or token changes.

## Key Findings

The wiki describes a coherent, runnable prototype organized around a repeating eight-step conversation loop: the candidate speaks into the microphone, audio packets travel through the browser and LiveKit into the bot, Deepgram transcribes the speech in real time, the turn analyzer waits for the end of the turn, the Krutrim LLM consumes the system prompt plus full conversation history and returns an evaluation with a follow-up, Deepgram synthesizes the reply, and the audio streams back to the browser for playback, illustrated with an example exchange about processes versus threads. The simulation app is identified as the heart of the AI functionality, with `run_ai_bot(room_url, token, room_name)` owning service initialization, transport creation, pipeline construction, event handling, and context management, supported by two thin management commands for launching the bot and minting user tokens. Persistence is modeled with a `Question` bank (text, EASY/MEDIUM/HARD difficulty, expected key points), an `InterviewSession` state machine (`Started` to `Completed`/`Failed` with user, total score, and timestamps), and per-exchange `InterviewTurn` records (session, question, AI message, user transcript, audio file, and a 0–10 score), while authentication hardens a custom Django user model with UUID primary keys against ID enumeration. Setup is documented end to end from Docker Compose services (Postgres, Redis, LiveKit) and eight environment variables through dependency installation, migrations, bot launch, token generation, and browser connection, alongside troubleshooting guidance for unresponsive bots, failed connections, missing audio, and premature interruptions.

## Suggestions & Future Directions

The wiki's own roadmap points first toward an orchestrator API with REST endpoints for starting and stopping interviews under programmatic control, plus WebSocket integration for live status updates, transcription display, and score visualization. A second strand calls for a frontend dashboard with login and registration, interview history, performance analytics, and question-bank management, complemented by recording and playback support so sessions can be saved, reviewed, and exported as transcripts. A third strand targets deeper evaluation, including automatic scoring against expected key points, code execution for programming questions, and multi-turn follow-up questioning, which together would move the project from a working conversational loop toward a genuinely instructive coaching tool.
