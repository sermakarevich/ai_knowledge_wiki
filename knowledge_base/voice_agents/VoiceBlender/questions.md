# Retrieval Practice: VoiceBlender/voiceblender

### Q1. What is VoiceBlender at a high level, and which defaults does it listen on?
> [!tip]- Answer
> VoiceBlender is a Go service that bridges SIP and WebRTC voice calls with multi-party audio mixing, a REST API, and real-time webhooks. The REST API listens on `:8080` by default and SIP on `127.0.0.1:5060` by default. See [[wiki/01-overview|Overview]].

### Q2. Which SIP capabilities and non-SIP leg types does VoiceBlender support?
> [!tip]- Answer
> SIP supports inbound/outbound calls with codec negotiation (PCMU, PCMA, G.722, Opus, AMR-WB, AMR-NB), digest auth, RFC 4028 session timers, optional TLS, 183 early media, and hold via re-INVITE. Other legs include WebRTC with trickle ICE, WhatsApp Business Calling over SIP-TLS with DTLS-SRTP and Opus, WebSocket legs with binary or `json_base64` framing, and experimental MoQ legs disabled by default. See [[wiki/01-overview|Overview]].

### Q3. How do rooms mix audio, bridge, and route by role?
> [!tip]- Answer
> Rooms mix N participants with mixed-minus-self audio at 8, 16, or 48 kHz (default 16 kHz). Two same-rate room mixers can be bridged with live-configurable direction, and a free-form `role` tag plus a who-hears-whom matrix controls routing atomically at leg-join time. See [[wiki/01-overview|Overview]].

### Q4. Which media and AI features sit on top of calls, and how are events delivered?
> [!tip]- Answer
> The media layer covers RFC 4733 DTMF, T.140 RTT, stereo WAV recording with pause/resume and S3/GCS upload, WAV/MP3 playback, named-provider TTS/STT, AI agents, and AMD with optional beep detection. Events are delivered via HMAC-SHA256 webhooks with `event_id`/`X-Event-Id`, the `GET /v1/vsi` WebSocket stream, and Prometheus metrics at `GET /metrics`. See [[wiki/01-overview|Overview]].

### Q5. What is the async rule in `API.md`, and what does the leg object plus `custom_data` look like?
> [!tip]- Answer
> Every endpoint triggering a SIP request validates synchronously, then queues the work and returns `202 Accepted` with a progressive status like `holding` or `ringing`, with outcomes reported via `leg.*` events or `leg.command_failed`. The leg object carries `id`, `type`, `state`, `room_id`, `muted`, `deaf`, `held`, `role`, headers, and `custom_data`, which is arbitrary JSON echoed on events and capped by `CUSTOM_DATA_MAX_BYTES` (default 1024). See [[wiki/02-top-level-files|Top-level-files]].

### Q6. How are `openapi.yaml` and `asyncapi.yaml` generated, and what workflow does `CLAUDE.md` mandate?
> [!tip]- Answer
> `openapi.yaml` (OpenAPI 3.1.0) is generated by `cmd/openapi-gen` from `RoutesMetadata()` in `internal/api/openapi_meta.go`, and `asyncapi.yaml` (AsyncAPI 3.0.0 for VSI on `/v1/vsi`) by `cmd/asyncapi-gen` from registries in `internal/api/vsi_meta.go`; neither is hand-edited. `CLAUDE.md` mandates `gofmt`, `make openapi`/`make asyncapi`/`make specs`, doc and env-template sync, unit plus `tests/integration/` tests, no API churn, and never running `git commit`. See [[wiki/02-top-level-files|Top-level-files]].

### Q7. Should a team adopt VoiceBlender for a production voice-AI product given its auth model and configuration approach?
> [!tip]- Answer
> Recommend it only if the team fronts the HTTP surface (REST, VSI, `/metrics`) with a reverse proxy or strict network placement, since access is gated solely by the `ALLOWED_IPS` allowlist with no credential auth. Its env-var-only configuration, generated API specs, and loopback integration tests make it operable and contract-stable, so the deciding factor is whether the team accepts owning edge authentication. See [[wiki/01-overview|Overview]].
