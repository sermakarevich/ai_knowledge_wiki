# A frontend-backend architecture for tool calls in full-duplex speech models

**Paper:** [A frontend-backend architecture for tool calls in full-duplex speech models](https://arxiv.org/pdf/2609.19334)

## Human Readable TL;DR

Imagine a friendly restaurant host who greets you instantly, listens while you hesitate and interrupt, but never cooks — the moment you ask about the specials or the bill, the host flashes a silent signal to the kitchen, says "let me pull that up," and waits while the chefs look everything up. This paper builds exactly that split for voice AI: a fast-talking speech frontend handles the natural back-and-forth conversation, and the moment a question needs facts or tools (like checking the weather), it raises a flag and hands the transcript to a knowledgeable text assistant in the back room. The back-room expert does the multi-step tool work and slips the written answer back onto the host's cue card, which the host then reads aloud as if it knew it all along. The result is a voice agent that stays warm and responsive while borrowing the brains of a much stronger tool-using model.

## TL;DR

The paper proposes a modular frontend-backend architecture that gives full-duplex speech-to-speech interaction strong agentic tool-call ability without forcing the speech model to internalize tool use. A duplex speech-to-text frontend (600M-parameter Parakeet streaming encoder plus NVIDIA Nemotron-Nano-9B-v2-Base backbone with joint user/agent-text decoding and streaming TTS) learns a delegation signal: when user speech needs a tool, the agent-text channel fires `<tc bos>` (replacing the regular agent-turn token, usually ~320 ms after user-turn end), produces a short filler (~1 s, e.g. "Give me a moment"), then `<tc eos>`, stays silent while the endpointed streaming ASR transcript is routed to a LangGraph ReAct text backend that runs multi-round tool calls with thread-keyed multi-turn state. The backend's natural-language answer is then prefilled back into the frontend's agent-text channel enclosed in `<pf bos>`/`<pf eos>` (~1 s after `<tc eos>` to simulate execution time), and the frontend is trained to repeat it exactly from `<agent bos>` before resuming normal duplex behavior, with prefill/pad/silence regions masked from the loss. Trained on ~530k hours pretraining, 111k hours SFT, ~16k hours ASR transcription and 8.5k hours of multi-turn tool-call speech data, the system reaches 92–97% frontend tool-call token recall and 81.2% irrelevance rejection, scores ~74.6% average on spoken BFCL with a Qwen3-30B-A3B backend, and with a larger Qwen3-235B-A22B backend reaches competitive Full-Duplex-Bench-V3 response quality and EVA-Bench results comparable to Gemini-class models while preserving turn-taking.

## Problem & Motivation

Full-duplex speech-to-speech models speak directly in the speech modality, which removes cascade latency and preserves paralinguistic cues with natural turn-taking and barge-in, but their tool-call ability as voice agents lags far behind text agents that already reliably decide when and how to invoke tools, query knowledge bases, and act on the world. The paper quantifies this with τ-Voice: leading commercial duplex voice models complete only 31–51% of grounded customer-service tasks under clean conditions versus 85% for text agents such as GPT-5 on corresponding text-mode tasks, with the gap widening further under realistic noise and accented speech. This frames the central design question of whether duplex speech models should directly internalize tool-call capabilities or instead delegate them to a backend text agent that already benefits from mature instruction following, tool calls, and long-horizon reasoning. The authors argue that audio-native modeling imposes a fundamental capacity tradeoff (audio tokens consuming modeling capacity), whereas a delegation-style backend agent is more modular and consumes little modeling capacity from the frontend speech model, concluding that backend delegation is an effective and modular way to combine natural duplex speech interaction with strong agentic tool-call capabilities.

## Main Original Ideas

1. **Delegation-token signaling in the agent-text channel** — Instead of internalizing tool syntax, the frontend learns a minimal control-token protocol: `<tc bos>` replaces the regular `<agent bos>` when a tool is needed, followed by a short filler and `<tc eos>`, which at inference time triggers sending the `<user eos>`-endpointed streaming ASR transcript to the backend while agent output is suppressed with pad tokens. This imposes minimal changes on the frontend duplex model by adding only a tool-call control token to its prediction targets.
2. **Prefill-and-repeat result integration** — The backend's natural-language tool response is enclosed in `<pf bos>`/`<pf eos>` and prefilled into the agent-text channel, and the frontend is trained to reproduce it exactly starting from `<agent bos>`; tool-call tokens, filler, and reproduced regions contribute to the loss exactly like regular agent text while prefill regions are masked and excluded. This lets the frontend speak answers it never had to reason out itself.
3. **Duplex speech-to-text frontend with joint decoding** — The frontend takes user speech encoding, agent text, and streaming user ASR transcripts as inputs, using the Parakeet streaming encoder feeding the Nemotron backbone with a separate ASR embedding/prediction head sharing the same backbone, so a single decoding pass jointly produces user and agent text, connected to VoiceChat-TTS with explicit turn-start and interruption control tokens for incremental codec-based speech generation.
4. **LangGraph ReAct backend with graceful fallback** — The backend is a LangGraph tool-augmented ReAct agent implemented as a state machine over a running message list with an instruction-following LLM agent node, a tools node, a conditional edge routing to tool execution whenever calls are emitted, and a thread-keyed checkpointer maintaining multi-turn state so each turn needs only the current transcript; syntactically invalid tool requests or plain-text replies are returned directly as prefill, so the larger backend reliably falls back to natural-language explanations when the frontend misfires on irrelevant queries.
5. **Large-scale tool-call speech training pipeline** — Frontend training uses pretraining plus supervised fine-tuning where text dialogues (covering when to call a tool, when to ask follow-ups, when not to call an unavailable tool, plus backchannels, pauses, and interruptions) are generated by models such as Nemotron 3 Nano, Gemma-4-31B-IT, and Qwen3.5-397B-A17B, LLM-judge filtered, audiofied with VoiceChat-TTS/Chatterbox diverse voices after dropping math/code-heavy content, quality-filtered with Parakeet-tdt-0.6b-v2 WER/CER, and augmented with simulated airline/retail database trajectories from interacting Qwen3.5-235B-A22B pairs, with random full versus name-and-description-only tool prompts for generalization.

## Key Findings

On single-turn spoken BFCL with AST scoring, the frontend's tool-call token recall is 97.2% (Simple), 92.0% (Multiple), 95.0% (Parallel), and 93.5% (Parallel-Multiple), with 81.2% accuracy rejecting irrelevant calls, and the full 30B-backend system averages 74.6% with external ASR versus 73.0% with internal ASR, performing close to GPT-realtime on several subsets with the largest remaining gaps on Parallel-Multiple and Irrelevance, while the external-ASR gain concentrates in Parallel-Multiple (55.1% to 61.1%) and even the 7B backend substantially beats Ultravox-v0.6-8B (71.7% vs. 43.3% average, the latter scoring 0.0% on irrelevance by invoking the single offered function on every prompt). On Full-Duplex-Bench-V3 over 100 real-human scenarios with naturalistic pauses, hesitations, and self-corrections, the system fulfills 54–67% of requests with the larger Qwen3-235B-A22B backend clearly better on response quality, keeps 100% turn-taking with a high by-design filler rate ("Let me pull that up") and a high interruption rate caused by backchannels at user disfluencies ("Okay, I am here") while still listening so the eventual call usually sees the complete request. On multi-turn EVA-Bench, the 235B-backend system significantly outperforms GPT-realtime-mini and Qwen3-Omni-30B-A3B-Instruct and performs similarly to Gemini 3.1 Flash Lite, including higher airline-domain completion than GPT realtime2 (72% vs. 54%) though trailing in ITSM and Medical HR chains of 6–8 tool calls. Importantly, adding tool-call training only slightly degrades core speech behavior: turn-taking precision/recall moves 85/94 to 82/91, ASR word error rate moves 10.80% to 11.47% (attributed to mostly synthetic tool-call data), OpenBookQA/CommonEval stay roughly flat, and Full-Duplex-Bench-V1 shows more responsive smooth turn-taking with lower latency at some cost on pause handling.

## Suggestions & Future Directions

The results point to closing the remaining Parallel-Multiple and irrelevance gaps, where even the delegated system trails GPT-realtime and where more accurate external ASR already helps, suggesting joint work on ASR robustness (noise, accents) and on the frontend's delegation precision so the backend's natural-language fallback is needed less often. The high interruption rate from premature backchannels during user disfluencies and the slight regressions in pause handling, ASR accuracy, and conversational eval scores indicate that tool-call speech data should become more naturalistic and less purely synthetic, and that filler/backchannel timing deserves explicit modeling so responsiveness does not come at the cost of cutting users off. Because the framework is explicitly modular across backend LLMs, a natural direction is scaling and specializing the backend per domain (the airline vs. ITSM/Medical-HR split shows domain sensitivity on long 6–8-call chains), clarifying the delegation signal and background-frontend interaction relative to concurrent KAME, MoshiRAG, Thinking-Machines, Qwen-audio-agent, and GPT-Live designs, and stress-testing the prefill-and-repeat handoff under streaming errors and longer multi-turn state.
