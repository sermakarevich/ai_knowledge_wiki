# Retrieval Practice: Realtime-Venus: A full-duplex interaction system with asynchronous delegation

### Q1. What is Realtime-Venus at a system level — which two models does it provide and how does the dual-loop runtime work?
> [!tip]- Answer
> Realtime-Venus provides two separately trained 9B models: Realtime-Venus-Omni for audio–visual interaction and Realtime-Venus-Audio for spoken interaction, each a complete conversational frontend with continuous perception, conversational control, and native speech generation. A dual-loop runtime keeps foreground interaction live while Realtime-Venus-Harness executes delegated tasks asynchronously and returns results into the ongoing dialogue. Both models share one post-training recipe mixing offline understanding, proactive full-duplex trajectories, and delegation workflows. See [[wiki/01-overview-full-duplex-system|Realtime-Venus: A Full-Duplex Interaction System with Asynchronous Delegation — Overview]].

### Q4. Why does the introduction frame live dialogue and background computation as a timescale-mismatch problem, and how does Realtime-Venus-Harness resolve it?
> [!tip]- Answer
> Continuous interaction and external computation run on different timescales: a background task needs a stable request record plus evidence, but its result must be interpreted in a conversation that may have changed during execution. Realtime-Venus-Harness binds each delegation request to its originating session plus an evidence snapshot, executes registered capabilities asynchronously while the frontend keeps interacting, and returns eligible results via freshness checks and playback-aware delivery. The frontend then interprets the returned information against possibly changed user intent. See [[wiki/04-introduction|Introduction: natural interaction with asynchronous delegation]].

### Q5. Which two prior systems does the related-work chunk cite for asynchronous tool use, and how does Realtime-Venus position its own delegation interface?
> [!tip]- Answer
> It cites GPT-Realtime (OpenAI, 2025) for asynchronous function calling and NemotronLabs VoiceChat (NVIDIA, 2026) for a separate output channel for tool-calling scripts. Realtime-Venus instead studies a private delegation interface shared by both separately trained frontends: the frontend handles live interaction and speech via Thinker–Talker while the harness fixes evidence at the request boundary, executes capabilities, and returns prepared replies to the originating session. The interaction loop is continuous and latency-sensitive while the capability loop runs on demand over longer durations. See [[wiki/05-related-work|Related work]].

### Q6. What is the shared per-second runtime transition (Eq. 1), and how do the two frontends differ in inputs and implementation?
> [!tip]- Answer
> Both frontends run the causal transition (s_{k+1}, O_k) = F_m(s_k, x^m_k, b_k; η_k), where only foreground text Y_k and speech tokens S_k of O_k = (c_k, Y_k, D_k, S_k) are user-facing and delegation text may span chunks. Media inputs are x^{audio}_k = u_k for Audio versus x^{omni}_k = (u_k, v_k) with aligned visual features for Omni, with retained state carrying context, partial spans, and previously admitted replies. Both adapt MiniCPM-o 4.5 (SigLIP2 + Whisper-Medium encoders for Omni, audio-only for Audio, Qwen3-8B backbone, discrete S3 tokens, streaming flow-matching decoder), and Omni alone adds a training-free long-video memory with motion-compensated gating, MaxSim + MAD-weighted relevance plus MMR-style novelty retrieval, and chronological reassembly. See [[wiki/06-system-overview-runtime|Unified Runtime Abstraction — Both Frontends]].

### Q7. How do the listen/speak/turn-end states, delegate/backend spans, and playback-synchronized scheduling (Eqs. 2–3) produce role-conditioned overlap handling?
> [!tip]- Answer
> Three streams share one conversational clock in one-second chunks, serialized as one <unit> per chunk with four added tokens <delegate>, </delegate>, <backend>, </backend>, while <|listen|> means perceive without speaking, <|speak|> marks active generation, and <|turn_eos|> closes a turn. Speech stays on clock via n_k = arg min_n |τ_{k-1} + D(Y_{k,1:n}) − t_k|, and the joint policy factorizes control/text/delegation (LLM) from acoustic tokens (speech decoder) per Eq. 3. Overlaps are role-conditioned: pauses and noise yield <|listen|>, short backchannels keep <|speak|>, and floor-taking interruptions emit <|turn_eos|> followed by stop/reject, repair/update, or redirect/follow-up. See [[wiki/07-interaction-control-states|Interaction-Control States and Listen/Speak Transitions]].

### Q8. What is the unified post-training recipe, and what is the only thing that differs between the Omni and Audio variants?
> [!tip]- Answer
> One unified post-training pass supports video, audio-only, and text-only inputs, mixing proactive duplex data (including speech-in queries), delegation data, and general understanding data across full-duplex and offline turn-based formats. Supervision is sparse — loss covers only response spans with per-sample normalization — and in full-duplex data covers per-second <|listen|>/<|speak|> decisions plus spoken text, with only the Thinker updated and the acoustic decoder fixed. The variants differ only in input modalities and data coverage: Omni interleaves visual plus audio tokens and uses video and audio data, while Audio keeps only audio segments and trains on the audio group. See [[wiki/08-training-recipe|4.6 Training recipe: Realtime-Venus-Omni and Realtime-Venus-Audio]].

### Q9. What are the exactly three stages of the unified data-construction pipeline, and what scale and coverage does Figure 8 report?
> [!tip]- Answer
> The pipeline has exactly three stages: scenario and interaction planning from structured seeds (setting, participants, goal, language, acoustics, target conditions), paralinguistic and acoustic realization (hesitations, laughter, breathing, secondary speakers, environmental audio in Chinese, English, and code-switching), and temporal alignment with model-specific materialization onto a shared session clock. Figure 8 reports ≈72,200 total corpus sessions with ≈1,600 h of aligned audio, split ≈36,100 Chinese and ≈36,100 English sessions under one trajectory with shared supervision for audio-only and audio-visual modalities. See [[wiki/09-data-pipeline|6.1 Unified Data Construction]].

### Q10. How does each trajectory couple a duplex target with a delegation target, and what are the fixed evaluation settings?
> [!tip]- Answer
> Each trajectory links an observed event to a duplex target (continue speaking, await input, yield the floor, stop queued output, or revise the response, chosen on conversational meaning) and a delegation target (keep simple acts local, invoke a capability for evidence/context/replanning needs, route external or executable requests to tools, possibly alongside a cancellable acknowledgment). Supervision specifies whether active work is retained, canceled, revised, reconciled, retried, or replaced by a fallback — e.g. stable-intent interruptions retain the plan while intent-changing corrections cancel and replan. Default evaluation samples video at 1 fps with at most 128 frames at ≈448×448, resamples audio to 16 kHz mono, processes full-duplex audio in one-second chunks with perception active, and generates speech at 24 kHz. See [[wiki/10-delegation-evaluation|Delegation Behavior Taxonomy and Evaluation Protocol]].

### Q12. What trade-offs do the interruption–continuation, FDB-v3 tool-use, and internal delegate-benchmark results reveal?
> [!tip]- Answer
> Realtime-Venus-Audio has the highest continuation rates for backchannels (0.97) and background speech (0.86) and ranks second to Omni for speech directed to others, yet its interruption-response rate (0.75) trails Joy-Duplex, GPT-4o, and Gemini 3.1 Live — strong continuation does not imply strong interruption handling. On FDB-v3 tool use, Omni reaches 86.0% selection F1, 53.1% argument accuracy, and 43.0% Pass@1 (Audio 82.0/52.2/42.0), both below GPT-Realtime's 87.6/68.0/60.0. On the internal delegate benchmark Omni leads overall routing 75.93% vs 68.89% (gap 7.04 points), with Audio higher on delegation recall (92.22% vs 68.33%) but far lower on non-delegation specificity (39.44% vs 84.44%), so Audio over-delegates routine requests while Omni under-delegates external ones. See [[wiki/12-full-duplex-evaluation|Full-duplex interruption–continuation trade-off evaluation]].

### Q15. Given the reported strengths (continuation, understanding, competitive tool selection) and weaknesses (interruption response, argument grounding, opposite delegation failure modes), would you recommend Realtime-Venus as the starting point for a live assistant that must take interruptions and call tools reliably?
> [!tip]- Answer
> I would recommend it as a starting point with reservations, because its dual-loop harness, role-conditioned overlap control, and strong continuation plus competitive tool selection directly address live delegation. I would not deploy it as-is for interruption-heavy or precision tool-use workloads, since interruption response trails Joy-Duplex/GPT-4o/Gemini 3.1 Live, argument accuracy and Pass@1 lag GPT-Realtime substantially, and the frontends fail oppositely (Audio over-delegates routine requests, Omni under-delegates external ones). The prudent path is to adopt the architecture and data pipeline while prioritizing interruption timing, argument grounding, and delegation calibration before production use. See [[wiki/12-full-duplex-evaluation|Full-duplex interruption–continuation trade-off evaluation]].
