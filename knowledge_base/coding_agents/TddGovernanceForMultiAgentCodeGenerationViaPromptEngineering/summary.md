# TDD Governance for Multi-Agent Code Generation via Prompt Engineering

**Paper:** [TDD Governance for Multi-Agent Code Generation via Prompt Engineering](https://arxiv.org/abs/2604.26615v1) — EASE 2026, 29 Apr 2026

## Human Readable TL;DR

Large language models write code like talented but impulsive cooks who keep improvising instead of following the recipe, so the same request can produce a different dish every time and small mistakes spread quickly when several AI cooks work together. This paper takes the classic test-driven development recipe — write the taste test first, then cook only enough to pass it, then clean up the kitchen — and turns it into strict kitchen rules enforced by a head chef. The AI chefs are only allowed to propose dishes on paper while a deterministic engine does all the actual cooking, checks each course in order, and cuts off endless re-cooking after three tries. The result is a calmer, more repeatable kitchen where discipline is built into the workflow rather than left to good intentions.

## TL;DR

The paper proposes an AI-native TDD framework that operationalizes classical Red-Green-Refactor principles as enforceable prompt-level and workflow-level governance rather than treating tests as auxiliary inputs. Classical TDD rules are distilled from a bounded Beck/Martin canon into a machine-readable JSON manifesto and distributed across planning, test generation, implementation, repair, and validation stages. A layered architecture separates non-authoritative LLM patch proposals from authoritative engine execution, enforcing phase ordering, validation gates, atomic mutation control, and bounded repair loops (N = 3 with failure-signature early termination) to improve stability and reproducibility in multi-agent code generation.

## Problem & Motivation

Modern LLM-based agents can take on complex coding tasks with role-specific agents collaborating under limited human supervision, yet they remain fundamentally non-deterministic and undisciplined in unconstrained workflows. Even identical prompts often produce different outputs, temperature zero does not guarantee consistency, and on complex benchmarks zero equal test outputs occur in up to 75.76% of cases; correct-looking code can still fail in clean environments from dependency and configuration issues. In multi-agent settings this instability compounds, because small logic errors propagate across the workflow and interaction failure modes such as incomplete answers, missing preconditions, and prompt sensitivity demand constant manual decomposition and steering.

Classical test-driven development, introduced through Extreme Programming in the formulations of Beck and Fowler, offers a natural antidote by defining correctness in advance: tests specify behavior before implementation, encourage minimal solutions, and require continuous behavior-preserving refactoring backed by automated tests. But TDD is demanding for humans because it requires sustained attention, constant feedback, and non-deferrable cleanup, so its discipline degrades under delivery pressure and productivity often dips during adoption. At the same time, existing LLM approaches such as TiCoder, TDFlow, WebApp1K test-as-prompt setups, Self-Refine loops, and static-analysis feedback improve correctness without enforcing phase ordering, minimal implementation, or bounded repair as a governed protocol. The paper therefore asks how classical TDD principles can be translated into enforceable, governance-aware prompt structures that guarantee bounded autonomy and phase discipline across multi-agent workflows, with LLMs conveniently absorbing the repetitive test-writing labor humans find tedious.

## Main Original Ideas

1. **TDD as governance, not auxiliary input.** The central conceptual move is reframing TDD from evaluation artifacts or prompt hints into an explicit control mechanism for incremental change. Phase ordering, validation gating, bounded repair, and state authority are integrated directly into the generative loop so that development discipline shapes the trajectory of model generation rather than being applied after the fact, making prompt engineering a mechanism for encoding software engineering process invariants.

2. **Bounded canonical principle extraction.** Rather than summarizing TDD books, the authors manually distill prescriptive must/should rules from a bounded corpus of Kent Beck and Robert C. Martin that are economically fragile for humans — the rules that break first under deadline pressure. Each principle is defined as a constraint on order, granularity, or feedback quality and organized into order (test-first, Red-Green-Refactor), granularity (minimal failing test, minimal passing code, one failing test at a time), feedback quality (FAST, independent, repeatable, self-validating, timely tests with meaningful assertions), and design hygiene (remove duplication, refactor continuously while green), with each entry normalized into a label, original human-era intent, canonical quote where available, and bibliographic pointer.

3. **Machine-readable TDD manifesto as runtime contract.** The extracted principles are formalized as a JSON governance schema in which every principle carries an identifier, title, original intent, AI-native interpretation, operational constraints, and anti-patterns. Interpretation fields guide role-specific prompt construction while constraint and anti-pattern fields map to runtime enforcement points such as phase gating, scope restriction, proposal validation, and bounded repair control, serving as the conceptual contract between TDD theory and orchestration (published as tdd_principles_manifesto.json with Figure 1 illustrating RED gating, refactoring gates, and FIRST quality checks).

4. **Governance-centric layered architecture.** The system strictly separates generative autonomy from state authority: language models never write to the file system and only return structured patch proposals, while the orchestration engine alone validates and applies them atomically. Every proposal passes four gates before mutation — structural schema validation, policy enforcement over disallowed paths and directories, phase-consistency checks, and optional human or rule-based approval in planner mode — followed by deterministic test execution, so generative variability cannot translate directly into uncontrolled state changes.

5. **Distributed prompt constraints plus bounded repair.** TDD discipline emerges from coordinated constraints spread across role-specific prompts — system invariants and phase purity, planner-ordered FAIL-then-PASS steps, RED-only test generation with meaningful assertions, minimal implementation forbidding unrelated features, repair with structured failure context and localized corrections, and review that prohibits production edits and invented requirements — paired with deterministic engine rules for test-first FAIL gating, rejection of no-op or unrelated changes, post-apply test gates with automatic rollback on refactoring failure, and refactoring permitted only while green. Each GREEN step is capped at N = 3 repair attempts with a failure signature S of exception type, failing tests, and normalized message, terminating early on repeated signatures, empty patches, semantically equivalent proposals, or passing tests to ensure bounded, reproducible convergence.

## Key Findings

The paper is a short five-page EASE 2026 proposal whose validation is explicitly preliminary rather than a full empirical evaluation. The authors report that explicit phase separation and validation gating appear to reduce unstable retry cycles compared with baseline prompting, and that enforcing test-first ordering with minimal implementation appears to limit speculative code generation and unnecessary feature expansion. Conceptually, the framework demonstrates that proposal/engine separation, the manifesto as a runtime constraint, and bounded repair with deterministic validation gates convert TDD from advisory guidance into a distributed governance protocol that preserves behavioral safety during iterative synthesis. At the same time, the authors are candid that current constraints live primarily at the prompt level with only partial runtime verification, that the bounded-autonomy model may over-constrain exploration in complex refactoring scenarios, that scaling to large multi-module repositories with complex dependencies will need richer planning and invariant enforcement, and that manifesto injection must be balanced against token budgets in a direct trade-off between governance strength and prompt compactness.

## Suggestions & Future Directions

The authors plan repository-scale industrial evaluation including CI/CD integration to measure stability, defect rates, and reproducibility, alongside broader cross-model studies to test robustness beyond the preliminary experiments. They propose configurable governance levels so teams can calibrate strictness to project complexity rather than imposing one fixed regime, and they suggest that deterministic validation plus bounded autonomy could support auditable AI-assisted development in regulated domains. Implicit in the limitations is further work on full semantic compliance beyond prompt-level enforcement, more advanced planning and invariant mechanisms for complex dependencies, and compact manifesto-injection strategies that preserve governance without exhausting context windows.
