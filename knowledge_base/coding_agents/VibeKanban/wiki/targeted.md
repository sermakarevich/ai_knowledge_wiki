# Vibe Kanban for Fleet: Targeted Analysis
**In one sentence:** Vibe Kanban is a board-first, fully local orchestrator of parallel coding-agent workspaces whose thin automation, branch-per-workspace isolation, adapter-trait multi-harness, and diff-first review plus live preview browser are directly reusable patterns for fleet's beads-DB orchestrator and coder workers.

## Key points
- Board-first with thin automation: no `Workflow` type exists; the only workflow-named type is the private two-variant `IssueWorkflowSignal` in `crates/remote/src/db/issues.rs:33`, and exactly three server-side syncs move cards while everything else is manual drag-drop.
- Restart is crash-and-mark, not resume: branches, worktree dirs, and SQLite rows survive, but every `status='running'` execution is flipped to `failed` by `cleanup_orphan_executions` in `crates/services/src/services/container.rs:273`, PTY sessions and dev servers are dropped, and worktrees heal lazily on next access.
- Isolation is one branch per workspace shared across its repos (`crates/workspace-manager/src/workspace_manager.rs:290-371`); review is diff-first with ephemeral inline comments serialized into the next agent prompt (`packages/web-core/src/shared/hooks/ReviewProvider.tsx:59`), and merge conflicts are typed errors, never silent auto-merges.
- Multi-harness support is one trait (`StandardCodingAgentExecutor` in `crates/executors/src/executors/mod.rs:222`) dispatched over the `CodingAgent` enum (`crates/executors/src/executors/mod.rs:109`) with nine production adapters plus a QA mock; adding a harness is a new enum variant plus adapter module, not a plugin registry.
- Top fleet borrows: diff-first review with comment-to-prompt delivery, subdomain-routed preview browser with log-scraped port detection, lazy worktree healing plus orphan sweeping, and the adapter trait with shared ACP (Agent Client Protocol, a JSON-RPC protocol for driving agents over stdio) harness.

## Design principles (board-first vs automation-first)
Vibe Kanban is board-first with thin automation. A repo-wide search for `struct Workflow` / `enum Workflow` / `trait Workflow` over `crates/` returns zero hits; the only workflow-named type is the private `IssueWorkflowSignal { ReviewStarted, WorkMerged }` in `crates/remote/src/db/issues.rs:33-36`, which is never exposed over the API, never stored, and covers only two of the three automations (the third bypasses it). The user-visible workflow is therefore an emergent convention composed of per-project status rows, a nullable issue-to-workspace link, PR rows joining issues to workspaces, and three narrow sync functions (`crates/remote/src/db/issues.rs:523-599`, `crates/remote/src/db/issues.rs:641-691`).

Manual moves dominate. Board position is just the `status_id` foreign key on the `issues` row (`crates/api-types/src/issue.rs:26`, DDL in `crates/remote/migrations/20260112000000_remote-projects.sql:53-89`), and cross-column drag sends `{status_id, sort_order}` through `POST /v1/issues/bulk` (`packages/web-core/src/shared/lib/remoteApi.ts:125-138`), applied as one transaction in `crates/remote/src/routes/issues.rs:430-584` with the ordering formula `1000 * columnIndex + issueIndex` in `packages/web-core/src/features/kanban/ui/KanbanContainer.tsx:647-655` and the move policy in `packages/web-core/src/features/kanban/ui/KanbanContainer.tsx:658-750`. Automation covers exactly three transitions, all server-side, name-matched, and idempotent: first-workspace-created moves Backlog/To-do (plus parent) to In progress only when `count_by_issue_id == 1` (`crates/remote/src/db/issues.rs:641-691` via `move_to_status_if_pending` at `crates/remote/src/db/issues.rs:601-635`); open/linked PR moves to In review (`crates/remote/src/db/issues.rs:579-590`, call sites in `crates/remote/src/routes/pull_requests.rs:152`, `crates/remote/src/routes/pull_requests.rs:237`, `crates/remote/src/routes/pull_requests.rs:351`); all-linked-PRs-merged (or local merge without PR via `POST /v1/workspaces/{id}/sync_issue_status_from_local_merge` in `crates/remote/src/routes/workspaces.rs:158-190`) moves to Done, returning early unless all PRs are `merged` (`crates/remote/src/db/issues.rs:534-542`, core logic in `crates/remote/src/db/issues.rs:523-574`). Everything else — initial status, Backlog/Cancelled triage, priority/assignee/tag edits, sub-issue completion (children have independent statuses, no parent roll-up per `docs/issue-management.mdx:101-104`) — is manual. Status semantics are data, not code: six default `project_statuses` rows seeded per project (`crates/remote/src/db/project_statuses.rs:13-20`), looked up case-insensitively by name (`crates/remote/src/db/project_statuses.rs:62-90`), so renaming "Done" silently disables merge-to-Done. The legacy local `TaskStatus` enum (`crates/db/src/models/task.rs:14-21`) no longer governs anything remote. The issue description doubles as the agent prompt via `buildWorkspaceCreatePrompt`/`buildLinkedIssueCreateState` (`packages/web-core/src/pages/kanban/IssueWorkspacesSectionContainer.tsx:131-156`). For fleet, which is automation-first (orchestrator plus beads DB driving coder workers), the lesson is inverted: borrow the board as a thin human overlay, not as the driver — keep fleet's state machine authoritative and replicate only the three-signal sync shape.

## Worker restart handling
What survives a server restart: all SQLite rows (`workspaces`, `workspace_repos`, `sessions`, `execution_processes`, logs, turns in `crates/db/src/models/mod.rs:1`), git branches plus committed files in source repos, and worktree directories on disk unless swept. What is lost: every in-flight child process (killed on shutdown by `kill_all_running_processes` via `perform_cleanup_actions` in `crates/server/src/startup.rs:185-192` and `crates/local-deployment/src/container.rs:1603-1633`), all terminal PTY sessions (in-memory `HashMap<Uuid, PtySession>` only in `crates/local-deployment/src/pty.rs:36-39`, fresh PTY per WebSocket connection in `crates/server/src/routes/terminal.rs:52-166`, unconditional `close_session` on socket end at `crates/server/src/routes/terminal.rs:165`), all dev-server processes (no auto-start path exists; restart via `POST .../dev-server/start` in `crates/server/src/routes/workspaces/execution.rs:37-137`), and in-memory log streams (`MsgStore` map in `crates/services/src/services/container.rs:89`, rebuilt from persisted logs on demand via `stream_raw_logs`/`stream_normalized_logs` in `crates/services/src/services/container.rs:797-872`).

Recovery mechanisms, in boot order (`initialize_deployment` in `crates/server/src/startup.rs:132-183`): (1) `cleanup_orphan_executions` (`crates/services/src/services/container.rs:273-326`) flips every `status='running'` row to `failed` with no exit code and snapshots current worktree HEAD per repo into `after_head_commit` — nothing is relaunched, no agent/setup/cleanup/dev-server restarts; (2) `backfill_before_head_commits` and `backfill_repo_names` restore position markers (`crates/server/src/startup.rs:132-183`); (3) lazy worktree healing on next access through `ensure_container_exists` (`crates/local-deployment/src/container.rs:1243-1287`) calling `ensure_workspace_exists` (`crates/workspace-manager/src/workspace_manager.rs:373-425`): branch still exists so re-add worktree at `<container>/<repo_name>`, branch gone so recreate from `target_branch`, uncommitted changes unrecoverable; creation itself is idempotent behind per-path async mutexes (`WORKTREE_CREATION_LOCKS` in `crates/worktree-manager/src/worktree_manager.rs:16-17`) with `create_worktree_with_retry` plus force-clean retry (`crates/workspace-manager/src/worktree_manager.rs:302-365`); (4) orphan and expiry sweeping: `cleanup_orphan_workspaces` removes container dirs with no matching `container_ref` (`crates/workspace-manager/src/workspace_manager.rs:538-610`, skipped under `DISABLE_WORKTREE_CLEANUP`), periodic every 30 minutes plus `cleanup_expired_workspaces` marking `worktree_deleted` after 72h untouched (1h if archived, never pinned/active/running) per `crates/db/src/models/workspace.rs:252-309` and `crates/local-deployment/src/container.rs:284-320`. Shutdown is cooperative via `CancellationToken` (`crates/server/src/main.rs:70`, honoured at `crates/server/src/main.rs:164-170`) then unconditional process kill (`crates/server/src/main.rs:236-242`). Fleet relevance: this crash-and-mark plus lazy-heal shape maps directly onto coder-worker restarts — persist worker rows, never auto-resume agents, re-derive live state on next access.

## Conflict resolution
Isolation first: one workspace maps to exactly one branch name shared across all its repos and one container directory holding one git worktree per repo at `<container>/<repo_name>` (`crates/workspace-manager/src/workspace_manager.rs:290-371`, `crates/local-deployment/src/container.rs:1243-1287`); branch names derive from `<short-uuid>-<slugged-label>` with optional prefix (`crates/services/src/services/container.rs:786-795`, slug helpers in `crates/utils/src/text.rs:4-24`); branch creation is a plain local branch at the target tip (`GitService::create_branch` in `crates/git/src/lib.rs:193-204`) followed by `git worktree add` (`crates/git/src/lib.rs:960-971`, `crates/git/src/cli.rs:85-108`); recovery never force-resets branches. Workspace rows carry `branch` plus `container_ref` (`crates/db/src/models/workspace.rs:41-54`) with per-repo `target_branch` join rows (`crates/db/src/models/workspace_repo.rs:11-21`), and deletion defaults to preserving branches while removing worktrees and history rows (`crates/server/src/routes/workspaces/core.rs:99-183`, `docs/workspaces/managing-workspaces.mdx:59-81`).

PR flow is push-then-CLI: `POST /workspaces/:id/pull-requests` (`crates/server/src/routes/workspaces/pr.rs:188-388`) resolves the target branch, pushes the workspace branch (`push_to_remote` in `crates/git/src/lib.rs:1479`), picks a host via `GitHostService::from_url`, delegates to `GhCli::create_pr` (`crates/git-host/src/github/cli.rs:225-261`, body via temp file, 1s–30s retry in `crates/git-host/src/github/mod.rs:205-221`), and stores a local `PullRequest` row; `attach_existing_pr` (`crates/server/src/routes/workspaces/pr.rs:390-541`) covers pre-existing PRs via `gh pr list --state all --head` (`crates/git-host/src/github/cli.rs:279-301`); merge itself happens on GitHub, Vibe Kanban only observes through `pr_monitor` polling every 60s (`crates/services/src/services/pr_monitor.rs:68`), updating rows and archiving workspaces only when zero open PRs remain (`crates/services/src/services/pr_monitor.rs:128-211`). Inline diff comments are a second, local-only layer: the `ReviewComment` interface (`packages/web-core/src/shared/hooks/useReview.ts:5-12`) lives in React context (`packages/web-core/src/shared/hooks/ReviewProvider.tsx:16-25`), authored per diff line via `CommentWidgetLine` (`packages/web-core/src/pages/workspaces/CommentWidgetLine.tsx:15-42`), rendered through `transformCommentsToAnnotations` where local drafts win ties over GitHub comments (`packages/web-core/src/shared/lib/diffDataAdapter.ts:166-224`), with GitHub comments read-only via `GET /workspaces/:id/pull-requests/comments` (`crates/server/src/routes/workspaces/pr.rs:850`, merge in `crates/git-host/src/github/mod.rs:300-353`).

On merge conflicts the system reports, blocks, and offers typed recovery — never silent auto-merge. Conflict state derives per repo on every branch-status read: `is_rebase_in_progress`, `conflicted_files` (from `git diff --name-only --diff-filter=U` in `crates/git/src/cli.rs:697-700`), and `ConflictOp::{Rebase, Merge, CherryPick, Revert}` from sentinel files (`crates/git/src/lib.rs:68-73`, `crates/git/src/lib.rs:1283-1304`, route at `crates/server/src/routes/workspaces/git.rs:411-429`). Rebase (`POST /rebase`, `crates/server/src/routes/workspaces/git.rs:144`) refuses dirty worktrees (`crates/git/src/lib.rs:1140-1143`) and in-progress rebases (`crates/git/src/lib.rs:1145-1148`), runs `git rebase --onto <new_base> <merge_base> <task_branch>` with `--fork-point` fallback (`crates/git/src/cli.rs:514-549`), and converts conflict stderr into typed `GitServiceError::MergeConflicts` with file list (`crates/git/src/lib.rs:1162-1201`) surfaced as `GitOperationError::MergeConflicts` (`crates/server/src/routes/workspaces/git.rs:756-770`). Direct merge (`POST /merge`, `crates/server/src/routes/workspaces/git.rs:141`) refuses when any open PR exists or the target is remote (`crates/server/src/routes/workspaces/git.rs:195-213`), blocks when the base moved ahead (`BranchesDiverged`), and falls back to in-memory squash with `fail_on_conflict(true)` returning conflicts without touching the tree (`crates/git/src/lib.rs:575-596`, `crates/git/src/lib.rs:1081-1126`). Recovery endpoints are `POST /rebase/continue` (`crates/server/src/routes/workspaces/git.rs:819-839`) and `POST /conflicts/abort` (`crates/server/src/routes/workspaces/git.rs:795-816`, impl `crates/git/src/lib.rs:1333-1368`).

## Workflow abstraction and implementation
The abstraction is kanban issues plus workspaces — there is no `Workflow` type. Issues are the planning side, workspaces plus sessions plus execution processes are the execution side, linked by nullable foreign keys. Key types: `Issue` with `status_id` FK (`crates/api-types/src/issue.rs:21-40`), `ProjectStatus` rows (`crates/api-types/src/project_status.rs:9-17`), `CreateIssueRequest`/`UpdateIssueRequest` with `some_if_present` deserialization for drag-drop deltas (`crates/api-types/src/issue.rs:60-147`), `Workspace` row (`crates/db/src/models/workspace.rs:41-54`, liveness computed not stored via `find_all_with_status`/`find_by_id_with_status` in `crates/db/src/models/workspace.rs:498-583` and `crates/db/src/models/workspace.rs:594-670`), `WorkspaceRepo` join (`crates/db/src/models/workspace_repo.rs:11-21`), `Session` grouping (`crates/db/src/models/session.rs:22-31`), `ExecutionProcess` with `status in running|completed|failed|killed` (`crates/db/src/models/execution_process.rs:39-48`) and `run_reason in setupscript|cleanupscript|archivescript|codingagent|devserver` (`crates/db/src/models/execution_process.rs:50-59`) plus `dropped` flag for superseded history (`crates/db/src/models/execution_process.rs:68-73`) and per-repo positions in `execution_process_repo_states`, `Repo` with per-repo scripts (`crates/db/src/models/repo.rs:36-54`), and remote-side `IssueWorkflowSignal` plus `sync_status_from_workflow_signal`/`sync_issue_from_workspace_created` (`crates/remote/src/db/issues.rs:32-36`, `crates/remote/src/db/issues.rs:523-599`, `crates/remote/src/db/issues.rs:641-691`).

Key tables: remote Postgres (Postgres, the server database) `project_statuses` and `issues` with `status_id` FK, `sort_order`, `parent_issue_id`, `issue_relationships` (`crates/remote/migrations/20260112000000_remote-projects.sql:30-89`, `crates/remote/migrations/20260112000000_remote-projects.sql:142-152`), remote `workspaces` with nullable `issue_id REFERENCES issues(id) ON DELETE SET NULL` plus `local_workspace_id` bridge (`crates/remote/migrations/20260112000000_remote-projects.sql:242-260`), PR rows carrying `issue_id` plus nullable `workspace_id` (`crates/remote/migrations/20260112000000_remote-projects.sql:266-280`); local SQLite `workspaces`, `workspace_repos`, `sessions`, `execution_processes`, `repos` (16 models in `crates/db/src/models/mod.rs:1-16`, file at `db.v2.sqlite` opened in `crates/db/src/lib.rs:77-80`). Key routes: issue CRUD plus `POST /v1/issues/bulk` and `/issues/search` (`crates/remote/src/routes/issues.rs:34-49`, bulk handler at `crates/remote/src/routes/issues.rs:430-584`), `POST /v1/workspaces` with `{project_id, local_workspace_id, issue_id}` (`crates/remote/src/routes/workspaces.rs:29-60`, sync at `crates/remote/src/routes/workspaces.rs:100-115`), local workspace CRUD plus nested `/git`, `/execution`, `/pull-requests` routers (`crates/server/src/routes/workspaces/mod.rs:24-61`), execution/dev-server routes (`crates/server/src/routes/workspaces/execution.rs:29-35`), PR routes (`crates/server/src/routes/workspaces/pr.rs:846-851`), diff websocket `GET /diff/ws` (`crates/server/src/routes/workspaces/git.rs:140`, handler in `crates/server/src/routes/workspaces/streams.rs:40-42`), and merge/rebase/conflict routes (`crates/server/src/routes/workspaces/git.rs:141-146`). Fleet mapping: beads DB already covers the issue side; what is missing is the workspace-side join (branch, container ref, target branch, run-reason executions) plus the three-signal sync shape.

## What fleet can borrow
- **Diff-first review with comment-to-prompt delivery.** What it is: worktree-vs-base-commit diffs (`GitService::get_diffs` in `crates/git/src/lib.rs:327-353` via temp-index `git diff --cached -M` in `crates/git/src/cli.rs:216-227`) rendered in `@pierre/diffs`, with ephemeral inline comments (`ReviewComment` in `packages/web-core/src/shared/hooks/useReview.ts:5-12`) serialized by `generateReviewMarkdown` (`packages/web-core/src/shared/hooks/ReviewProvider.tsx:59-88`) and prepended to the next agent prompt via `buildAgentPrompt` (`packages/web-core/src/shared/lib/promptMessage.ts:11-26`, send path in `packages/web-core/src/features/workspace-chat/ui/SessionChatBoxContainer.tsx:501-534`). Why it matters for fleet: coder-worker output needs human review without leaving the loop, and prompt-concatenation is the cheapest reliable feedback channel. Anchor: `packages/web-core/src/shared/hooks/ReviewProvider.tsx:59-88`.
- **Preview browser with subdomain-routed proxy plus log-scraped port detection.** What it is: a separate proxy listener routing `{devPort}.localhost:{proxyPort}` to `localhost:{devPort}` (`crates/preview-proxy/src/lib.rs:384-400`, dispatch in `crates/preview-proxy/src/lib.rs:366-382`), with toolbar, device modes, click-to-component inspect, and Eruda console (`packages/ui/src/components/PreviewBrowser.tsx:46-92`), while the dev port itself is never allocated — only regex-scraped from logs (`packages/web-core/src/shared/hooks/usePreviewUrl.ts:151-220`). Why it matters for fleet: workers running dev servers need one-click live verification, and log scraping avoids building a port allocator. Anchor: `crates/preview-proxy/src/lib.rs:384-400`.
- **Branch-per-workspace isolation with single shared branch name.** What it is: one auto-generated `<short-uuid>-<slugged-label>` branch across all repos in a workspace plus one worktree per repo (`crates/services/src/services/container.rs:786-795`, `crates/workspace-manager/src/workspace_manager.rs:290-371`). Why it matters for fleet: parallel coder workers must never share a working tree, and a single branch name per task keeps multi-repo changes reviewable as one unit. Anchor: `crates/workspace-manager/src/workspace_manager.rs:290-371`.
- **Crash-and-mark restart plus lazy worktree healing.** What it is: `cleanup_orphan_executions` flips running rows to `failed` and snapshots HEAD (`crates/services/src/services/container.rs:273-326`), shutdown kills children (`crates/local-deployment/src/container.rs:1603-1633`), and missing worktrees recreate idempotently on next access (`crates/workspace-manager/src/worktree_manager.rs:88-116`). Why it matters for fleet: worker crashes are inevitable, and mark-dead plus heal-on-access is simpler and safer than auto-resuming agents. Anchor: `crates/services/src/services/container.rs:273-326`.
- **Executor adapter trait with shared ACP harness.** What it is: `StandardCodingAgentExecutor` (`crates/executors/src/executors/mod.rs:222`) over the `CodingAgent` enum (`crates/executors/src/executors/mod.rs:109`), with ACP-speaking CLIs sharing `AcpAgentHarness` (`crates/executors/src/executors/acp/harness.rs:30`) instead of per-agent spawn code.
