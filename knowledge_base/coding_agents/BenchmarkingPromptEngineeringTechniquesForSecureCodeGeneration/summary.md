# Benchmarking Prompt Engineering Techniques for

**Paper:** [Benchmarking Prompt Engineering Techniques for Secure Code Generation with GPT Models](https://arxiv.org/abs/2502.06039v1)

## Human Readable TL;DR

Asking an AI coding assistant for help is a bit like asking a fast but careless cook to prepare dinner: the meal arrives quickly, but it may contain something that makes you sick. This paper tests whether simply wording the request more carefully — like telling the cook "you are very hygiene-aware" — makes the generated Python code meaningfully safer. The answer is yes for newer models, where one short security prefix cuts vulnerable programs roughly in half, and asking the model to critique and fix its own code removes a quarter to two-thirds of remaining flaws depending on the model. The catch is that the older, weaker model mostly ignores such polite nudges and only improves when forced to review its own output, so prompt wording matters more the smarter the assistant gets.

## TL;DR

The authors build an automated benchmark over 202 high-risk Python prompts from LLMSecEval and SecurityEval, testing prefix/suffix prompt augmentations plus Recursive Criticism and Improvement (RCI) and chain-of-thought on pinned GPT-3.5-turbo, GPT-4o-mini, and GPT-4o snapshots at temperature 1 with 10 samples per prompt, scored by Semgrep and CodeQL agreement on the suspected CWE (SAFVS/OFVP). The single most effective proactive technique is the prefix "You are a developer who is very security-aware and avoids weaknesses in the code" (pe-03-a), cutting SAFVS by 47% on GPT-4o-mini and 56% on GPT-4o but hurting GPT-3.5-turbo, while one RCI iteration fixes 24.5% (GPT-3.5), 49.5% (GPT-4o-mini), and 64.7% (GPT-4o) of flawed snippets and stacked prefix+RCI reaches 61–69% reduction on the 4o family. They package this into an open-source benchmark tool and a BetterChatGPT-based prompt agent, and qualify the results with validity threats around scanners, training-data exposure, Python-only scope, and OpenAI-only models.

## Problem & Motivation

Programmers using AI assistants write more insecure code while rating it as more secure, and prior measurements are grim: roughly a third of Copilot-marked GitHub snippets contain security issues, around 40% of Copilot completions over 89 CWE scenarios were vulnerable, and GPT-3.5 produced initially secure programs in only 5 of 21 use cases. Prompt engineering can steer models without retraining and has reduced reasoning mistakes elsewhere, with hints that wording matters for security — only 3 of 100 encryption answers were violation-free until explicitly requesting a "secure" solution (rising to 42), and small prompt changes showed compounding effects. However, the effect of prompt techniques on code vulnerabilities remains underexplored because prior studies were constrained by narrow tasks, outdated models, a single sample per prompt, or temperature 0, which motivated the authors' research question "Can we enhance GPT's secure code generation via prompt engineering?" and an automated, realistic benchmark with default temperature, multiple samples, and state-of-the-art models.

## Main Original Ideas

1. **Automated secure-coding benchmark workflow:** a pipeline running High-risk Coding Prompts through Prompt Augmentation, Response Generation via the OpenAI Chat API (10 samples per prompt, up to 3 regenerations), regex plus `ast.parse` Code Extraction with a code-only follow-up, dual-scanner Code Security Scan with Semgrep and CodeQL, and Metrics Calculation filtered to the suspected CWE plus MITRE mappings, released with data at https://github.com/mbscit/securecodingprompts.
2. **Broad prompt-augmentation suite:** a table of task-independent prefix/suffix attempts (security persona, best-practices, line-by-line checks, CWE-avoidance, threat-of-fine) alongside dataset-dependent CWE-list prefixes and an adversarial pe-negative control, plus multi-step RCI (critique then improve, up to 3 iterations, from baseline or pe-03-a) and chain-of-thought variants, each applied by script with stable IDs.
3. **Relative-comparison metrics and validity framing:** the Scanners-Agree Filtered Vulnerable Samples (SAFVS) percentage and its k-run Observed set (OFVP) with box-plot distributions, explicitly positioned as a relative comparison rather than an absolute security measure since scanners miss issues but preserve proportional differences, with 100-sample baselines and HumanEval functionality checks to study variance and cost.
4. **Prompt Agent prototype:** a BetterChatGPT-based assistant that transparently prepends the winning security prefix before completion and optionally intercepts markdown code blocks for RCI critique-and-rewrite post-processing, demonstrating how proactive prevention and iterative refinement combine in a real coding-assistant workflow.

## Key Findings

On GPT-3.5-turbo every proactive single-prompt technique backfired, increasing vulnerable samples by up to 31.1% over the 5.97% baseline (worst: pe-02-c at 7.82%), and only post-generation RCI helped — 24.5% fixed in iteration one (4.50%), then further gains of 8.9% and 14.1% by iterations two and three (4.01%, 3.47%, +41.9% total) — while the adversarial pe-negative prompt raised vulnerabilities 69.3% to 10.10%. Results flip on the newer models: on GPT-4o-mini every technique beats baseline, with pe-03-a cutting risk 47% (4.06%) and RCI-from-baseline cutting 49.5% in one iteration (3.86%) plus 9.1% more in a second with no further gain in a third, stacked prefix+RCI topping the table at 2.97% (−61.2%); on GPT-4o (subset run for cost reasons) all tested techniques beat the 7.43% baseline, pe-03-a best single-prompt at 3.27% (−56%), RCI-from-baseline at 2.62% (−64.7%), and RCI-on-pe-03-a best overall at 2.33% (−68.7%), while pe-negative spikes to 18.76% (+152.7%). Cross-model comparison shows sensitivity to prompt wording grows with model capability, GPT-3.5-turbo paradoxically has the most secure baseline likely due to incomplete low-AST-height code (echoing the thesis that more capable coders suggest more insecure code), RCI works on all models but improves most on advanced ones with diminishing returns, 10 samples approximate the central tendency of 100 samples well, HumanEval pass@10 is essentially unchanged while RCI drops pass@1 about 10 points (possibly from security hardening, on only 10 samples and no scanner hits on HumanEval), and costs are stark (USD 28 for all GPT-4o-mini attempts versus ~USD 3080 estimated for GPT-4) with RCI adding large multi-call latency of 10+ seconds.

## Suggestions & Future Directions

The authors' validity discussion reads as a research agenda: decontaminate or refresh public datasets since post-2023 models may have seen LLMSecEval/SecurityEval and CWE/CodeQL docs, complement the two static scanners with manual audit, dynamic analysis, or stronger detectors since code can bypass scanners without becoming secure, and study real project context rather than isolated snippets including how developers treat textual warnings. They flag internal issues worth following up — snapshot drift across vendors and time, sharp sensitivity to small phrasings (persona versus pe-03-a perform very differently), the need for inferential statistics beyond descriptive OFVP box plots, and tuning the optimal RCI iteration count per model given diminishing returns and higher token cost and latency. External generality calls for replicating beyond OpenAI snapshots, beyond Python, and beyond the tested subset of phrasings and combinations, including a classifier that only augments likely-code prompts, deeper functionality-versus-security tradeoff measurement on larger HumanEval samples, and usability work since the prefix seems harmless but verbose, over-cautious RCI may alienate advanced programmers.
