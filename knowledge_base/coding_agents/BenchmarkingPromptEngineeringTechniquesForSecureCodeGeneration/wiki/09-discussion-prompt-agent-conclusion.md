# Discussion, Prompt Agent, Threats to Validity and Conclusion
**In one sentence:** The authors package their best prompt techniques into a BetterChatGPT-based Prompt Agent with a security prefix and RCI post-processing, then qualify the benchmark with construct/internal/external validity threats and conclude that the prefix and RCI substantially cut vulnerabilities for the GPT-4o family but not GPT-3.5-turbo.
## Key points
- The Prompt Agent enhances the prompt in the back end before LLM completion and can optionally apply RCI post-processing before presenting output, which the authors say can significantly reduce the risk of generating vulnerable code.
- The Code Security Prefix adds verbatim `"You are a developer who is very security-aware and avoids weaknesses in the code"`, the most successful prefix for GPT-4o-mini and GPT-4o (attempt pe-03-a).
- With GPT-4o the agent reduces vulnerabilities on average by 64.7% without the prefix and 68.7% with the prefix, aligning with attempts `ptfscg rci-from-baseline-iter-1` and `ptfscg rci-from-pe-03-a-iter-1` respectively.
- The prefix did not noticeably impair chatbot functionality in first impressions, while RCI often delayed responses by more than 10 seconds even for a single short snippet and was overly cautious/verbose.
- The conclusion reports the prefix cut vulnerable-code generation by 47% (GPT-4o-mini) and 56% (GPT-4o), while GPT-3.5-turbo responded negatively to similar security-enhancing prompts.
- A single RCI iteration fixed 24.5% (GPT-3.5), 49.5% (GPT-4o-mini), and 64.7% (GPT-4o) of flawed snippets.
- Key validity threats are training-data exposure, dependence on two static scanners, isolated Python snippets, model/snapshot variability, prompt-phrasing sensitivity, no inferential statistical tests, and OpenAI-only models.

## VI. Prompt Agent
**Covers:** Discussion, prompt-agent application — concept (Fig. 7), implementation, usability

The developed "Prompt Agent" integrates advanced prompt engineering techniques into automated code generation workflows with the primary goal of enhancing security of code generated by LLMs such as GPT-4o by systematically improving prompts and incorporating iterative refinement.

Concept: the agent takes a prompt in the front end, enhances it in the back end before sending it to the LLM for completion, and after receiving the response can optionally apply post-processing using RCI before presenting the output to the user. Figure 7 visualizes the process (Original Prompt → Preprocessing adding prefix and/or suffix → Chatbot/LLM → RCI post-processing → Response from Agent).

Implementation is based on BetterChatGPT [20] with two additional features:

| Feature | Mechanism |
|---|---|
| a) Code Security Prefix (preprocessing) | When enabled per-prompt, prepends verbatim: "You are a developer who is very security-aware and avoids weaknesses in the code". Most successful prefix for GPT-4o-mini and GPT-4o in evaluation (attempt pe-03-a). As an alternative, a classifier could predict if the user's prompt is likely to generate code and only augment in those cases. |
| b) Code Security Agent (RCI postprocessing) | When enabled in settings, intercepts markdown code blocks in the response, sends them to the LLM for security critique and improvement, then extracts the improved code and inserts it back into the original answer. |

With the prefix enabled the result aligns with the `ptfscg rci-from-pe-03-a-iter-1` attempt, best in the benchmark for the 4o-family; without the prefix it aligns with `ptfscg rci-from-baseline-iter-1`.

Usability (first impressions, not extensively tested due to time constraints):
- Code Security Prefix did not noticeably impair chatbot functionality (used GPT-4o-mini and GPT-4o) and could be valuable for programmers of all skill levels.
- Code Security Agent often delayed responses by more than 10 seconds even for a single relatively short snippet because RCI sends additional LLM requests; RCI was overly cautious and too verbose — helpful for beginners but a potential deal breaker for advanced programmers, so post-processing with RCI does not seem viable for most use cases.
- The agent provides a foundation for further evaluation and is available in the authors' repository (https://github.com/mbscit/securecodingprompts).

## VII. Threats to Validity
**Covers:** Discussion, threats to validity — construct, internal, external

A. Construct validity (whether the study measures prompt-technique efficacy):
- Training Data Influence: public datasets risk prior model exposure; GPT-3.5-turbo (trained up to 2021) would not have seen SecurityEval or LLMSecEval but might include MITRE CWE and CodeQL documentation, while GPT-4o and GPT-4o-mini (trained post-2023) could incorporate these datasets.
- Scanner Limitations: dependence on two static scanners risks false positives/negatives, and generated code might bypass scanners without fixing underlying vulnerabilities.
- Code Context and Usability: isolated snippets lack software architecture/operational environment, and textual warnings in LLM responses were ignored on the assumption developers might also overlook them.
- Impact on Code Functionality: security-oriented prompt modifications could impair functionality; this trade-off was only briefly examined.

B. Internal validity (whether outcomes stem from experimental conditions):
- Model and Snapshot Variability: differences between LLMs even from the same vendor, plus newer model snapshots altering performance, threaten reproducibility and longitudinal comparison.
- Prompt Effects: small variations led to significant differences — attempts `ptfscg-persona` and `pe-03-a` reflected similar principles but showed markedly different effectiveness, and combining RCI with `pe-03-a` showed systematic tuning can alter results significantly.
- Statistical Validation: notable differences rest on observed outcomes and descriptive statistics; no inferential statistical tests were conducted.

C. External validity (generalizability):
- Model-Specific Outcomes: findings on GPT-3.5-turbo, GPT-4o-mini, and GPT-4o may not apply to other LLMs due to architectural differences.
- Dataset and Language Constraints: exclusive focus on Python code and a small set of prompts restricts applicability to other languages/domains.
- Iterative Generalization: multiple iterations improved some models but showed diminishing returns for others; the optimal iteration count per LLM remains unexplored.
- Scalability of Attempts: only a limited subset of prompt variations was evaluated; wider phrasings, combinations, and refinements remain for future work.

## VIII. Conclusion
**Covers:** Conclusion with headline numbers

The authors developed a benchmark of prompt engineering effects on code security across GPT models: vulnerability rates and sensitivity to prompt changes vary by model. For GPT-4o-mini and GPT-4o, adding the prefix "You are a developer who is very security-aware and avoids weaknesses in the code." reduced vulnerable code generation by 47% and 56%, respectively, while GPT-3.5-turbo responded negatively to similar prompts. Recursive Criticism and Improvement (RCI) mitigated vulnerabilities across models, with one iteration fixing 24.5% (GPT-3.5), 49.5% (GPT-4o-mini), and 64.7% (GPT-4o) of flawed snippets. These insights can help end-users and be integrated into LLM-based coding assistants, as demonstrated by the prompt agent concept.
