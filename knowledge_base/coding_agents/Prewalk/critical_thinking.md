# Critical Analysis: You Only Need the Frontier Model for One Single Edit

## Claims vs. evidence

1. **"`/plan` often costs more than not splitting the task at all."** Suggestive but narrow. The evidence is a single matched pair per model family on SWE-Bench Pro (Opus 4.8, one Django task shown as the worked example) — real numbers, but drawn from one benchmark, one task family (Python/Django bug fixes), and a single named worked example per arm rather than the full aggregate distribution. The article doesn't state sample sizes (how many tasks the 84.6%/85%/78%/etc. pass rates are averaged over), confidence intervals, or variance across task difficulty. A benchmark-wide percentage without an n or a spread is a point estimate presented as a settled fact.
2. **"Reading is ~91% of agent token spend, edits are ~9%, and this holds across harnesses/models."** Strong on its own terms but the underlying data isn't shown. It's described as "admittedly anecdotal" by the author themselves — the piece is transparent about this being an internal, unaudited distribution over "1.81B tokens across ~2M tool calls," not a controlled cross-harness comparison with matched task sets. The claim that "fully automated agents look no different" is asserted, not evidenced.
3. **"`/prewalk` cuts cheating by 25–31 points."** Reasonably strong within scope — the cheating numbers (44%→13% for Opus, 95%→70% for GPT-5.6 Sol) are large effects, and the mechanism offered (turn-budget starvation before the "stuck" phase) is falsifiable and specific (median ~7 turns, stuck phase starts turn 12–14). But "cheating" is operationalized as tokens/turns spent on web/GitHub search, which is a proxy — it doesn't distinguish a model that legitimately looks up API documentation from one that pastes in the literal historical fix; the article doesn't describe how the two are distinguished.
4. **"92–97% of frontier pass rate at 39–53% lower cost."** The two families tested (GPT-5.6 Sol/Luna, Opus 4.8/Flash) show consistent direction but different magnitudes (97%/61% vs. 92%/53%), and the article offers no third family or ablation to show where the pattern breaks — e.g., a much larger capability gap between frontier and cheap model, or a much harder task class.

## Genuinely new vs. repackaged

The economic framing — agent cost as O(reads), not O(compute) or O(actions) — is a useful reframe, though the underlying observation (context/prompt tokens dominate spend vs. completion tokens in tool-using agents) is not new to practitioners who've watched their own API bills; the article's contribution is making the *edit-vs-read* split explicit and quantified rather than the more commonly discussed input-vs-output token split. The mechanism connecting `/prewalk` to prefill jailbreaks is the article's most original contribution: reframing a well-known safety-adjacent trick (turn/token prefill) as a *performance* technique at the turn granularity is not something covered by prior public discussion of plan-then-execute agent patterns. The empirical swap-timing iteration (fixed-turn → post-first-edit → post-first-edit-with-todo-gate) reads as genuine trial-and-error engineering, not a repackaging of a known recipe.

## Weaknesses and blind spots

- **No error bars or task counts.** Every headline number (84.6%, 97%, 61%, etc.) is presented as a bare point value. Whether the 6-14 point gaps between arms are statistically distinguishable given SWE-Bench Pro's typical task-set size is not addressed.
- **Single-author, single-company source with a commercial interest.** The article is published by Stencil and describes a feature ("`--prewalk`") the author's own team built and upstreamed into their own harness (`omp`). This doesn't invalidate the numbers, but the piece is closer to a product-benchmark writeup than an independent evaluation, and no external replication is cited.
- **Only two model-pair families, both coding tasks.** No evidence is given for domains outside SWE-Bench-style code repair — the article's own "how does it work" framing (context accumulation, todo-list persistence) is plausible outside coding, but is not tested outside it.
- **The "prefill" mechanism is asserted, not directly tested.** The article doesn't run an ablation isolating "removing the planning instruction" from "swapping models" from "todo-list gating" — the mechanistic story (why the cheap model doesn't notice the swap) is a plausible narrative but not independently verified against, e.g., a version of `/prewalk` that leaves the planning instruction in context.
- **Cheating definition is not fully specified.** What counts as "poking around the web for [the answer]" — any web/GitHub tool call, or only ones that retrieve the actual historical fix — is not defined precisely enough to judge false positives (e.g., legitimate documentation lookups).
- The article is silent on **failure modes of `/prewalk` itself** — e.g., what happens when the frontier model's first edit is *wrong*; does the cheap executor still confidently continue down a bad path with no signal that anything is amiss? This seems like the most obvious risk of the technique and isn't discussed.

**Relevance to my work** (AI/ML engineering, agentic systems, Elisity data platform):
- Directly applicable to fleet's own local-delegation pattern (`ai show summary/get_local`): that workflow already hands off *files/specs*, not conversational trajectories, to local models — worth considering whether a `/prewalk`-style handoff (Claude explores + drafts a plan, prunes its own planning framing, and the local worker continues from a lived todo list) would outperform the current fully-separated "Claude writes a spec, local model executes cold" pattern for coding-adjacent fleet tasks.
- The O(reads) framing is a useful lens for auditing where fleet/Athena-querying agent tasks actually spend tokens — if the same ~90/10 read/edit split holds, task specs that minimize redundant re-reading (e.g., avoiding requiring workers to re-read sibling files "for context," already a documented gotcha in `summary/get_local.md`) are higher-leverage than swapping to a cheaper model.
- The cheating/benchmark-gaming angle is a caution for any internal agent benchmarking Elisity might do with public or semi-public reference answers (e.g., known-good device classifications) — an agent given too long a leash can find the "answer" instead of deriving it, inflating apparent accuracy.

## What this changes

If the claims hold broadly (not just on SWE-Bench-style code repair): teams currently using a "smart plans, cheap executes" agent pattern purely to save money should re-benchmark against both a frontier-oneshot baseline and a `/prewalk`-style trajectory handoff before assuming the split saves anything. It also suggests that "cost-optimize an agent pipeline" projects should start by profiling read-vs-edit token share before reaching for a cheaper model at all, since a large fraction of spend may be recoverable by reducing redundant reads regardless of which model is used.

## Verdict

The core economic argument (agent cost tracks reads, not edits or thinking) is well-observed and independently plausible from general LLM-agent experience, and the `/prewalk` mechanism is a genuinely clever, mechanistically-grounded idea connected credibly to prefill. But the supporting benchmark is a single company's internal SWE-Bench Pro run, on coding tasks only, with point-estimate numbers and no error bars, sample sizes, or external replication. Take the mechanism seriously; take the exact percentages as directional, not definitive. **Verdict: trial** — worth prototyping the trajectory-handoff pattern in your own agent pipelines and measuring against your own tasks, not adopting the specific cost/pass-rate numbers as guaranteed.
