# Scanning methodology and Copilot Chat fix setup
**In one sentence:** Static-analysis findings were filtered to Warning/Error severity, manually verified as Copilot-generated via line numbers and comments, then a 90-snippet / 295-weakness subset was repaired with Copilot Chat using three prompts and rechecked with the analyzers.
## Key points
- Tool severities are Recommendation (code-quality suggestions), Warning (potential abnormal/unsafe behavior), and Error (may fail to compile or run) — only Warning and Error findings were counted.
- Repository-label results were checked one by one against the line numbers in the analysis output to confirm a real weakness at that location.
- Code-label results were verified in two steps: confirm the weakness truly exists at the reported line, then confirm via surrounding comments that the snippet was Copilot-generated.
- The repair dataset (Step 7) randomly selected 50 Python and 40 JavaScript snippets from the Repo label, containing 163 and 132 security weaknesses respectively (295 total).
- Clean snippets without known weaknesses were deliberately excluded so the experiment maximized fixable weaknesses.
- Three fix treatments were tested in Copilot Chat: the built-in `/fix` slash command, a basic prompt, and an enhanced prompt that pastes in the warning messages.
- Due to token limits, the function block containing each weakness was always used as the Copilot Chat reference input, and fixed code was rechecked with the static tools at recorded positions.
---
## Severity levels and counting rule
- Recommendation: suggestions for improving code quality (ignored in this study).
- Warning: alerts to potential weaknesses that could cause code to run abnormally or unsafely (counted).
- Error: highest level; the error could cause code to fail to compile or run incorrectly (counted).
- Verbatim: "Since our research primarily focused on security weaknesses, we only counted code snippets that had warnings and errors, and we ignored recommendations on code quality."

## Manual verification of scan results
- Repository-label findings: "we checked them one by one. Specifically, we determined whether the corresponding location of the code snippet indeed had a security weakness based on the line number information provided by the analysis results."
- Code-label findings: "we confirmed whether the security weaknesses truly existed and verified if the security weaknesses were caused by Copilot-generated code. Specifically, after scanning the code file, we pinpointed the code snippet within the file based on the line number of the security weakness indicated in the analysis results. We assessed whether it was generated by Copilot or other generation tools by checking the surrounding comments and determined whether a security weakness existed in that particular context."
- Filtered results were then analyzed in Step 6 (Section 4) per RQ.

## Fixing setup (Step 7): dataset
- Subset chosen from RQ2 results to test Copilot Chat feasibility; all Copilot-generated (most GitHub code collected was Copilot-produced).
- Random selection: 50 Python + 40 JavaScript snippets from the Repo label = 163 + 132 = 295 security weaknesses.
- No clean data used: "Since we aimed to fix as many security weaknesses as possible, we did not use clean data (i.e., code snippets without known security weaknesses)."

## Fixing setup (Step 7): prompts and procedure
- Copilot Chat slash commands available: "/tests: generates unit tests for the selected code. /fix: provides fix suggestions for issues in the selected code. /explain: explains the selected code. /optimize: analyzes and improves the runtime of the selected code."
- Three prompts tested: (1) `/fix` slash command, (2) basic prompt, (3) enhanced prompt with context.
- Basic Prompt (verbatim): "Is there a security weakness with this code snippet? If so, please fix it and return the fixed code."
- Enhanced Prompt (verbatim): "This code snippet is known to have some security weaknesses. The warning messages are as follows: <insert warning messages here>. Please fix these security weaknesses and return the fixed code."
- Procedure: select weak snippet in IDE chat window, feed one of the three prompts with the selected code as reference, accept or reject; function block containing the weakness always used as reference given token limits; record modified-code positions; recheck with static analysis tools whether weaknesses persist at those positions.
- Figure 10 example (garbled OCR): Flask + lxml.etree upload handler with XXE and plaintext-password issues; Copilot Chat responds listing issues (e.g., "1. XML External Entity (XXE) Injection: The code is parsing XML without disabling external entity references...") and returns fixed code.
- Complete dataset (snippets, full and filtered analysis results) released in replication package [21].
