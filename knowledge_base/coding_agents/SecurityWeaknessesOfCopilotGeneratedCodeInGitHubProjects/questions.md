# Retrieval Practice: Security Weaknesses of Copilot-Generated Code in GitHub Projects: An Empirical Study

### Q1. What are the headline numbers of the study — dataset size, weakness rates, CWE coverage, and Copilot Chat fix rate?

> [!tip]- Answer
> The study analyzes 733 AI-generated snippets (672 Copilot, plus CodeWhisperer and Codeium), finding weaknesses in 29.5% of Python and 24.2% of JavaScript snippets across 43 CWE categories led by CWE-330, CWE-94, and CWE-79.
> Eight of the 43 CWEs are on the 2023 CWE Top-25, and feeding Copilot Chat with static-analysis warning messages fixed up to 55.5% of issues.
> The authors attribute the risk to training on billions of lines of public code containing unsafe patterns, including Codex pre-training on buggy GitHub data. See [[wiki/01-abstract-introduction|Abstract and Introduction]].

### Q2. What is the study's scope and how does it differ from Pearce et al.'s security work on code generators?

> [!tip]- Answer
> The study collects Copilot plus CodeWhisperer and Codeium code actually reused in GitHub projects (for generalizability) and checks it with static analysis across all CWE types in an open-source setting.
> Prior work showed high functional effectiveness (e.g., 91.5% valid-code rate) but mixed developer-experience and security results, including Pearce et al.'s finding of 40% CWE-flagged suggestions across 89 prompted scenarios.
> This study differs by using developer-written production code from GitHub rather than author-prompted high-risk scenarios, and by using multiple analyzers over all CWE types instead of scenario-targeted CWEs. See [[wiki/02-background-copilot-usage|Background: Copilot Usage and Related Work]].

### Q3. Why does the study use static analysis, which tools does it combine, and what is the static/dynamic trade-off?

> [!tip]- Answer
> Static analysis analyzes programs without executing them, giving greater coverage at low cost, but it can be unsound and imprecise; dynamic analysis captures real runtime behavior (more sound/precise) but is incomplete, narrow-coverage, and expensive.
> The study therefore scans each snippet with two tools — CodeQL (general-purpose, rule-based) plus a language-tailored tool (Cppcheck and Bandit, i.e., Bandit for Python and ESLint for JavaScript) — to catch weaknesses from different perspectives and avoid omissions.
> This follows prior practice such as Pearce et al. using CodeQL and Siddiq et al. using Bandit on generated code. See [[wiki/03-static-analysis-background|Static Analysis Background]].

### Q4. What is RQ3 and how was the 733-file dataset collected and filtered?

> [!tip]- Answer
> RQ3 asks "Can Copilot Chat help fix the security weaknesses found in the code generated by Copilot?" and answers it with a loop: collect generated code → analyze for weaknesses → attempt fixes in Copilot Chat → re-analyze the fix.
> Collection used the GitHub REST API with {by, use, with} + {GitHub Copilot, CodeWhisperer, Codeium} keywords restricted to Python and JavaScript, yielding 3,589 results after dedup (3,141 Code-label, 445 Repository-label).
> Filtering kept fully Copilot-generated Repository-label projects and Code-label files with Copilot-attribution comments while excluding practice-problem files, with two authors agreeing at Cohen's Kappa 0.84. See [[wiki/04-research-questions-design|Research Questions and Study Design]].

### Q5. What is the final dataset composition after labeling agreement, and what kind of projects hold the generated code?

> [!tip]- Answer
> Disagreements were resolved by negotiated agreement, retaining 116 Repository-label projects and 335 Code-label files for a final 733-file dataset: 672 Copilot, 38 CodeWhisperer, and 23 Codeium, split into 419 Python (190 Repository + 229 Code) and 314 JavaScript (208 Repository + 106 Code).
> Repository-label files count wholesale as AI-generated per their README, while Code-label files contain only snippets whose AI origin is confirmed later via warnings plus comments.
> Host projects tend to be small and low-popularity individual/small-team efforts, with the notable exception of OnmyojiAutoScript (1,672 stars, 505 forks). See [[wiki/05-data-collection-filtering|Data Collection, Labeling Agreement, and Filtering]].

### Q6. How large are the dataset files and which application domains dominate per language?

> [!tip]- Answer
> Combined files average 183.38 LoC (median 74, min 7, max 4,394, std ±390.83), with Python larger (mean 218.22, median 92) than JavaScript (mean 136.89, median 63).
> Authors consensus-coded six domains — Game, Web Application, Utility Tool, AI Application, Network Communication, Others — with Python led by Utility Tool (39.0%) and JavaScript by Web Application (49.8%).
> Each snippet was dual-scanned (CodeQL plus Bandit/ESLint), with 14 duplicate Bandit and 2 duplicate ESLint results deduplicated before counting. See [[wiki/06-dataset-characteristics|Dataset characteristics]].

### Q7. How were scanner findings verified as real Copilot-generated weaknesses, and how was the Copilot Chat repair experiment set up?

> [!tip]- Answer
> Only Warning and Error severity findings counted (Recommendations excluded); Repository-label hits were checked line-by-line for real weaknesses, while Code-label hits additionally required comment evidence that the snippet was Copilot-generated.
> The repair subset randomly selected 50 Python + 40 JavaScript Repository-label snippets containing 163 + 132 = 295 weaknesses, deliberately excluding clean snippets to maximize fixable cases.
> Three treatments were tested in Copilot Chat — the built-in `/fix` command, a basic prompt, and an enhanced prompt pasting in the warning messages — using the enclosing function block as input and rechecking fixes with the analyzers. See [[wiki/07-methodology-scan-and-fix|Scanning methodology and Copilot Chat fix setup]].

### Q8. RQ1: what fraction of the 733 snippets contained weaknesses, and how are weaknesses distributed per snippet?

> [!tip]- Answer
> A snippet counted as vulnerable if either of its two language tools flagged it after manual filtering, with two-author agreement at Kappa 0.85 (Repository) and 0.82 (Code): 200 of 733 snippets (27.3%) were vulnerable — 124 of 419 Python (29.5%) and 76 of 314 JavaScript (24.2%).
> The 200 vulnerable snippets held 628 total weaknesses (387 Python, 241 JavaScript), averaging ~3 per snippet (combined mean 3.14, median 2.00, max 22 in a 1,595-LoC file; Python mean 3.12/median 2.00, JavaScript mean 3.17/median 1.00).
> Over half of vulnerable snippets (102 of 200, i.e., 13.9% of all 733; 65 Python, 37 JavaScript) had more than one issue. See [[wiki/08-rq1-prevalence|RQ1: How Secure Is the Code Generated by Copilot]].

### Q9. How were warnings mapped to CWEs, and which CWE types dominate overall?

> [!tip]- Answer
> Two authors independently mapped warnings to CWE IDs over ten days at Kappa 0.82, resolving ties with a third author as security expert, yielding 628 CWE instances of 43 types in the 200 vulnerable snippets.
> CWE-330 (Use of Insufficiently Random Values) dominates with 114 instances (18.15%), followed by CWE-94 Code Injection (62, 9.87%), CWE-79 Cross-site Scripting (60, 9.55%), and CWE-78 OS Command Injection (39, 6.21%).
> Of the 628 instances, 233 map to eight MITRE 2023 Top-25 CWEs, and patterns split by language (Python: data/system calls) and by domain and language-within-domain (e.g., Web: JavaScript CWE-79 vs. Python CWE-89). See [[wiki/09-cwe-classification|CWE Classification of Copilot-Generated Weaknesses]].

### Q10. What are the top-5 CWE types per language?

> [!tip]- Answer
> Python's top five are CWE-330, CWE-78 (OS Command), CWE-427 (Uncontrolled Search Path Element), CWE-457 (Use of Uninitialized Variable), and CWE-772 (Missing Release of Resource), while JavaScript's are CWE-94 (Code Generation Control), CWE-79 (XSS), CWE-22 (Path Traversal), CWE-685 (Wrong Number of Arguments), and CWE-770 (Unlimited Resource Allocation).
> The ranks diverge at every position (rank 1: CWE-330 vs. CWE-94; rank 2: CWE-78 vs. CWE-79; rank 3: CWE-427 vs. CWE-22; rank 4: CWE-457 vs. CWE-685; rank 5: CWE-772 vs. CWE-770).
> Per-domain breakdowns appear in Fig. 14 (Python) and Fig. 15 (JavaScript), and the same chunk previews RQ3 fix rates of 19.3% (`/fix`), 31.8% (basic), and 55.5% (enhanced) over 295 CWEs. See [[wiki/10-cwe-distribution-by-language|CWE Distribution by Language]].

### Q11. Which CWEs does Copilot Chat fix well or fail on under `/fix`, basic, and enhanced prompts?

> [!tip]- Answer
> Fig. 17 reports before→fixed counts per prompt, with enhanced prompts best overall — e.g., CWE-330 goes 55 before → 5 (9.1%) via `/fix`, 13 (23.6%) via basic, 54 (98.2%) via enhanced; CWE-79 reaches 21/30 (70.0%) via enhanced versus 0% via `/fix`.
> Fully fixed under all three prompts are CWE-20 (2/2), CWE-259 (12/12), CWE-456 (3/3), and CWE-571 (4/4), while CWE-284 (13), CWE-457 (1), CWE-732 (1), and CWE-78 (15) are fixed by none.
> CWE-94 is the largest hard case (42 before, only ~14–17% fixed by any prompt), and the chunk's interleaved RQ1/RQ2 text reiterates ~a quarter of snippets weak with 628 weaknesses of 43 types. See [[wiki/11-rq3-copilot-chat-fixes|RQ3: Copilot Chat Fixes]].

### Q12. What does the discussion conclude about Top-25 versus rare CWEs and about domain/language patterns?

> [!tip]- Answer
> Eight identified CWEs are on the 2023 Top-25 yet cover over 200 weaknesses (37.1% of 628), showing the most dangerous known weaknesses are prevalent in AI-generated code, while some Top-25 entries are absent (possibly sanitized) and 30 non-Top-25 types persist — e.g., a single but high-risk CWE-732 permission-assignment instance.
> CWE types track context: games lean to CWE-330/CWE-284, Utility Tools show high proportions from diverse inputs, and Network Communication shows relatively fewer weaknesses (attributed to mature protocols and strict standards).
> Language splits hold Python toward CWE-330/CWE-427/CWE-78 (system-level/automation) and JavaScript toward CWE-22/CWE-94 (Node.js file/dynamic execution), including Python CWE-89 (SQL injection) versus JavaScript CWE-79 (XSS) in web code. See [[wiki/12-discussion-top-cwes|Discussion: Top CWEs and Severity]].

### Q13. What five preventive practices do the authors recommend for AI-generated code?

> [!tip]- Answer
> They recommend CWE-aware targeted countermeasures by language (path validation/dynamic execution for JavaScript; system calls/library loading for Python), careful selection among suggestions with tool assistance, and using the CWE Top-25 plus analyzer docs and MITRE mitigations as standardized audit/remediation guides.
> They further recommend security-from-the-start prompt engineering and security-plus-utility instruction tuning, matching the fix method to complexity (quick Copilot Chat for access-control/config issues; developer review for multi-layered logic), and pairing static-analysis warnings with detailed Copilot Chat context and instructions to raise fix success. See [[wiki/13-implications-prevention|Prevention of Security Weaknesses]].

### Q16. (Evaluation) Given the study's prevalence, CWE, and fix-rate evidence, what Copilot workflow should a team adopt and why?

> [!tip]- Answer
> A team should require dual-tool static scanning (CodeQL plus Bandit/ESLint) on every Copilot-generated snippet with Warning/Error triage, since ~27% of snippets are weak, average ~3 issues each, span 43 CWEs, and over a third of instances sit in Top-25 CWEs.
> Fixes should route through Copilot Chat with warning-fed enhanced prompts rather than bare `/fix`, because enhanced prompts fixed 55.5% overall (98.2% of CWE-330) versus 19.3% for `/fix`, while zero-fix CWEs (CWE-78, CWE-284) and complex logic still mandate human review.
> Prevention should be language- and domain-targeted (e.g., XSS/path-traversal checks in JavaScript web code, injection/search-path checks in Python utilities) per the study's context-dependent patterns. See [[wiki/13-implications-prevention|Prevention of Security Weaknesses]].
