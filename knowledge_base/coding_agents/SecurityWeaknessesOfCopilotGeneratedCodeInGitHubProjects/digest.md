# Security Weaknesses of Copilot-Generated Code in GitHub Projects: An Empirical Study — Digest

## 1. [[wiki/01-abstract-introduction|Abstract and Introduction: Security Weaknesses of Copilot-Generated Code in GitHub Projects]]
**In one sentence:** This empirical study analyzes 733 Copilot/CodeWhisperer/Codeium-generated snippets from GitHub projects, finds a high rate of security weaknesses (29.5% Python, 24.2% JavaScript across 43 CWE categories), and shows up to 55.5% can be fixed via Copilot Chat fed with static-analysis warnings.
## Key points
- Analyzed 733 code snippets generated by GitHub Copilot and two other AI tools (CodeWhisperer and Codeium) collected from GitHub projects.
- 29.5% of Python snippets and 24.2% of JavaScript snippets contained security weaknesses.
- Weaknesses span 43 Common Weakness Enumeration (CWE) categories, including CWE-330 (Use of Insufficiently Random Values), CWE-94 (Improper Control of Generation of Code), and CWE-79 (Cross-site Scripting).
- Eight of the 43 CWEs are among the 2023 CWE Top-25, highlighting their severity.
- Feeding Copilot Chat with warning messages from static analysis tools fixed up to 55.5% of the security issues in Copilot-generated code.
- LLM-based tools are trained on billions of public open-source lines of code that include unsafe coding patterns, so generated code may inherit security weaknesses.
- GitHub Copilot's underlying Codex model was pre-trained on untrusted GitHub data known to contain buggy programs, and Snyk reports Copilot may replicate existing weaknesses when the user's codebase already contains them.
- Copilot's algorithms are incentivized to suggest code to be accepted rather than code with other qualities (e.g., readability), and GitHub states users are responsible for ensuring security and quality of their code.

## 2. [[wiki/02-background-copilot-usage|Background: Copilot Usage and Related Work]]
**In one sentence:** This chunk sets up the study's scope — real Copilot/CodeWhisperer/Codeium-generated code collected from GitHub and checked with static analysis tools for all CWE types — and surveys related work showing code generators are functionally effective but their security remains under-examined.
## Key points
- The study collects code generated by Copilot plus CodeWhisperer and Codeium that has actually been used in GitHub projects, explicitly to increase generalizability beyond Copilot alone.
- Collected snippets are analyzed with static analysis tools and classified with Common Weakness Enumeration (CWE) across all CWE types, framed through the lens of the open-source development environment.
- Prior functional evaluations report high effectiveness: Yetistiren et al. report Copilot generates valid code with a 91.5% success rate, while Sobania et al. found no significant difference vs. a Genetic Programming generator and Nguyen and Nadi tested 33 LeetCode problems in four languages.
- Developer-experience studies report Copilot provides a useful starting point but does not necessarily improve task time or success rate, with difficulties understanding, editing, and debugging suggestions (Vaithilingam et al.) and a 20-participant interaction theory (Barke et al.).
- Security-focused prior work reports substantial weakness rates in prompted generations: Pearce et al. found 40% of suggestions across 89 cybersecurity scenarios contained CWE-classified bugs, and Elgedawy et al. compared four models over nine tasks with 61 code outputs.
- Sandoval et al. and Asare et al. compare AI-assisted vs. human code: Sandoval et al. report AI users produced critical security errors at no more than 10% of the control-group rate, while Asare et al. found Copilot differs by vulnerability type but is "not as bad as" human developers.
- This study differentiates itself from Pearce et al. by using developer-written production code from GitHub rather than author-prompted high-risk scenarios, and by using various static analysis tools to examine all CWE types rather than only scenario-targeted CWEs.

## 3. [[wiki/03-static-analysis-background|Static Analysis Background]]
**In one sentence:** Static analysis is a low-cost, high-coverage but unsound/imprecise way to detect vulnerabilities without execution, so the study combines general-purpose CodeQL with language-specific tools (Cppcheck, Bandit) to cover multiple languages and perspectives.
## Key points
- Vulnerability detection uses static, dynamic, or hybrid analysis, and detecting vulnerabilities is critical to improve security and ensure quality.
- Static analysis offers greater coverage and analyzes programs without executing them, but it can be unsound and imprecise.
- Dynamic analysis is more sound and precise because it captures actual runtime behaviour, but it can be incomplete and lacks coverage.
- Static analysis tools are widely used for security analysis due to ease of use and low cost compared with dynamic analysis.
- Common tools listed via OWASP and Snyk include CodeQL (general-purpose automatic analysis), FindBugs/SpotBugs for Java, ESLint for JavaScript, Bandit for Python, and GoSec for Go.
- Prior work examples: Kaur et al. compared tools on C/C++ and Java; Tomasdottir et al. studied ESLint; Pearce et al. used CodeQL on generated Python and C++; Siddiq et al. used Bandit on generated Python.
- Using multiple tools discovers weaknesses from different perspectives and levels, avoiding omissions and improving accuracy.
- This study first scanned collected snippets with CodeQL (open-source; supports Java, JavaScript, C++, C#, Python; finds weaknesses based on known weaknesses/rules), then supplemented with language-tailored tools (Cppcheck and Bandit).

## 4. [[wiki/04-research-questions-design|Research Questions and Study Design]]
**In one sentence:** RQ3 asks whether Copilot Chat can fix security weaknesses in Copilot-generated code via a collect → analyze → fix-in-Chat → re-analyze loop, and the study collects Python/JavaScript Copilot-labeled code from GitHub using {by, use, with} + tool-name keywords, deduplicated to 3,589 results and manually filtered with high agreement (Kappa 0.84).
## Key points
- RQ3 is: "Can Copilot Chat help fix the security weaknesses found in the code generated by Copilot?" because most weaknesses in RQ1/RQ2 come from Copilot.
- The RQ3 method is a loop: collect generated code → analyze for weaknesses → check for fixes in Copilot Chat → re-analyze to check if the fix is correct.
- Rationale given: "The purpose of Copilot Chat is to assist developers by answering questions about their code or providing fixes for issues identified in the code," integrated with Copilot and claimed to assist in fixing security weaknesses.
- Search used GitHub REST API with keyword combinations {by, use, with} + {GitHub Copilot, CodeWhisperer, Codeium}, restricted to Python and JavaScript, retaining Code-label files and Repo-label projects.
- After removing duplicates there were 3,589 search results: 3,141 from the Code label and 445 from the Repository label (raw Table 1 total 9,927 before dedup).
- Filtering kept Repository-label projects fully generated by Copilot per description/README (Criterion 1) and Code-label files with comments showing Copilot generation (Criterion 2), and excluded simple practice-problem files such as LeetCode/BOJ-number exercises (Exclusion 1).
- Two authors independently filtered all data over two weeks with Cohen's Kappa 0.84 (>0.8), indicating high agreement.
- Python and JavaScript were chosen as dynamically typed languages needing no compilation database, the two most popular languages with developers and most frequently used with Copilot.

## 5. [[wiki/05-data-collection-filtering|Data Collection, Labeling Agreement, and Filtering]]
**In one sentence:** Two authors labeled GitHub search results, resolved disagreements by negotiated agreement, and retained 116 Repository-label projects and 335 Code-label files, yielding a 733-file dataset (672 Copilot, 38 CodeWhisperer, 23 Codeium) dominated by small, low-popularity projects.
## Key points
- Labeling disagreements between the two authors were resolved through a negotiated agreement approach [5] during a meeting.
- Manual filtration retained 116 projects under the Repository label and 335 code files under the Code label.
- Repository-label files are treated wholesale as AI-generated because the README states all code was generated by Copilot and other tools.
- Code-label files are known to contain only snippets (possibly a few lines) of AI-generated code, with attribution decided later via warning messages plus code comments (Section 3.3.2).
- Final dataset: 733 distinct code files — 672 from Copilot, 38 from CodeWhisperer, and 23 from Codeium.
- Language split: Python 419 files (190 Repository + 229 Code); JavaScript 314 files (208 Repository + 106 Code).
- Projects with AI-generated code tend to be small and low-popularity, possibly individual/small-team efforts, consistent with Yu et al. [83]; low popularity may correlate with project newness since Copilot itself is recent.
- Notable exception: the project OnmyojiAutoScript received 1,672 stars and 505 forks.

## 6. [[wiki/06-dataset-characteristics|Dataset characteristics: lines of code and application domains]]
**In one sentence:** Files containing Copilot-generated code vary widely in size (mean 183.38 LoC, median 74) and fall into six application domains dominated by Utility Tool and Web Application code, which the authors scan with CodeQL plus Bandit/ESLint before filtering duplicates.
## Key points
- Python files (n described in Fig. 9): mean 218.22 LoC, median 92.00, min 7.00, max 4394.00, std dev ±447.71.
- JavaScript files: mean 136.89 LoC, median 63.00, min 8.00, max 4005.00, std dev ±292.81.
- Combined Python+JavaScript: mean 183.38 LoC, median 74.00, min 7.00, max 4394.00, std dev ±390.83.
- Generated code was categorized into six application domains: Game, Web Application, Utility Tool, AI Application, Network Communication, and Others, after authors discussed "until they reached a consensus."
- Python is led by Utility Tool (39.0%), followed by Game (15.9%), Web Application (15.6%), AI Application (15.6%), Network Communication (8.2%), and Others (5.4%).
- JavaScript is led by Web Application (49.8%), followed by Utility Tool (30.1%), Game (8.5%), Network Communication (5.7%), AI Application (2.8%), and Others (2.8%).
- The authors chose static over dynamic analysis because "the static analysis has higher coverage and is able to analyze programs without executing them," while dynamic analysis "suffers from limited coverage and can be expensive."
- Each snippet was scanned with two tools (CodeQL plus Bandit for Python / ESLint for JavaScript); initial filtering removed 14 duplicate results by Bandit and 2 by ESLint, keeping one copy.

## 7. [[wiki/07-methodology-scan-and-fix|Scanning methodology and Copilot Chat fix setup]]
**In one sentence:** Static-analysis findings were filtered to Warning/Error severity, manually verified as Copilot-generated via line numbers and comments, then a 90-snippet / 295-weakness subset was repaired with Copilot Chat using three prompts and rechecked with the analyzers.
## Key points
- Tool severities are Recommendation (code-quality suggestions), Warning (potential abnormal/unsafe behavior), and Error (may fail to compile or run) — only Warning and Error findings were counted.
- Repository-label results were checked one by one against the line numbers in the analysis output to confirm a real weakness at that location.
- Code-label results were verified in two steps: confirm the weakness truly exists at the reported line, then confirm via surrounding comments that the snippet was Copilot-generated.
- The repair dataset (Step 7) randomly selected 50 Python and 40 JavaScript snippets from the Repo label, containing 163 and 132 security weaknesses respectively (295 total).
- Clean snippets without known weaknesses were deliberately excluded so the experiment maximized fixable weaknesses.
- Three fix treatments were tested in Copilot Chat: the built-in `/fix` slash command, a basic prompt, and an enhanced prompt that pastes in the warning messages.
- Due to token limits, the function block containing each weakness was always used as the Copilot Chat reference input, and fixed code was rechecked with the static tools at recorded positions.

## 8. [[wiki/08-rq1-prevalence|RQ1: How Secure Is the Code Generated by Copilot in GitHub Projects?]]
**In one sentence:** Of 733 tool-generated Python and JavaScript snippets scanned with CodeQL plus Bandit/ESLint and manually filtered, 27.3% (200) contained security weaknesses, averaging 3 weaknesses per vulnerable snippet and exceeding one weakness in over half of vulnerable snippets.
## Key points
- 733 snippets were collected (672 Copilot, 38 CodeWhisperer, 23 Codeium) across Python and JavaScript and scanned with two tools per language: CodeQL plus Bandit for Python and CodeQL plus ESLint for JavaScript.
- A snippet counted as vulnerable if at least one of the two tools flagged it, after manual filtering that kept only results marked 1 and discarded Code-label findings not traceable to tool-generated code via preceding prompt comments.
- Two authors filtered independently over two weeks with Cohen's Kappa 0.85 (Repository label) and 0.82 (Code label), both above 0.8, then aggregated the kept results to count snippets with weaknesses.
- 200 of 733 snippets (27.3%) contained security weaknesses: 124 of 419 Python snippets (29.5%) and 76 of 314 JavaScript snippets (24.2%).
- 102 of the 200 vulnerable snippets (over half; 13.9% of all 733) had more than one security issue: 65 Python (15.5%) and 37 JavaScript (11.8%).
- 628 total security weaknesses were found in the 200 snippets (387 in Python, 241 in JavaScript), averaging ~3 per snippet regardless of language, with a maximum of 22 weaknesses in a single 1,595-LoC snippet.
- Per-snippet distributions (Fig. 13): Python mean 3.12 / median 2.00 / max 22 / std 3.79; JavaScript mean 3.17 / median 1.00 / max 19 / std 4.13; combined mean 3.14 / median 2.00 / max 22 / std 3.91 (all min 1.00).

## 9. [[wiki/09-cwe-classification|CWE Classification of Copilot-Generated Weaknesses]]
**In one sentence:** Two authors manually mapped scanner warnings to CWE IDs (Cohen's Kappa 0.82, with a security expert breaking ties) and found 628 CWE instances of 43 types in 200 snippets, led by CWE-330 (18.15%), with 233 instances belonging to eight MITRE 2023 Top-25 CWEs.
## Key points
- Manual CWE mapping was done independently by two authors over ten days with Cohen's Kappa of 0.82 (above 0.8, high agreement); disagreements were discussed and resolved with a third author acting as security expert.
- 200 code snippets with security weaknesses contained 628 CWE occurrences across 43 CWE types, showing varied weaknesses when using Copilot and other code generation tools.
- CWE-330 (Use of Insufficiently Random Values) dominates at 114 occurrences (18.15%), followed by CWE-94 Code Injection 62 (9.87%), CWE-79 Cross-site Scripting 60 (9.55%), and CWE-78 OS Command Injection 39 (6.21%).
- 233 of the 628 weaknesses map to eight CWEs on the MITRE 2023 CWE Top-25 list (used as baseline since snippets are mainly from 2022–2023), including high-ranking CWE-79 and CWE-78.
- CWE patterns differ by language: Python weaknesses center on data processing and system calls (e.g., CWE-78 OS Command Injection, CWE-427 Uncontrolled Search Path Element), while JavaScript centers on dynamic code generation and web issues (e.g., CWE-94 Code Injection, CWE-79 Cross-site Scripting).
- CWE patterns differ by application domain and by language within a domain: Python's worst domain is Utility Tool versus JavaScript's Web Applications; within Web Applications, JavaScript's top CWE is CWE-79 (XSS) while Python's is CWE-89 (SQL Injection).
- Low-frequency CWEs (many under 1%) show weakness types track the specific scenarios where developers use generation tools, so vigilance and caution remain necessary when programming.

## 12. [[wiki/12-discussion-top-cwes|Discussion: Top CWEs and Severity in Copilot-Generated Code]]
**In one sentence:** Copilot-generated code contains 43 diverse CWE types, with 8 of the 2023 CWE Top-25 accounting for 37.1% (over 200 of 628) of identified weaknesses, while the remaining 30 non-Top-25 types and clear domain/language patterns mean developers face varied, context-dependent security risks.
## Key points
- The dataset contains 43 distinct CWE types, so a single body of Copilot-generated code can hold multiple different weakness types.
- Eight of the identified CWEs appear in the 2023 CWE Top-25 list, covering more than 200 weaknesses or 37.1% of the 628 identified, showing the most prevalent and dangerous known weaknesses are also prevalent in AI-generated code.
- Some 2023 CWE Top-25 entries were not detected at all, suggesting Copilot may sanitize or prevent certain weaknesses from being suggested.
- Thirty identified weakness types fall outside the Top-25; they are less common but still exploitable, e.g. a single instance of CWE-732 (Incorrect Permission Assignment for Critical Resource) that is rare yet high-risk when it occurs.
- CWE types track application domains: game code leans toward CWE-330 (Use of Insufficiently Random Values) and CWE-284 (Improper Access Control); Utility Tools show a relatively high proportion, attributed to diverse user inputs.
- Language patterns differ: Python snippets skew toward CWE-330, CWE-427 (Uncontrolled Search Path Element), and CWE-78 (OS Command Injection), while JavaScript snippets skew toward CWE-22 (Path Traversal) and CWE-94 (Code Injection), linked to Node.js file operations/dynamic execution versus Python system-level operations and automation scripts.
- Web development splits the same way: Python back-end/database interaction is prone to CWE-89 (SQL Injection) when input is embedded without parameterized queries or validation, while user-facing JavaScript is prone to CWE-79 (Cross-site Scripting), CWE-94, and CWE-22, amplified by dependency complexity and sensitive-data handling.
- Network Communication code shows a relatively lower proportion of weaknesses, attributed to high security demands, mature protocols, stringent industry standards, and built-in transmission safeguards.

## 13. [[wiki/13-implications-prevention|Prevention of Security Weaknesses in AI-Generated Code]]
**In one sentence:** The authors recommend five preventive practices — targeted CWE-aware countermeasures by language, CWE Top-25-based standardized assessment, security-aware prompt engineering, matching fix method to issue complexity, and pairing static analysis warnings with detailed Copilot Chat instructions.
## Key points
- Apply targeted countermeasures guided by CWE frequency in the dataset, focusing on language-specific high-risk CWEs when using Copilot for Python vs JavaScript.
- Select among code suggestions carefully (with tool assistance) because security weaknesses appear in certain suggestions but not all [43].
- Watch language-specific risks: path validation (e.g., CWE-22 Path Traversal) and dynamic execution (e.g., CWE-94 Code Injection) skew toward JavaScript, while system calls and library loading skew toward Python.
- Use the CWE Top-25 list as a standardized guide for understanding, auditing, and remediating common dangerous weaknesses such as privilege control and environment configuration.
- Refer to static analysis tool documentation fixes [8] and MITRE mitigation measures [46] for standardized remediation of common weaknesses.
- Incorporate security from the start via prompt engineering (e.g., prompt patterns in [79]) and joint security-plus-utility instruction tuning [32].
- Distinguish issue complexity: standard fixes like access control and environment configuration suit quick Copilot Chat fixes, while complex multi-layered-input logic needs developer review and design.
- Pair static analysis tools with Copilot Chat: feed the tool's specific warning plus detailed context and clear instructions to significantly improve fix success.

## The argument in five moves
1. Real Copilot/CodeWhisperer/Codeium code reused in GitHub projects is worth studying for security, because lab prompts miss production reality and prior work focused on correctness over weaknesses.
2. A GitHub keyword search ({by, use, with} + tool names) for Python/JavaScript, deduplicated to 3,589 results and manually filtered with high agreement, yields a 733-file dataset of small, low-popularity projects across six application domains.
3. Dual-tool static scans (CodeQL plus Bandit/ESLint) with manual Warning/Error verification show ~27% of snippets are weak (29.5% Python, 24.2% JavaScript), averaging ~3 weaknesses each across 43 CWE types led by CWE-330, CWE-94, and CWE-79, including eight 2023 Top-25 entries.
4. CWE patterns are context-dependent by language and domain — Python toward system calls and data handling, JavaScript toward dynamic execution and web issues — while some Top-25 types are absent and rare non-Top-25 types remain exploitable.
5. Copilot Chat can repair part of its own damage — /fix resolves ~19%, basic prompts ~32%, and warning-fed enhanced prompts ~55% — with stark per-CWE variance (near-total on CWE-330/CWE-259/CWE-685, zero on CWE-78/CWE-284), so continuous scanning plus warning-enriched chat repair and targeted, complexity-aware prevention are required.
