# Practices and Challenges of Using GitHub Copilot:

**Paper:** [Practices and Challenges of Using GitHub Copilot: An Empirical Study](https://arxiv.org/abs/2303.08733v3)

## Human Readable TL;DR

Think of GitHub Copilot as an eager junior pair-programmer who types really fast but sometimes hands you code that looks right and doesn't run, so this paper eavesdrops on hundreds of real developers swapping stories on Stack Overflow and GitHub Discussions to learn where that assistant actually helps and where it trips people up. The big picture is that developers love it like a power drill for boring, repetitive work — cranking out tests, data-wrangling code, and front-end boilerplate in JavaScript and Python — but they grumble when it offers only one shaky suggestion, gets worse as files grow, or raises worries about who gets to see their code. The authors' advice boils down to treating Copilot like a double-edged sword: stick to popular languages and mainstream editors where setup help is easy to find, enjoy the speed boost, but keep your eyes open and review everything it writes.

## TL;DR

This paper presents an empirical study of the practices and challenges of using GitHub Copilot from the practitioners' perspective, mining 169 Stack Overflow posts and 655 GitHub Discussions collected on 23 November 2022. Guided by six research questions, the authors map which programming languages, IDEs, and technologies developers pair with Copilot, what functions they implement with it, and what benefits versus limitations they report, using descriptive statistics for the first three questions and the Constant Comparison qualitative method for the rest. The results show Copilot concentrated around JavaScript and Python work — front-end element control and machine-learning tasks such as data and image processing — inside mainstream IDEs, with useful code generation (49.0% of benefit mentions) and faster development as the dominant upsides, set against complaints about too few suggestions, degrading quality in large files, code-privacy worries, unfriendly experiences, and integration difficulty in lesser-known IDEs. The authors conclude that Copilot is a double-edged sword that optimizes workflows when matched to suitable languages, technologies, and IDEs, and they outline future questionnaire and interview work on when, for what purposes, and by whom it should be used.

## Problem & Motivation

Prior research on Copilot had clustered around code correctness, quality, security, readability, and developer expectations, yet offered little empirically grounded evidence about how developers actually use the tool day to day and what goes wrong when they do. The authors set out to fill that gap by turning to first-hand developer voices rather than lab experiments, asking which languages, editors, and technologies practitioners combine with Copilot, which functions they delegate to it, and which benefits, limitations, and challenges emerge in real programming activities. The motivation is frankly practical: the answers should help developers choose an IDE or technology stack, decide whether Copilot fits a given task, and weigh its advantages against its restrictions before committing to it.

## Main Original Ideas

1. **Six-question empirical framing.** The study organizes the entire inquiry into RQ1–RQ6 covering languages, IDEs, technologies, implemented functions, benefits, and limitations/challenges, each paired with an explicit rationale about the decision it is meant to inform, so the paper reads as a systematic map of Copilot practice rather than a single benchmark.
2. **Dual-source mining design.** Instead of relying on Stack Overflow alone, the authors combine 169 filtered Stack Overflow posts (from 557 hits for the term "copilot", deduplicated to 521 and manually filtered) with all 655 discussions in the "Copilot" category of GitHub product discussions, exploiting the Q&A format of the former and the broader intentions of the latter, such as error reports and development conversations.
3. **Disciplined extraction and analysis split.** Every data item (D1–D6) is counted only when explicitly mentioned as used with Copilot, with repeat mentions by one developer in a single post counted once, and the analysis applies descriptive statistics to the language/IDE/technology questions while reserving Constant Comparison coding — with pilot labelling (Cohen's Kappa 0.773), multi-author review, and consensus — for functions, benefits, and limitations.

## Key Findings

Developers pair Copilot most visibly with JavaScript for front-end work and Python for machine-learning work, alongside technologies such as Node.js (41.7% in the extracted figure), .NET (15.0%), Vue, React, and Ajax, and they implement data processing above all (26.7% of function mentions), followed by testing, front-end element control, and image processing. Tooling concentrates heavily in mainstream IDEs — Visual Studio Code, Visual Studio, IntelliJ IDEA, NeoVim, and PyCharm together account for 85.9% of IDE use with Copilot — while lesser-known editors such as Sublime Text bring installation and support friction. On the upside, the benefits table is led decisively by useful code generation (24 cases, 49.0%), which developers say reduces workload and rescues them when they have no idea how to write something, with faster development (16.3%), better code quality described as shorter and more correct code (10.2%), adaptation to personal code patterns, and a fun, non-annoying experience rounding out the list. These positives are mirrored by persistent complaints: Copilot sometimes offers too few solutions ("multiple solution is too little"), suggests code that "don't work" with quality that "becomes unacceptable" as files grow, triggers code-privacy fears about reuse of developers' code without permission, and delivers an unfriendly experience for a vocal minority, which is why the authors stress weighing integration, experience, budget, and privacy before adopting it.

## Suggestions & Future Directions

For practitioners, the clearest recommendation is to use Copilot inside mainstream IDEs, where installation is smooth and problems are likely already answered on Stack Overflow or GitHub Discussions, and to match it to the tasks where it shines — front-end JavaScript and Python-based data and machine-learning work — rather than forcing it into unsupported setups. More broadly, the authors urge developers to treat adoption as an explicit trade-off between faster, easier coding and the tool's restrictions, letting AI absorb redundant work only where the language, technology, and editor fit. For researchers, the stated next steps are questionnaire and interview studies digging into when Copilot's challenges flip into advantages and how disadvantages can be converted, along with finer questions of user type — developers, educators, students — and the specific purposes, moments, and people for which Copilot use pays off. The paper also points to replication via its shared dataset of extracted labels and acknowledges validity limits from manual coding bias and from covering only two discussion sources.
