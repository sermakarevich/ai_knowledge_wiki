# Towards Practical and Useful Automated Program Repair for Debugging

**Paper:** [Towards Practical and Useful Automated Program Repair for Debugging](https://arxiv.org/abs/2407.08958v1) — SE 2030 Workshop, November 2024

## Human Readable TL;DR

Imagine calling a plumber who insists on flooding your whole house first just to prove there is a leak — that is how today's automatic bug-fixers work, demanding a full test suite and endless reruns before they help. The authors instead imagine a mechanic who looks over your shoulder while the car is stalled, asks you what strange noise you heard, traces the wiring from that spot, and sketches a few quick fixes for you to preview. Under the hood this means finding the faulty lines from the debugger state alone, asking a language model with a rich description of the failure, and checking candidate fixes by simulating the run rather than restarting the program. Early results from their ROSE prototype suggest this stall-side assistance can already fix many bugs in seconds and measurably speed up human debugging.

## TL;DR

Current automated program repair is impractical for real debugging because it assumes a comprehensive test suite as the correctness criterion, relies on frequent program re-execution that is slow and often infeasible, and largely handles only single-location bugs. The paper envisions PracAPR, an interactive IDE repair system that starts from a debugger-suspended program where a problem is observed, takes a developer-provided problem specification, and performs test-free flow-analysis-based fault localization, combined LLM-based local repair and strategy-driven global repair, and re-execution-free validation via simulated trace comparison with previewable suggestions. It grounds the vision in the existing ROSE test-free repair framework and its repair and user-study results, diagnoses why naive ChatGPT-based prompts fail and how augmented prompts with test input, related methods, and execution traces succeed, and reframes multi-location repair around single-fault multi-location bugs with eight partial-patch relationships driving tailored global strategies.

## Problem & Motivation

Programs are rarely bug-free, and debugging can consume up to half of programming time, which is what makes automated program repair so attractive: automatically generating a patch that corrects a program's misbehavior. Over more than a decade the community has produced over sixty repair techniques, broadly classified as pattern-based, constraint-based, search-based, and learning-based, yet the authors argue these remain far from usable as an everyday debugging aid inside the IDE. The core obstacle is a set of unrealistic assumptions, above all the dependence on a high-quality test suite as the correctness criterion, even though developers often write too few tests or none at all, bugs are frequently reported without any revealing test, and over ninety percent of Defects4J bug-revealing tests were only added after the bug was identified. Prior test-free repair work does not close this gap because it targets narrow bug classes such as heap-property faults or static-analyzer warnings rather than the general semantic bugs encountered while debugging. Compounding this, current approaches require frequent program re-execution for validation, which is difficult when a failure only appears after a long run or inside an interactive session, and which makes repair slow — minutes to hours per bug — while developers are unwilling to wait long for suggestions, especially if the tool were integrated into the IDE where quick responses are expected. A further limitation is that commonly arising complex bugs spanning multiple program locations are barely repairable by existing tools, motivating a repair system designed from the start around the suspended debugger state, developer interaction, speed, and multi-location fixes.

## Main Original Ideas

**1. PracAPR interactive IDE repair vision and pipeline.** The central proposal is PracAPR, an interactive system living in the IDE alongside the debugger that assumes the program is stopped where a problem is observed, asks the developer to describe the problem as a problem specification, and drives all downstream steps — fault localization, patch generation, and validation — from that specification rather than from a test suite. Its five-stage pipeline runs from problem specification to test-free fault localization yielding repair locations, to patch generation with local and global branches, to re-execution-free validation yielding validated patches, and finally to patch presentation where the developer can preview any repair with before-and-after differences and accept it into the program. The explicit design goals are no test suite, no re-execution, and quick suggestions suitable for live debugging.

**2. Test-free flow-analysis-based fault localization from debugger state.** Without tests, PracAPR localizes faults by flow analysis that combines the problem symptom with live debugger values and the current runtime stack to compute a backward slice containing potential repair locations. This turns the suspended execution — what the developer sees as wrong, what the variables currently hold, and how the program got there — into the fault signal, replacing coverage-based spectra that depend on passing and failing test runs.

**3. Re-execution-free validation via simulated trace comparison.** Instead of rerunning the program, PracAPR generates simulated traces through a live-programming mechanism that reflect the real executions of the original and repaired programs, then compares those traces to infer patch correctness. This makes validation possible in settings where recreating the failure environment is costly or impossible, and it is also the key to keeping repair fast enough for interactive use.

**4. ROSE as the proven foundation with preview interaction.** The vision is grounded in ROSE, the authors' existing interactive test-free framework in which the developer chooses a patch for a preview highlighting the code before and after the repair with differences and can ask ROSE to apply it. PracAPR is explicitly planned on top of ROSE, inheriting its fault-localization and simulated-trace validation machinery while improving problem specification through richer failure presentation plus constraint- and natural-language-based specifications, and enhancing validation with learning-based trace comparison over more execution information.

**5. LLM-based local repair with failure-aware augmented prompts.** For single-location fixes, PracAPR relies on a ChatGPT-based component that must accurately infer the problem and return only a small number of promising patches, in contrast to existing ChatGPT prompts that supply just the buggy method, a failing test name, and a failing assertion. The paper shows with the Defects4J Chart_3 `createCopy` example that a shallow failure message like `expected:<101.0> but was:<102.0>` leads ChatGPT to blame the data-copying loop rather than the missing `minY`/`maxY` update in the invoked `add` method, while an augmented prompt adding the failing test code with inputs, definitions of related methods, and an execution trace with line order and key variable and field values lets it correctly diagnose the min/max update failure and generate the right patch. The same discussion acknowledges residual ambiguity — for instance, knowing a start-greater-than-end case is invalid but not whether to throw, return a special value, or do something else — which motivates soliciting targeted user feedback such as expecting an exception, forbidding a line from executing, or forbidding a value.

**6. Hybrid, conversational, and post-processing mitigations for LLM repair.** To push LLM repair further, the authors plan to combine ChatGPT with traditional pattern-based and search-based methods to supply effective patterns and fix ingredients, to use conversational repair that highlights the negative influence of previous patches so the model reflects on its mistakes, and to add post-processing that refines and re-fixes patches. This is framed by an ongoing study asking which bugs ChatGPT fails on, what its most common mistakes are, and how to improve it, treating the language model as a strong but guidable local patch generator rather than a standalone oracle.

**7. Tailored strategy-driven global repair for single-fault multi-location bugs.** For bugs whose single underlying fault requires edits in several places, the paper argues that evaluation on Defects4J as a whole is misguided because the dataset is full of multi-fault bugs that decompose into independent single-fault bugs with different failures, whereas developers fix one failure at a time. Using their own detector they found 118 single-fault multi-location bugs in Defects4J v1.2, of which contemporary approaches repair at most eight, and by analyzing developer ground-truth patches for a sample of about a third (75 bugs) they distill eight partial-patch relationships — definition-use, one-action wrapping, related-issue fixes, different-issue fixes, effectively-one-hunk, setup-use, new-failure-inducing fixes, and fix-plus-undo — that will each drive a specialized global-repair strategy.

## Key Findings

ROSE's test-free machinery proves surprisingly effective: its fault localization includes the correct repair location for eighty-nine percent of tested bugs and its patch validation ranks every correct repair in the top five, while a ROSE-based tool repairs as many as thirty-six of forty QuixBugs and thirty-seven of sixty Defects4J bugs in only seconds rather than minutes or hours. A user study reinforces the practical value, with ROSE helping forty-four percent more participants succeed at a debugging task and reducing debugging time by about sixteen and a half percent, supporting the claim that test-free, fast, previewable repair genuinely eases debugging. On the LLM side, the Chart_3 case study demonstrates both the failure mode and the remedy: shallow prompts produce a confident but wrong loop-condition patch, whereas prompts enriched with test inputs, callee behavior, and traced states yield a correct min/max update, though ambiguity about intended behavior can persist even then. For multi-location repair, the quantitative gap is stark — 118 detected single-fault multi-location bugs versus at most 8 repaired by techniques including DEAR, HERCULES-style evolution, VarFix, and recent neural approaches — and the qualitative output is the eight-way taxonomy of how partial patches relate, learned from developer patches and intended as the blueprint for targeted global repair rather than one-size-fits-all multi-hunk search.

## Suggestions & Future Directions

The immediate agenda is to build PracAPR on top of ROSE with two concrete upgrades: richer interactive problem specification that better presents failure information and accepts more expressive forms such as constraints and natural language to guide localization and validation, and learning-based trace comparison that exploits more execution information for patch ranking. In parallel, the authors propose completing their three-question study of ChatGPT repair failures, mistakes, and improvements, and operationalizing its lessons through feedback-seeking interaction, hybrid pattern and ingredient guidance, mistake-aware conversational repair, and refinement post-processing so that local repair returns few but trustworthy patches. For global repair, the direction is to turn each of the eight partial-patch relationships into a dedicated generation strategy for single-fault multi-location bugs and to evaluate on that properly isolated bug class rather than on raw Defects4J multi-fault instances. The closing hope is that, with these pieces in place, PracAPR takes a significant step toward making automated repair fast, test-free, multi-location-capable, and therefore an everyday part of debugging by 2030.
