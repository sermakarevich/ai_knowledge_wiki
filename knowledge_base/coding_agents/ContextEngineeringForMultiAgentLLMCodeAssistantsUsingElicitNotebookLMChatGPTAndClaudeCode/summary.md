# Context Engineering for Multi-Agent LLM Code Assistants Using Elicit, NotebookLM, ChatGPT, and Claude Code

**Paper:** [Context Engineering for Multi-Agent LLM Code Assistants Using Elicit, NotebookLM, ChatGPT, and Claude Code (Haseeb, 2025)](https://arxiv.org/abs/2508.08322v1)

## Human Readable TL;DR

Imagine a lone handyman sent to renovate a huge unfamiliar house with only a single sticky note of instructions — he will inevitably skip rooms, use the wrong tools, and improvise parts that do not fit. This paper instead proposes sending a whole renovation crew with a proper job folder: one person clarifies the owner's vague request into a punch list, another looks up manuals and how-to guides, a third condenses those into a short cheat sheet, and then a foreman dispatches plumbers, electricians, and an inspector who each see only their own assignment plus the shared house rules. On a real 180,000-line web application the crew finished complex multi-room jobs in one visit far more often than the lone handyman, though the whole operation costs noticeably more in phone calls and coordination.

## TL;DR

Single-agent LLM coders fail on repository-level tasks because a fixed static context (e.g. one CLAUDE.md) cannot supply the task-specific intent, external knowledge, and scattered in-repo details that multi-file changes require, leading to missed edits and hallucinated APIs. The paper defines context engineering as systematically constructing all relevant information — clarified intent, high-level plans, external knowledge, and repository-specific details — through a coordinated multi-agent process, implemented here as a four-component pipeline: GPT-5 Intent Translator producing a structured task spec, Elicit semantic retrieval of top 3–5 external documents, NotebookLM synthesis into a concise table-of-contents plus Q&A summary, and a Claude Code hub-and-spoke multi-agent system (orchestrator plus backend-architect, frontend-specialist, devops-engineer, and code-reviewer roles) with hybrid vector-plus-lexical code retrieval and layered L1–L5 context. Evaluated on five non-trivial tasks in the RainMakerz Next.js codebase, the system reached 4/5 single-shot successes (80%) with zero hallucinated functions versus 2/5 (40%) for a single-agent Claude baseline, at roughly 3–5× the token cost (~100k tokens and 30–40 messages per task), with gains attributed to front-loaded clarification, distilled retrieval augmentation, role decomposition, and a dedicated reviewer.

## Problem & Motivation

Large language models show promise for code generation yet struggle with complex multi-file projects because of limited context windows and hallucinations when facing unfamiliar APIs or frameworks outside their training data. The paper argues that purely prompt-driven single-agent solutions treat repository coding as single-step generation when it is really multi-step planning across distant files, architecture constraints, and domain knowledge, so a default Claude Code agent with only a basic CLAUDE.md prompt produces incomplete or incorrect solutions — missing edits in distant files or misusing libraries. A fixed static context cannot cover every task, and the authors situate their answer in prior evidence that the right information plus task decomposition is what scales LLMs to hard coding problems: MASAI's specialized sub-agents, HyperAgent's Planner/Navigator/Editor/Executor team, AllianceCoder's retrieved API descriptions, CodePlan's pseudocode planning, and DARS's feedback-driven re-sampling. Context engineering is therefore framed as the missing discipline of supplying each agent not just more information but the right information in the right form, decomposed into manageable subtasks.

## Main Original Ideas

1. **Context engineering as layered multi-agent workflow** — The central definition is systematically constructing and supplying clarified intent, high-level plans, external knowledge, and repository-specific details via a coordinated process, operationalized as four stages (GPT-5 intent translation, Elicit retrieval, NotebookLM synthesis, Claude Code execution) rather than a single bigger prompt.
2. **GPT-5 Intent Translator for front-loaded clarification** — An ambiguous request such as "add a calendar view to the scheduling page" is rewritten by a distinct specialized model into an explicit structured spec (update UI component X, fetch data Y, adjust styling, add unit tests), including library choice and data needs, mirroring CodePlan's planning step but performed before any coding agent acts.
3. **Two-source retrieval with distilled synthesis** — External knowledge (papers, docs, best-practice guides) is fetched semantically via Elicit and then condensed by NotebookLM into a high-signal table-of-contents summary plus answers to implementation questions, while internal codebase context comes from a code-specialized embedding index (tree-sitter AST chunking by function/class over ChromaDB/Zilliz) combined with grep and file-path lexical search, avoiding dumping long noisy paragraphs into prompts.
4. **Claude Code hub-and-spoke team with isolated contexts and L1–L5 layering** — A central Claude manager delegates to role-specialist sub-agents defined as YAML/Markdown profiles (e.g. backend-architect on Sonnet with Read/Write/Edit/Bash tools), each running in an isolated context window holding only task-relevant material plus shared CLAUDE.md project memory (architecture overviews, style guidelines, known bugs), with every prompt composed from five layers: L1 task spec, L2 external knowledge, L3 project memory, L4 retrieved code, and L5 execution artifacts, executed through a plan–delegate–test–review loop with `npm test` feedback, orchestrator file locks, and GitHub Actions CI integration.

## Key Findings

On a sample of five non-trivial RainMakerz tasks the multi-agent system succeeded on four (80%) without human corrections versus two (40%) for the single-agent baseline, often producing working solutions on the first attempt where the baseline needed follow-ups. A CustomBlock pitch-deck case study spanning a React component, options UI, TypeScript types, and manager registration completed in one automated session including a self-corrected serialization-whitelist failure and reviewer-driven refactoring, while the baseline produced only the component and left runtime errors. Context adherence improved markedly: every function or class the system used existed in the repository (e.g. correctly calling `renewSession()` instead of the baseline's hallucinated `refreshToken()` or `getEvents()`), which the authors attribute to semantic code retrieval plus project memory. Ablation-style observations show each layer matters — clarified specs prevent wrong-sub-problem focus, Elicit plus NotebookLM summaries supply outside concepts such as debounce handling that the baseline botched, and the dedicated reviewer catches null-pointer and security issues coders overlook — while early orchestration bugs (two agents editing one file, dropped steps) were fixed by explicit Planner role assignment and edit locks. The cost is real: about 30–40 messages and ~100k tokens per successful task versus 10k–20k for the baseline (3–5× overhead), though the paper argues this is justified because baseline retries on hard tasks approach 50k tokens plus expensive developer debugging time, and per-agent prompts stay small enough to preserve coherence.

## Suggestions & Future Directions

The authors are candid that retrieval noise, a brittle fixed plan-to-review sequence with only simple re-try rather than DARS-style multi-trajectory branching, heavy reliance on a comprehensive test suite, and difficult cross-agent error tracing limit the current system, proposing robust retrieval ranking and filtering, adaptive or RL-based meta-controllers, search-based or graph-based planning in the AllianceCoder spirit, context compression and result caching plus smaller specialist models for cost control, static analysis and spec-verification agents for sparse-test settings, and SeaView-style trajectory visualization for debugging. Generality is claimed beyond the Next.js/TypeScript target by swapping retrieval sources and roles (demonstrated by adding a database-migrator agent without touching the orchestrator), with a production path through CI-integrated automated reviews and a future human-in-the-loop mode where developers approve plans or supply hints. Stated next steps are scaling evaluation to diverse projects and benchmarks for rigorous quantification, making the planner and orchestrator dynamic and error-aware, and exploring structured human–AI collaboration, all under the thesis that carefully engineered context and workflow unlock capabilities monolithic prompts cannot.

## Authors & Institutions

The paper is authored by Muhammad Haseeb (muhammadhaseeb@vt.edu), published as arXiv:2508.08322v1 [cs.SE] on 9 August 2025. The work was implemented and evaluated on the RainMakerz Next.js web application codebase of roughly 180,000 lines of code, and it builds on and compares against prior systems including HyperAgent, MASAI (Arora et al., 2024), CodePlan (ICLR 2025), DARS (Aggarwal et al., 2025), AllianceCoder (Gu et al., 2025), SeaView, and Anthropic's multi-agent research systems.
