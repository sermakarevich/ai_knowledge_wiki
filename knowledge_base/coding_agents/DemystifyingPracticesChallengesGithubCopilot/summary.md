**Paper:** [Demystifying Practices, Challenges and Expected Features of Using GitHub Copilot](https://arxiv.org/abs/2309.05687v1) — arXiv, 11 Sep 2023

## Human Readable TL;DR

GitHub Copilot is like a very fast junior pair-programmer who has read billions of lines of open-source code and can type out boilerplate for you, but who still needs constant supervision. Researchers read through more than a thousand real developer conversations on Stack Overflow and GitHub Discussions to see where this assistant actually gets used, what it is good at, and where it trips people up. They found it is used most for everyday JavaScript and Python work inside Visual Studio Code, especially for crunching data and building website pieces, because it saves typing and speeds things up. The catch is that, like a power tool that only fits certain outlets, it is often hard to plug into other editors, sometimes gives short, broken, or hard-to-understand answers, and raises worries about price, subscriptions, and who owns the code it sees. So the overall message is that Copilot is a double-edged sword: great when matched to the right job and editor, frustrating when forced elsewhere.

## TL;DR

This paper presents an empirical repository-mining study of GitHub Copilot practices based on 303 Stack Overflow posts and 927 GitHub Discussions collected before 18 June 2023, extending a prior SEKE 2023 conference paper with 134 new posts, 272 new discussions, a new purpose analysis, and a new expected-features analysis. Using descriptive statistics for languages, IDEs, and technologies and Constant Comparison qualitative coding for functions, purposes, benefits, limitations, and expected features, the authors map 19 languages, 25 IDEs, 23 technologies, 14 implemented functions, 15 limitations, and 29 expected features. The headline results are that JavaScript and Python dominate, Visual Studio Code dominates at 48.0%, Node.js dominates at over 45%, data processing is the leading implemented function, helping generate code is the leading purpose, useful code generation and integration is the leading benefit, difficulty of integration is the leading limitation at 28.1%, and integration with more IDEs is the leading expected feature at 28.8%, leading the authors to frame Copilot as a double-edged sword requiring trade-offs around integration, experience, budget, and privacy.

## Problem & Motivation

The motivation starts from the rapid rise of large-language-model code completion after the June 2021 launch of GitHub Copilot, the OpenAI Codex-powered AI pair programmer trained on billions of lines of GitHub code that suggests code or whole functions as an IDE plug-in. Prior work had concentrated narrowly on the correctness, safety, readability, and comprehensibility of generated code, or on early experiences of assessment overhead, leaving little empirically rooted evidence about how practitioners actually use Copilot across languages, editors, technologies, and tasks, what benefits and frictions they encounter, and what features they want next. The authors argue this gap matters because Copilot shifts the pair-programming paradigm and is difficult for teams to adopt at scale without understanding real-world practices and failure modes. They therefore mine two large developer communities, Stack Overflow and GitHub Discussions, to provide first-hand, practice-grounded guidance for developers deciding whether and how to adopt Copilot and for the Copilot team prioritizing improvements.

## Main Original Ideas

1. **Eight-item mining framework from communities to research questions:** the study defines data items D1–D8 mapping one-to-one onto RQ1.1–RQ2.3 covering language, IDE, technology, implemented function, purpose, benefit, limitation and challenge, and expected feature, with descriptive statistics for the first three and Constant Comparison qualitative coding with multi-author agreement for the rest.

2. **Practice map of languages, editors, technologies, and functions:** the paper systematically quantifies 19 languages, 25 IDEs, 23 technologies, and 14 functions in one figure and tables, showing concentration on JavaScript and Python at about one fifth each, Visual Studio Code at 48.0% and mainstream IDEs at 86.2% overall, Node.js above 45%, and data processing as the leading function followed by test at 15.1% and front-end element control at 13.2%.

3. **Benefit-limitation mirror with quantified frictions:** the work catalogs purposes led by helping generate code, benefits led by useful code generation and integration, and 15 limitations led by difficulty of integration at 114 mentions (28.1%) and difficulty of accessing Copilot at 69 mentions (17.0%), followed by generation limits such as too few solutions and a roughly 1000-character response cap, poor quality that degrades in larger files, code-privacy threats, unfriendly experience, subscription difficulty, pricing, customization, comprehension, and configuration problems.

4. **Expectation catalog anchored to frictions:** the study extracts 29 expected features led by integration with more IDEs at 32 mentions (28.8%), shortcut customization at 12 mentions (10.8%), on-request rather than always-on suggestions, team, CLI, and on-premises versions, proxy support, format customization, partial acceptance, compatibility with other generators, filters, UI configurability, training-source selection, code explanation, and data-collection controls.

5. **Implication set for effective use and product evolution:** the paper translates the evidence into advice to prefer mainstream IDEs while GitHub broadens support, to lean on Copilot for front-end JavaScript and Python machine-learning work, to ship team, CLI, and on-premises variants alongside Labs, X, and Nightly, and to add in-IDE code explanation and rich suggestion customization, while framing all of this as navigating a double-edged sword.

## Key Findings

Usage concentrates sharply rather than spreading evenly. JavaScript and Python each account for about one fifth of language mentions among 19 languages, with C#, Java, C++, HTML+CSS, TypeScript, Golang, and others trailing, while Visual Studio Code alone accounts for 48.0% of IDE mentions among 25 IDEs and the top five mainstream editors together reach 86.2%, a dominance the authors link both to Copilot launching first on VS Code and to integration failures elsewhere. On technologies, Node.js exceeds 45% among 23 frameworks, APIs, and libraries, which the authors view as consistent with JavaScript leadership, with .NET, Vue, React, Flutter, and Ajax mentioned less often and machine-learning libraries such as Pandas, Dlib, and OpenCV plus front-end libraries such as Htmx, Vanilla JS, and Next.js appearing only once each. For functions, developers most often ask Copilot to write data-working code, with only test and front-end element control joining data processing above 10%, and string processing, image processing and algorithm work at 7.5% each for the latter two, the remainder appearing only once or twice. The qualitative results reinforce this picture: the dominant intent and payoff is faster generation and integration of useful code, but the dominant cost is making Copilot connect and stay connected, compounded by access blocks from server instability, missing proxy support, and region restrictions, plus generation caps, non-working suggestions, privacy worries about training on private code, subscription and pricing pain that grew after free-plan restrictions, and comprehension difficulty that some users contrast with praise for Copilot interpretation. Expectations follow directly from those pains, demanding broader IDE coverage, Tab-key alternatives and partial acceptance, less interruptive triggering, clearer visual distinction and filtering of suggestions, team and offline deployment options, and built-in explanation such as comments alongside generated code. Methodologically, pilot labelling reached a Cohen's Kappa of 0.773 with three-author coding, discussion to full agreement, and an open dataset for replication, though the authors acknowledge residual manual-coding bias, a small pilot, and generalizability limits from relying on only two communities.

## Suggestions & Future Directions

For practitioners, the authors recommend staying on mainstream IDEs where installation is smoother and community fixes are easy to find, matching language and stack to Copilot strengths in front-end and machine-learning tasks, and explicitly weighing integration effort, user experience, budget, and code privacy before adopting, since well-matched use lets AI absorb redundant work while mismatched use breeds frustration. For the Copilot team, the priorities are supporting more IDEs, stabilizing servers with proxy and region-tolerant access, lifting or explaining generation caps, improving quality on larger files, offering subscription, team, CLI, on-premises, and pricing options, and above all allowing customization of accept keys, formats, colors, partial acceptance, filters, IDE UI, and training sources, alongside direct in-IDE code explanation rather than requiring separate Labs or X flows. For researchers, the paper points to questionnaire and interview studies to supplement repository mining, deeper analysis of who uses Copilot, when, and how across roles such as developers, educators, and students, investigation of when challenges flip into advantages and how to convert disadvantages into advantages, and focused work on why comprehension attitudes diverge and how generated code can be better explained and trusted.
