# Rethinking Code Review Workflows with LLM

**Paper:** [Rethinking Code Review Workflows with LLM Assistance: An Empirical Study (Aðalsteinsson et al., 2025)](https://arxiv.org/abs/2505.16339v1)

## Human Readable TL;DR

Imagine proofreading a hundred-page contract in fifteen minutes when you have never seen the deal it describes — that is what reviewing a large, unfamiliar pull request feels like. This paper asked real developers at a car-software company what hurts most about code review, then built them an AI helper and watched them use it in two styles: one that hands you a guided tour before you start reading, and one that stays quiet until you ask it a question. Like a tour guide versus a reference librarian, the proactive guide won over newcomers and anyone facing big or low-risk changes, while experienced owners of the code preferred asking their own questions. The takeaway is that the AI works best as a junior partner who briefs you and double-checks your work, not as a replacement judge — provided it lives inside the tools developers already use, keeps answers short and precise, and earns trust without encouraging blind reliance.

## TL;DR

Code review remains essential for quality, defect detection, and knowledge sharing, but it now strains under scale, speed, reviewer fatigue, and inconsistent depth, while LLM support for review remains underexplored relative to code generation. The authors run a two-phase qualitative program at WirelessCar Sweden AB: Phase 1 uses exploratory semi-structured interviews to answer RQ1 on current practices, challenges, expectations, and where AI can help, and Phase 2 runs a field experiment with a RAG-based review assistant under two interaction modes to answer RQ2 on trust, satisfaction, barriers, and preferred interaction. Mode A (Co-Reviewer) proactively generates an up-front summary of major changes and concerns plus follow-up Q&A, while Mode B (Interactive Assistant) stays passive and answers only targeted on-demand queries. Developers value AI summaries and contextual clarifications especially for large or unfamiliar pull requests, generally prefer the AI-led mode in unfamiliar or low-risk cases but shift toward human-led review as familiarity or criticality rises, and remain held back by trust and false-positive worries, response latency, overly long output, missing broader context, and integration friction.

## Problem & Motivation

The paper positions code review as a cornerstone of modern software engineering that is buckling as systems scale and delivery cycles accelerate, producing delayed reviews, superficial passes over large or complex pull requests, costly context switching, missing rationale about why a change was made, reviewer fatigue, and inconsistent outcomes. Large Language Models have integrated smoothly into code generation, bug detection, test creation, and documentation, yet their role in review is underexplored, and the authors argue the missing question is not whether LLMs can detect issues but how engineers actually want to collaborate with an LLM assistant during review. Prior work covers replicating reviewer edits, controlled issue-detection experiments, emotional responses to AI versus human feedback, large-scale standards enforcement, fine-tuning for detection, and multi-agent autonomous review, but leaves the preferred human–AI interaction open, which matters because hallucinations rule out treating LLMs as human replacements. The study therefore takes a support-not-replace stance and grounds its design in a real industrial setting where some but not all teams may use AI, combining observation with a field intervention so that prototype modes and integration guidance emerge from developers' stated pain points rather than from laboratory metrics alone.

## Main Original Ideas

1. **Two-phase diagnostic-then-exploratory program** — Rather than benchmarking detection accuracy, the paper structures inquiry as RQ1 (diagnostic: how reviews are performed, what challenges developers face, what tasks AI can support, and the right automation–human balance) feeding directly into RQ2 (exploratory: trust, satisfaction, adoption barriers, and preferred interaction mode), with Phase 1 thematic analysis of semi-structured interviews driving the prototype that Phase 2 evaluates.

2. **AI-led Co-Reviewer versus on-demand Interactive Assistant** — The central design contrast pits Mode A, which opens with an automatically generated summary highlighting major changes and potential concerns to cure the missing-context problem on large or complex pull requests, against Mode B, which preserves the reviewer's normal workflow and answers only explicitly prompted questions, a deliberate response to evidence that pre-highlighted lines can narrow attention and cause reviewers to miss other areas.

3. **Familiarity-split field experiment with think-aloud observation** — Each of the ten Phase 2 developers reviews two real WirelessCar pull requests of similar moderate size and complexity, one per mode with rotated assignment to mitigate ordering effects, under normal working conditions with think-aloud protocol, researcher observation notes, and post-session interviews comparing both modes to the regular workflow, while four participants own the reviewed code and six do not so that reliance can be compared across codebase familiarity.

4. **RAG pipeline with injected full-PR sub-agent** — The assistant retrieves motivating context such as the Jira feature requirement through tools like `search_requirements`, and Mode A adds a `start_review` sub-agent that receives the entire pull request data injected into its prompt rather than retrieved piecemeal through a query engine, on the rationale that a complete review must consider every file change; the artifact is released as open source under GPLv3.

## Key Findings

Participants report that the assistant is often accurate, confirming their own judgments or surfacing issues they would not have caught, including race conditions and deadlock risks on large pull requests that a human given fifteen minutes could not cover well, while reducing effort spent hunting through code, documentation, and Jira tickets and even suggesting documentation updates aligned with the change. That upside is tempered by incorrect or strange suggestions such as wrongly flagged imports, lengthy hard-to-scan summaries where critical findings blur into low-priority noise, and the well-known false-positive trap in which flooded reviewers stop reading feedback and miss real issues. Trust emerges as the gating factor: the tool feels low-stakes and worth using when adoption stays optional and it demonstrably catches missed issues, yet misplaced trust wastes hours chasing impossible suggestions, and Mode A in particular raises over-reliance concerns about being colored by the AI's framing and missing everything else. Interaction preferences prove situational rather than absolute, with Mode A favored for orientation in unfamiliar or complex code, large pull requests that otherwise require manual breakdown, low-risk changes reviewers are happy to let the AI carry, newcomers learning a team and codebase, and teams with weak review discipline or pair-programming habits, while Mode B is preferred by reviewers who already know the codebase or want full control, and several participants propose patterns beyond the study design such as author-side pre-review before submitting the pull request or human-led review first with the AI validating afterward. Practical friction centers on missing broader context such as architecture docs, internal conventions, READMEs, and connected repositories, slow response times that break reviewer flow, output that lacks concise file-and-line precision, and the insistence that any real deployment live inside GitHub, GitLab, the IDE, or Slack rather than in a separate interface, with interaction quality also depending partly on the reviewer's own prompting skill.

## Suggestions & Future Directions

The authors' implications call for embedding assistance directly into existing tools such as GitHub, GitLab, IDEs, or Slack, for example as expandable in-line GitHub comments with chat follow-ups or a Slack pipeline bot, so adoption requires no workflow switch. Output must become concise, well-structured, and actionable with precise file and line references that prioritize critical findings over noise, and responses must be fast enough to preserve flow, with slower comprehensive agentic reviews acceptable only inside automated pipelines. Tools should offer both proactive AI-led summaries and reactive on-demand Q&A with adaptive selection by pull-request size, familiarity, risk, and reviewer experience, and they must grow more context-aware by injecting diffs, source files, requirements tickets, documentation, and related repositories, extending the paper's retrieval-augmented starting point into deeper integration. Finally, the pre-review finding points upstream: repurposing the assistant to help authors generate summaries, validate requirements, and catch simple defects before submission could raise code quality before human reviewers ever see the change, while future work must address hallucination control, false-positive calibration, latency, and longitudinal trust without sliding into over-reliance.
