# coding_agents -- for software engineers using AI coding assistants

## What this means for you

- Use generation where it pays: Copilot-style assistants speed up routine, well-specified work (boilerplate, CRUD, scaffolding, tests) by roughly 40–55% in controlled studies, with the largest gains on simple tasks. Complex or domain-specific logic gains far less, and debugging/validation overhead offsets much of the saving.
- Budget for verification as the hidden tax: reviewing suggestions, refining prompts, and reworking output can consume up to half of assisted development time. Your role shifts from writer to reviewer; acceptance or merge rates are misleading proxies for real productivity.
- Treat every suggestion as potentially insecure: about a quarter of Copilot-generated snippets committed to real GitHub projects contain confirmed weaknesses (29.5% Python, 24.2% JavaScript, ~3 flaws each across 43 CWE types led by CWE-330, CWE-94, CWE-79, CWE-78, over a third in the CWE Top-25), tracing to insecure training-data patterns resurfacing.
- Prompt deliberately for security and diagnosis: a security-aware persona prefix cut scanner-agreed vulnerabilities ~47–56% on GPT-4o-mini/GPT-4o (but backfired on GPT-3.5-turbo); one self-critique-and-fix iteration removed ~25–65% depending on model; feeding analyzer warnings into Copilot Chat fixed ~55% versus ~19% for a bare `/fix`. Coercive urgency framing lowered correctness and raised warnings. Framing sensitivity grows with model capability, but model choice and task difficulty dominate correctness, maintainability, and style.
- Engineer context and process for repo-level work, not bigger single prompts: a multi-agent pipeline (intent clarification, retrieval plus distilled synthesis, role-specialist agents with a reviewer) reached 80% single-shot success versus 40% for a single agent with zero hallucinated APIs at ~3–5x token cost; a TDD-governance protocol (test-first gating, proposal/engine separation, bounded N=3 repair) stabilized synthesis. Both are still preliminary/small-scale.
- Debug with static context plus runtime evidence, structured diagnosis, and validation loops: serve on-demand static-dynamic context (e.g. Code Property Graph plus statement-level traces with values and branch outcomes) through retrieval rather than dumping it into the prompt; replace one-shot patching with budgeted typed what/why/how questions distilled into an explicit hypothesis (faulty behavior, evidence, root cause, modification suggestion); validate with up to 3 refinement rounds of compile-plus-test plus diagnostics/diff/trace-diff feedback (139/136 correct on Defects4J V1.2/V2.0 with GPT-3.5, 162/171 with GPT-4o; dynamic traces alone worth +19 fixes). Expect a speed-versus-depth trade-off across models (fast/localized versus complex/large-context at higher cost).
- A second repair approach corroborates the same workflow: DebugRepair's self-directed debugging (purify the failing test to the failure-triggering scenario, have the model insert print statements and reason from observed versus expected values, iterate in sessions with patch augmentation) fixes 224 Defects4J bugs on GPT-3.5 and all QuixBugs Java/Python at $0.036 per bug — apply the same pattern by hand when stuck (trim the repro, add prints, compare actuals to expecteds before patching). For live debugging without a test suite, the PracAPR/ROSE direction (localize from debugger state, specify the problem explicitly, validate without re-execution) repaired 36/40 QuixBugs and 37/60 Defects4J bugs in seconds.
- Refactor sparingly and stop early: iterative readability refactoring follows restructuring-then-stabilization (unchanged lines 45% v0→v1 climbing to 92% v4→v5; early renames ~9% and insertions ~11% fading under 1%) but never fully stabilizes, and even clean code drifts (code lines ~58 to 73+, methods and empty lines rise, inline comments nearly removed). Degraded inputs normalize toward the same end state. Naming-focused prompts keep late rename churn high (~20%, 25–30% on degraded inputs); comment-focused prompts front-load comment edits then stabilize. Functionality breaks are rare but non-zero per iteration.
- Split refactoring work by kind: give the model high-volume surface clean-ups (long statements, magic numbers, renames, annotation hygiene) with one-shot examples, five candidates per input, and test gating — StarCoder2 cut smells 44.36% versus 24.27% for developers this way — and keep modularization, encapsulation, and coupling decisions with humans, where developers still win and the model breaks tests (~57% Pass@5 at best).
- Use review assistants as situational, human-led aids inside your existing tools: they confirm judgment or catch missed issues (e.g. race conditions, deadlocks on large PRs) and cut search across code, docs, and tickets, but also produce noisy suggestions (wrongly flagged imports, overlong summaries). AI-led summaries suit unfamiliar/complex code, large PRs, low-risk changes, and newcomers; on-demand Q&A suits code you know or where you want control. Insist on embedded (GitHub/GitLab/IDE/Slack), concise, file-and-line-precise, fast, context-aware output.

## Decisions this informs

- Where to deploy assistants: routine/data-processing/test/front-end scaffolding (today concentrated in JavaScript/Python, VS Code) versus complex, security-sensitive, or domain-specific logic where verification cost erases savings. Enterprise evidence (Zoominfo: 33% suggestion / 20% line acceptance, ~20% time savings, 72% satisfaction) confirms the win is real but smaller in production than in controlled studies — and weakest on HTML/CSS/JSON/SQL.
- How to staff the workflow: shift review time into the plan, keep human verification plus tests and static analysis non-optional, and coach novices (largest speedups, worst over-trust) differently from experts (smaller gains, better verification).
- Which prompts and models to pick: specific, diagnostic, well-contextualized prompts over vague or coercive ones; security-aware prefixes and RCI/analyzer-fed repair where supported; model and architecture choice over wording tweaks for reliability. Write task descriptions carefully: 46% of equivalent rephrasings changed Copilot's output, so phrasing alone can gain or lose a correct recommendation.
- How to set up repo-scale generation: invest in intent clarification, retrieval plus synthesis, specialist-plus-reviewer agents, test-first gating, and bounded repair rather than single mega-prompts — while treating the 80%-success multi-agent result as small-sample and token-expensive.
- How to structure debugging: match technique family to bug class (template/dynamic/search/specification-guided and memory-safety for security bugs; pattern/fuzzing/evolutionary/specification-guided for semantic bugs; mined-pattern/grammar/mutation-search for syntactic bugs), evaluate on shared suites (HumanEval/MBPP, DebugBench/VulnLoc, Defects4J, ProFuzzBench/SCTBench, TransCoder), and run diagnosis-to-validation loops with explicit budgets.
- How to govern refactoring and review: set explicit stopping criteria and comment-preservation mechanisms; use targeted prompts carefully; default to human-first-then-AI-validate or author-side pre-review; pick Co-Reviewer versus Interactive Assistant mode per PR size, familiarity, risk, and team discipline.

## Risks and unknowns

- Persistent insecure/subtly-flawed output inherited from training data; quality direction unresolved and context-dependent (some studies report fewer defects/better maintainability, others report subtle errors and harder-to-maintain code).
- Over-trust and skill-erosion, highest for novices and when AI leads; false-positive flooding that makes reviewers stop reading and miss real issues.
- Over-refactoring: structural drift, comment loss, oscillatory renaming under naming-focused prompts, and rare functionality breaks on each iteration.
- Prompt unevenness: security prefixes help newer GPT models but harm older ones; influence framing moves algorithmic benchmarks but vanishes on real-world maintenance tasks.
- Evidence limits: Python/JavaScript and Copilot over-representation; short/atomic tasks; small samples (median 17 in in-IDE research; 7–10 developers at one company for review; 5 tasks/one codebase for context engineering; explicitly preliminary TDD governance); self-reported time/satisfaction; scanner/metric proxies as relative signals; Java-only repair/refactoring benchmarks; baselines partly reused rather than re-run.
- Practitioner pain concentrates on IDE-integration and access difficulty (28.1%/17.0% of complaints) rather than generation quality alone.
