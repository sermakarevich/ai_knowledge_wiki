# AI coding best practices — digest

Focus: What are the evidence-backed best practices for using AI coding assistants for writing, debugging, and refactoring code?

## 1. [[topics/01-code-generation/digest|Code generation]]

**In one sentence:** AI code generation reliably accelerates routine coding work but ships insecure or subtly flawed code often enough that prompt wording, verification, and workflow governance — not raw generation — determine its net value.

## Key points
- Copilot-style generation speeds up routine work (boilerplate, CRUD, scaffolding, tests) by roughly 40–55% in controlled studies, with the largest gains on simple, well-specified tasks and for less experienced developers, while complex or domain-specific logic gains far less and debugging/validation overhead offsets much of the saving ([[research_topics/coding_agents/GithubCopilotProductivitySecurity/summary|Copilot survey]], [[research_topics/coding_agents/ImpactOfAiToolOnEngineeringAtAnzBank/summary|ANZ Bank]], [[research_topics/coding_agents/ImpactOfLLMAssistantsOnSoftwareDeveloperProductivity/summary|LLM productivity review]]).
- Verification is the hidden tax: reviewing suggestions, refining prompts, and reworking output can consume up to half of assisted development time, shifting the developer role from writer to reviewer and making acceptance or merge rates misleading proxies for real productivity ([[research_topics/coding_agents/HumanAiExperienceInIntegratedDevelopmentEnvironments/summary|In-IDE HAX review]], [[research_topics/coding_agents/ImpactOfLLMAssistantsOnSoftwareDeveloperProductivity/summary|LLM productivity review]], [[research_topics/coding_agents/DemystifyingPracticesChallengesGithubCopilot/summary|Copilot practices]]).
- About a quarter of Copilot-generated snippets committed to real GitHub projects contain confirmed security weaknesses (29.5% Python, 24.2% JavaScript, ~3 flaws each across 43 CWE types led by CWE-330, CWE-94, CWE-79, CWE-78), with over a third of instances in the CWE Top-25, tracing to insecure training-data patterns resurfacing in suggestions ([[research_topics/coding_agents/SecurityWeaknessesOfCopilotGeneratedCodeInGitHubProjects/summary|Copilot weaknesses]], [[research_topics/coding_agents/GithubCopilotProductivitySecurity/summary|Copilot survey]]).
- Prompt engineering moves security substantially but unevenly: a security-aware persona prefix cut scanner-agreed vulnerabilities ~47–56% on GPT-4o-mini/GPT-4o while backfiring on GPT-3.5-turbo, one self-critique-and-fix (RCI) iteration removed ~25–65% of flaws depending on model, and feeding analyzer warnings into Copilot Chat fixed ~55% versus ~19% for a bare `/fix` — whereas coercive urgency framing lowered correctness and raised security warnings ([[research_topics/coding_agents/BenchmarkingPromptEngineeringTechniquesForSecureCodeGeneration/summary|Secure-code prompting]], [[research_topics/coding_agents/SecurityWeaknessesOfCopilotGeneratedCodeInGitHubProjects/summary|Copilot weaknesses]], [[research_topics/coding_agents/InfluenceTacticsPromptFraming/summary|Prompt framing]]).
- Sensitivity to prompt wording grows with model capability and matters less than model choice: newer models respond more to both helpful and adversarial framing, yet architecture and task difficulty dominate correctness, maintainability, and style metrics, so framing is a nudge for tone and documentation, not a reliability lever ([[research_topics/coding_agents/BenchmarkingPromptEngineeringTechniquesForSecureCodeGeneration/summary|Secure-code prompting]], [[research_topics/coding_agents/InfluenceTacticsPromptFraming/summary|Prompt framing]]).
- Repository-level generation needs engineered context and enforced process, not bigger single prompts: a multi-agent pipeline (intent clarification, external retrieval plus distilled synthesis, role-specialist agents with a reviewer) reached 80% single-shot success versus 40% for a single agent with zero hallucinated APIs at ~3–5× token cost, while a TDD-governance protocol (test-first gating, proposal/engine separation, bounded N=3 repair) stabilized multi-agent synthesis — both still preliminary or small-scale ([[research_topics/coding_agents/ContextEngineeringForMultiAgentLLMCodeAssistantsUsingElicitNotebookLMChatGPTAndClaudeCode/summary|Context engineering]], [[research_topics/coding_agents/TddGovernanceForMultiAgentCodeGenerationViaPromptEngineering/summary|TDD governance]]).
- Real-world Copilot use concentrates on JavaScript/Python in VS Code (48.0% of IDE mentions) for data processing, test, and front-end work, where the top practitioner complaint is IDE-integration and access difficulty (28.1%/17.0%) rather than generation quality, and novices gain speed at the cost of over-trust while experts gain less but verify better ([[research_topics/coding_agents/DemystifyingPracticesChallengesGithubCopilot/summary|Copilot practices]], [[research_topics/coding_agents/HumanAiExperienceInIntegratedDevelopmentEnvironments/summary|In-IDE HAX review]], [[research_topics/coding_agents/ImpactOfAiToolOnEngineeringAtAnzBank/summary|ANZ Bank]]).
- An earlier community-mined study independently converges on the same usage map — JavaScript for front-end, Python for machine learning, mainstream IDEs jointly 85.9%, useful generation (49.0%) and speed (16.3%) leading benefits, file-growth degradation and privacy fears leading complaints ([[research_topics/coding_agents/PracticesAndChallengesOfUsingGitHubCopilot/summary|Copilot practices-challenges]]).
- Zoominfo's enterprise deployment (400+ developers, phased rollout with governance) measured 33% suggestion and 20% line acceptance with ~20% time savings and 72% satisfaction, concentrated in boilerplate/tests/naming/docs for the top four languages (~30% acceptance) and weaker on HTML/CSS/JSON/SQL, with domain-logic gaps requiring scrutiny ([[research_topics/coding_agents/ExperienceWithGithubCopilotForDeveloper/summary|Zoominfo Copilot]]).
- Phrasing alone moves correctness: 46% of semantically equivalent paraphrases changed Copilot's output, with ~28% of passing methods reachable only one way — so writing clear descriptions is a first-order practice, while CodeBLEU and test-passing each mislead in isolation ([[research_topics/coding_agents/OnTheRobustnessOfCodeGenerationTechniques/summary|Copilot robustness]]).

## 2. [[topics/02-debugging/digest|Debugging]]

**In one sentence:** LLM-based debugging and repair now work best when static code context is combined with runtime execution dynamics, structured diagnosis, and validation feedback — but speed-versus-depth trade-offs, context/noise limits, and the need for human verification and standard benchmarks persist.

## Key points
- Pre-trained LLMs fine-tuned on large code/bug datasets are the dominant trend in automated program repair, with transfer learning, neural fault localization over AST/control flow, and AI-generated tests steadily improving context-aware fixes while reducing manual effort [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- Repair techniques divide by bug class: template/dynamic/search/specification-guided and memory-safety methods for security bugs, pattern/fuzzing/evolutionary/specification-guided methods for semantic bugs, and mined-pattern/grammar-based/mutation-search methods for syntactic bugs [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- Standardized benchmarks are the evaluation harness: HumanEval/MBPP for generation, DebugBench/VulnLoc for debugging and localization, Defects4J for real bugs, ProFuzzBench/SCTBench for protocols and concurrency, and TransCoder for translation [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- Models show a consistent speed-versus-depth trade-off: Codex leads on real-time completion and common bugs, GPT-4 on complex large-context bugs at higher cost, CodeT5 on localized tasks and summaries, and GraphCodeBERT on structural/data-flow settings at higher resource cost [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- PracRepair mirrors human debugging in three stages: on-demand static-dynamic context (Joern Code Property Graph plus JavaAgent/ASM statement-level traces with variable values and branch outcomes served through a retrieval interface, not dumped into the prompt) [[research_topics/coding_agents/PracRepair/summary|PracRepair]].
- It replaces one-shot patching with budgeted question-driven diagnosis: one typed what/why/how question per round via a ReAct-style reasoning–retrieval loop, distilled into an explicit four-field repair hypothesis (faulty behavior, evidence, root cause, modification suggestion) [[research_topics/coding_agents/PracRepair/summary|PracRepair]].
- It treats validation as behavioral evidence: up to 3 refinement rounds of hypothesis-guided generation, compile-plus-test validation, and feedback as diagnostics plus code diff plus aligned trace diff, reaching 139/136 correct fixes on Defects4J V1.2/V2.0 (GPT-3.5) and 162/171 (GPT-4o), with ablations confirming each stage and dynamic traces alone worth +19 fixes, at lower per-bug cost than ReInFix, RepairAgent, and ChatRepair [[research_topics/coding_agents/PracRepair/summary|PracRepair]].
- DebugRepair corroborates the runtime-evidence thesis with a second architecture — test purification, hybrid simulated instrumentation, hierarchical debugging sessions with patch augmentation — fixing 224 Defects4J bugs on GPT-3.5 (11 ahead of ReinFix) and 295 on DeepSeek-V3 plus all QuixBugs Java/Python at $0.036 per bug [[research_topics/coding_agents/DebugRepair/summary|DebugRepair]].
- The PracAPR vision extends the thesis toward live debugging: test-free flow-analysis localization from a debugger-suspended program, failure-aware augmented prompts, and re-execution-free simulated-trace validation, grounded in the ROSE prototype (89% localization, 36/40 QuixBugs and 37/60 Defects4J in seconds, +44% task success in a user study) [[research_topics/coding_agents/TowardsPracticalAndUsefulAutomatedProgramRepairForDebugging/summary|PracAPR vision]].

## 3. [[topics/03-refactoring/digest|Refactoring]]

**In one sentence:** Iterative LLM readability refactoring converges toward a stable, normalized style across starting points and LLM review assistance helps most as a situational human-led aid — but both need guardrails, concise context-aware behavior, and human verification because over-refactoring, false positives, and trust limits persist.

## Key points
- Iterative readability refactoring follows a restructuring-then-stabilization trajectory: on already-clean Java code with a general prompt, unchanged lines climb 45% (v0→v1) through 76%, 86%, 89% to 92% (v4→v5), with early renames (9%) and code insertions (11%) fading to all change types under 1% while adjacent-version similarity rises 0.86 to 0.90 without ever reaching 1.00 [[research_topics/coding_agents/FromRestructuringToStabilization/summary|RestructuringStabilization]].
- Even clean code drifts structurally under repeated refactoring: code lines grow from 58 to over 73, empty lines and method counts rise and stabilize from the third version onward, comment lines fall slowly, and inline comments are almost completely removed [[research_topics/coding_agents/FromRestructuringToStabilization/summary|RestructuringStabilization]].
- Degraded inputs are normalized toward the same end state: Meaningless-identifier variants start at 31% unchanged (24% renames) and NoComment variants at 44% unchanged (14% renames), then follow the Original trajectory to 90% and 89% unchanged, with code lines converging 56 to about 73, methods 3.1 to about 6, and cross-variant similarity settling near 0.87 within 3% [[research_topics/coding_agents/FromRestructuringToStabilization/summary|RestructuringStabilization]].
- Targeted prompts steer the change mix without breaking convergence, but need care: naming-focused prompts keep rename rates high late (around 20% on Original, 25–30% on degraded variants, with oscillatory renaming on NoComment) while comment-focused prompts front-load comment edits (around 36% of changes on Meaningless in v0→v1) then stabilize without inflating documentation; functionality breaks are rare but non-zero per iteration, so explicit stopping criteria and comment-preservation mechanisms are recommended [[research_topics/coding_agents/FromRestructuringToStabilization/summary|RestructuringStabilization]].
- The review assistant contrasted two RAG-based interaction modes at WirelessCar: Mode A (Co-Reviewer) proactively generates an up-front summary of major changes and concerns via a `start_review` sub-agent with full PR data injected, while Mode B (Interactive Assistant) stays passive and answers only targeted on-demand queries, each tested by ten developers reviewing two matched real pull requests with rotated assignment, think-aloud observation, and post-session interviews [[research_topics/coding_agents/RethinkingCodeReviewWorkflowsWithLLM/summary|CodeReviewWorkflows]].
- Review assistance often confirms reviewer judgment or surfaces missed issues such as race conditions and deadlocks on large pull requests while cutting search effort across code, docs, and Jira tickets, yet it also produces strange or noisy suggestions (e.g. wrongly flagged imports, overlong summaries), triggering the false-positive trap where flooded reviewers stop reading and miss real issues, with over-reliance risk highest when the AI leads [[research_topics/coding_agents/RethinkingCodeReviewWorkflowsWithLLM/summary|CodeReviewWorkflows]].
- Preference is situational rather than absolute: AI-led summaries win for unfamiliar or complex code, large pull requests, low-risk changes, newcomers, and weak-review-discipline teams, while on-demand assistance wins where reviewers know the codebase or want full control, with proposed extensions to author-side pre-review and human-first-then-AI-validate patterns; developers insist deployment live inside GitHub, GitLab, IDEs, or Slack with concise file-and-line-precise output, fast responses, and deeper context (diffs, source files, requirements, docs, connected repos) [[research_topics/coding_agents/RethinkingCodeReviewWorkflowsWithLLM/summary|CodeReviewWorkflows]].
- A paired StarCoder2-vs-developer study sharpens the refactoring guidance: the model out-cleans developers on surface smells (44.36% vs 24.27% reduction) but passes only 57% of tests at best-of-five, dominating syntactic within-class work (renames, annotations, long statements) while losing architecture-sensitive work (modularization, encapsulation, coupling) — so deploy the model on high-volume surface clean-ups with test gating and one-shot plus best-of-five prompting, and keep humans on structural design [[research_topics/coding_agents/LlmCodeRefactoringCapability/summary|RefactoringCapability]].

## The picture in five moves
1. Generation earns its keep on routine, well-specified work, where speedups are largest and verification overhead is smallest.
2. That speedup is taxed by review, prompt refinement, and rework — and by a persistent rate of insecure or subtly flawed suggestions — so verification and workflow governance decide net value.
3. When flaws surface, diagnosis beats one-shot patching: static context plus runtime traces, typed questions, and compile-plus-test validation loops produce the correct fixes.
4. Model and prompt choices modulate outcomes — security-aware and diagnostic prompts help, coercive phrasing hurts — but architecture, task difficulty, and context depth dominate.
5. Refactoring and review then normalize rather than reinvent: iteration converges diverse inputs toward one readable style, and assistants confirm judgment or catch missed issues inside human-led review.
6. Across all three, human verification, stopping criteria, and embedded concise context-aware tooling are the guardrails that keep speed from becoming over-trust.
