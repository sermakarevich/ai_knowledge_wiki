# Debugging

**In one sentence:** LLM-based debugging and repair now work best when static code context is combined with runtime execution dynamics, structured diagnosis, and validation feedback — but speed-versus-depth trade-offs, context/noise limits, and the need for human verification and standard benchmarks persist.

## Key points
- Pre-trained LLMs fine-tuned on large code/bug datasets are the dominant trend in automated program repair, with transfer learning, neural fault localization over AST/control flow, and AI-generated tests steadily improving context-aware fixes while reducing manual effort [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- Repair techniques divide by bug class: template/dynamic/search/specification-guided and memory-safety methods for security bugs, pattern/fuzzing/evolutionary/specification-guided methods for semantic bugs, and mined-pattern/grammar-based/mutation-search methods for syntactic bugs [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- Standardized benchmarks are the evaluation harness: HumanEval/MBPP for generation, DebugBench/VulnLoc for debugging and localization, Defects4J for real bugs, ProFuzzBench/SCTBench for protocols and concurrency, and TransCoder for translation [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- Models show a consistent speed-versus-depth trade-off: Codex leads on real-time completion and common bugs, GPT-4 on complex large-context bugs at higher cost, CodeT5 on localized tasks and summaries, and GraphCodeBERT on structural/data-flow settings at higher resource cost [[research_topics/coding_agents/AiDrivenAdvancementsAutomatedProgramRepairCodeGeneration/summary|Survey]].
- PracRepair mirrors human debugging in three stages: on-demand static-dynamic context (Joern Code Property Graph plus JavaAgent/ASM statement-level traces with variable values and branch outcomes served through a retrieval interface, not dumped into the prompt) [[research_topics/coding_agents/PracRepair/summary|PracRepair]].
- It replaces one-shot patching with budgeted question-driven diagnosis: one typed what/why/how question per round via a ReAct-style reasoning–retrieval loop, distilled into an explicit four-field repair hypothesis (faulty behavior, evidence, root cause, modification suggestion) [[research_topics/coding_agents/PracRepair/summary|PracRepair]].
- It treats validation as behavioral evidence: up to 3 refinement rounds of hypothesis-guided generation, compile-plus-test validation, and feedback as diagnostics plus code diff plus aligned trace diff, reaching 139/136 correct fixes on Defects4J V1.2/V2.0 (GPT-3.5) and 162/171 (GPT-4o), with ablations confirming each stage and dynamic traces alone worth +19 fixes, at lower per-bug cost than ReInFix, RepairAgent, and ChatRepair [[research_topics/coding_agents/PracRepair/summary|PracRepair]].
- DebugRepair adds a second, complementary runtime-evidence architecture: self-directed debugging that replaces outcome-level symptoms with intermediate runtime states via test semantic purification (iterative backward slicing with alias handling, −18.6% trace tokens), hybrid simulated instrumentation (LLM-generated prints with consistency checks plus deterministic AST fallback), and hierarchical debugging sessions with patch augmentation — correctly fixing 224 Defects4J bugs on GPT-3.5 (+26.2% over SOTA LLM baselines; 11 ahead of ReinFix) and 295 on DeepSeek-V3, all 40 QuixBugs Java plus all 40 Python, with +51.3% average gains across five backbones at $0.036 per bug [[research_topics/coding_agents/DebugRepair/summary|DebugRepair]].
- The PracAPR vision paper reframes repair for live debugging: an interactive IDE system starting from a debugger-suspended program with a developer-provided problem specification, using test-free flow-analysis fault localization, failure-aware augmented LLM prompts (test inputs, callee definitions, execution traces — shown to fix a Chart_3 misdiagnosis that shallow prompts get wrong), and re-execution-free validation via simulated trace comparison, grounded in the ROSE prototype (correct location for 89% of bugs, 36/40 QuixBugs and 37/60 Defects4J fixed in seconds, +44% task success and −16.5% debugging time in a user study) plus a taxonomy of eight partial-patch relationships for single-fault multi-location bugs [[research_topics/coding_agents/TowardsPracticalAndUsefulAutomatedProgramRepairForDebugging/summary|PracAPR vision]].

---
## What the sources agree on
- Runtime and contextual evidence beyond static code and error messages is what separates shallow fixes from correct ones: the survey credits neural fault localization, test generation, and multi-modal context, while PracRepair demonstrates it concretely with traces and trace diffs — and DebugRepair and the PracAPR-vision paper independently converge on the same lesson, with print-trace runtime states fixing Chart-24/Lang-6 style misdiagnoses and augmented prompts (inputs, callees, traces) fixing a Chart_3 misdiagnosis.
- Iterative, feedback-driven loops beat single-shot patching: the survey notes feedback loops and interactive debugging with human help as the trend, and PracRepair's refinement rounds (89 → 139 correct over three rounds) quantify the gain; DebugRepair's hierarchical sessions and the ROSE user study (+44% task success, −16.5% time) reinforce it from two more angles.
- Evaluation must run through shared suites (Defects4J, HumanEval, DebugBench and peers), and human verification remains required because APR still mislocalizes faults, overfits to tests, and produces locally correct but globally wrong or insecure patches — with DebugRepair's patch-augmentation module and the vision paper's simulated-trace comparison as two explicit overfitting countermeasures.

## Where they differ
- Scope and method: the survey is a broad secondary synthesis (27 papers across APR and code generation, many models and bug classes) while PracRepair and DebugRepair are single primary frameworks with controlled Defects4J-family experiments, and the vision paper is a position piece grounding its claims in the ROSE prototype plus case studies rather than head-to-head counts.
- Specificity of guidance: the survey catalogues families of approaches and their trade-offs (speed vs. depth, task fit), whereas PracRepair prescribes one concrete pipeline (on-demand CPG plus traces, typed questions, trace-diff refinement) with budgets (10 diagnosis, 3 refinement rounds), DebugRepair prescribes another (purification, simulated instrumentation, session/round hierarchy with a 32-patch budget), and the vision paper prescribes IDE integration (debugger-state start, problem specification, no re-execution).
- Generality claims: the survey ranges over languages and bug types but stays at taxonomy level; PracRepair shows the strongest edge on hard multi-function bugs and cross-model RWB generalization, but its evidence is Java-only (Defects4J, RWB); DebugRepair adds Python evidence (40/40 QuixBugs Python) and post-cutoff HumanEval-Java checks against memorization, while the vision paper's multi-location taxonomy (118 single-fault multi-location Defects4J bugs, at most 8 repaired by prior tools) reframes evaluation rather than claiming a fix rate.

## Evidence quality
- The survey is secondary evidence: systematic review with inclusion criteria and tabular comparison, useful for landscape and trade-offs, but it runs no new experiments and inherits the limits of its 27 sources (benchmark overfitting, uneven language coverage).
- PracRepair is primary experimental evidence: head-to-head Defects4J counts under GPT-3.5/GPT-4o with and without perfect fault localization, scenario splits (SL/SH/SF/MF), ablations isolating each stage, RWB post-cutoff generalization across five models, and cost comparison — the strongest link in this sub-topic.
- DebugRepair is primary experimental evidence of comparable strength: 15-baseline comparison on Defects4J plus QuixBugs Java/Python under GPT-3.5 with DeepSeek-V3 and Qwen-family generality checks, per-module ablations (purification −26.8%, debugging −26.3%, augmentation −22.8% when removed), HumanEval-Java post-cutoff checks, and per-bug cost leadership (32 patches, 38k tokens, $0.036) — caveated by perfect-fault-localization setting, reused baseline numbers, and manual correct-patch judgment.
- The PracAPR-vision paper is weaker, position-level evidence: ROSE prototype results (localization, fix counts, one user study) plus illustrative case studies (Chart_3 prompt augmentation) and a developer-patch-derived taxonomy, valuable for deployment direction (test-free, IDE-integrated, multi-location) but not for fix-rate claims.
- Caveats on PracRepair: baselines reuse published numbers rather than re-runs, correct-patch counting relies partly on manual semantic-equivalence judgment, ablations are confined to Defects4J V1.2 with GPT-3.5, and Java-only benchmarks plus fixed hardware/budget choices (temperature 1.0, 10-minute validation cap) limit external validity.
