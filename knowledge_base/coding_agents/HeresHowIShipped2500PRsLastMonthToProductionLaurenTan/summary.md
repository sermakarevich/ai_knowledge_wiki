# here's how i shipped 2,500 PRs last month to production - Lauren Tan https://x.com/poteto

**Video:** [here's how i shipped 2,500 PRs last month to production - Lauren Tan https://x.com/poteto](https://youtu.be/Z-jNqqIYGm4) — Lauren Tan

## Human Readable TL;DR

Lauren Tan argues that shipping thousands of pull requests a month with agents is less like running a factory assembly line and more like running a Michelin-star kitchen, where the head chef wins by setting up equipment, recipes, and training so well that dozens of line cooks can work without constant supervision. Her breakthrough was teaching agents to check their own work the way a cook tastes a dish, by giving them tools that run the app, take performance traces, and remember how every feature is supposed to behave. She then redesigned the codebase itself the way a good kitchen bans clutter and weeds a garden, so the easy, default way of cooking is also the correct way and bad habits cannot spread like a virus.

## TL;DR

Lauren Tan (Potato on X), working on Grokbot at SpaceX AI, reports shipping around 2,000 pull requests to production in a month by compounding trust in agents rather than by chasing PR count directly. Her thesis is that a well-set-up agent environment produces a personal or team-scale production system for high-quality code at much greater rates, but only if agents can be trusted to work unsupervised. The path she describes runs from Cursor agent-window performance work through verification skills such as Control Glass with a reusable CLI and maintained feature map, through engineer-like PAC skills for code quality, to an agent-friendly codebase and framework (Dune) organized as a five-layer trust stack with architecture first and human review last.

---

## Problem & Motivation

The talk starts from a concrete bottleneck: after joining Cursor about six months earlier to fix performance in the agents window that replaced the Cursor IDE, Tan faced an insurmountable wall of pull requests with no signal on regressions, where manual Chrome DevTools performance traces and heap snapshots could not keep up. The frustration produced the guiding question of "I am the bottleneck," and the realization to use agents themselves to run the app, take traces, understand hotspots, and hill-climb performance automatically. More generally, she describes the hardest phase of agent adoption as the 1-to-5 agent stage of constant babysitting and course-correction, where nothing happens unsupervised or agents do the wrong thing, while naive scaling toward around 100 sub-agents or cloud agents without trust merely multiplies slop pull requests, regressions, and bugs. The motivation is therefore to escape babysitting by imparting engineer knowledge into a team of agents through environment, tooling, and codebase investments that compound into unsupervised trust.

## Main Original Ideas

1. **Michelin kitchen over software factory:** Tan rejects the factory assembly-line metaphor for agent output and replaces it with a Michelin kitchen where agents are line cooks, sous-chefs, and dishwashers, leaders provide equipment, training, and staffing ratios, and humans retain responsibility for the final creative outcome rather than mass production.

2. **Trust continuum from babysitting to fleets:** she frames progress as moving along a continuum from 1–5 agents requiring constant intervention toward roughly 100 agents operating with trust, warning that scale without trust is the failure mode and that verification is the first lever for escaping the babysitting trap.

3. **Verification skills as critical infrastructure:** beginning with Control Glass, agents are taught to run the app reproducibly via the Chrome DevTools Protocol, collect traces and evidence, and check performance bars through a reusable CLI kept in the skill directory instead of per-session ad-hoc scripts, which turns self-verification with empirical evidence into maintained team infrastructure.

4. **Feature map as materialized memory:** paired with the CLI, a stored feature map records how the app works, how users reach features through shortcuts and DOM elements, and what features do, maintained by automation in the codebase, so agents no longer guess at intent from vague reports such as a small UI screenshot plus question marks and can connect internal and external requests.

5. **PAC skills for engineer judgment:** beyond correctness of whether a button actually works, a PAC plugin collects debugging, feature-development, and prototyping playbooks that encode Tan's personal software-engineering workflows, with the proposal that senior engineers contribute a team repository of such skills alongside verification skills plus real metrics, statistics, and telemetry.

6. **Codebase as memory with garden and virus dynamics:** Tan claims the codebase is the best form of memory because models extend patterns already in their context window rather than refactoring each pull request, so one workaround or comment spreads like a virus into a de facto pattern within days or weeks, while workarounds are weeds requiring a gardener role to remove early and a single paved path so agents never have to guess.

7. **Five-layer trust stack in priority order:** when correcting an agent, work the layers from strongest to weakest, namely codebase and architecture that make bad patterns categorically impossible, then static analysis including linters, compiler diagnostics, and CI, then rules, Bugbot, and skills for guidance agents may forget, with style guides and human review as the weakest last resort.

8. **Dune as an agent-friendly framework:** Dune, the client framework powering Grokbot born from Cursor agent-window performance lessons, assumes agents love shortcuts and therefore makes the easy path the right path even if locked down and annoying for humans, with co-located features, entry points like routes, transcript cards, Grokbot VM hosting, client separation, main versus renderer thread import boundaries enforced through the dependency graph to protect 60fps (16ms) and 120fps (8ms) budgets, and a ban on code comments to stop agents copying workaround justifications.

9. **Grokbot outer loop operations:** the broader system aggregates company signals through connectors for Slack, Datadog, Sentry, and PlanetScale, with Grokbot routines subscribing to Slack threads and Sentry alerts to auto-start cloud agents, plus Cursor automations and SDK bots reusing the same agent infrastructure for chores like automatic bug-report reproduction and pull-request opening.

## Key Findings

Verification skills alone go very far, while formal verification with formal methods, Lean, TLA+, and business-logic invariants remains harder, still an open question, and usable by few, so the practical starting investment is teaching agents to run the app and gather empirical evidence rather than waiting for proofs. Control and verification skills become infrastructure the team constantly maintains rather than one-off prompts, because an agent that verifies its own work with reproducible runs and stored knowledge of features is dramatically more trustworthy than one that merely generates code. Codebase design may be the most important investment if agents will write all future code, since keeping the tree in a state you would be happy for an agent to copy, deleting tech debt, enforcing one blessed path with conventions plus CI and lint guidance, and writing a lint rule to stop the bleeding before cleanup all pay off across every future pull request. The Dune experience suggests that strict, even human-annoying conventions suit minimal-context contributors including agents, designers, PMs, and executives, because tribal knowledge of the best engineers moves out of forgettable style-guide comments into the framework and codebase as materialized memory. Tan stresses she never set out to ship thousands of PRs per month and that the volume followed from compounding skills, tools, and codebase changes into trust, which reframes throughput as a side effect of environment quality rather than a target to optimize directly.

## Suggestions & Future Directions

The closing prescription is operational: every time you must correct or intervene on an agent, push the fix down the five layers in order until the environment is trusted enough that agents can just be free, starting with data structures, algorithms, and architecture that make the mistake impossible, then static analysis, then rules, Bugbot, and skills. Teams should invest in shared verification skills with reusable CLIs and automation-maintained feature maps, build a team repository of senior-engineer workflow skills in the style of the PAC plugin, and assign explicit gardening ownership so workarounds are removed before agents copy them across the codebase. Framework authors should consider stricter agent-friendly conventions with dependency-graph enforcement of critical boundaries such as renderer budgets, even at the cost of human convenience, and operators should wire the outer loop so production signals from Slack, observability, error tracking, and databases automatically kick off cloud agents that reproduce issues and open pull requests on shared infrastructure. The open research direction named in the talk is practical formal verification of business-logic invariants that ordinary teams can actually use, which would extend the trust continuum beyond what verification skills alone can provide.
