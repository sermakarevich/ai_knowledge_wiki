# DebugRepair: Enhancing LLM-Based Automated Program Repair via Self-Directed Debugging
**Paper:** [DebugRepair: Enhancing LLM-Based Automated Program Repair via Self-Directed Debugging](https://arxiv.org/abs/2604.19305v1) — arXiv, Apr 2026

## Human Readable TL;DR
Most AI bug-fixers work like a doctor who only hears "it hurts" without ever taking a temperature: they see the crash message but never watch what the program was actually doing just before it broke. DebugRepair instead teaches the AI to act like a human debugger, sticking in temporary print statements to watch key variables change step by step until the real mistake shows itself. Before doing that it trims the failing test down to just the lines that trigger the bug, like cutting a long recipe down to only the steps that burned the dish, so the logs stay short and focused. The result is far more correct fixes across Java and Python benchmarks, at a lower cost per bug than prior approaches.

## TL;DR
DebugRepair is a self-directed debugging framework for feedback-based LLM automated program repair that replaces reliance on outcome-level failure symptoms such as stack traces with intermediate runtime evidence collected through simulated instrumentation. It combines test semantic purification by iterative backward slicing with alias handling, hybrid simulated instrumentation with LLM-generated prints guarded by consistency checks plus a deterministic rule-based AST fallback, and debugging-driven conversational repair organized as hierarchical debugging sessions and inner repair rounds with patch augmentation. Evaluated primarily with GPT-3.5 under perfect fault localization, it correctly fixes 224 Defects4J bugs, all 40 QuixBugs Java and all 40 Python bugs, and with DeepSeek-V3 fixes 295 Defects4J bugs, outperforming 15 baselines while remaining model-agnostic with 51.3% average gains across five additional LLMs, and ablations confirm every component contributes substantially.

## Problem & Motivation
Feedback-based LLM repair methods such as ChatRepair, ContrastRepair, and TSAPR iteratively refine patches from test execution feedback, yet they rely primarily on outcome-level symptoms like stack traces that show how a failure is observed while hiding the intermediate runtime states needed for root-cause analysis. This forces the model to guess at bug causes without evidence and frequently yields plausible-but-wrong patches that mask symptoms rather than fixing logic errors. The paper illustrates this with the Defects4J Chart-24 bug in `getPaint`, where `g` is computed from the raw input `value` instead of the clamped `v`: from the `IllegalArgumentException` alone the LLM merely clamps `g`, whereas inserted prints revealing `value = -0.5`, `v = 0.0`, and `g = -127` make it obvious that `g` was derived from the wrong variable. The same lesson recurs in the Lang-6 case, where outcome-guided search only tweaks `pos` to `pos + 1` while a runtime trace of `pos` evolving to the invalid boundary exposes the missing bounds check. DebugRepair therefore mimics developer practice by having the LLM proactively insert instrumentation, observe execution, and reason from observed versus expected values.

## Main Original Ideas
1. **Test Semantic Purification:** backward traversal from the failure-triggering statement keeps preceding statements whose defined variables or used objects intersect the required set, repeating iteratively until no new objects appear so alias-induced side effects such as `listB.add` mutating aliased `listA` are captured, then reconstructs a minimal test preserving the original signature and order plus directly and indirectly dependent helper methods and class fields. This strips irrelevant test scenarios and cuts average runtime-output tokens by 18.6%, keeping later instrumentation and repair focused on the failure-triggering scenario.
2. **Simulated Instrumentation with hybrid LLM and rule-based design:** an LLM prompt over the buggy function, purified test context, and error info asks for targeted print statements, guarded by a two-stage consistency check requiring line-wise equivalence after stripping prints and comments plus successful compilation, retried up to ten attempts. On persistent failure a deterministic AST-based fallback inserts `START_DEBUG`/`END_DEBUG` markers with `VAR`, `COND`, `LOOP`, and `RETURN` logs using temp variables to avoid repeated-execution side effects, and executing the verified instrumented function yields the runtime trace of critical variables before failure.
3. **Debugging-Driven Conversational Repair:** a repair prompt fusing the buggy and instrumented functions, purified context, serialized trace, and prior failure feedback drives evidence-based reasoning by contrasting observed values against expected behavior, with an inner loop appending each failed candidate and its compilation or runtime error to history up to `K_round` rounds and an outer loop discarding history and capturing a fresh trace in a new debugging session up to a global `N_session × K_round` budget of 32 patches including augmentation. A patch-augmentation module then generates logically similar but differently implemented variants of the first plausible patch to combat test overfitting, validating all variants against the test suite.

## Key Findings
With GPT-3.5 DebugRepair correctly fixes 224 Defects4J bugs (111 on V1.2, 113 on V2.0 from 283 plausible) and all 40 QuixBugs Java plus all 40 Python bugs, exceeding second-ranked ReinFix by 11 bugs at smaller patch size and beating ChatRepair by 62, ContrastRepair by 81, and TSAPR by 23, alongside 85–195% gains over conventional learning-based methods at a fraction of their patch budgets. It leads unique-fix counts against both retrieval/hybrid and feedback baseline groups, dominates complex single-function and single-hunk scenarios while staying competitive on single-line bugs where long traces can slightly hinder pattern matching, and with DeepSeek-V3 reaches 295 Defects4J fixes, 59 ahead of the strongest reproduced baseline. Generality holds across Qwen2.5-7B, 32B, Coder-7B, GPT-3.5, and DeepSeek-V3 with 51.3% average improvement, scaling with size, code specialization, and reasoning strength, and post-cutoff HumanEval-Java results support genuine design gains over memorization. Ablations show removing purification drops correct fixes 224 to 164, removing debugging to 165, removing augmentation to 173, and removing either instrumentation branch costs 15–19%, while cost analysis reports only 32 patches, 38,000 tokens, and $0.036 per bug, the cheapest of all compared approaches.

## Suggestions & Future Directions
Because DebugRepair targets patch refinement through dynamic execution states, its mechanism is highly orthogonal to ingredient-search approaches like ReinFix and exploration approaches like TSAPR's Monte Carlo tree search, inviting integrated hybrids that combine retrieval, tree exploration, and runtime-state refinement for further gains. The single-line caveat that print traces lengthen context suggests adaptive instrumentation that stays minimal or switches off for simple pattern-matchable bugs, and the hierarchical session/round and augmentation budgets merit further tuning beyond the reported sensitivity plots. The authors note SWE-bench is currently out of scope since its default setting withholds explicit test cases, so extending self-directed debugging to issue-only settings is an open direction, alongside the promised public release of implementation and detailed repair results to aid reproducibility.
