# Phase one: generate
**In one sentence:** Code generation is now the cheap part, so output quality is controlled through the technical standard library and specifications, and correctness is enforced by a fast back-pressure wheel (tests/builds/scanners), anti-placeholder discipline, TODO-list loops, and loop-back self-improvement.
## Key points
- Generation is cheap and controllable: wrong patterns mean fix the standard library, building the wrong thing entirely means fix the specifications — illustrated by a CURSED lexer spec that defined one keyword twice for two opposing scenarios, unnoticed for a month.
- Correctness comes from back pressure with a fast wheel: type systems, test/build, security scanners, or static analysers can all serve, but the loop must turn fast, trading compilation speed against correctness (Rust = extreme correctness, slower builds, more LLM attempts).
- The staple per-change rule is: after implementing functionality or resolving problems, run the tests for that unit of code that was improved; dynamically typed languages must additionally wire in a static analyser/type checker (Dialyzer, Pyrefly) or face "a bonfire of outcomes".
- Because each Ralph loop has a fresh context window and does one thing only, every test and doc (rustdoc or cursed stdlib docs) must record why the test and implementation matter, so future loops can decide to delete, modify, or fix failures.
- Claude biases toward minimal/placeholder implementations, countered by an explicit "DO NOT IMPLEMENT PLACEHOLDER OR SIMPLE IMPLEMENTATIONS. WE WANT FULL IMPLEMENTATIONS" sign plus a rule to implement missing functionality per specs and fix even unrelated failing tests; leftover placeholders are harvested by more Ralph loops into a TODO list.
- The TODO list is generated by a prompt stack using up to 500 subagents to compare `src/` and `examples/` against `specs/*`, maintaining a priority-sorted `@fix_plan.md`, with the stdlib required to be built in cursed itself (not Rust) and missing modules specced at `specs/stdlib/FILENAME.md`; the list is watched like a hawk, deleted often, and regenerated by explicit planning loops ("I don't [plan]. The models know what a compiler is better than I do. I just ask it.").
- Ralph must be looped back on himself for evaluation (extra logging, or compiling and inspecting LLVM IR output) and allowed to self-improve `@AGENT.md` (how to compile/run) and `@fix_plan.md` (bugs noticed, even unrelated ones) via subagents.

## Phase one: generate
**Covers:** phase one: generate

Generating code is now cheap, and the code Ralph generates is within the operator's complete control through the technical standard library and the specifications.

Steering rules:

- If Ralph is generating the wrong code or using the wrong technical patterns, update the standard library to steer it to the correct patterns.
- If Ralph is building the wrong thing completely, the specifications may be incorrect.

CURSED lesson: the lexer specification defined a keyword twice for two opposing scenarios; this was only noticed a month in, wasting a lot of time. The conclusion drawn is that "it's easy to blame the tools instead of the operator."

Context notes in the chunk: from design doc to code via the Groundhog AI coding assistant (and new Cursor vibecoding meta), following the "You are using Cursor AI incorrectly..." post and teasing the "N-factor of weeks of co-worker output in hours" technique at `https://ghuntley.com/specs`.

## Phase two: backpressure
**Covers:** phase two: backpressure

This is where the engineering hat goes on: since generation is easy, the hard part is ensuring Ralph generated the right thing. Programming languages have inbuilt back pressure through their type systems.

Language trade-off, quoted in substance:

- "Rust! It's got the best type system. However, one thing with Rust is that the compilation speed is slow. It's the speed of the wheel turning that matters, balanced against the axis of correctness."
- Language choice requires experimentation. For the CURSED compiler, extreme correctness meant Rust, but slower builds; LLMs are "not very good at generating the perfect Rust code in one attempt," so they need more attempts — which "can be either a positive or a negative thing."

The "test and build" wheel: anything can be wired in as back pressure to reject invalid generation — security scanners, static analysers, anything — but "the wheel has got to turn fast."

Staple prompt used when building CURSED:

> After implementing functionality or resolving problems, run the tests for that unit of code that was improved.

Dynamically typed languages, quoted warning:

> If you're using a dynamically typed language, I must stress the importance of wiring in a static analyser/type checker when Ralphing

Named examples: `https://www.erlang.org/doc/apps/dialyzer/dialyzer.html` and `https://pyrefly.org/`. Without one: "you will run into a bonfire of outcomes."

## Capture the importance of tests in the moment
**Covers:** capture the importance of tests in the moment

Because Ralph does one thing and one thing only every loop, with each loop in a new context window, it is crucial in that moment to ask Ralph to write out the meaning and importance of each test — what it is trying to do.

Documentation rule:

> Important: When authoring documentation (ie. rust doc or cursed stdlib documentation) capture the why tests and the backing implementation is important.

Rationale: this is like leaving notes for future LLM iterations explaining why a test exists, because future loops will not have the reasoning in their context window. Worked example in the chunk is an Elixir test module `Anole.Database.QueryOptimizerTest` with `@moduledoc` (caching, batching, analysis; real plus mocked DB calls) and a `@doc` on the `init/0` ETS-table test (`:anole_query_cache`, `:anole_query_stats`, both `:set` type).

Observed benefit: it helps LLMs decide whether a test is no longer relevant or is important, affecting whether to delete, modify, or resolve a test failure.

## No cheating
**Covers:** no cheating

Claude has the inherent bias to do minimal and placeholder implementations. Counter-prompt variation used at stages of CURSED:

> After implementing functionality or resolving problems, run the tests for that unit of code that was improved. If functionality is missing then it's your job to add it as per the application specifications. Think hard.

> If tests unrelated to your work fail then it's your job to resolve these tests as part of the increment of change.

> 9999999999999999999999999999. DO NOT IMPLEMENT PLACEHOLDER OR SIMPLE IMPLEMENTATIONS. WE WANT FULL IMPLEMENTATIONS. DO IT OR I WILL YELL AT YOU

Expectation-setting: do not be dismayed if early on Ralph ignores this sign and does placeholder implementations — models chase their reward function, and "the reward function is compiling code." Remedy: run more Ralphs to identify placeholders and minimal implementations and turn them into a to-do list for future Ralph loops.

## The todo list
**Covers:** the todo list

The prompt stack below was used over the last couple of weeks to build the TODO list. Stance: "Ralph will test you. You have to believe in eventual consistency and know that most issues can be resolved through more loops with Ralph, focusing on the areas where Ralph is making mistakes."

Prompt stack, quoted in substance:

> study specs/* to learn about the compiler specifications and fix_plan.md to understand plan so far.
>
> The source code of the compiler is in src/*
>
> The source code of the examples is in examples/* and the source code of the tree-sitter is in tree-sitter/*. Study them.
>
> The source code of the stdlib is in src/stdlib/*. Study them.
>
> First task is to study @fix_plan.md (it may be incorrect) and is to use up to 500 subagents to study existing source code in src/ and compare it against the compiler specifications. From that create/update a @fix_plan.md which is a bullet point list sorted in priority of the items which have yet to be implemeneted. Think extra hard and use the oracle to plan. Consider searching for TODO, minimal implementations and placeholders. Study @fix_plan.md to determine starting point for research and keep it up to date with items considered complete/incomplete using subagents.
>
> Second task is to use up to 500 subagents to study existing source code in examples/ then compare it against the compiler specifications. From that create/update a fix_plan.md which is a bullet point list sorted in priority of the items which have yet to be implemeneted. Think extra hard and use the oracle to plan. Consider searching for TODO, minimal implementations and placeholders. Study fix_plan.md to determine starting point for research and keep it up to date with items considered complete/incomplete.
>
> IMPORTANT: The standard library in src/stdlib should be built in cursed itself, not rust. If you find stdlib authored in rust then it must be noted that it needs to be migrated.
>
> ULTIMATE GOAL we want to achieve a self-hosting compiler release with full standard library (stdlib). Consider missing stdlib modules and plan. If the stdlib is missing then author the specification at specs/stdlib/FILENAME.md (do NOT assume that it does not exist, search before creating). The naming of the module should be GenZ named and not conflict with another stdlib module name. If you create a new stdlib module then document the plan to implement in @fix_plan.md

TODO-list lifecycle: eventually Ralph runs out of things to do or goes completely off track — "It's Ralph Wiggum, after all" — and then it is a matter of taste. Through CURSED the TODO list was deleted multiple times; it is watched "like a hawk" and thrown out often. After throwing it out, run a Ralph loop with explicit instructions as above to generate a new TODO list.

## Loop back is everything
**Covers:** loop back is everything

Program in ways where Ralph can loop himself back into the LLM for evaluation — "incredibly important." Always look for opportunities: as simple as instructing extra logging, or, for a compiler, asking Ralph to compile the application and then look at the LLVM IR representation.

Quoted instruction:

> You may add extra logging if required to be able to debug the issues.

## Ralph can take himself to university
**Covers:** ralph can take himself to university

The `@AGENT.md` is the heart of the loop: it instructs how Ralph should compile and run the project. If Ralph discovers a learning, permit self-improvement:

> When you learn something new about how to run the compiler or examples make sure you update @AGENT.md using a subagent but keep it brief. For example if you run commands multiple times before learning the correct command then that file should be updated.

Bug capture during a loop — if Ralph determines something needs fixing, capture that reasoning:

> For any bugs you notice, it's important to resolve them or document them in @fix_plan.md to be resolved using a subagent even if it is unrelated to the current piece of work after documenting it in @fix_plan.md
