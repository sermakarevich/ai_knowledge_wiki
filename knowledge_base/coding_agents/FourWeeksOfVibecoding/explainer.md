# 4 Weeks of Vibecoding: What I Built, What I Learned, and… | Pokharna Talks — In Plain Language

## What is this about?

This is the story of a complete beginner who went from zero to shipping
real websites in just four weeks — without learning to write code.

In mid-February 2026, the author could not set up a project on GitHub,
had never used the text-command window programmers use (the terminal),
and had never saved a change to shared code (a commit).

One month later, he had 197 saved changes across several live websites.

Before this, he had spent about ten years building shared-living
(coliving) businesses, advising more than 70 operators in 14 countries,
and running a newsletter with 36,000 readers — but had never shipped
a single line of code himself.

His point: "vibecoding" is a misleading name. It sounds like you need
to understand programming languages and frameworks. He says you do not.

His definition, in plain words: you do not write code. You describe in
detail what you want built and exactly how it should behave. The AI
coding tool does the typing and building for you.

And he stresses this is real work, not practice toys: a full
two-sided property marketplace, a large website rebuild, a detailed
product plan for a third project, and his own rebuilt blog.

## Why does it matter?

Because it challenges who gets to build software.

The usual story is: no coding skill means no product. You must either
learn to program (months of work) or hire someone and wait in line.

The author says that barrier has fallen. What used to sit as a task
ticket in a waiting list for weeks can now become a working feature
on a live site within hours.

That matters for anyone with deep knowledge of a subject — a shop
owner, a teacher, a charity organiser — who knows exactly what their
users need but cannot program.

It also matters because it reframes the skill that counts. It is no
longer "can you write code?" but "do you know clearly what should
exist, and can you describe it precisely?"

The author's own claim makes the point concrete: in four weeks he
shipped more working product than in the previous two years combined.

## How does it work?

The method has three steps: know it, say it, let the AI build it.

**1. Know what you want.** The author leaned on years of subject
knowledge instead of programming knowledge. He did not know the
coding languages behind his sites, but he knew exactly which fields
a property listing needs, what an admin screen must allow, how a
visitor goes from searching to booking, and how search-friendly
page structures work.

**2. Say it out loud.** Instead of typing formal requirement
documents, he spoke them into a voice-memo app on his phone —
while walking, driving, or between calls. He talked through the
steps a user takes, what information gets stored, tricky edge
cases, and what he disliked about existing solutions.

**3. Let AI turn words into a working site.** AI transcribed the
recordings and organised them into a structured requirements
document. That document was then fed to an AI coding tool
(Claude Code), which wrote the code and updated the live site.

A concrete example: his marketplace has three kinds of users —
renters, property operators, and site admins — each with their own
area of the site, plus listing approvals, messaging, reviews,
lead tracking, data downloads, and over 2,500 search-friendly pages.

## Where can this be used?

Anywhere someone understands a problem deeply but cannot program.

- **Small business owners.** A letting agent, a clinic, or a local
  shop could describe their booking, listing, or ordering needs
  and get a working site instead of waiting on a developer.
- **Subject-matter publishers.** The author rebuilt a 170-page
  information site into a planned 300-page one, adding 15
  interactive helpers (cost calculators, readiness checks,
  document generators), plus directories of vendors and operators.
- **Product managers and founders.** He says writing requirement
  documents used to be a major slow task; now he "speaks in PRD"
  — talks through requirements aloud and has them built the
  same day. A full product plan for a new project was written
  precisely enough to build from with no follow-up questions.
- **Personal projects and portfolios.** His own blog was one of
  the first rebuilds — a learning project that became a full
  article system plus an About page that works as a filterable
  showcase of his work.

The pattern is the same everywhere: if you can describe the users,
the steps they take, and the rules clearly, the tool can build it.

## Conclusions & takeaways

The author's closing message is simple: this is not a story about
AI tools. It is a story about intent — deciding what should exist
and describing it well enough to get built.

He lists the classic excuses — "I can't code," "I can't set up
a project," "I don't understand the technology" — calls them all
valid, and then calls them all irrelevant now.

The new dividing line, he says, is not technical versus
non-technical. It is clarity versus lack of clarity: people who
know what needs to exist versus people who do not.

So the takeaway is a challenge rather than a tutorial. The tools,
he says, are ready. The open question is whether you know what
you want clearly enough — and whether you will start.

> "Start. The tools are ready. The question is whether you are."

## Jargon decoder

| Term | What it means in plain language |
|---|---|
| Vibecoding | Building software by describing what you want in everyday words and letting AI write the code |
| AI coding tool | A program (here, Claude Code) that turns written instructions into working website code |
| GitHub repo | A shared online folder where all versions of a project's code are stored |
| Commit | A single saved batch of changes to the project, with a short note saying what changed |
| Terminal | A text window where you type commands to control the computer directly |
| Two-sided marketplace | A website bringing two groups together — e.g. renters looking for rooms and operators listing them |
| Admin panel / portal | A private section of the site where staff approve listings, manage users, and view data |
| SEO pages | Pages shaped so search engines like Google find and show them to the right people |
| PRD (product requirements document) | A detailed written plan describing what a product must do, for whoever builds it |
| Jira ticket / backlog | A task card in a to-do list developers work through, often waiting weeks for attention |
