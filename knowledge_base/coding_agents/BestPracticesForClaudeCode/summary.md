# Best practices for Claude Code - Claude Code Docs

**Article:** [Best practices for Claude Code - Claude Code Docs](https://www.anthropic.com/engineering/claude-code-best-practices) — Anthropic Engineering

## Human Readable TL;DR

Think of Claude Code like a brilliant but forgetful junior engineer with a small desk: the more papers you pile on it, the more it forgets what you told it first, so you have to keep the desk tidy and give it a checklist it can verify itself. Instead of hovering over its shoulder, you hand it a test or a screenshot to compare against, let it explore the codebase and propose a plan before touching anything, and write down the house rules once in a CLAUDE.md file so every session starts on the same page. For quick one-off jobs you just call it from the command line and pick whether you want a plain answer, structured JSON for scripts, or a live stream of results.

## TL;DR

Claude Code is an agentic coding environment whose context window — holding every message, file read, and command output — is the scarcest resource, filling by tens of thousands of tokens per session and degrading recall and accuracy as it fills. The guide's core prescriptions are to always give Claude a runnable verification check (tests, build, linter, output diff, screenshot comparison) so it iterates without the user as the verification loop, to separate Explore, Plan, Implement, and Commit phases using plan mode, to write specific prompts with scoped files, symptom descriptions, success criteria, codebase patterns, and git history pointers, and to supply rich content directly via @-references, pasted images, allowlisted URLs, and piped data. Environment setup is persistent via a concise, broadly-applicable CLAUDE.md (generated with /init, checked into git, importing extra files with @path/to/import), with sometimes-relevant knowledge moved to on-demand skills, and one-off automation uses non-interactive claude -p with plain text by default, --output-format json (single object with a result field) for scripts, and --output-format stream-json --verbose (line-delimited JSON starting with an init event) for real-time processing.

## Problem & Motivation

The guide starts from a shift in interaction model and a single governing constraint. Unlike a chatbot that answers and waits, Claude Code reads files, runs commands, makes changes, and autonomously works through problems while the user watches, redirects, or steps away, which means users describe what they want while Claude explores, plans, and implements. The constraint is that the context window holds the entire conversation including every file read and every command output, so a single debugging session or codebase exploration can generate and consume tens of thousands of tokens, and as the window fills Claude starts forgetting earlier instructions and making more mistakes. Everything else follows: vague prompts, missing verification signals, premature implementation without research, and bloated persistent configuration all waste the most important resource, forcing the user back into the loop to notice mistakes, restate intent, and re-explain project conventions every session.

## Main Original Ideas

1. **Context window as the resource to manage** — The guide frames context, not model capability, as the thing to optimise, with pointers to startup-loading walkthroughs, per-file-read cost awareness, custom status lines for continuous tracking, and token-reduction strategies, because forgetting and errors grow as the window fills.

2. **Give Claude a check it can run** — Verification is anything returning an in-conversation signal Claude can read: a test suite, a build exit code, a linter, a script diffing output against a fixture, or a browser screenshot compared against a design. Without it, "looks done" is the only signal and the user becomes the verification loop where every mistake waits to be noticed; with it, the session becomes one the user can walk away from, confirmed at the end by running /verify against the running app and by asking Claude to show evidence (test output, command plus return value, screenshot) rather than asserting success.

3. **Explore first, then plan, then code** — Research and planning are separated from implementation across four phases: Explore in plan mode (Shift+Tab until plan mode on, or claude --permission-mode plan) where Claude reads without changing anything, Plan with a detailed implementation proposal editable via Ctrl+G, Implement after approving or leaving plan mode with verification attached, and Commit with a descriptive message and PR. Planning is skipped only when the diff could be described in one sentence (typo, log line, rename) and required when the approach is uncertain, multiple files change, or the code is unfamiliar.

4. **Specific prompts with sources and success criteria** — Precision reduces corrections: scope the task to files, scenarios, and test preferences, point to sources such as git history, reference existing codebase patterns to follow or avoid, and describe the symptom plus what fixed looks like, including a failing reproduction test. Vague prompts are reserved for exploration where the user can course-correct.

5. **Rich content supplied directly** — Instead of describing where code lives, reference files with @ so Claude reads them before responding, paste or drag in images and screenshots, give documentation and API URLs (allowlisting frequent domains via /permissions), pipe data in such as cat error.log | claude, and let Claude fetch the rest via Bash, MCP tools, and file reads.

6. **Persistent environment via a concise CLAUDE.md** — A few setup steps compound across sessions: run /init to generate a starter from project structure, then include Bash commands, code style, and workflow rules that apply broadly, keeping it short and human-readable. Code-style examples are ES modules import/export over CommonJS require and destructured imports, and workflow examples are typechecking after a series of changes and preferring single-test runs over full suites for performance. Bloat is the enemy, enforced by the cut test of whether removing a line would cause mistakes, an include/exclude table (include unguessable commands, divergent style rules, test runners, repo etiquette, architecture decisions, env quirks, and gotchas; exclude derivable-from-code details, standard conventions, full API docs, volatile info, tutorials, file-by-file descriptions, and platitudes), treating the file like code with regular pruning, /context to confirm loading, /doctor to propose cuts, singular IMPORTANT emphasis, git check-in for team compounding, and @path/to/import for extra files, with sometimes-relevant domain knowledge moved to skills loaded on demand.

7. **Non-interactive scripting with tiered output formats** — One-off queries run as claude -p with a quoted prompt defaulting to plain text, structured scripting uses --output-format json returning a single JSON object with a result field, and real-time processing uses --output-format stream-json --verbose printing one JSON object per line starting with an init event.

## Key Findings

The guide is prescriptive rather than empirical, so its findings are workflow contrasts rather than measured results. Before-and-after prompt pairs show the pattern repeatedly: scoping tests to the logged-out edge case without mocks beats a bare request for tests, asking for git-history synthesis beats asking why an API looks weird, pointing at an existing widget implementation and constraining libraries beats asking for a calendar widget from nothing, and naming the auth flow, token refresh path, and failing-test-then-fix sequence beats reporting a login bug. For verification the same contrast holds: a validateEmail task with example cases plus a run-the-tests instruction beats an undecorated function request, a pasted design screenshot with take-a-screenshot-compare-list-differences-and-fix beats a request to make a dashboard look better, and a pasted build error with fix-and-verify plus address-the-root-cause beats reporting a failing build. Gating options trade determinism against flexibility: in-prompt checks work on any task today, /goal conditions add a per-turn evaluator that can stall with the goal still set, Stop hooks deterministically block turn-end until a script passes but are overridden after eight consecutive blocks, and verification subagents or dynamic workflows add a fresh-model second opinion so the worker is not its own grader.

## Suggestions & Future Directions

The guide's suggestions are to adopt the full loop rather than individual tricks: discover pages via /docs/llms.txt before exploring, keep CLAUDE.md minimal and let skills carry episodic knowledge, default to plan mode for unfamiliar or multi-file work, attach a runnable check to every implementation prompt, and prefer evidence over assertions. It points outward to follow-ups the reader should consult next: the interactive walkthrough of startup loading and per-read costs, a custom status line for live context tracking, dedicated token-reduction guidance, and the goal, hook, and subagent verification patterns for sessions that need stronger gates. For teams, the direction is to check CLAUDE.md into git so conventions compound, allowlist shared documentation domains, and standardise on the evidence habit of test output, command plus return value, or screenshot on every claimed completion.
