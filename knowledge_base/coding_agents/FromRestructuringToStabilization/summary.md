# From Restructuring to Stabilization: A Large-Scale Experiment on Iterative Code Readability Refactoring with Large Langu

**Paper:** [From Restructuring to Stabilization: A Large-Scale Experiment on Iterative Code Readability Refactoring with Large Language Models](https://arxiv.org/abs/2602.21833v1) — arXiv, 25 Feb 2026

## Human Readable TL;DR

Imagine asking a very tidy friend to reorganize your bookshelf five times in a row: the first pass moves lots of books around, but by the fourth or fifth pass they are mostly just straightening spines that are already in place. That is what GPT-5.1 does to Java code — a big first cleanup (renaming variables, splitting methods, trimming comments), then smaller and smaller touch-ups that never quite reach absolute zero. Remarkably, even when handed deliberately messed-up code with nonsense names or stripped comments, the model steers it back toward nearly the same tidy end state, like water finding the same level in different-shaped glasses. Telling it to focus on names versus comments changes what it fiddles with, but not the overall settle-down pattern — except that nagging about names can make it flip-flop on the same renames.

## TL;DR

The authors run a large-scale iterative refactoring experiment — 230 Java snippets from TheAlgorithms-Java, each in Original, Meaningless-identifier, and NoComment variants, refactored over five iterations under general and targeted prompts with GPT-5.1 at temperature 0 (10,350 generated snippets) — and find a consistent restructuring-then-stabilization dynamic suggesting the model converges toward an internalized notion of optimally readable code. Already-clean code is largely preserved but not untouched (unchanged lines rise 45% to 92% across iterations while code lines grow 58 to over 73 and inline comments are nearly eliminated), degraded variants converge to nearly identical structural end states (≈0.87 cross-variant similarity), and targeted prompts steer the mix of change types without breaking convergence, though naming-focused prompts can induce oscillatory renaming. Functionality breaks are rare but non-zero, so the authors recommend guardrails such as explicit stopping criteria and care with valuable comments.

## Problem & Motivation

Readable code eases maintenance, debugging, and collaboration, while poorly written code raises costs and bug risk, so the promise that LLMs can transform convoluted human or AI-written code into readable versions matters a great deal in practice. Prior work had shown that LLMs can refactor in a single shot, but left open what happens when a model repeatedly refactors its own output — whether it converges to a stable higher-quality solution or drifts into superficial, oscillating, or regressive changes — and how unguided versus targeted prompts or varying initial code quality affect multi-iteration trajectories. The paper frames this as three research questions: how iterative refactoring evolves on code that already follows readability best practices (RQ1), whether degraded variants of the same snippet converge when refactored independently (RQ2), and whether prompts that explicitly emphasize a readability aspect make targeted refactoring more effective (RQ3).

## Main Original Ideas

1. **Iterative refactoring experiment at scale.** The study samples 230 Java files meeting size, method-density, and code-ratio criteria from TheAlgorithms-Java, derives three variants per file (Original, Meaningless with scrambled identifiers and comment content, NoComment with all comments removed), and crosses them with three prompts (general, naming-targeted, comment-targeted) over five stateless GPT-5.1 iterations, yielding 10,350 snippets for analysis.

2. **DiffParser and multi-level comparison framework.** The authors build reusable, LLM-agnostic tooling that classifies line-level changes (renames, syntax-only, comment, mixed, and code sub-types such as access, call, control, literal, operator, and other-structural, plus insertions and deletions) and compares versions horizontally (a version against all its predecessors, catching back-and-forth where v0 equals v2 but not v1), vertically (variants within one version), and combined (whether variants converge to one optimal form), using sequence-, token-, and AST-based similarity.

3. **Restructuring-then-stabilization convergence account.** Rather than assuming the model stops when done, the paper characterizes the trajectory quantitatively — early iterations dominated by renames, code insertions, method decomposition, and comment pruning, later iterations with all change types under 1% and adjacent-version similarity climbing from 0.86 to 0.90 without ever reaching 1.00 — and interprets this as evidence of an internalized "optimally readable" target plus a persistent over-refactoring tendency.

## Key Findings

On already-clean code with the general prompt, the model preserves structure while still restructuring noticeably: unchanged lines climb from 45% (v0→v1) through 76%, 86%, and 89% to 92% (v4→v5), with the first transition dominated by renaming (9%) and code insertions (11%), while code lines grow from 58 to over 73, empty lines and method counts rise and stabilize from the third version onward, comment lines fall slowly, and inline comments are almost completely removed. Changed-line similarity between adjacent versions rises from 0.86 to 0.90 and early-to-late pairs (v1→v4 at 0.87, v2→v5 at 0.88) show early convergence, yet no pair reaches 1.00, indicating persistent micro-changes rather than full stability. Degraded variants follow the same trajectory after heavier first passes — Meaningless starts at 31% unchanged with 24% renames and NoComment at 44% unchanged with 14% renames — reaching 90% and 89% unchanged by the final transition, with code lines converging from 56 to about 73 and method counts from 3.1 to about 6 across all variants, and cross-variant similarity settling within a narrow band around 0.87 (Original–NoComment falling from 0.98, the renamed pairs rising from 0.85, ending within 3% of each other). Targeted prompts steer the change mix without altering overall convergence: the naming-focused prompt keeps rename rates high even late (around 20% on Original, about 25–30% on degraded variants, with chaotic alternating renames on NoComment), while the comment-focused prompt concentrates comment insertions, deletions, and changes in the first iteration (around 36% of changes on Meaningless) and then stabilizes quickly without inflating documentation, achieving slightly lower cross-variant similarity than the naming prompt. The authors qualify all of this with validity threats — the line-pair dataset could not cover every diff case, repeated-variable renames were counted per occurrence without checking consistency, only GPT-5.1 was tested in the main run (though gpt4.1-mini and gpt5.1-mini anecdotes show the same trends with larger models more "opinionated"), temperature 0 reduces but does not eliminate non-determinism, averaging can hide individual back-and-forth sequences, and readability itself was only checked anecdotally rather than measured directly.

## Suggestions & Future Directions

The practical message is that LLMs can normalize diverse snippets toward a consistent style but need guardrails: practitioners should add explicit stopping criteria to counter over-refactoring, phrase naming instructions carefully to avoid rename oscillations, and build mechanisms that preserve valuable explanatory comments the model would otherwise prune. For research, the authors call for exploring larger and more diverse code bases, systematically varying prompt strategies and contextual anchoring, capturing code growth and contraction (e.g., comment-section expansion) as explicit change types, and moving beyond anecdotal checks toward direct measurement of whether the refactored code is actually more readable to humans, supported by their public replication package at https://github.com/brains-on-code/IterativeRefactoringLLM.
