# PracRepair: LLM-Empowered Automated Program Repair Inspired by Human-Like Debugging Practices

**Paper:** [PracRepair: LLM-Empowered Automated Program Repair Inspired by Human-Like Debugging Practices](https://arxiv.org/abs/2606.17612v1)

## Human Readable TL;DR

Imagine a car mechanic who tries to fix your engine by only staring at the blueprint and listening to you say "it makes a noise," without ever opening the hood, starting the engine, or test-driving it after a repair. That is roughly how most current AI bug-fixers work: they read the code and the error message but never watch the program actually run and fail. PracRepair instead works like a careful human mechanic: it starts the engine with instruments attached to watch exactly which parts move and which values go wrong, asks itself a chain of focused questions like a detective ("what just happened here, why did it happen, and how should I fix it?"), and after each attempted fix it test-drives the car again and compares the before-and-after behavior to sharpen the next attempt. The result is a repair assistant that fixes substantially more real-world Java bugs than its predecessors, especially tricky ones spanning multiple functions, while actually costing less per fixed bug.

## TL;DR

PracRepair is a fully automated LLM-based automated program repair (APR) framework that mirrors three human debugging practices: static-dynamic evidence gathering, question-driven failure diagnosis, and feedback-guided patch refinement. In Stage I it builds a failure-relevant context basis by parsing the project with Joern into a Code Property Graph unifying AST, CFG, and data-dependence relations, collecting statement-level runtime traces (executed statement sequence, in-scope variable values with object fields recursively serialized to depth 3, and branch outcomes) via non-intrusive JavaAgent/ASM bytecode instrumentation scoped to the buggy function under triggering tests and organized into per-<triggering test, buggy function> Execution Trace Tables, and exposing all of it through a uniform on-demand retrieval interface rather than dumping full projects and traces into the prompt. In Stage II it runs a budgeted diagnosis loop (up to 10 rounds, averaging under 5) that asks and answers one typed diagnostic question at a time — what-questions establishing factual failing-execution behavior from dynamic evidence, why-questions linking abnormal runtime states to faulty logic from static plus dynamic evidence, how-questions deciding the fix from the diagnosed root cause plus static context — via a ReAct-style interleaving of reasoning and retrieval, accumulating a QA history that is summarized into an explicit four-field repair hypothesis (faulty behavior, supporting evidence, suspected root cause, modification suggestion). In Stage III it iterates up to 3 refinement rounds of hypothesis-guided zero-shot patch generation, validation by compilation plus test execution (plausible only if everything compiles and passes within 10 minutes) with patched-trace collection, and feedback extraction that categorizes failures into compilation, runtime, remaining, and regression outcomes and returns validation diagnostics, code diff, and aligned trace diff (changed branch outcomes, added/removed executions, divergent runtime values) back into Stage II for re-diagnosis until a plausible patch is found or the budget is exhausted.

## Problem & Motivation

Software defects are increasingly common and non-local: in real systems the cause and effect of a bug often extend beyond a single function and demand reasoning over call relationships, data dependencies, and execution logic, while developers spend roughly 35% to 50% of their time and 50% to 75% of project budgets on testing, verification, and debugging at a cost exceeding 100 billion dollars per year. Automated program repair aims to generate patches automatically, and early approaches built on hand-designed fix patterns or bug-fix datasets were limited by narrow pattern coverage, strong data dependence, and weak generalization, whereas recent LLM-based methods such as ChatRepair, ThinkRepair, RepairAgent, and ReInFix improved Defects4J results but still rely primarily on static or retrieved context, error messages, and coarse-grained pass/fail validation outcomes. PracRepair argues this misses the two dynamic signals human developers use in IDE-like debugging — failure-execution dynamics showing how the failure is triggered through executed paths, runtime states, and branch outcomes, and patch-validation dynamics showing how a candidate patch changes behavior — without which LLMs miss root causes or produce incomplete, overfitted fixes, especially when root causes depend on runtime state and value evolution. Exploiting these signals faces three challenges the framework is built around: complete failure traces are large and noisy and overwhelm the repair context (C1), raw static-plus-dynamic context is not self-explanatory so the model must be guided to which states matter and how they relate to faulty logic (C2), and patch-validation dynamics are typically reduced to coarse outcomes that give later iterations no fine-grained evidence of what changed and why the patch still fails (C3). The paper's Compress-21 `writeBits` motivating example makes this concrete: a static-only fix that masks the cache byte still fails with the same `Unknown property 128` error, an unguided dynamic-context attempt still flounders, and a first dynamic-informed patch (`if (shift == 0)` to `if (shift < 0)`) removes the original error but introduces `Badly terminated header`, with only structured validation feedback localizing the remaining fault to the post-loop flush and yielding the passing `if (length > 0 && shift < 7)` fix.

## Main Original Ideas

1. **Static-dynamic context construction with on-demand access** — Static context comes from a Joern-built Code Property Graph exposing classes, methods, statements, control branches, call edges, and definition–use chains, while dynamic context comes from focused statement-level trace collection on the buggy function under triggering tests; instead of feeding everything at once, both are served through a uniform retrieval interface (entity/dependency localization, definition inspection, structural and semantic relation inspection, execution-path, runtime-value, and statement-state inspection) so retrieval follows the current diagnostic need just as a developer steps into code and watches variables on demand.
2. **Question-driven failure diagnosis in what/why/how form** — Rather than generating a patch directly or dumping context into one-shot chain-of-thought, the model makes a structured decision each round to raise exactly one typed question (specifying type, target entity or behavior, and evidence needed) or stop, answers it by retrieving through the unified interface in a ReAct-inspired reasoning–retrieval loop, and appends a QA record of question, evidence, answer, and repair implication, progressively narrowing uncertainty until the accumulated history is distilled into the explicit four-field repair hypothesis that bridges diagnosis and generation.
3. **Feedback-guided patch refinement with trace-level diffs** — Validation is treated as behavioral evidence rather than a pass/fail gate: each failed candidate yields categorized outcomes plus three complementary feedback forms (validation diagnostics such as compiler errors, exceptions, timeouts, and updated failing tests; the patch-to-original code diff; and the original-vs-patched trace diff aligned by statement and execution order), which are fed back as optional diagnostic input so the next QA rounds can ask why a changed branch still leaves a value abnormal and refine the hypothesis for the next generation–validation round, with diagnosis capped at 10 rounds and refinement at 3 (upper bounds, with at most 3 independent sessions per bug at temperature 1.0).

## Key Findings

Under perfect fault localization PracRepair is the strongest method tested: summed over Defects4J it produces 275 correct and 332 plausible fixes with GPT-3.5 (139/167 on V1.2 and 136/165 on V2.0) and 333 correct with 413 plausible with GPT-4o (162/213 on V1.2 and 171/200 on V2.0), beating the strongest baseline ReInFix by 21 and 16 correct fixes on V1.2 and 13 and 26 on V2.0 under GPT-3.5 and GPT-4o respectively, while also surpassing ChatRepair, ThinkRepair, and RepairAgent under GPT-3.5 and fixing bugs across all six Defects4J projects. Its advantage is complementary rather than overlapping: it holds 75 unique correct fixes under GPT-3.5 against 29 for ThinkRepair, 26 for RepairAgent, and 12 for ChatRepair, and 93 against 51 for ReInFix under GPT-4o, and it stays ahead without exact fault locations, where PracRepair without perfect localization fixes 105 bugs correctly with 133 plausible patches on V1.2 versus 80 for ThinkRepair and 63 for Codex. Scenario analysis shows robustness from single-line through multi-function bugs with the clearest edge on the hardest multi-function setting (27 and 18 MF fixes on V1.2 and V2.0 with GPT-4o versus 22 and 15 for ReInFix, the only other MF-capable baseline), and single-function results of 120/135 on V1.2 and 121/153 on V2.0 under GPT-3.5/GPT-4o that consistently top all baselines. Ablations on Defects4J V1.2 with GPT-3.5 confirm every piece earns its keep: removing all three stages drops correct fixes to 84, adding back refinement alone reaches 105, adding diagnosis reaches 115, and adding static-dynamic context construction reaches the full 139; removing dynamic traces alone costs 19 correct fixes (139 to 120), question-driven diagnosis beats both one-shot CoT without tools (107) and ReAct-style free tool use (121), and refinement rounds climb from 89 with none to 107, 119, and 139 after one, two, and three rounds before plateauing, justifying 3 as the default. Generalization holds on the post-cutoff RWB benchmarks across GPT-4, GPT-3.5, DeepSeek-v3, DeepSeek-Coder, and Llama-3 with best or tied-best results (23 of 44 on RWB V1.0 with GPT-4 and DeepSeek-v3 versus 21 for ReInFix and 19 for ThinkRepair, plus 13 of 29 on RWB V2.0 with DeepSeek-Coder versus 12 and 10), suggesting gains are not memorization, and it does all this cheaply at $0.04 per repaired bug under GPT-3.5 (versus $0.06 for ReInFix, $0.14 for RepairAgent, $0.42 for ChatRepair) and $1.13 under GPT-4o (versus $1.45 for ReInFix).

## Suggestions & Future Directions

The authors' stated next step is to extend PracRepair beyond Java to more languages for stronger generalizability, which directly addresses the main external-validity limit that both Defects4J and RWB are Java-only and may not represent other languages or much larger codebases. A natural companion effort is broader multi-language and large-scale evaluation, since the current claims rest on Java benchmarks plus the hardware and budget choices in the paper (Ubuntu 20.04 workstation, GPT-3.5-turbo and GPT-4o at temperature 1.0, ablation confined to Defects4J V1.2 with GPT-3.5). On the methods side, the refinement plateau after three rounds and the reliance on manually judged semantic equivalence for correct-patch counting (exact developer match first, then manual assessment) invite work on adaptive stopping, richer oracles, and automated correctness checking to reduce manual-validation load and internal-validity risk. Finally, because the ablations show dynamic traces, typed diagnostic questions, and trace-diff feedback each contribute independently, future repair agents could borrow these pieces separately — for example, adding trace-diff feedback to existing iterative or agent-based pipelines like ChatRepair, RepairAgent, or ReInFix — and explore cheaper instrumentation, smarter trace filtering for noisy long executions, and tighter integration with retrieval-based repair-ingredient search.
