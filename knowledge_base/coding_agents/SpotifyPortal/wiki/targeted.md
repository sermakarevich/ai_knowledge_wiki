# Targeted Analysis: the 90%, What Generalizes, What Got Worse
**In one sentence:** The roughly 90% saving comes from keeping bulk file contents out of Claude's context by sending them to a cheaper worker model that returns only a short summary, and while this routing pattern generalizes to other setups, editing, reasoning, and latency do not improve.
## Key points
- The measured saving (about 90% on average) comes from bulk reading: large files go to the Gemini 2.5 Flash worker, and only a short structured summary enters Claude's context.
- Code writing saves tokens too by keeping reference reads and generated code out of Claude's context, with code written straight to disk, but this part was not measured with a number.
- Enforcement matters: automatic hooks (triggered checks before a tool call) make the saving happen, while advisory prompt rules in CLAUDE.md could be ignored.
- The pattern that transfers elsewhere is simple: send heavy Input/Output (I/O, reading and writing lots of text) grunt work to a cheaper model and keep the frontier (most capable, most expensive) model for reasoning.
- Small files are left out on purpose with a line-count threshold, because delegation adds delay and is not worth it for small reads.
- What got worse or did not work: editing with bad line numbers, reasoning misses such as a thread-safety bug, extra latency of 10–30 seconds per call, and stateless (no memory between calls) one-shot calls that must re-send files on follow-up.

## 1. The 90% broken down by mechanism
The article verifies three mechanisms behind the saving, but only one has a measured number.
(a) Bulk-read delegation is the measured ~90%. Instead of Claude reading several large files directly, the files are wrapped in Extensible Markup Language (XML, a tagging format) tags and sent to the bulk-reader mode running on Gemini 2.5 Flash. The worker reads the full contents and returns only short structured bullets. Only that short summary enters Claude's context, so most input tokens never reach the expensive model. The benchmark on a Java monorepo (a single large repository holding many projects) across four scenarios reports mean (average) bulk-read savings around 90%.
(b) Code-write output avoidance is real but unquantified. Without delegation, Claude would both read the reference files and generate the new file as expensive output tokens (tokens the model produces, which cost more than input tokens). With delegation, the code-writer mode receives the spec (task description) plus a required reference file, matches existing patterns, and writes the code straight to disk. Claude never sees the generated code. The article states this case is harder to measure and gives no percentage for it.
(c) Enforcement turns advice into savings. The first version used routing rules in CLAUDE.md (Claude Code's project instruction file), which were advisory and easy to ignore. The current shunt plugin uses PreToolUse hooks that fire before every tool call: check-file-size blocks Read calls over a configurable threshold (default 350 lines, set by the SHUNT_MIN_LINES environment variable), and check-bash-read catches cat, head, tail, less, and more on large files. The block message points Claude to the /bulk-reader skill with exact syntax. So hooks guarantee the cheap path is used.
To be clear: the ~90% mean is measured only for bulk reading; the code-write saving is confirmed by design but unmeasured. No per-mechanism percentages beyond that are given in the source.
## 2. What generalizes beyond Spotify's setup
These takeaways do not depend on Portal (Spotify's agent platform) specifically:
- Route heavy I/O grunt work to a cheaper model and keep the frontier model for reasoning. Reading five files to answer one question, or generating patterned tests and configs, needs little thinking and works fine on a cheaper worker.
- Enforce with hooks, not advisory prompt rules. Automatic checks before tool calls beat written instructions that the model can skip, and one plugin replaces per-project copies of rules.
- Threshold small work out. Targeted reads (with offset/limit) and piped commands such as cat file | grep pass through, so only large bulk reads pay the delegation cost.
- Use reusable, shareable, and composable declarative modes. A mode is a declared agent with instructions, model choice, and tools — no servers to manage. Modes are public (shared company-wide) or private, work across projects, and new ones such as doc-writer, reviewer, or translator are only a few clicks away.
- Decouple the routing decision from the worker. The plugin decides when to delegate; the mode decides how to respond. Either side can change — model, prompt, or Model Context Protocol (MCP, a standard for connecting models to tools) tools — without rewriting the other.
- Anything that can shell out to a Command Line Interface (CLI, a text-command tool) can reuse the pattern. Modes are callable from the CLI or Application Programming Interface (API, a way for programs to call a service), and scripts handle request building, error unwrapping, and token reporting, so any tool that can run a shell command can delegate the same way.
## 3. Failure modes and what got worse
- Editing cannot be delegated. Worker summaries do not include reliable line numbers, so Claude must still read the exact section directly before making edits.
- Reasoning cannot be delegated. The worker found surface patterns but missed a subtle thread-safety bug (an error where parallel threads interfere with each other); Claude spotted it in seconds once given the right context. Debugging, architectural decisions, and safety-critical code are explicitly excluded from routing.
- Latency gets worse. Each delegation is a network round trip (Claude Code to Portal backend to worker model and back), typically 10–30 seconds, and Portal caps a single invocation at 30 seconds, so large generations must be split.
- Small files go backwards. For small reads the delay outweighs the token saving, which is why the line threshold exists and small or targeted work passes through.
- Calls are one-shot and stateless. Every delegation is ephemeral (temporary, nothing stored server-side), so follow-up questions must re-send the files. Re-sending is free where it matters because the bulk text still never enters Claude's context, but it adds repeated worker cost and delay.
- Shared-mode trust and precedence need care. Modes are resolved case-insensitively by name, preferring your own mode, then your team's, then public ones, and forking the public bulk-reader makes yours take precedence automatically — convenient, but it means a public mode you did not write can shape answers unless you fork and control it.
