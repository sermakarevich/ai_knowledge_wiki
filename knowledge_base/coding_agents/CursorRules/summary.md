## Human Readable TL;DR

Think of Cursor Rules like house rules taped to the fridge for a brilliant houseguest who forgets everything between visits: since the AI retains no memory between completions, you write down the conventions once and they get slipped into its briefing notes at the start of every chat. Project rules are like room-specific notes filed in `.cursor/rules` that only surface when you walk into the matching room, user rules are personal preferences that follow you everywhere, team rules are building-wide policies set by the landlord that override everything else, and `AGENTS.md` is the sticky-note alternative for when you don't want the full filing system. Keep each note short, specific, and pointed at a real example, and the guest stops making the same mess twice.

## TL;DR

Cursor Rules provide persistent, reusable prompt-level context for Agent (Chat) to compensate for LLMs retaining no memory between completions, with applied rule contents prepended to model context. The system supports four rule types: version-controlled Project Rules in `.cursor/rules/*.mdc`, global User Rules defined in Customize → Rules, dashboard-managed Team Rules on Team/Enterprise plans, and plain-markdown `AGENTS.md` files as a simple alternative. Project rule inclusion is governed by frontmatter (`alwaysApply`, `description`, `globs`) yielding four modes — Always Apply, Apply Intelligently, Apply to Specific Files, and Apply Manually via `@`-mention — while Team Rules use free-form text with optional glob scoping, apply across all team repositories and projects, and merge in precedence order Team → Project → User. Supporting mechanics include glob scoping with `*` and `**`, rule creation via `/create-rule` or Customize, best practices keeping rules focused, actionable, scoped, and under 500 lines, nested `AGENTS.md` support with specificity precedence, repository import only via packaged plugins, and FAQs clarifying that rules affect only Agent (Chat), not Cursor Tab or Inline Edit.

## Problem & Motivation

The motivating problem is that large language models do not retain memory between completions, so without persistent instructions every Agent session starts from scratch and the user must repeat project conventions, architectural decisions, and workflow expectations. This repetition is error-prone and wasteful: the agent guesses at style, violates domain-specific patterns, and repeats mistakes the user has already corrected. Rules address this by bundling prompts, scripts, and references into version-controlled, shareable artifacts that are injected at the start of model context, making it easy to manage and share workflows across a team. The design must balance competing needs — always-on standards versus noise in context, automatic relevance versus user control, per-project specificity versus organization-wide consistency — which is why the docs devote so much attention to scoping mechanisms, precedence, and guidance on keeping rules lean rather than dumping entire style guides into context.

## Main Original Ideas

1. **Four complementary rule types** — The docs define Project Rules (versioned `.mdc` files in `.cursor/rules` for domain knowledge, workflows, and architecture), User Rules (global Customize → Rules preferences for communication style and coding conventions, used only by Agent Chat), Team Rules (organization-wide rules created and enforced from the Cursor dashboard on Team/Enterprise plans), and `AGENTS.md` (plain markdown in project root and subdirectories for straightforward cases without metadata). Together they cover the spectrum from personal to project to organization scope.

2. **Frontmatter-driven inclusion logic** — Each Project Rule is markdown plus frontmatter, and the combination of `alwaysApply`, `description`, and `globs` deterministically controls inclusion: `alwaysApply: true` means always included with globs and description ignored; `alwaysApply: false` with globs means auto-attached when a matching file is in context; with description only means the Agent reads the description and pulls the rule when relevant; with neither means `@`-mention-only manual invocation. A plain `.md` file in `.cursor/rules` is ignored precisely because it lacks this frontmatter, directing simple users to `AGENTS.md` instead.

3. **Four application modes with glob scoping** — The same mechanism surfaces in the UI as Always Apply (every chat), Apply Intelligently (Agent decides from description), Apply to Specific Files (glob match), and Apply Manually (e.g. `@my-rule` in chat). Glob patterns use `*` for a single path segment and `**` for recursive directories, comma-separated for multiples, with examples such as `src/**/*.tsx`, `**/*.ts`, `src/**`, and `docs/**/*.md, docs/**/*.mdx` enabling fine-grained file scoping.

4. **Team Rules administration and precedence** — Team Rules are free-form text without Project Rules folder structure, created and managed from the dashboard, visible to all members, and automatically applied across all repositories and projects for the team. A globbed Team Rule (e.g. `**/*.py`) applies only when matching files are in context while an unglobbed one applies to every conversation; `Enable this rule immediately` controls active-versus-draft and `Enforce this rule` controls required-versus-toggleable, with non-enforced rules disableable in Customize by default. All applicable rules merge in the order Team Rules → Project Rules → User Rules with earlier sources winning conflicts, ensuring organizational standards are maintained, including in compliance workflows with the caveat that AI guidance should not be the only security control.

5. **Nested AGENTS.md as the lightweight path** — As an alternative to `.cursor/rules`, `AGENTS.md` files can live in the project root and any subdirectory, are automatically applied when working with files in that directory or its children, and combine across nesting levels with more specific instructions taking precedence. This gives small projects and simple conventions a zero-metadata option while preserving composability for layered frontend, component, and backend instructions.

6. **Creation, reuse, and import ergonomics** — Rules are created by typing `/create-rule` in Agent chat (which generates frontmatter and saves under `.cursor/rules`), by asking the agent to create a rule, or via Customize sidebar → Rules → Add Rule, and they stay fresh by `@`-referencing canonical files and templates rather than copying contents. Good rules are focused, actionable, and scoped, kept under 500 lines and split into composable rules, avoiding copied style guides (use a linter), restated npm/git/pytest commands, rare edge cases, and duplicated codebase contents, following the maxim to start simple and add a rule only when the Agent repeats the same mistake. Rules are never imported standalone but arrive with a plugin published through a marketplace (repository with `.cursor-plugin/marketplace.json`, imported via From GitHub Repository or team marketplace), and `@`-mentions allow rules to reference files and other rules or be applied manually in chat.

## Key Findings

The docs' concrete examples show what well-scoped rules look like in practice: an always-applied copyright-header rule, a glob-scoped component rule for `src/components/**/*.tsx` (named exports, co-located CSS, small composable components), a description-driven backend rule for RPC service conventions (one service per file, boundary validation, structured errors, template references), and a manual migration rule (paired up/down scripts, backfill patterns). Broader example sets cover frontend standards (Tailwind styling, Framer Motion animations, component naming; zod validation with schema-derived types), Express and React templates, workflow automation (run `npm run dev`, fetch console logs, suggest performance fixes; extract comments and README into markdown docs), and a multi-step Cursor-setting recipe touching reactive storage types, defaults, settings tabs, and runtime reads. Operational findings include the troubleshooting matrix (Apply Intelligently needs a description, Apply to Specific Files needs a matching glob), the confirmation that `@filename.ts` references and `@`-mentions work for manual application, and the scope boundary that rules do not affect Cursor Tab or other AI features and User Rules do not apply to Inline Edit (Cmd/Ctrl+K).

## Suggestions & Future Directions

The documentation's implicit guidance is to treat rules as living, minimal artifacts rather than exhaustive manuals: start simple, check rules into git, update the rule whenever the Agent errs (including via `@cursor` on a GitHub issue or PR to have the Agent update it), and prune aggressively using community and provider examples instead of reinventing conventions. It steers users toward linters for style enforcement, toward file references instead of pasted contents to avoid staleness, and toward splitting large rules into composable pieces to keep context lean. For teams, the direction is dashboard centralization with enforcement for required standards, glob scoping for language- or area-specific policies, and plugin-packaged distribution for shared rule sets, while keeping in mind that enforced AI guidance is a complement to, not a replacement for, real security controls.
