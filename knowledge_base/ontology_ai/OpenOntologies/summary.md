# Open Ontologies: Tool-Augmented Ontology Engineering with Stable Matching Alignment

**Paper:** [Open Ontologies](https://arxiv.org/abs/2605.09184v1) — arXiv, 9 May 2026

## Human Readable TL;DR

Building formal ontologies with an LLM is a bit like asking a brilliant intern to file legal contracts: the drafts look fluent, but hidden contradictions slip through and nobody checks them. Open Ontologies gives that intern a strict clerk's office — a Rust toolbox of validators, reasoners, and search tools reachable through the Model Context Protocol — so every draft gets checked and corrected before filing. Its matching step works like a school dance with strict one-to-one pairing: instead of letting every class claim many partners, each class keeps only its best match, which wipes out thousands of false pairings at once. The striking result is that handing the intern the raw paperwork actually makes things worse than letting it guess from memory, while letting it query the clerk's structured tools more than doubles accuracy.

## TL;DR

Open Ontologies is a Rust (~17,400 lines), single-binary, MIT-licensed ontology engineering system that exposes construction, OWL-RL reasoning, SHACL validation, alignment, and lifecycle operations as MCP tools for LLM-orchestrated workflows. Its alignment module scores candidate class pairs with six weighted signals (label, property, parent, instance, restriction, neighbourhood) with a label-similarity fallback, then applies stable 1-to-1 matching that keeps only the top target per source and vice versa. On OAEI Anatomy this reaches F1 = 0.832 with the highest reported precision (P = 0.963, R = 0.733), while on OAEI Conference it reaches micro-averaged F1 = 0.438 (P = 0.693, R = 0.320). The ablation shows stable matching dominates signal design: weights vary F1 by less than 0.004 with matching on, while removing matching drops F1 to 0.728. On the OntoAxiom benchmark (9 ontologies, 3,042 axioms, Claude Opus 4), structured MCP tool access (F1 = 0.717) far beats both unaided inference from name lists (F1 = 0.431) and reading the raw OWL file (F1 = 0.323), demonstrating that tool structure is a qualitatively different access modality rather than merely richer input.

## Problem & Motivation

Large language models can generate syntactically valid OWL and orchestrate multi-step ontology engineering workflows, but they cannot guarantee logical consistency or verify that generated axioms are mutually coherent, while existing alignment systems achieve strong pairwise matching on benchmarks yet operate as standalone pipelines disconnected from construction and lifecycle management. Meanwhile AI-assisted construction tools extract terms or hold conversations without integrating formal validation into the construction loop, and programmatic frameworks such as the OWL API, ROBOT, Owlready2, and SSSOM target expert users rather than LLM-orchestrated workflows. Open Ontologies addresses both gaps by exposing ontology construction, reasoning, alignment, and lifecycle tools via the Model Context Protocol, enabling integrated workflows in which an LLM generates OWL, validates it against formal constraints, and refines it based on symbolic feedback.

## Main Original Ideas

1. **Rust-native MCP tool system** — an open-source implementation (~17,400 lines) shipping as a single binary with no JVM or Python dependency, combining an Oxigraph in-memory SPARQL 1.1 triple store, OWL-RL forward chaining plus partial SHIQ tableaux consistency checking, a SHACL validator, and a pattern enforcer with configurable rule packs, alongside infrastructure-as-code-style lifecycle operations (plan with blast-radius scoring, enforce, apply, monitor via SPARQL watchers, drift comparison, all in an append-only lineage trail).
2. **Six-signal scoring with label-penalty fallback** — each candidate class pair is scored as a weighted sum over label similarity (Jaro-Winkler plus token Jaccard, 0.25), property overlap (0.20), parent overlap (0.15), instance overlap (0.15), restriction similarity (0.15), and neighbourhood similarity (0.10), with confidence falling back to label similarity × 0.85 whenever all structural signals are zero so unsupported matches are penalised against the threshold.
3. **Stable 1-to-1 matching as the dominant constraint** — candidates are sorted by confidence and only the top-scoring target per source (and vice versa) is retained, eliminating many-to-many spurious matches; together with the label penalty and a raised label pre-filter (0.70 to 0.75), this cut Anatomy candidates from 12,557 to 1,154.
4. **Disentangled evaluation of tool structure versus information availability** — the OntoAxiom ablation compares unaided inference from name lists, raw OWL file reading, and structured MCP/SPARQL tool access, isolating whether gains come from richer input or from the tool modality itself.

## Key Findings

On the OAEI Anatomy track (2,737 mouse classes, 3,304 human classes, 1,516 reference mappings), the system achieves F1 = 0.832 with the highest reported precision of any system (P = 0.963, R = 0.733), trailing AML (0.936), BERTMap (0.924), and LogMap (0.912) on F1 but exceeding all on precision, with the recall gap attributed to conservative penalisation of true matches with low label similarity. The trajectory is dramatic: the initial run produced 12,557 candidates at P = 0.102, R = 0.846, F1 = 0.182, and the three fixes above lifted it to 1,154 candidates at F1 = 0.832. On the Conference track (7 ontologies, 21 pairs, 15 evaluated), the same method gives micro-averaged F1 = 0.438 (P = 0.693, R = 0.320), well below LogMap (0.67) and BERTMap (0.71), because heterogeneous modelling styles minimise label overlap; per-pair scores range from 0.667 (cmt-iasted) down to 0.211 (edas-sigkdd).

The ablations are the paper's sharpest claims. Across five weight configurations with stable matching, Anatomy F1 spans only 0.830–0.834, while all three no-matching configurations score an identical 0.728, so signal engineering buys less than 0.004 F1 once the assignment constraint is in place; the explanation is that most Anatomy class pairs carry no structural data, so reweighting zero-valued signals has no effect and the top-1 selection does all the work. Threshold sensitivity with matching shows the usual precision–recall trade-off (0.70: F1 0.717; 0.75: 0.809; 0.80: 0.831; 0.85: 0.808). On OntoAxiom, raw-file reading (F1 = 0.323) scores about 25% worse than the unaided LLM (0.431) because the model makes systematic Turtle parsing errors — notably F1 = 0.0 on domain extraction in 4 of 9 ontologies, confusing property and class IRIs, mishandling language tags, and missing multi-line axiom blocks — while MCP tools reach 0.717 (+66% over unaided, +122% over raw file), with raw-file performance varying by Turtle complexity (NordStream 0.692 and FOAF 0.647 at the top; Time 0.087, Pizza 0.154, ERA 0.058 at the bottom). Supporting results include OWL-RL versus HermiT on LUBM showing different reasoning profiles rather than a speed contest (at 50,000 axioms, 15 ms versus 24,490 ms, a 1,633× ratio, with HermiT computing 312 Pizza subsumptions OWL-RL does not), and an LLM-driven rebuild of the Manchester Pizza Tutorial producing a 91-class ontology in under 5 minutes at 96% class coverage (95/99 classes) versus roughly 4 hours of manual work.

## Suggestions & Future Directions

The paper names two open alignment challenges: the Conference track, where label-centric methods fail under heterogeneous modelling and will need richer structural or semantic signals, and the Anatomy recall gap (0.733 versus 0.922), where integrating domain-specific background knowledge such as UMLS — as LogMap and AML do — could rescue true matches with low label similarity, noting the module already accepts pluggable similarity functions and ONNX embedding models. It draws the broader lesson that effort spent on signal engineering yields minimal returns once stable matching is applied, and that giving an LLM more information does not always help when the access modality is raw syntax. Stated limitations and next steps include submitting to the official OAEI 2026 campaign since current results are measured against published reference alignments rather than independently evaluated, extending the signal ablation beyond Anatomy where structural signals are mostly zero, probing the Condition D methodology (Claude subagents reading via the Read tool may overestimate raw-file performance), acknowledging OWL-RL incompleteness for OWL-DL, single-developer maintenance of the codebase, and evaluation so far on Claude only.
