# Disagreements — ontology_ai

Scope: only the three topic digests (`topics/*/digest.md`) and the eight source summaries they link. No wiki pages, raw sources, or web.

## Putting the full ontology in the LLM context helps a lot vs putting the raw OWL file in context hurts

**Side A — full ontology in context is the key mechanism.** The DBLP NL-to-SPARQL paper reports that placing the complete domain OWL ontology (declared types, domain/range, class hierarchy) in the system prompt drives single-call zero-shot query generation to 89.9% Match and 81.3% Exact on the revised 1,000-question DBLP-QuAD 3.1, 98/100 on SemOpenAlex, and 100% on 21 neuroimaging competency questions, with the wrapper alone contributing about 25 Exact-match points ([[../../NaturalLanguageKnowledgeGraphQueryExecution/summary|NaturalLanguageKnowledgeGraphQueryExecution]]). The sibling MRI-metadata study concurs: the full-Turtle representation reaches 100% on its 21-question set while anonymised abstract forms collapse to 5–19%, and SPARQL over the readable ontology beats SQL from the same ontology 100% to 57% ([[../../NaturalLanguageAccessToDomainSpecificMetadata/summary|NaturalLanguageAccessToDomainSpecificMetadataAReusableFrameworkForLlmQueryGeneration]]).

**Side B — dumping the raw OWL file in context is worse than giving the model nothing.** The OpenOntologies ablation on the OntoAxiom benchmark (9 ontologies, 3,042 axioms, Claude Opus 4) finds structured MCP/SPARQL tool access at F1 0.717, unaided inference from name lists at 0.431, and raw OWL file reading last at 0.323 — about 25% worse than guessing from memory — owing to systematic Turtle parsing errors (F1 0.0 on domain extraction in 4 of 9 ontologies: confused property/class IRIs, mishandled language tags, missed multi-line axiom blocks) ([[../../OpenOntologies/summary|OpenOntologiesToolAugmentedOntologyEngineeringWithStableMatchingAlignment]]). Its stated lesson: more information does not help when the access modality is raw syntax.

**Likely reason — different setting, different task, different metric.** Side A uses purpose-built, LLM-oriented ontologies (readable names, `rdfs:comment`/`rdfs:label`, explicit domain/range per its six design principles) plus a task harness (SPARQL instructions, domain rider, output cleaning/repair) for a *query-generation* task scored by execution accuracy. Side B dumps heterogeneous pre-existing ontologies as raw Turtle with no instructions or harness for an *axiom-mining* task scored by structural F1 including domain/range triples. Model and date also differ (local Qwen3 variants vs Claude Opus 4; both arXiv 2026).

**Verdict — evidence favours Side A conditionally, and both results stand in-setting.** There is no genuine conflict once conditioned: a well-designed ontology delivered with instructions and repair helps enormously; raw complex Turtle dumped without tool support hurts. The topic-03 digest's own synthesis agrees ("tool structure beats raw context"). Practical takeaway for engineers: invest in readable naming plus annotations and domain/range discipline, and prefer structured/tool-mediated access over pasting raw files when the ontology was not designed for LLM consumption.
