# Natural Language Access to Domain-Specific Metadata: A Reusable Framework for LLM Query Generation

**Paper:** [Natural Language Access to Domain-Specific Metadata: A Reusable Framework for LLM Query Generation](https://arxiv.org/abs/2607.18029v2) — arXiv, 10 Sep 2026

## Human Readable TL;DR

Imagine a huge hospital archive where every MRI scan is filed with messy shorthand that only the filing clerks understand, so ordinary doctors can never find what they need. This paper shows that if you first relabel everything with clear, full English names and helpful sticky-note descriptions — like renaming a cryptic drawer code to "Patient Handedness: Right, Left, or Unknown" — then an AI assistant can translate plain questions into exact database queries with no extra training. It is like giving a tourist a well-signposted city map instead of asking them to memorise GPS coordinates: with good signs, even a modest local guide gets you everywhere, while with blank signs even the smartest guide gets lost.

## TL;DR

The authors present NLKGQ (Natural Language Knowledge Graph Query), a reusable framework and ontology-first development process that lets researchers query domain-specific metadata in plain language. The process captures domain vocabulary in a formal OWL ontology with readable names and semantic annotations, builds a knowledge graph via a domain-specific ETL pipeline, and uses a domain-agnostic harness that places the full ontology in the LLM system prompt to generate SPARQL zero-shot — with no fine-tuning, retrieval augmentation, or multi-agent orchestration. Demonstrated on a large MRI neuroimaging archive (80 studies, 2,000 experiments, ~10M triples in Apache Jena Fuseki), the best configurations reach 100% accuracy on a 21-question expert competency set, and an ablation across eight ontology representations shows readable names and annotations dominate accuracy far more than model choice or prompt engineering. A controlled comparison against a SQL database auto-generated from the same ontology on identical questions and models gives 100% SPARQL versus 57% SQL, which the authors attribute to OWL structural advantages preserved in Turtle but flattened in SQL DDL.

## Problem & Motivation

Research facilities, enterprises, and agencies accumulate large archives with rich metadata — subject demographics, acquisition parameters, experimental configurations, provenance — but answering ad-hoc questions requires writing SQL or SPARQL, which demands both query-language skill and insider domain vocabulary that most researchers lack. Prior results frame the stakes: top models exceed 90% on simple schemas like Spider, yet GPT-4o drops to 0% execution accuracy on real enterprise schemas with hundreds of tables (BEAVER), with failures traced to schema retrieval and column mapping, while reformulating the same enterprise questions over a knowledge graph raises accuracy from 16% to 54%. The paper argues that how domain knowledge is structured matters as much as which LLM is used, and that prior work treats the ontology or schema as a given to be coped with — via fine-tuning, in-context examples, query-time graph exploration, RAG pipelines, or multi-agent orchestration — rather than designing it for LLM consumption from the start.

The demonstration domain sharpens the constraints. The MRI neuroimaging archive is governed by GDPR for human-subject data, so all processing must stay on institutional infrastructure rather than external LLM services, and the practical goal is the smallest locally runnable model on modest hardware. The authors therefore evaluate eight locally deployed Qwen3 variants (8B to 35B parameters, dense and mixture-of-experts, including quantized variants) and ask what combination of ontology design, model, prompt, and backend yields reliable zero-shot query generation under those privacy and cost constraints.

## Main Original Ideas

1. **NLKGQ framework and ontology-first reusable process.** The contribution is split into a development process — capture vocabulary and semantics in OWL, build a KG via ETL, then co-evolve ontology, competency questions, and a domain-specific prompt rider through iterative testing — and a domain-agnostic reusable framework comprising the query server, web application, and combinatorial test driver that also supports production deployment. The query server builds a system prompt from generic SPARQL instructions, the complete domain ontology in Turtle, and a small rider for KG-specific conventions, then applies harness fixes such as stripping chain-of-thought blocks, extracting SPARQL from markdown, repairing PREFIX declarations from ontology ground truth, and optional error-feedback retry that mainly helps smaller models with syntax errors.

2. **Six LLM-oriented OWL design principles.** The authors formalise six rules that cost nothing in formal expressiveness but measurably improve accuracy: use full English words rather than abbreviations, use a consistent `has<Property>` naming pattern, use descriptive directional relationships, declare explicit domain and range, add natural-language annotations (`rdfs:comment`, `rdfs:label`, `skos:altLabel`) for context and synonyms, and avoid opaque codes in favour of meaningful URIs. A concrete example such as `mro:hasHandedness` with its label, comment listing expected values, domain, and range lets the LLM generate correct FILTER clauses without prior exposure, in direct contrast to opaque identifiers like Wikidata's `wdt:P552` that must be learned through tuning or exploration.

3. **Co-evolution loop with test-driven infrastructure.** Ontology, competency/regression test cases, and prompt rider evolve together: confusing names are renamed in the ontology, recurring LLM mistakes become new rider directives, and poorly handled user questions become new test cases, each iteration validated by re-running the full suite so regressions are immediately visible. The test driver evaluates each question by calling the LLM, executing the generated query, and comparing canonicalised results, sweeping over model, temperature, prompt, ontology representation, backend, repetitions, and fix-retry policy with parallel execution and CSV logging. The authors stress this requires domain knowledge and comfort with iterative testing but no machine-learning, database, or SPARQL expertise.

4. **Virtual ontology representations as a controlled ablation.** Eight representations auto-generated from the full Turtle — default, no-comments, compact, compact-typed, compact-grouped, raw-graph, abstract-dict, and abstract-graph — progressively strip semantic information to isolate which features LLMs rely on while holding model, prompt, and benchmark fixed. This design lets the paper separate the effect of naming, annotations, typing, and graph structure, revealing a 90-point spread driven by representation alone.

5. **Generic OWL-to-SQL converter for a like-for-like backend comparison.** Unlike prior SQL-versus-SPARQL comparisons across different schemas and datasets, the authors auto-generate a PostgreSQL 17 schema from the same authoritative ontology — each class becoming a table, datatype properties becoming typed columns, object properties becoming foreign keys with direction from `owl:inverseOf`, and annotations becoming column comments — load the same KG data (6 tables, 182 columns in the largest table), and evaluate both backends on the same 21 questions with the same readable naming and models. An additional Entity-Attribute-Value variant (narrow three-column tables per class) further probes how relational shape affects LLM generation.

## Key Findings

Across more than 16,000 runs (8 models × 8 ontology representations × 3 prompts × 4 temperatures for SPARQL, plus 8 models × 2 schema variants × 4 temperatures for SQL), the best SPARQL configurations reach 100% on the 21-question set with the default full Turtle ontology at temperature 0.0, achieved by both the full-precision Qwen3.6-27B dense model and its Q8-quantized variant, while the FP8 variant reaches 95% and smaller or MoE models fall sharply (35B MoE variants at 57%, 14B at 38%, 8B at 24%). Representation dominates: stripping only comments and labels drops accuracy to 81%, compact name-retaining forms reach 62–71% with compact-typed outperforming compact by suggesting type information reduces cross-class confusion, raw triples fall to 48%, and anonymised abstract forms collapse to 19% and 5%, confirming that the LLM uses name semantics rather than graph structure alone. Temperature and system prompt have modest effects by comparison — all three prompts reach 100% with the 27B dense model at temperature 0.0, and higher temperatures degrade gracefully to 90–95% — and the simplest baseline prompt matches elaborate guardrail and procedural prompts, suggesting minimal guidance suffices with a well-designed ontology.

The backend gap is large and structural. Best auto-generated SQL reaches only 12/21 (57%) with comments versus 9/21 (43%) without, so column comments add three cases for the best model — proportionally larger than the 19-point SPARQL annotation effect — yet SPARQL still leads by 43 points on identical questions. Per-question results show SPARQL correct on all 21 while SQL fails on dataset introspection, sorting, demographics joins, time-of-day filters, aggregations with hours and counts, and ontology introspection. The authors attribute this to OWL features lost in mechanical DDL translation: annotations critical to both backends, explicit class-level domain/range grouping flattened into column lists, and `owl:inverseOf` allowing bidirectional traversal while SQL forces the LLM to know which table owns the foreign key and join from the correct side. The EAV alternative reaches only 11/21 (52%) with comments and 2/21 (10%) without, partly because relationship attributes expose prefixed internal identifiers that SPARQL's variable patterns and wide-table clean primary keys avoid.

For deployment, the results are encouraging for privacy-constrained institutions. The Q8 model on a vintage-2020 4× Quadro RTX 5000 system (64GB total VRAM) matches full precision at 100% SPARQL and achieves the highest SQL accuracy, 1.8× slower but equally accurate, demonstrating no need for recent-generation GPUs, with Apple Silicon workstations noted as a plausible always-on path. Counterintuitive lessons are that dense 27B models beat larger 35B MoE variants at a given compute budget for precise schema adherence, Q8 quantization preserves accuracy fully while FP8 drops slightly, and the full 80KB (~18K-token) ontology fits comfortably in 32K–64K context windows so compactness sacrifices accuracy for no practical reason at this scale.

## Suggestions & Future Directions

The paper is explicit about limits that bound generalisation. The evaluation covers a single MRI metadata domain, 21 co-evolved competency questions where test-set performance may overstate novel-query accuracy, Qwen3-family models only with no cloud frontier comparison for privacy reasons, Jena Fuseki in Docker for metadata volume, context-window bounds on ontology complexity, and SQL baselines auto-generated rather than hand-designed by a database expert — so the SPARQL advantage is specific to that setting and its magnitude against expert schemas is, in the authors' words, unmeasured. A hand-designed relational schema with denormalised views, natural keys, and documented join paths would likely narrow the gap, and the ordering under terse linearizations has previously favoured SQL, so the finding is that representation richness determines the winner rather than any inherent superiority of SPARQL.

Future work centres on cross-domain validation of the domain-agnostic claims with openness to collaboration, including reuse of the DICOM- and BIDS-grounded ontology at other MRI sites with site-specific ETL adaptation, alongside expansion of the competency set toward more complex patterns, multi-turn conversational refinement where the LLM revises queries from user feedback, and evaluation of non-Qwen and cloud-hosted model families where privacy permits. The practical suggestion for new domain metadata projects is to invest in favoured ontology design and the co-evolution loop with the test driver from the start, since readable names and annotations are cheap to define yet deliver the largest accuracy gains, while keeping the SPARQL server lightweight by materialising implied relationships at ETL time rather than reasoning at query time.

## Authors & Institutions

The paper is authored by Blake G. Fitch and Cato Elia Kurtz, both of the Max Planck Institute for Biological Cybernetics in Tübingen, Germany. The system was demonstrated and deployed at a neuroimaging research facility for researchers with varying query expertise, with the authors noting intent to open source the framework and disclosing generative-AI assistance with manuscript editing, LaTeX formatting, and coding, particularly the web server.
