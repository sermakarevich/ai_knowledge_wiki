# Ontology Richness and Design Principles
**In one sentence:** Schema and ontology richness — not the query language itself — determines which backend an LLM can query more reliably, so the authors design finite-size OWL ontologies for LLM consumption with six expressive-naming principles and compare SPARQL and SQL backends derived from the same ontology, data, and models.
## Key points
- Central claim: schema and ontology richness, not the query language itself, determines which backend an LLM can query more reliably.
- Rasheed and Aguado [18] test reduced/condensed ontology prompt formats but take the KG ontology as given to fit it into the prompt, rather than designing the ontology for LLM consumption from the start.
- The work targets finite-size domain-specific ontologies that fit in the LLM context window, and measurements show departing from expressive naming of ontological elements hurts accuracy.
- No prior work addresses the end-to-end reusable process — capture domain vocabulary in a formal ontology, build a KG from domain metadata via ETL, and enable LLM-driven NL querying — while prior work treats the ontology/schema as given and focuses on query generation.
- Controlled comparison: unlike Sequeda et al. [21], who compare SQL vs SPARQL across different schemas and datasets, the authors auto-generate a relational schema from the same authoritative ontology and evaluate both backends on the same competency questions with the same readable naming, data, and LLM models.
- Contribution has two parts: a development process — (1) capture vocabulary in OWL, (2) build a KG via ETL, (3) iterate ontology, competency questions, and prompt rider together until accuracy is acceptable — and a domain-agnostic reusable framework (NLKGQ query server, web application, combinatorial test driver) that also supports production deployment.
- ETL/KG facts: Python pipeline with rdflib [19] maps DICOM headers, NIfTI sidecars [7, 11], Siemens TWIX raw headers, experiment registry, and participant management system [13] to MRO terms, producing ~10 million triples from a 180TB MRI archive loaded into Apache Jena Fuseki [2] for SPARQL 1.1 [27] querying.
- NLKGQ server builds a system prompt of (1) generic SPARQL instructions, (2) the complete domain ontology in OWL Turtle, and (3) a small domain-specific rider, then applies harness fixes (strip `<think>` blocks, extract SPARQL from markdown, fix PREFIX declarations from ontology ground truth, optional error-feedback retry that mainly helps smaller models with syntax errors).

## Six OWL design principles
The first step is formalizing entities, properties, relationships, and meanings in an OWL ontology [15, 26] following six principles "that cost nothing in formal expressiveness but measurably improve LLM accuracy": (1) Full English words: `hasAcquisitionTime` rather than `acqT` or `AT`; (2) Consistent naming pattern `has<Property>` (e.g., `hasSubjectId`, `hasRepetitionTime`); (3) Descriptive relationships such as `isSubjectOfExperiment` that clearly indicate direction; (4) Explicit domain and range specifying which classes a property connects; (5) Natural language annotations (`rdfs:comment`, `rdfs:label`, `skos:altLabel`) for context, readable names, and synonyms; (6) No opaque codes — meaningful URIs throughout, no arbitrary or auto-generated identifiers. The chunk stresses: "These are not cosmetic choices. They are engineering decisions made during ontology development," costing little since "the ontology must be designed regardless, and readable names are no harder to define than opaque ones," and aligning with FAIR guidelines [29], particularly Reusable.
**Covers:** Section 3.1 (Capturing Domain Vocabulary)
## MRO example vs opaque identifiers
Concrete MRO example:
```turtle
mro:hasHandedness a owl:DatatypeProperty ;
    rdfs:label "Handedness"@en ;
    rdfs:comment "Subject handedness: Right, Left, Ambidextrous, or Unknown. (MRO)"@en ;
    rdfs:domain mro:Subject ;
    rdfs:range xsd:string .
```
"The property name, label, comment, domain, and range together allow the LLM to use this property correctly without any prior exposure to our ontology. The comment tells the LLM what values to expect, enabling it to generate correct FILTER clauses." Contrast: "Wikidata's wdt:P552 (handedness): the identifier P552 carries no semantic information, so the mapping must be learned through fine-tuning, few-shot examples, or graph exploration." Frontier LLMs can assist domain experts in formalizing vocabulary into OWL, lowering the barrier for practitioners without semantic web expertise. ## ETL and knowledge graph construction
With the ontology defined, a domain-specific ETL pipeline collects metadata and populates a KG; the pattern is the same for each new domain — identify metadata sources, write extraction code, map fields to ontology terms, generate RDF. The pipeline can anonymize sensitive fields and compute aggregates (e.g., experiment duration from individual acquisition timestamps). "Rather than relying on an OWL reasoner at query time, the ETL pipeline materializes all implied relationships as concrete RDF triples (e.g., generating both directions of inverse properties and explicit class memberships) during KG construction; this is sufficient for the OWL constructs we use." The ontology guides what to extract and how to name it. The KG is loaded into a SPARQL server (Apache Jena Fuseki [2]), queryable with SPARQL 1.1 [27] via web interface or HTTP API, keeping "the SPARQL server lightweight and query latency predictable."
**Covers:** Section 3.2 (ETL and Knowledge Graph Construction)
## NLKGQ query server and web application
The NLKGQ server constructs a system prompt with "(1) generic SPARQL generation instructions (output format, error handling, query patterns to prefer or avoid), (2) the complete domain ontology in OWL Turtle format, and (3) a small domain-specific rider with conventions particular to the knowledge graph (e.g., preferred identifier patterns, directives addressing recurring LLM mistakes)," appending the NL question as the user message for SPARQL generation. Harness logic strips chain-of-thought `<think>` blocks, extracts SPARQL from markdown, fixes PREFIX declarations using the ontology as ground truth, and optionally retries failed queries with the error; "Retrying failed queries is technically not zero-shot; however, it primarily helps smaller models recover from syntax errors, while the best-performing models rarely trigger it." The web app shows generated SPARQL for transparency, with prefix compression to readable prefixed names (toggle for full URIs), CSV download, an LLM-powered "Explain" button, Python script export, interactive ontology graph visualization, and "Save Test Case" packaging for the evaluation framework; "Displaying the generated query builds user trust and helps researchers learn which phrasings produce useful results." Deployed at a neuroimaging research facility for researchers with varying query expertise; Figure 2 shows the web interface processing an NL query.
