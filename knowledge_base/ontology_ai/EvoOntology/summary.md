# EvoOntology: A Self-Evolving Ontology Layer for Data Agents

**Paper:** [EvoOntology: A Self-Evolving Ontology Layer for Data Agents (Chong et al., 2026)](https://arxiv.org/pdf/2609.15779)

## Human Readable TL;DR

Imagine a tourist dropped into a giant foreign supermarket where every aisle uses different labels, some in other languages, and the only help is a clerk who can fetch one item at a time if asked precisely. Asking blindly aisle by aisle wastes hours, while carrying a thick printed guidebook is heavy and goes out of date the moment shelves move. EvoOntology is like a smart local guide standing between the tourist and the store: it keeps a living map of what things are called, where they actually sit on the shelves, what rules apply (such as discounts that only work on certain days), and photos proving each claim, and it rewrites its own map whenever it watches tourists get lost. The tourist only carries a pocket index card and asks the guide for details on demand, so trips get shorter and cheaper even though the guide keeps learning in the background.

## TL;DR

EvoOntology proposes a self-evolving ontology layer that sits between heterogeneous data sources (tables, CSV, docs, databases, charts, logs) and ReAct data agents to close the agent–data gap. The layer is a triple Lt = (St, Γt, Rt): a typed Content graph St with Terms (domain concepts), Mappings (grounding to exact fields and join paths), Constraints (business rules), and Evidence (data observations) linked by Semantic Relations and Structural References; a Schema layer Γt defining the object model; and a Tool layer Rt exposing the ontology as an MCP server via `fbrowse(q, k, n)` for top-n semantic matches and `fresolve(I, c)` for full records plus linked objects, with only a compact session manifest in the prompt. A builder agent constructs the initial state L0 = (S0, Γ0, R0) without gold answers through workload-guided probing (C = propose(W), probe(c, D), verify to C+, construct S0), and an evolution agent then refines it from historical trajectories via Diagnose (extract signatures Σt = analyze(Tt, Lt)) → attribute (α: Σt → {Content, Tool, Schema} with stated hypothesis) → single-level patch (L′t = patch(Lt, σ, α(σ))) → backbone-conditional paired validation (Lt+1 = L′t iff φ(L′t, V; m) − φ(Lt, V; m) ≥ τ, reciprocal two-fold split-and-swap score), logging rejections. Across six backbones on DDR-Bench 10-K, InsightBench, and BIRD under Oracle Knowledge, EvoOntology consistently beats ReAct baselines and static semantic-layer prompts while cutting total tokens per task by ~20% through shorter trajectories.

## Problem & Motivation

Data agents aim to fulfill natural-language instructions over heterogeneous data, yet the data resides outside the agent in relational databases, semi-structured filings, and unstructured documents while the agent sees it only through generic tools such as SQL interfaces and file readers. Because neither structure nor content is known a priori, the agent must blindly explore by repeatedly issuing probing queries, guessing where concepts live, and inspecting irrelevant content, and grounding discovered in one trajectory is typically discarded rather than retained. Raw-querying methods (text-to-SQL, table-QA, code-executing analysts and their pipeline variants with decomposition, retrieval, and verification) work for small simple sources but scale poorly to wide heterogeneous workloads spanning different naming conventions, schemas, and granularities, improving standardized benchmarks while leaving the representation gap untouched. Semantic-layer approaches ranging from OWL ontologies and dbt metric layers to LLM-oriented semantic representations fail differently: full-context injection scales poorly to large sources under context limits, the layers are usually predefined and manually maintained at high cost, detached from downstream trajectories showing how agents actually use them, and coarse updates give little basis for identifying which entry affected a decision, so they neither scale nor adapt to new sources, tasks, and agent behaviors. Bridging the gap therefore requires an intermediate ontology layer that explicitly represents domain concepts, grounds them in the underlying data, and lets agents interact at the semantic rather than physical level — interactive, queryable at runtime, and continuously adapting to both data and agent behavior, which is exactly what EvoOntology sets out to build.

## Main Original Ideas

1. **Typed Content graph with four node families and two edge families** — Terms represent domain concepts, Mappings ground them to exact fields and linking paths, Constraints govern valid use (e.g. Profit = Revenue − Cost, Revenue excludes cancelled orders, Time grain = Month), and Evidence supports semantic claims with probe observations, connected by Semantic Relations (association, hierarchy, composition, equivalence, derivation) between Terms and Structural References linking Terms to Mappings and attaching Constraints and Evidence to what they govern or support, as illustrated through a financial-analysis example with Cost, Revenue, Time, and Channel terms over fact_cost.

2. **Schema layer separating representational capacity from instantiated content** — The Schema layer Γt defines the fields of the four node families, admissible Semantic Relation types, and permitted reference patterns, so schema updates extend what the ontology can express without rewriting existing content, enabling localized evolution such as adding a Legality Status Code term without touching Card and Legality objects or tools.

3. **MCP Tool layer with on-demand retrieval instead of prompt injection** — The Tool layer Rt exposes only `fbrowse(q, k, n)` (Query → Ranked Terms) and `fresolve(I, c)` (Term IDs → Mappings, Relations, Constraints plus linked Evidence), with a compact session manifest as the sole ontology content in the prompt and detailed records fetched per step, which avoids the static-fragment competition and unprunable context that makes Baseline + SL drop 15.0 Trajectory-Wise points on Claude-Sonnet-5.

4. **Evidence-grounded builder initialization without gold answers** — From training workload W and sources D the builder proposes candidates C = propose(W) from recurrent entities, metrics, operations, and analytical conditions, issues probe(c, D) per candidate to find fields and linking paths and inspect types, values, and semantic consistency, and commits only verified candidates C+ = {c ∈ C | verify(probe(c, D)) = 1} via S0 = construct(C+, D; Γ0) to form L0 = (S0, Γ0, R0), retaining supporting records as Evidence so every entry is anchored in a probe query rather than natural-language description alone.

5. **Trajectory-grounded four-step self-evolution loop with single-level patches** — Historical trajectories serve as behavioral evidence where successes reveal effective structures and failures expose missing, misleading, or poorly exposed components; the evolution agent extracts recurrent signatures Σt = analyze(Tt, Lt), attributes each via α to Content (add/remove/revise objects), Tool (modify/add/remove tools or manifest exposure), or Schema (revise the object model) with an expected behavioral effect, and applies one-level-only patches L′t = patch(Lt, σ, α(σ)), allowing multiple dependent Content objects under the same hypothesis, which isolates the attributed hypothesis per round.

6. **Backbone-conditional paired validation gate with reciprocal evaluation** — For backbone m, candidate and parent are scored on the same validation set V under identical decoding and interaction budgets, retaining the candidate only when φ(L′t, V; m) − φ(Lt, V; m) ≥ τ, using reciprocal Score = (ScoreA→B + ScoreB→A) / 2 under two-fold split-and-swap with a shared adaptation fold and a held-out fold accessed only after freezing, while rejected signatures, interventions, and outcomes are logged to avoid repeats and limit regressions, and each backbone evolves independently from the same L0 so accepted updates reflect backbone-specific patterns.

## Key Findings

On DDR-Bench 10-K, EvoOntology improves Trajectory-Wise accuracy on all six backbones with an average gain of +17.8 points, ranging from +4.8 on Qwen3.5-Flash (14.3 → 19.1) to +26.7 on GPT-5.5 (64.2 → 90.9), including +25.0 on GPT-5.6-sol, +8.8 on Claude-Sonnet-5, +19.3 on Claude-Opus-4.8, and +22.0 on DeepSeek-V4-Flash, while static Baseline + SL is flat or negative (down to −15.0 on Claude-Sonnet-5) because a static fragment competes with other instructions and cannot be pruned per turn. Episodic memory helps less: ReAct + Memory lifts Trajectory-Wise from 69.5 to 75.8 (+6.3) but remains 13.7 points below EvoOntology at 89.5 (+20.0), since memory only replays what was done rather than exposing typed composable structure. On InsightBench overall performance improves on every backbone with mean gain 1.9 points and largest gain +6.1 on DeepSeek-V4-Flash (39.8 → 45.9), smaller than DDR-Bench because short reference-style grading saturates once the answer aligns, while Baseline + SL recovers most Insight gain yet drops −3.3 Summary on Claude-Sonnet-5 where EvoOntology improves both by exposing content through queryable tools. On BIRD under Oracle Knowledge EvoOntology improves both EX and VES for every backbone with average gains of 7.4 and 8.6 points (e.g. Claude-Opus-4.8 78.3/+10.8 EX and 80.5/+10.9 VES), whereas Baseline + SL shows EX drops up to −5.6 on GPT-5.5 while VES rises, indicating static semantics improve SQL well-formedness but distract from correctness.

The builder versus evolution split is cleanly separated: on DDR-Bench mean Trajectory-Wise rises 12.3 points from Baseline to Initial plus a further 7.7 points from Initial to Evolved, and on BIRD mean EX improves 5.1 points with the initial ontology plus another 3.7 after evolution, confirming the builder gives an effective starting point while self-evolution is essential for the full gain. Figure 4 shows all backbones improve monotonically across accepted rounds (GPT-5.6-sol reaching 93.5 Traj-Wise after five rounds, Claude-Opus-4.8 reaching 92.3 after four) with flattening in the last two rounds as recurrent cross-filing gaps get covered, validating converging refinement rather than a single fortunate patch. Ablations identify the gate and attribution as load-bearing: removing the gate drops −11.2 Traj-Wise as unfiltered regressions compound, removing attribution drops −6.3 as content edits are made for manifest problems and vice versa, removing diagnose drops −4.8, and replacing the typed patch with free-form rewrite drops −1.7. Structure masking shows Mappings (−13.4) and Evidence (−8.7) as the two load-bearing families versus Constraints (−3.5) and Relations (−2.1), consistent with Mappings being the sole grounding to columns and join paths and Evidence enabling verification against value distributions. Level ablations show Tool-only +13.2, Content-only +8.7, and Schema-only +3.6 versus +20.0 for the full three-level loop, proving complementarity, with attribution shares of 57% Tool (6 rounds), 34% Content (11 rounds), and 9% Schema (3 rounds) pointing to manifest reshaping as the dominant lever.

Evolution is backbone-specific and efficient: pairwise Jaccard overlap of accepted Term-identifier sets never exceeds 0.62 (Claude–Claude 0.55, GPT–GPT 0.61, with Opus retaining more detailed manifest variants and GPT-5.5 adding SQL fragment libraries under Evidence), and every cross-backbone transfer drops at least 6.6 Traj-Wise points with average column drops from −6.6 to −10.9, though identifier overlap alone cannot prove semantic divergence. Content growth concentrates early (Terms 61 → 80 after five rounds under GPT-5.6-sol, per-round growth below 5% after round three, flattening with performance), and although the manifest raises input tokens per turn from 3.2K to 4.1K at fixed 0.4K output, trajectory length falls from 14.6 to 11.2 (Initial) to 8.4 turns (Evolved), cutting total cost from 52.6K to 50.4K to 42.0K tokens per task — roughly 20% below baseline while Traj-Wise rises 69.5 → 89.5. A card-legality case study makes localization concrete: the initial ontology knows Card and Legality but not how to interpret legalities.status relative to legalities.format, so the evolution agent attributes a Content gap and adds a Legality Status Code term grounded to legalities.status with mapping, value-distribution evidence, and the constraint requiring legalities.status = 'Banned' with legalities.format = <target format>, after which browse surfaces the new term and resolve returns its grounding without any Tool or Schema change.

## Suggestions & Future Directions

The paper's own results point naturally toward handling semantic equivalence beyond identifier matching, since different backbones may encode similar concepts under different Term identifiers and Jaccard overlap therefore understates convergence while cross-backbone transfer still penalizes reuse. A promising direction is learning a shared or distillable core (especially Mappings and Evidence, the two load-bearing families) that transfers across backbones while keeping backbone-specific Tool exposure, given that Tool-level manifest reshaping drives 57% of the gain yet every store performs best on its own backbone. Practical deployment would also benefit from extending the paired gate with cost-aware or online criteria, because the current backbone-conditional validation is strong against regressions but requires repeated full evaluations, and from testing on live, drifting sources where the early-round growth pattern (most expansion in the first three rounds) may need continual lightweight Diagnose cycles rather than a frozen final ontology. Finally, the card-legality and currency-constraint examples suggest generalizing probe-based verification to richer constraint types (temporal grains, format-dependent rules, unit conversions such as FX Convert) and to noisier unstructured evidence from docs, charts, and logs, where value-distribution checks alone may be insufficient.
