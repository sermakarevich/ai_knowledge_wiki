A.4
Details of Baseline
In this section, we provide detailed descriptions of all baseline
methods evaluated in our experiments, including their underly-
ing assumptions, graph interaction mechanisms, and reasoning
paradigms. All baselines are implemented following their origi-
nal papers and, unless otherwise specified, are evaluated under the
same evaluation protocols as GraphScout to ensure fair comparison.
BaseLLM. BaseLLM serves as a non-graph baseline to assess the
extent to which LLMs can answer domain-specific questions relying
solely on their internal parametric knowledge. For this baseline,
the model is prompted directly with the question, without access
to any external graph or retrieved context.
TextRAG. TextRAG [14] treats the knowledge graph as a textual
corpus by linearizing node attributes and edge information into
plain text. A dense retriever is employed to fetch the most relevant
text chunks based on semantic similarity with the input question,
and the retrieved text is appended to the prompt for answer gener-
ation.
GraphRAG. GraphRAG [54] extends TextRAG by incorporating
structural information during retrieval. Instead of retrieving iso-
lated text chunks, GraphRAG retrieves subgraphs centered around
core entities identified from the question, typically using 2-hop
neighborhood expansion. The retrieved subgraphs are then lin-
earized into text sequences and provided as context to the LLM.
Cypher. The Cypher baseline directly queries the underlying
knowledge graph using Cypher. For each question, the LLM is
prompted to generate a Cypher query, which is executed against the
graph to retrieve relevant nodes or attributes. The query results are
then returned to the LLM for answer synthesis. To adapt this method
to the tasks considered in this paper, we additionally incorporate a
node retrieval module to identify candidate nodes prior to Cypher
query execution.
GraphCoT. GraphCoT [24] is a reasoning-based GraphRAG
method that enables multi-step interaction between the LLM and
the graph through a predefined set of graph traversal tools. The
model incrementally explores the graph, retrieves intermediate ev-
idence, and updates its reasoning context in a chain-of-thought
manner. By decomposing complex queries into multiple reasoning
steps, GraphCoT mitigates information loss caused by long lin-
earized contexts and serves as a strong iterative reasoning baseline.

B.1
Diversity Analysis of Graph Quizzer
To analyze the diversity of the data generated by Graph Quizzer, we
perform an additional automatic annotation analysis on the gener-
ated questions. Specifically, during this analysis, we use DeepSeek-
Chat as the judging LLM, while deliberately withholding the per-
question task configurations assigned during generation, including
the specific combinations of difficulty levels, question structural
patterns, and answer types specified for each individual question.
Instead, we only provide the definitions of these categories together
with each generated question, allowing the model to independently
determine the task category combination that each question actu-
ally corresponds to.
This de-conditioned annotation strategy is designed to analyze
the generated data from the perspective of the questions’ intrinsic
semantics and structures. On the one hand, during generation,
Graph Quizzer may not always strictly adhere to the predefined task
instructions; on the other hand, this post hoc annotation process
enables us to explicitly verify the actual task attributes reflected by
each question at the semantic level.
As shown in the figure 7, the distributions of question difficulty
and answer type are relatively balanced, indicating good coverage
of the generated data along these dimensions. In contrast, the distri-
bution of question structural patterns is more uneven, with hybrid
questions accounting for a larger proportion. We hypothesize that
this phenomenon primarily arises because, when generating ques-
tions of medium and higher difficulty, simple and single-structure
question patterns are often insufficient to meet the required dif-
ficulty level, thereby encouraging the model to generate hybrid
questions that incorporate multiple structural elements.

B.2.3
Why GraphCoT fails but GraphScout succeeds. The
failure of GraphCoT mainly stems from a tool-to-schema mismatch
and the lack of a robust recovery strategy. Specifically, Graph-
CoT assumes that “Aphasia, Primary Progressive” is a Disease
node and repeatedly queries non-existent neighbor types (e.g.,
Disease-downregulates-Gene, Disease-associates-Gene). Once
the tool reports that the neighbor type does not exist, GraphCoT
keeps retrying with the same (incorrect) schema assumption, and
eventually concludes that the graph contains no relevant informa-
tion, leading to an incorrect termination.
In contrast, GraphScout exhibits a two-level advantage that com-
bines reasoning and tool usage. On the reasoning level, it ex-
plicitly diagnoses the entity-type mismatch (the retrieved node is
a Symptom, not a Disease) and formulates a corrective plan: first
resolve the underlying disease(s) that present the symptom, then
query downregulated genes, and finally aggregate cellular compo-
nents. On the tool level, GraphScout leverages executable Cypher
queries to (i) validate available relation types from the retrieved
node, (ii) traverse the graph to candidate diseases, (iii) verify which
candidate disease actually contains DISEASE_DOWNREGULATES_GENE
edges, and (iv) perform aggregation (count(DISTINCT g)) over
GENE_PARTICIPATES_CELLULAR_COMPONENT. This synergy between
schema-aware reasoning and executable graph operations enables
GraphScout to both recover from initial ambiguity and produce
a verifiable answer, correctly identifying neuron projection as the
most frequent cellular component among downregulated genes.
B.3
Prompt Design for Graph Quizzer
Graph Quizzer relies on a carefully structured prompting scheme to
guide a strong language model to perform task-oriented yet flexible
exploration over an open and programmable graph interface. In-
stead of using rigid question templates, the prompts specify abstract
task objectives, including question pattern, answer type, and diffi-
culty level, while leaving the concrete exploration strategy to the
LLM. This design encourages diverse graph exploration behaviors
while ensuring that the collected evidence can be reliably grounded
in the underlying knowledge graph.
Base System Prompt for Graph Quizzer
You are a graph-analysis agent operating on a heteroge-
neous knowledge graph stored in Neo4j.
Your objective is to perform multi-round, task-oriented ex-
ploration to collect graph evidence that supports a specific
question pattern, answer type, and difficulty constraint.
You interact with the graph through a programmable
Python sandbox with access to a read-only Cypher in-
terface. Your exploration should be:
• Task-oriented: focus on evidence relevant to the
current task specification.
• Incremental: gather information over multiple
rounds rather than exhaustively traversing the
graph.
• Verifiable: ensure that all collected evidence can
be reproduced via explicit Cypher queries.
Once sufficient evidence has been collected, you should
stop exploration and construct exactly one graph reasoning
question together with its answer.
B.3.1
Difficulty-Specific Exploration Prompts. controls the
expected depth and structural complexity of exploration, ranging
from shallow, local queries to multi-hop, compositional reasoning
over heterogeneous graph structures. It determines the allowed
traversal depth, the number of intermediate entities, and whether
hybrid reasoning patterns are permitted.

Difficulty Level: SIMPLE
Design Goal. Encourage shallow, interpretable graph ex-
ploration that can be resolved with minimal reasoning
steps.
Exploration Constraints.
• Restrict traversal depth to 1–2 hops.
• Prefer a single dominant relationship type.
• Avoid compositional or hybrid reasoning patterns.
Evidence Scope. Collected evidence should support direct
fact retrieval or simple aggregation, and be sufficient to
answer the question without multi-step inference.
Typical Use Cases. Single-hop entity lookup, attribute
retrieval, or basic neighborhood queries.
Difficulty Level: MEDIUM
Design Goal. Promote controlled multi-step reasoning
while maintaining clear semantic structure.
Exploration Constraints.
• Explore 2–4 hop paths with explicit intermediate
nodes.
• Involve at least two distinct relationship types or
node types.
• Allow limited use of filtering, ranking, or property
constraints.
Evidence Scope. The collected evidence should form a
clear reasoning chain that can be verbalized into a natural-
language question.
Typical Use Cases. Multi-hop entity discovery, con-
strained aggregation, or relational queries requiring in-
termediate reasoning.
Difficulty Level: HARD
Design Goal. Encourage non-trivial, compositional graph
reasoning that cannot be resolved by local lookup.
Exploration Constraints.
• Allow hybrid or combined question patterns.
• Explore 3–5 hop heterogeneous paths.
• Require traversal through multiple intermediate en-
tities and relation types.
• Explicitly avoid staying within a single entity’s im-
mediate neighborhood.
Evidence Scope. Evidence must support multi-step depen-
dency between reasoning stages, ensuring that the final
answer depends on earlier intermediate results.
Typical Use Cases. Recommendation-style reasoning,
cross-entity synthesis, and complex relational verification.
B.3.2
Query Pattern-Specific Exploration Prompts. specifies
the abstract structural form of a graph question using a (possibly
incomplete) triple representation. Rather than fixing concrete tem-
plates, the pattern defines which components are given and which
must be discovered through exploration, thereby guiding the direc-
tion and scope of evidence collection.
Pattern: ⟨ℎ, _, _⟩(Entity-Centric Exploration)
Task Definition. Only the subject entity ℎis given, while
both the predicate and object are unspecified.
Exploration Objective. Collect broad but structured in-
formation about the subject entity, including:
• the node type and key attributes of ℎ,
• dominant outgoing relation types,
• representative neighboring entities and their types,
• simple graph statistics.
Design Constraint. Exploration should remain local and
avoid aggregating excessive or irrelevant neighborhoods.
Pattern: ⟨ℎ,𝑟, ∗⟩(Object-Finding)
Task Definition. The subject entity ℎand predicate 𝑟are
specified, while the object is unknown.
Exploration Objective. Identify target entities that satisfy
the given relation(s), possibly involving:
• single-hop or multi-hop predicate chains,
• filtering or aggregation constraints,
• explicit intermediate nodes as supporting evidence.
Design Constraint. The exploration must yield a repro-
ducible query result and avoid ambiguous answer sets.
Pattern: ⟨ℎ, ∗,𝑡⟩(Relationship Discovery)
Task Definition. Both subject ℎand object 𝑡are given,
while the relationship between them is unknown.
Exploration Objective. Discover and explain how ℎand
𝑡are connected in the graph by:
• enumerating valid relation paths,
• identifying intermediate entities,
• selecting concise and interpretable paths as evi-
dence.
Design Constraint. Preference is given to short or seman-
tically meaningful paths rather than exhaustive enumera-
tion.
Pattern: ⟨ℎ,𝑟,𝑡⟩(Verification)
Task Definition. Subject, predicate, and object are all
specified.
Exploration Objective. Verify whether the specified rela-
tionship (or constrained relation chain) holds in the graph.
Evidence Requirement. The final answer must be de-
rived from an explicit verification query (e.g., existence
check or count-based test) and supported by at least one
concrete witness when the result is positive.

Hybrid Pattern (Compositional Graph Reasoning)
Task Definition. Combine exactly two different question
patterns into a single coherent question, where the second
reasoning step depends on the result of the first.
Exploration Objective. Ensure that:
• both reasoning steps are necessary to answer the
question,
• intermediate results from the first step are explicitly
reused,
• the final question cannot be answered by a single
local lookup.
B.3.3
Answer-Type-Specific Prompt Constraints. imposes ex-
plicit constraints on the form and computability of the final answer,
including entity, boolean, numeric, and set-valued outputs. Each
answer type is associated with verifiable evidence requirements
(e.g., uniqueness, existence, aggregation), ensuring that generated
questions admit deterministic, graph-grounded supervision.
Answer Type: ENTITY
Objective. Produce exactly one uniquely identifiable real-
world entity as the answer.
Hard Constraints.
• The candidate answer set must be reduced to exactly
one entity.
• The model must verify uniqueness using an explicit
Cypher aggregation.
• Internal node identifiers are forbidden; only human-
readable names are allowed.
Answer Type: BOOLEAN
Objective. Verify whether a specified relationship or con-
straint holds in the graph.
Hard Constraints.
• The boolean value must be derived from an explicit
verification query (e.g., existence check or count-
based test).
• TRUE is returned iff the computed count is strictly
greater than zero.
• At least one concrete witness must be identified
when the result is TRUE.
Answer Type: NUMBER
Objective. Return a single numeric value computed from
the graph.
Hard Constraints.
• The number must be produced by a Cypher aggre-
gation query returning exactly one row.
• LIMIT clauses are forbidden in final counting
queries.
Answer Type: SET
Objective. Return a small, interpretable set of entities.
Hard Constraints.
• The total set size must be computed explicitly.
• If the set size exceeds a predefined threshold (e.g.,
10), additional constraints must be introduced.
• The final answer must be a comma-separated list of
entity names.
B.4
Prompt Design for Graph Solver
B.4.1
Tool Interface Formatting. We adopt the Qwen3 chat
template, which automatically injects tool descriptions into the
model prompt at runtime. When a non-empty tool set is provided,
the template constructs a system-level instruction that appends a
dedicated Tools block containing the JSON schemas of all avail-
able tools. This block is enclosed by < 𝑡𝑜𝑜𝑙𝑠> . . . < /𝑡𝑜𝑜𝑙𝑠>
tags and precedes the dialogue history. The same system message
also specifies a strict tool invocation protocol, requiring the model
to emit function calls as structured JSON objects wrapped by <
𝑡𝑜𝑜𝑙_𝑐𝑎𝑙𝑙> . . . < /𝑡𝑜𝑜𝑙_𝑐𝑎𝑙𝑙>, and received by < 𝑡𝑜𝑜𝑙_𝑟𝑒𝑠𝑝𝑜𝑛𝑠𝑒>
. . . < /𝑡𝑜𝑜𝑙_𝑟𝑒𝑠𝑝𝑜𝑛𝑠𝑒>. As a result, both tool semantics and call-
ing conventions are explicitly grounded in the prompt, enabling
deterministic parsing and execution of tool calls during inference.

Formatting of Graph Descriptions. To ensure clarity and
reproducibility, we explicitly standardize the formatting of graph
descriptions and code examples in the Graph Solver.
