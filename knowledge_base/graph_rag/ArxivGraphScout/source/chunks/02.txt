Preliminary
Formally, a knowledge graph is denoted by K ⊆E × R × E, where
E is the set of entities and R is the set of relations. A fact in a
knowledge graph is commonly represented as a triple (ℎ,𝑟,𝑡) for
convenience, where ℎ,𝑡∈E. The graph-based question answering
task under a retrieval-augmented setting is defined as
𝑓: Q × K →Y,
(1)
where Q is the set of graph reasoning questions in natural lan-
guage [24] and Y is the set of answers. The graph reasoning process
of an LLM can be modeled as a policy 𝜋(𝑎𝑡| 𝑞,𝑐𝑡), which selects
the next action 𝑎𝑡given the input question 𝑞and the historical
reasoning trajectory 𝑐𝑡. Here, 𝜋(·) is the policy distribution of an
LLM, 𝑞∈Q is a question, 𝑎𝑡∈A is an action selection at step 𝑡,
𝑐𝑡= (𝑜1,𝑎1, · · · ,𝑜𝑡−1,𝑎𝑡−1,𝑜𝑡) is the contextual observation-action
sequence. When the process reaches an answer, the reasoning tra-
jectory can be denoted as 𝜏= (𝑜1,𝑎1, · · · ,𝑎𝑇,𝑜𝑇), where 𝑇is the
number of reasoning steps and 𝑜1 = 𝑞. Existing prompting-based
methods [13, 27, 33, 34] rely on external guidance and primarily
focus on enriching the action space A with more hand-crafted tools
and auxiliary prompts. However, a predefined set of tools A and
a fixed policy 𝜋(·) significantly limit the exploration potential of
LLMs. Therefore, our goal is to unlock the intrinsic exploration ca-
pability of LLMs by incorporating flexible exploration tools Agraph
and learning an optimized policy 𝜋𝜃(·) for graph reasoning.
3.2
Agentic Graph Exploration Tools
As the adage states, “If a craftsman wants to do his work well, he
must first sharpen his tools”. Existing GraphRAG methods typically
rely on a predefined set of tools, such as retrieving neighboring
nodes, checking relations, or extracting node attributes. While sim-
ple, these approaches struggle with neighborhood explosion and
multi-hop collaborative patterns. In contrast, GraphScout exposes
an agentic graph exploration interface Agraph, which integrates two
complementary tools: a Code Interpreter for high-order pattern
analysis and a Node Retriever for global graph retrieval. This
agentic interface is invoked proactively by the LLM, formatted as
<tool_call> {
"name":"tool_name",
"arguments":{"tool_arguments"}}
</tool_call>.
3.2.1
Code Interpreter. The Code Interpreter provides a safe
Python execution environment with access to a Cypher-based graph
query interface, allowing the model to write executable code for
precise and compositional graph queries. Through this interface, the
model can flexibly control query logic, process intermediate results,
and adapt its exploration strategy based on the evolving interaction
context, rather than following predefined traversal templates. In
our implementation, large-scale knowledge graphs are stored in
a Neo4j database. During a preprocessing stage, each dataset is
imported into Neo4j and equipped with appropriate schema-level
and property-level indexes, enabling efficient execution of Cypher
queries.
3.2.2
Node Retriever. The Node Retriever is implemented as
a FAISS-based vector search module that supports fuzzy entity
grounding. Given textual mentions in questions or intermediate hy-
potheses, it retrieves candidate node identifiers based on semantic
similarity, enabling robust mapping from language to graph entities
prior to structured querying.
By combining a programmable Code Interpreter with a light-
weight Node Retriever, GraphScout extends the action space as
A = Agraph ∪L, where L is the intrinsic verbal reasoning actions
of an LLM. Therefore, GraphScout significantly expands the explo-
ration space available to the LLM while keeping the tool interface
minimal. More details are provided in Appendix B.4.1.
3.3
Graph Quizzer
Using these agentic graph exploration tools Agraph, Graph Quizzer
employs a strong LLM as a senior scout to flexibly explore graph
problems Qtrain at varying difficulty levels according to general
task specifications. As shown in the upper panel of Figure 2, Graph
Quizzer explores the higher-order neighborhoods and global graph
semantics by alternating verbal reasoning and tool use until a stop-
ping condition is met. Through this exploration loop, Graph Quizzer
generates high-quality graph question-answering pairs Dtrain =
(Qtrain, Ytrain, Ctrain) for subsequent LLM post-training, effectively
eliminating laborious dataset curation. We explicitly record inter-
mediate node clues Ctrain = {𝑐|𝑐= (𝑒𝑖,𝑒𝑗, · · · ,𝑒𝑘) and 𝑒𝑖∈E} to
mitigate reward sparsity during the ensuing training process.
3.3.1
Task specification. Each quizzer episode begins by sam-
pling an exploration objective that specifies the structural and se-
mantic requirements of the graph question to be generated. Rather
than relying on using fixed templates, objectives are specified at an
abstract level to guide task-oriented exploration while preserving
flexibility. Each objective is characterized by a combination of an-
swer type, query pattern, and difficulty, which together ensure
diversity among generated questions.
Answer type. The answer type defines the expected form of the
final answer and the corresponding supervision signal. We consider
four common types: entity (identifying a graph entity), boolean
(judging whether a given statement is true or false), number (count-
ing or aggregation), and set (a collection of entities). This diversity
encourages the quizzer to produce supervision beyond simple entity
retrieval.
Query pattern. The query pattern specifies the abstract struc-
tural form of a graph query, indicating which components are
given and which must be discovered through exploration. Following
PolyG [34], we adopt standard patterns including ⟨ℎ, _, _⟩, ⟨ℎ,𝑟, ∗⟩,
⟨ℎ, ∗,𝑡⟩, and ⟨ℎ,𝑟,𝑡⟩, as well as hybrid patterns that combine multi-
ple forms to support more compositional reasoning.
Difficulty. The difficulty level controls the required reasoning
depth and is categorized as simple, medium, or hard, corresponding
to single-hop to deeper multi-hop reasoning. Varying difficulty
allows quizzer to generate exploration trajectories with different
lengths and structural complexity.
Together, these three factors define a structured yet flexible
objective space that enables Graph Quizzer to cover diverse graph
reasoning behaviors without relying on rigid, hand-crafted task
templates. Additional details are provided in Appendix B.3.

3.3.2
Exploration initialization. Given a sampled exploration
objective, Graph Quizzer initializes the scout with a compact en-
vironment context 𝑐env and a concrete seed node 𝑒𝑖, providing the
minimal context required for task-oriented exploration.
Graph description. The scout is provided with a concise de-
scription of the target knowledge graph, including core schema-
level information such as node types, edge types, and commonly
used properties. This description also specifies the underlying explo-
ration tools Agraph, grounding the scout’s subsequent interactions
in a concrete execution environment.
Seed node. Each exploration episode is anchored at a seed node
𝑒𝑖∈E sampled from the target graph. To mitigate bias from im-
balanced node-type distributions, we adopt a two-stage sampling
strategy: first uniformly sampling a node type, followed by random
selection of a node instance within that type. This strategy ensuring
balanced coverage across graph structures and reasoning scenarios.
3.3.3
Exploration process. Starting from the initialized seed
node 𝑒𝑖, the scout performs a bounded, multi-step exploration pro-
cess conditioned on the sampled exploration objective. Exploration
proceeds as an iterative explore-assess loop, in which the scout
actively retrieves graph evidence and continuously evaluates its
progress toward satisfying the objective.
At each step, the scout formulates a concrete retrieval action,
such as inspecting neighboring relations, expanding along selected
paths, or aggregating graph statistics, and executes it through the
graph interaction interface. The returned results are summarized
into a local exploration state, which is used to assess whether the
accumulated evidence is sufficient to meet the specified answer
type, query pattern, and difficulty constraints.
This process is explicitly task-oriented: rather than exhaustively
traversing the graph K, the senior scout prioritizes a partial rea-
soning trajectory 𝑐𝑡that is most relevant to the current objective
and terminates exploration early once sufficient supporting infor-
mation has been collected. To prevent unbounded interaction, the
exploration length is capped by a fixed budget of tool calls (we use
𝑇=10), encouraging efficient and focused exploration behaviors.
3.3.4
Question reporting. Once the senior scout determines that
the exploration objective has been satisfied, it transitions from the
question-exploration stage to the question-reporting stage. Using
the collected reasoning trajectory 𝑐𝑇, the senior scout constructs a
natural-language graph question 𝑞together with its corresponding
answer 𝑦, ensuring that 𝑦is directly verifiable on the underlying
graph. In addition to the final question-answer pair (𝑞,𝑦), Graph
Quizzer records a set of evidence clues 𝑐= (𝑒𝑖,𝑒𝑗, · · · ,𝑒𝑘), each ele-
ment being a node identifier explicitly used during question and
answer formation. These clues provide an explicit link between
the generated answer 𝑦and concrete graph entities 𝑒𝑖encountered
during exploration. As a result, each quizzer episode generates
a structured supervision tuple: (question, answer, clue_nodes),
where the question 𝑞is expressed in natural language, the answer 𝑦
is grounded in the graph, and the evidence clues 𝑐anchor supervi-
sion to explicit graph-level facts. This design enables downstream
models to learn not only to produce correct answers, but also to
align their reasoning processes with relevant evidence clues.
3.4
Graph Solver
Graph Solver further trains a small-parameter LLM as a junior scout
to tackle the graph-reasoning questions Qtrain proposed by Graph
Quizzer, using reward signals for answer correctness and alignment
with evidence clues. As shown in the bottom panel of Figure 2, the
junior scout iteratively reasons the possible solution paths via explo-
ration tools Agraph in a multi-turn paradigm until it outputs a final
answer. The reasoning policy can be denoted by 𝜋𝜃(𝜏|𝑞), where
𝜋𝜃(·) is the parameterized LLM and 𝜏is the trajectory involving
verbal reasoning steps and tool actions. This simple yet effective
design empowers LLMs to perform intrinsic exploration over ques-
tions Qtrain and complex graphs K, going beyond the limited tools
and static prompts used in existing GraphRAG methods.
3.4.1
Problem formulation. Graph Solver formulates graph ques-
tion answering as learning a multi-turn decision policy for task-
oriented interaction with a knowledge graph. Given a natural lan-
guage question𝑞, the model must decide how to sequentially invoke
tools Agraph to retrieve evidence, aggregate information, and ulti-
mately produce an answer. Formally, each episode corresponds to a
trajectory 𝜏= (𝑜1,𝑎1,𝑜2,𝑎2, . . . ,𝑜𝑇,𝑎𝑇) of alternating observations
and actions, where the initial observation is the question itself, i.e.,
𝑜1 = 𝑞. Actions {𝑎𝑡}𝑇
𝑡=1 are expressed as tool calls, and observa-
tions {𝑜𝑡}𝑇
𝑡=1 include structured tool responses and the model’s
intermediate verbal reasoning. The objective is not to follow prede-
fined traversal rules, but to acquire a generalizable solver strategy
𝜋𝜃(𝜏| 𝑞) that coordinates entity grounding, graph traversal, and
answer synthesis under a fixed interaction budget.
