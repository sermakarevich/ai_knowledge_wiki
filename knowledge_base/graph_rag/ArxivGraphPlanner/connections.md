# Connections

- [[papers/AgentAsARouter/summary|Agent-as-a-Router]] — same-problem-different-method: also treats LLM routing as a sequential/contextual-bandit decision problem rather than static classification (their C-A-F loop vs. GraphPlanner's MDP), but scopes to coding tasks with a fine-tuned Orchestrator + vector-store memory instead of a graph-structured policy — useful comparison of "memory as a vector store" vs. "memory as a shared-hub heterogeneous graph" for the same routing problem.
- [[papers/ArxivMemGraphRAG/summary|MemGraphRAG]] — shares-technique: both use a persistent graph structure to accumulate and reuse experience across interactions (MemGraphRAG's conflict-resolving Global Memory vs. GraphPlanner's cross-episode `G_history`), though MemGraphRAG applies this to knowledge-graph-based retrieval construction while GraphPlanner applies it to routing decisions — worth reading together on the general pattern of "graph memory that persists across tasks/episodes and gets read back into the current decision."
- [[ai_papers/agent_memory/GraphBasedAgentMemory/summary|Graph-based Agent Memory (survey)]] — shares-technique: this survey's taxonomy of graph-structured agent memory (storage, retrieval, evolution) directly frames GraphPlanner's GARNet design — GraphPlanner is effectively an unlisted worked example of the survey's "graph memory drives agent decision-making" category, specialized to the routing use case.
- [[ai_papers/multi_agent_systems/Ruflo/summary|Ruflo]] — applies-in-practice: a production multi-agent orchestration platform (15-agent swarm on Claude Code) that already does "capability-matched routing" — GraphPlanner's learned, cost-aware routing policy is a plausible upgrade path for Ruflo-style systems that currently route agents via simpler heuristics rather than a trained graph policy.
